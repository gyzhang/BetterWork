# 附录 A 术语表

> **这份附录解决什么问题**：这本书里有三十多个术语，其中一部分有稳定中文译法（用了中文），一部分没有（保留了英文原词）。
> 这份表把**每一个词为什么这样处理**写清楚，并给出它**首次被定义的位置**。遇到本书用法与其他材料不一致时，以本表为准。

---

## A.1 三条定词规则

本书给一个英文词定中文译法时，只问三个问题：

| 序 | 问题 | 判定 |
|---|---|---|
| 1 | 中文技术语境里有没有一个**稳定、无歧义**的译法？ | 有 → 用中文 |
| 2 | 这个译法会不会**误导**读者（让人误以为是另一件事）？ | 会 → 保留英文原词 |
| 3 | 这个词在**中文政策或国家标准文本**里是否已经定型？ | 已定型 → 跟随官定译法 |

**第 2 条是最常被忽略的一条。** 举两个例子：

- `harness` 硬译成"挽具 / 马具"会让人以为是某种约束装置，而它实际指的是**围绕循环的运行时外壳**——所以保留英文。
- `Loop` 直译成"循环"会和编程里的循环混淆——所以写成 **Agent Loop**。

**第 3 条决定了"智能体"这个词的使用。** 中文政策文件与国家标准已经用"智能体"，所以本书不用"代理 / 代理体 / 智能代理"。

> **一处必须说明的取舍**
>
> 本书使用"智能体"而非"AI 智能体"，也不使用"Agent"作为中文正文里的主词。原因是**"智能体"在中文标准文本里已经是术语**，加限定词反而制造了第二套叫法。但**在代码、文件名、配置项里仍然使用英文 `agent`**——那是标识符，不是术语。

### A.2.5 待确认口径的词

有几个词在中文社区**同时存在两种以上说法**，本书的选择如下。**当你看到别的材料用另一种说法时，可以对照这一栏。**

| 本书用法 | 其他常见说法 | 为什么不选其他 |
|---|---|---|
| **智能体** | 代理、AI Agent、智能代理 | 国家标准与政策文本用"智能体" |
| **提示词** | 提示、prompt | "提示"太泛 |
| **产物** | 工件、交付物、artifact | "工件"偏工业制造语境 |
| **沙箱** | 沙盒、sandbox | 两者皆可，"沙箱"在中文安全文档里更常见 |
| **追踪** | 链路追踪、trace | 本书指事件序列，加"链路"会限制范围 |
| **对账** | 核对、勾稽 | "勾稽"过专，"核对"偏轻，不足以承载"独立算术检查"的语义 |
| **检查点** | 断点、存档点 | "断点"是调试器概念，容易混 |

## A.3 五组最容易混的词

这一节是这份附录里最实用的部分。**这五组词在真实讨论里被混用，而混用会导致具体的工程错误。**

### A.3.1 Harness vs 框架 vs MCP

| 词 | 它拥有什么 | **它不拥有什么** |
|---|---|---|
| **Harness** | 执行循环、上下文、权限、生命周期、持久化、可观测 | 不提供模型能力 |
| **框架 / 运行时** | 提供机制：图、检查点、流式、中断恢复 | **不拥有策略**——权限与口径仍归你 |
| **MCP** | 一个**无状态**的线上协议，规范工具发现与传输 | **不拥有循环、不持有状态、不做记忆** |

**判据只有一句**：**问"这一层拥有执行循环、状态、工具传输、权限、恢复里的哪几项"。**

**最常见的错误**是期待 MCP 管记忆或决策循环。**MCP 定义的是智能体与工具之间的契约，仅此而已。**

### A.3.2 上下文窗口 vs 记忆

| | 上下文窗口 | 记忆 |
|---|---|---|
| 是什么 | **一次请求能带的 token 上限** | **跨会话保留的记录** |
| 谁管 | 模型 / 提供方的规格 | **宿主** |
| 会不会自动包含你需要的东西 | **不会** | 不会，需要按作用域选择 |
| 溢出的后果 | 截断，或请求失败 | 不适用 |

**常见错误**：把"我把内容放进了记忆"当成"模型会用到它"。**放进去和用上是两件事**——中间隔着一次**选择**。

### A.3.3 检索 vs 搜索 vs 查询

| 词 | 做什么 | 结果形态 |
|---|---|---|
| **搜索** | 提交一个字符串，拿回一个列表 | 链接 / 标题 |
| **查询** | 在结构化数据上执行条件 | **行** |
| **检索** | 从语料里找出**可能相关**的片段 | **片段 + 相似度** |

**常见错误**：把"检索到了"当成"内容支持这个结论"。第 8 章的全部内容就在这个差额里。

### A.3.4 凭证 vs 风险 vs 禁止

本书的**配色语义**有一条硬规则（见第 14 章的图与第 6 章的数据卡）：

| 颜色 | 语义 | **不得用于** |
|---|---|---|
| 主题蓝族 | 信息、结构、流程 | —— |
| 红 `#DF203C` | **风险、禁止项** | **不得进入任何渐变、阴影、光晕**；单图占比 ≤ 5% |
| 暖色 `#B9770E` | 可选提醒块 | 低频使用 |

**关于涨跌的颜色**：在中文财务阅读习惯下，**涨为红、跌为绿**。这与英文材料的习惯相反。**任何图表都必须在图例里写明这个约定，不得假设读者知道。**

### A.3.5 强表述 vs 弱表述（本书的一个自我约束）

| 表述 | 含义 | 用在哪 |
|---|---|---|
| **"已验证 / 其测试已通过"** | 有实测支撑 | 本书对参考实现的代码引用 |
| **"位于可运行的参考实现中"** | 代码存在且可运行，但本书未逐一执行 | 需要降级时 |
| **"教学实现待补"** | **参考实现里没有，必须自行补** | 第 8 章（嵌入向量检索）、第 13 章（用量与成本事件） |

**第三行是本书最容易被忽略的一栏。** 它标注的地方意味着：**那一节不是"参考现成实现"，而是"你必须自己建"。** 完整清单见附录 B 的缺口一节。

## A.5 一个关于术语的提醒

术语表的用途**不是统一说法**，而是**避免把两个不同的东西说成一个词**。

本书里出现过三次同一种失败，它们都是术语混用造成的：

| 混用了 | 于是发生了 | 在哪一章 |
|---|---|---|
| "缓存值"与"计算值" | 一个没有缓存值的公式被当成了 0 | 第 14 章 |
| "历史上下文"与"当前事实" | 上一期的预算被补进了本期 | 第 18 章 |
| "已批准"与"已证实" | 一次人的决定被当成了证据变强 | 第 17 章 |

**这三处的共同修法都不是"更小心"，而是"给每一类东西一个不同的名字，并让这个名字进入程序能检查的地方"。**

这本书对术语的严格要求，来自这里。
