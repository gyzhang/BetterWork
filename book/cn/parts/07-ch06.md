# 第 6 章 确定性工具：把算术从模型手里拿走

**本章承诺**：读完这一章，你能设计出"模型无法从中得到错数"的工具——并且能说清一个工具在什么情况下必须**拒绝给出数字**，而不是给一个看起来合理的数字。

**读完后你能回答**

- 一个工具要满足哪四条，才能被叫作"确定性工具"？猜的和算的，在日志里长得一样吗？
- 为什么"把结果截断"和"限制内存占用"是两件不同的事？混淆它们的后果是什么？
- 工具遇到"分母为零""缺少本期值""单位不一致"这三种输入时，各自该做什么？

---

先看一个数字。

某份经营分析报告里写着：

> 6 月市场活动费用较 5 月下降 **12.4%**，成本控制成效显著。

读这份报告的人会得出一个结论：市场活动在收缩。

但真实情况可能是：**5 月的市场活动费用是 0**（那个月没有活动），6 月花了 8.6 万元。

于是 `(8.6 - 0) / 0` —— 这个除法没有意义。可它必须输出一个数字，因为报告模板里那一格不能空着。有人选了输出 `0%`，有人选了输出 `100%`，有人让程序算出 `Infinity` 然后被显示成 `∞%`。

**这一格里的任何一个数字，都是编的。**

而且它编得很成功：`下降 12.4%` 和 `成本控制成效显著` 放在一起，读起来像一个结论。没有人会停下来问"5 月的基数是多少"。

> **核心判断 1**
>
> 工具的价值不在于它能算出多少种东西，而在于**它在什么情况下会拒绝算**。
> 一个"任何输入都能给出数字"的工具，产出的不是结果，是**伪装成结果的猜测**。它比模型编造更危险，因为人们相信工具。

这一章要做的，是让工具的"拒绝"变成一种**被设计过的输出**，而不是程序崩溃。

---

## 6.1 四条判据：什么才算确定性工具

"确定性"这个词被用得很松。给它四条可检验的判据：

| # | 判据 | 反例 |
|---|---|---|
| 1 | **同输入必得同输出** | 里面读了当前时间、当前随机数、环境变量 |
| 2 | **不依赖外部状态**（或依赖被显式传入） | 从全局配置里读单位、从环境猜地区 |
| 3 | **不做超出声明的事** | 声明"计算"，实际顺手写了文件 |
| 4 | **对无法计算的情形明确拒绝** | 分母为零时返回 0 |

第 1 条和第 2 条合起来是"可复现"：**给定同样的输入，任何人任何时间重跑，必须得到同样的结果。**这一条不成立，第 13 章的评估就无从谈起——你没法判断两次结果不同是因为改了配置还是因为工具本身不稳定。

<div align="center"><img src="images/fig-6-1-determinism-tests.png" alt="图 6-1 确定性工具的四条判据与检验方式" width="1150"/></div>

**读图指引**：看第三列"怎么测"。**四条判据都必须有对应的检验动作**——一条判据如果不能被检验，它就只是一句设计意图。

第 3 条是"权限"问题，第 11 章会展开。

第 4 条是这一章的重点。它有一个反直觉的推论：

> **一个工具的能力清单，必须配一份等长的"拒绝清单"。**
> 只写"我能算什么"的工具，会在遇到它算不了的东西时，用某种方式硬算。

看参考实现里同一个文件的两面。这是它"能算什么"：

```ts
// 参考实现源码（BetterWork · packages/tool-runtime/src/business-metrics.ts）
export const analyzeBusinessMetrics = (input: z.input<typeof inputSchema>): BusinessMetricsResult => {
  const parsed = inputSchema.parse(input);
  const names = new Set([...Object.keys(parsed.current), ...Object.keys(parsed.previous ?? {})]);
  for (const name of Object.keys(parsed.budget ?? {})) names.add(name);
  const metrics: BusinessMetricResult[] = [...names].sort().map((metric) => {
    const current = parsed.current[metric];
    if (current === undefined) throw new Error(`当前期间缺少指标：${metric}`);
    ...
  });
```

注意第二行那个 `throw` 的位置：**它发生在计算任何东西之前。**

对比集是通过三个来源合并出来的（本期、上期、预算表里出现过的所有指标名）。这个"并集"设计本身很聪明——它保证了"上期有、本期没有"这种情形会被**发现**，而不是被静默跳过。

然后第一件事就是检查本期值是否存在。**不存在就抛错，不进入计算。**

### 6.1.1 为什么"上期有、本期没有"必须报错

如果实现换一种写法——遍历本期的键、然后去上期找对应值——那么"上期有、本期没有"的指标**根本不会出现在结果里**。

结果是：报告里少了三个指标，而没有任何地方说明为什么少了。

**这是"缺失"被伪装成"不存在"的典型形态。**两者在输出层面的差别是：一个明确的报错 vs 一份看起来完整、其实缺了三行的表。

第 0 章讲过数据纪律的第一条是"缺失和零要分开"。这里出现了它的第二种形态：**"缺失"和"从未存在过"也要分开。**

## 6.2 三种不能算的情形，三种不同的处理

参考实现给出了三种处理方式，它们**不一样**，而这正是这一章最值得学的地方。

<div align="center"><img src="images/fig-6-2-three-refusals.png" alt="图 6-2 三种不能算的情形与各自的处理" width="1150"/></div>

**读图指引**：三行的处理方式互不相同——**算能算的、抛错、拒绝**。差别不是风格，而是由"下游拿到什么会更安全"决定的。

### 6.2.1 分母为零：算能算的部分，明确标记不能算的部分

```ts
// 参考实现源码（BetterWork · packages/tool-runtime/src/business-metrics.ts）
if (previous !== undefined) {
  result.previous = previous;
  result.change = current - previous;
  if (previous === 0) warnings.push('comparison-zero-baseline');
  else result.changeRate = (current - previous) / Math.abs(previous);
}
if (budget !== undefined) {
  result.budget = budget;
  result.budgetVariance = current - budget;
  if (budget === 0) warnings.push('budget-zero-baseline');
  else result.budgetVarianceRate = (current - budget) / Math.abs(budget);
}
```

这里有一组刻意的设计决定，逐条列出来：

| 决定 | 理由 |
|---|---|
| **绝对变化额照算**（`change`） | 减法不涉及除法，没有分母为零的问题。**不能因为比例算不了，就连绝对值也不给** |
| **相对变化率不产生这个字段**（不是给 0） | 给 0 会被下游读成"持平"。**不产生字段，下游就会被强制处理"没有这个值"** |
| **往 `warnings` 推一条明确的标记** | 缺失必须**可见**。它不能只体现在"少了一个字段"上 |
| **除的是绝对值**（`Math.abs(previous)`） | 保证"降低"总是负号、"升高"总是正号，不会因为基数本身是负数而让符号翻转 |

第四条最容易忽略，也最容易出错。如果基数 `previous = -100`、本期 `current = -50`，用 `previous` 直接做分母会得到 `-0.5`，看起来像"下降 50%"——**实际上是从 -100 变成 -50，是变好了。**

参考实现的注释专门标注了这一点：**产品实现除以绝对值；而课程里的"带符号分母"定义在负基数下会有不同结论。**这不是谁对谁错的问题，是**口径必须被写下来**的问题——同一个函数名在不同教材里可能意味着不同的算法，而这正是第 0 章"把隐含假设变成显式契约"的又一个实例。

### 6.2.2 缺少本期值：拒绝，而不是跳过

```ts
const current = parsed.current[metric];
if (current === undefined) throw new Error(`当前期间缺少指标：${metric}`);
```

**抛错**，不是跳过。原因是跳过会让"数据不全"变成"报告缺了几行"——而看报告的人不会知道缺了。

注意这里的判据是 `=== undefined`，不是 `== null`，也不是 `!current`。差别很实际：

- `!current` 会把 **`0`** 当成缺失——而 0 是一个合法的值；
- `== null` 会同时挡掉 `null` 和 `undefined`，但在这个 schema 下值必须是有限数，`null` 早在入口就被拒了。

**判断"缺失"的代码，必须写得能区分"零"和"没有"。**这一行是整个第 0 章纪律的最小实现。

### 6.2.3 越界路径：在解析之后判断，而不是在字符串上判断

看参考实现里读文件的工具：

```ts
// 参考实现源码（BetterWork · packages/tool-runtime/src/read-text-file.ts）
const workspace = await realpath(context.workspacePath);
const requestedTarget = path.resolve(workspace, input.path);
const target = await realpath(requestedTarget);
const relative = path.relative(workspace, target);
if (relative.startsWith('..') || path.isAbsolute(relative))
  throw new Error('File is outside the active workspace');
```

四行代码，四个必须按顺序发生的动作：

| 步骤 | 在做什么 | 如果省掉会怎样 |
|---|---|---|
| `realpath(workspacePath)` | 解析**工作目录本身**的符号链接 | 用户的工作目录本身就是软链时，后面所有比较都基于一个错误的基准 |
| `path.resolve(...)` | 把用户给的相对路径拼成绝对路径 | — |
| `realpath(requestedTarget)` | **解析目标路径的符号链接** | 一个指向 `/etc` 的软链会绕过检查。**这是最关键的一步** |
| `relative` + 双向判断 | 判断"是否真在目录内" | 只看 `startsWith('..')` 会漏掉绝对路径的情形；只看 `isAbsolute` 会漏掉相对逃逸 |

**第四步为什么要两个条件？**因为 `path.relative` 在两者不在同一驱动器/根时会返回一个绝对路径。少判一个条件，就会在某个平台上出现一个静默的绕过。

> **核心判断 2**
>
> **边界检查必须做在"解析之后"。**
> 在原始字符串上检查（比如"路径里不能有 `..`"）永远是有洞的——因为路径允许的表达方式太多：符号链接、硬链接、大小写不敏感、编码差异、Windows 的 8.3 短名。
> 代价是每次检查都要做一次真实的文件系统调用。**这个开销必须付。**

## 6.3 工具描述：说清什么时候**不该**用它

工具的 `description` 是给模型看的。大多数人的写法是"这个工具能做什么"。这只写了一半。

对比这两种写法：

```text
❌ Calculate business metrics for a period.

✅ Calculate deterministic period-over-period and budget variances for named
   business metrics. Provide current values and optional previous/budget values;
   the tool never guesses missing values or calculates formulas.
```

第二种多出来的部分是**否定式约定**：

- `deterministic` —— 说明结果是确定的，不是估计；
- `never guesses missing values` —— 说明缺值不会拿到数字；
- `does not calculate formulas` —— 划清和"电子表格"的边界。

**这三句在减少的是一类特定的错误：模型以为它可以省略参数、或者以为工具会替它补上缺的数据。**

一个可操作的写法模板：

| 要写的部分 | 例子 |
|---|---|
| **做什么** | 计算指定期间的确定性和预算偏差 |
| **必须给什么** | 本期值必填；上期与预算选填 |
| **不会做什么** | 不猜缺失值、不算公式、不做单位换算 |
| **什么时候别用** | 只有一个期间的数据时，不要用它来"估"变化 |

第四行是最少被写、收益最大的一行。

### 6.3.1 名字也是契约的一部分

参考实现里的 MCP 工具名做了一层处理：

```ts
// 参考实现源码（BetterWork · apps/desktop/src/main/services/mcp-client-service.ts）
const toolNameForModel = (tool: McpToolSummary): string =>
  `mcp_${tool.connectionId}_${tool.name}`.replace(/[^a-zA-Z0-9_-]/gu, '_').slice(0, 180);
```

三件事：**加前缀做命名空间**（避免两个服务端的同名工具互相顶掉）、**清洗非法字符**、**限制长度**。

为什么把连接 ID 放进工具名？因为模型看到 `mcp_finance_metrics/read` 这样的名字，就知道它来自哪个外部系统。**上下文里的一个字符串，也在承担告知责任。**（MCP 的命名空间与授权归属详见第 7 章。）

## 6.4 结构化结果与结构化错误

一个工具的执行结果有三种可能，它们必须被区分：

| 结果 | 形态 | 谁来处理 |
|---|---|---|
| **成功** | 结构化数据 | 走正常回填 |
| **可恢复的业务性失败** | 结构化错误（说明缺什么、参数有什么问题） | 回填成观测，**让模型换一种做法** |
| **不可恢复的失败** | 抛出异常（路径越界、schema 不合、未知工具） | 收口为运行失败 |

区分的判据在第 4 章讲过：**"我允许你做但你失败了"是观测；"你想做我没允许的事"是运行失败。**

但"结构化错误"要落到什么形状，这里给一个具体建议——**错误必须能让模型据此改**：

```json
{ "error": "当前期间缺少指标：市场活动费用", "code": "missing-current-metric", "metric": "市场活动费用" }
```

对比一个不合格的写法：

```json
{ "error": "计算失败" }
```

第二种写法里，模型没有任何可用的信息，只能重试同样的调用——然后触发第 5 章讲的"无进展重复"。

**判断一个错误信息好不好，用一个简单的问题**：**下一个拿到它的人（或模型）能据此做出一个不同的动作吗？**不能，就说明它写得不合格。

### 6.4.1 单位必须是一个显式参数

一个真实的高频错误：工具返回了一个数字，但报告里写错了单位。

原因通常是工具"知道"单位——它从某处读了配置，或者按习惯写死了"元"。于是：

- 工具返回 `86000`；
- 报告模板写"万元"；
- 输出变成"86000 万元"。

**处理规则**：**单位必须是输入参数的一部分，并且必须被原样带回输出。**

```json
{ "amount": 86000, "unit": "元" }
```

而不是：

```json
{ "amount": 86000 }
```

第二条的接收方只能靠猜。而**在数字类的工作里，"猜单位"的错误率远高于"猜格式"。**因为格式错了看得出来，单位错了看着完全正常。

## 6.5 依赖注入：让工具不依赖宿主

看这个工具的构造方式：

```ts
// 参考实现源码（BetterWork · packages/tool-runtime/src/read-text-file.ts）
export type ReadTextFile = (
  input: { path: string },
  context: Parameters<AgentTool['execute']>[1],
) => Promise<unknown>;

export const createReadTextFileTool = (reader?: ReadTextFile): AgentTool => ({ ... });

export const readTextFileTool: AgentTool = createReadTextFileTool();
```

三行的结构值得细看：

1. **工厂函数** `createReadTextFileTool(reader?)` —— 接受一个可选的读取实现；
2. **默认导出** `readTextFileTool` —— 不传参数时用内置的 `realpath` + `readFile` 实现；
3. **执行时的分岔**：

```ts
async execute(rawInput, context) {
  const input = inputSchema.parse(rawInput);
  if (reader) return reader(input, context);
  // 内置实现...
}
```

**校验在任何情况下都先跑。**即使注入了自定义 reader，参数也必须先过 schema。这是一个容易漏的细节：**注入的是"实现"，不是"绕过契约的理由"。**

为什么要注入？三个实际收益：

| 收益 | 说明 |
|---|---|
| **可测试** | 测试里注入一个假 reader，就能构造"文件不存在""内容是二进制"这些真实文件系统上难造的场景 |
| **可换后端** | 同一个工具既能读本地文件，也能读某个平台上受权限控制的对象存储 |
| **不污染依赖** | 工具包不需要依赖 Electron / SQLite / 具体云 SDK |

第三条在参考实现里被写成一条架构规范：

> 需要 Application 层资源的 Tool 用「**工厂 + 闭包注入**」，使 `tool-runtime` 不依赖 Electron、SQLite 或服务商 SDK。

**这不是为了架构好看，是为了让工具能被单独测试。**一个工具如果必须在完整应用启动后才能运行，它就永远不会被单元测试覆盖——而工具是全书最需要测试的一层。

## 6.6 一个容易被忽略的诚实标注：截断不是资源上限

看读文件工具返回的东西：

```ts
return {
  path: relative,
  content: content.slice(0, maxChars),
  truncated: content.length > maxChars,
};
```

三个字段的设计是合格的：**截断被显式标记**（`truncated`），而不是让调用方从"长度正好是 20000"去猜。

但参考实现的注释里明确写了一句更诚实的话：

> 返回文本的截断**不是**读入内存的字节上限。

**这句话值得单独抄下来。**因为 `readFile(target, 'utf8')` 已经把整个文件读进内存了，`slice(0, maxChars)` 只是在**返回**时截断。

| 你以为的限制 | 实际的限制 |
|---|---|
| 单次最多处理 2 万字符 | 单次最多**返回** 2 万字符；内存里可能躺着 500MB |

**后果**：一个 2GB 的日志文件可以让进程直接 OOM，而工具的"上限"看起来还在生效。

> **核心判断 3**
>
> **"我限制了输出"和"我限制了资源"是两件事。**
> 把前者当成后者，会造出"看起来有保护、实际没有"的系统。而这类系统的危险在于：**它的保护是可见的**——代码里明明白白写着 `maxChars = 20_000`，评审时会通过。

同样形状的问题在别处也出现过，第 0 章的 `cmd | tail` 是同一类：**你做了一个限制动作，但它限制的不是你以为的那个东西。**

正确的做法是把限制做在**读取前**：先 `stat` 拿文件大小，超过阈值直接拒绝；或者用流式读取，边读边累计。这两种都能真正限制内存，而 `slice` 不能。

## 6.7 测试预言：不能让工具自己证明自己

确定性工具最容易做的测试是"跑一遍，看结果对不对"。这个测试的问题在于：**"对不对"由谁判定？**

如果答案是"我看了一眼觉得对"，那这个测试是不可复现的。做法是**测试预言**（oracle）：用一条**独立的路径**算出预期值，写在测试里。

```ts
// 参考实现的测试方式（示意，见 business-metrics.test.ts）
const result = analyzeBusinessMetrics({
  period: '2026-06',
  current: { 市场活动费用: 86_000, 办公费用: 12_000 },
  previous: { 市场活动费用: 75_000, 办公费用: 12_000 },
  budget: { 市场活动费用: 90_000 },
});

// 预期值是手算并写在测试里的常量，不是从函数里"取"出来的
expect(result.metrics.find((m) => m.metric === '市场活动费用')?.change).toBe(11_000);
expect(result.metrics.find((m) => m.metric === '市场活动费用')?.budgetVariance).toBe(-4_000);
```

关键在注释那句：**预期值是独立算出来的常量，不是把函数的输出复制进测试。**

复制输出的测试有一个更糟的性质：**它会随着 bug 一起更新。**你把错误的输出粘进 expect，测试就绿了，而且以后永远绿。

> **定义**：测试预言
>
> 一份**独立于被测实现**推导出的预期结果。
>
> **它不是什么**：不是"把当前输出复制到 expect 里"。那不是测试，那是快照——快照能发现**变化**，发现不了**错误**。
>
> **本书中的用法**：确定性工具的测试里，每个断言的目标值都必须能说清"我是怎么算出来的"。说不清就删掉那个断言。

## 6.8 故意失败：四种输入，四种拒绝

拿参考实现的这四个工具行为做一个对照实验。**每一个都必须以某种方式"不给出数字"**，而不是给出一个数字。

| # | 输入 | 期望行为 | 常见错误实现 |
|---|---|---|---|
| 1 | 上期值为 `0` | 不产生 `changeRate` 字段 + 推一条 `comparison-zero-baseline` | 返回 `changeRate: 0` 或 `Infinity` |
| 2 | 本期缺某个指标，但上期有 | 抛错，且错误信息指明是哪个指标 | 静默跳过该指标 |
| 3 | 路径为 `../../etc/hosts` | 抛错"在工作目录之外" | 检查字符串里有没有 `..` |
| 4 | 金额单位在输入里是"万元"，输出标"元" | 单位必须被原样带回，不得自行换算 | 工具内部统一成"元"后不标注 |

四条里第 4 条最容易被当成"不算 bug"。它的失败方式是：**报告里的数字看起来完全正常，只是差了两个数量级。**

### 6.8.1 一次实验：把第 1 条改成"返回 0"

把零分母的处理从"不产生字段"改成"返回 0"，然后跑一份完整的两期数据。

观察输出：**报告看起来更完整了。**每一行都有变化率，没有空着的格子。

继续往下走，让模型基于这份结果写一段经营分析。它会写：

> 各项费用的变化幅度已在表中列出，其中市场活动费用……

**它不会注意到"上期为零"这件事，因为报告里没有任何地方提示过。**一个被填成 0 的缺失值，在流转了几步之后，已经完全变成了一个事实。

这就是第 0 章那条纪律的完整版：

> **缺失值被填成默认值的那一刻，错误就完成了；此后每一跳都会让它显得更合理。**

## 6.9 行业视角：机构里，"给不出数"是一个需要被接受的答案

第 6 章的核心是"工具必须能拒绝"。在机构场景里，被拒绝之后发生的事更值得注意：**往往会有人用一个"看起来合理的数"把空补上。**

| 不能算的情形 | 机构里常见的错误补法 | 正确处置 |
|---|---|---|
| 分母为零 | 报成 0% 或 100% | 明确标记"不可比" |
| 缺当期口径 | 套用上一期的权重 | **拒绝，并指出缺的是哪一项** |
| 数据被截断 | 把它当成全部数据 | 报告覆盖范围，不报"合计" |
| 结果来自单一来源 | 被当成"唯一口径" | 标注来源与局限 |

第二行和第三行是同一类：**缺的东西被悄悄替换成了一个不是它的东西。** 第 14 章把这条讲成"缺失和零必须分开"；在机构里它进一步变成一条**汇报纪律**——**一份报告可以写"这一项本期无法给出"，但不能写一个凑出来的数。**

这条纪律的代价是当场被质疑，收益是长期被信任。**在需要审计的场景里，这个交换是划算的。**

## 6.10 这一章在整本书里的位置

到这里，你已经能造出一个**值得信任的本地工具**：可用、可测、会拒绝、不越界。

但真实工作里，大量能力不在你的仓库里。你要接的是数据库、监控系统、工单系统——它们各有各的接口，各有各的认证方式，各有各的"今天又改了一版"。

**每接一个外部系统就写一套适配器，是维护不过来的。**于是需要一个标准。

第 7 章讲 MCP——以及它最容易被人误解的那一点：**能发现一个工具，不等于被授权使用它。**

---

**本章小结**：确定性工具要满足四条——同输入同输出、不依赖未显式传入的外部状态、不做超出声明的事、**对无法计算的情形明确拒绝**。三种"不能算"要分开处理：分母为零时算能算的（绝对值），明确标记不能算的（比例），并且**不产生那个字段**；缺少本期值要抛错而不是跳过；越界路径要在 `realpath` 解析之后再判断。工具的 `description` 必须包含"不会做什么"。**单位是显式参数，必须原样带回。**截断输出不等于限制资源——这是同一类错误在不同层次上的重现。

**行动清单**

1. 给你的每个工具写一份"拒绝清单"：列出它**不应该**给出数字的情形，并为每种情形写一条测试。
2. 检查所有涉及除法的代码：分母为零时是"不产生字段""抛错"还是"返回 0"？**把返回 0 的全部改掉。**
3. 把所有"缺失"判断从 `!value` 改成 `value === undefined`（或等价的严格判断），确保 `0` 不被当成缺失。
4. 检查所有路径校验：有没有做 `realpath`？有没有同时判 `startsWith('..')` 和 `isAbsolute`？
5. 检查所有"截断"实现：它限制的是**输出**还是**读取**？如果是前者，补一个读取前的尺寸检查。
6. 把工具的错误信息改写成"下一个拿到它能做出不同动作"的形状。
