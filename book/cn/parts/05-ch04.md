# 第 4 章 Agent Loop：一个必须能停下来的循环

**本章承诺**：读完这一章，你能独立实现一个有界循环，并说清它为什么**一定**会停——不是"通常会停"，是"在数学上不可能不停"。

**读完后你能回答**

- `maxToolRounds: 1` 到底允许了几次模型调用、几次工具轮次？边界差一位会差出什么？
- 一个工具每次都返回成功，任务却永远完不成——这两件事为什么能同时成立？
- 为什么"未知工具"应该让整轮运行失败，而"工具执行报错"应该只变成一条观测结果？

---

一次工具交换是简单的。**研究不一样。**

一个真实的研究过程长这样：读完第一篇材料，发现它定义了一个你没听过的术语；于是去查这个术语；查到的定义和第二篇材料里的说法矛盾；于是再去找第三份材料来判；找到的材料格式不支持，读失败了；换一个来源……

**没有人能事先写出这个过程的步骤。**这正是第 1 章说"不确定性在链条右端"的含义。

所以需要的不是一个更聪明的动作，而是一个**可以重复做决定的机制**——但重复这件事本身带来一个新问题：

> **一个可以再决定一次的循环，也可以再决定一次、再决定一次、再决定一次……**

这一章的全部内容，就是**在允许重复的同时保证一定会停**。

> **核心判断 1**
>
> 循环设计的第一性问题不是"怎么让它继续"，而是"**什么条件下它必须停**"。
> 代价是你要接受"任务没完成就被掐断"这个结果的存在——**并且给它一个明确的终态，而不是让它挂在那里。**

---

## 4.1 循环需要四件东西，缺一件就不成立

| 要素 | 承载什么 | 少了它会怎样 |
|---|---|---|
| **消息列表** | 把观测结果带到下一轮 | 模型下一轮看不到上一轮发生了什么，每次都从零开始 |
| **工具注册表** | 可执行能力的全集 | 模型请求的工具无处解析；或者更糟——动态创建它 |
| **轮次计数** | 重复次数的上限 | 一个反复请求工具的提供方会让循环永不停止 |
| **终止判定** | 什么算结束、什么算失败、什么算取消 | 运行永远停在"好像还在跑"的状态 |

参考实现把这个循环写成一行 `for`：

```ts
// 参考实现源码（BetterWork · packages/agent-core/src/agent-engine.ts）
for (let round = 0; round <= maxToolRounds; round += 1) {
```

**它用了 `<=` 而不是 `<`。**这一个符号的差别，是本章第一个要讲清的技术点（见 4.4）。

---

## 4.2 循环的骨架（教学伪代码）

先用伪代码把逻辑讲清楚，再看真实实现：

```text
启动运行
初始化消息、工具注册表、轮次上限

对第 0 轮到第 N 轮（含第 N 轮）：
  检查取消 → 已取消则走取消终态
  请求模型的下一次响应
  收集完整的工具调用与回答文本
  如果没有工具调用：
    产出完成终态，结束
  如果轮次已经用完：
    产出失败终态，结束
  对每一个请求的调用：
    只在允许的注册表里解析工具
    校验参数并执行
    把结果或可恢复错误作为观测回填

被取消 → 产出取消终态
其他不可恢复错误 → 产出失败终态
```

这段伪代码里有四处是"必须这样"的，值得逐条标记：

| 位置 | 为什么必须这样 |
|---|---|
| **检查取消在最前面** | 取消可能发生在任何时刻；最前面检查能保证"取消后不再发起新的模型调用" |
| **"没有工具调用"判定为完成** | 这是循环唯一正常的出口。注意它是**基于内容**判定的，不是基于轮次 |
| **"轮次用完"判定为失败** | 用完配额意味着任务没做完。**不能算成功** |
| **执行前先在注册表里解析** | 解析失败 = 未知工具 = 不可恢复，必须立刻失败，不能"创建一个" |

> **核心判断 2**
>
> **"到达上限"必须是失败，不能是成功。**
> 一个在上限处返回成功的系统，会把"我没做完"报告成"我做完了"。这是所有截断类 bug 里最难查的一种，因为报告是绿色的。

## 4.3 拆开真实实现

现在逐段看参考实现。先是初始化：

```ts
// 参考实现源码（BetterWork · packages/agent-core/src/agent-engine.ts）
const events = new RunEventFactory(input.runId);
const messages: AgentMessage[] = [ /* 系统提示、专家配置、Skill 说明、历史、本次输入 */ ];
const tools = new Map(input.tools.map((tool) => [tool.name, tool]));
const maxToolRounds = input.maxToolRounds ?? 20;

yield events.create({ type: 'run.started', taskId: input.taskId, sessionId: input.sessionId });
```

四件事：

1. **事件工厂**（下一节讲）；
2. **消息装配**（第 2 章已经讲过）；
3. **工具注册表**：用 `Map` 按名字索引。**这是一个关键设计**——它不是数组，所以解析是 O(1) 且**只能命中已注册的工具**。数组 + 查找函数也能做，但 `Map` 让"不存在"这件事变成一个明确的 `undefined`，而不是"我没找到但你也许能找到"。
4. **轮次上限**：默认 20。

### 4.3.1 默认值 20 是策略，不是保证

`?? 20` 这个默认值必须被理解成**策略参数**，而不是安全保证：

- 它对一个"查三个来源、算一次、写一份摘要"的任务足够了。
- 它对一个需要遍历五十个文件的任务**不够**——它会在第二十轮失败。
- 它**不构成任何成本上限**（见 4.4.2）。

参考实现明确把"为绑定的 Skill 覆盖默认上限"做成了可配置项。**正确的做法是：默认值给一个保守的数，然后按任务类型显式覆盖它**，而不是全局调大。

### 4.3.2 流式处理与增量事件

```ts
for await (const chunk of input.model.stream({ messages, tools: [...], signal: input.signal })) {
  if (input.signal.aborted) throw abortError();

  if (chunk.type === 'reasoning-delta') {
    yield events.create({ type: 'reasoning.delta', delta: chunk.delta });
  } else if (chunk.type === 'text-delta') {
    if (!messageStarted) {
      messageStarted = true;
      yield events.create({ type: 'message.started', messageId });
    }
    content += chunk.delta;
    yield events.create({ type: 'message.delta', messageId, delta: chunk.delta });
  } else if (chunk.type === 'tool-call') {
    pendingToolCalls.push(chunk.toolCall);
    yield events.create({ type: 'tool.requested', toolCall: chunk.toolCall });
  }
}
```

三个设计决定值得注意：

**决定一：流式片段立刻转成事件产出。**注意 `yield` 发生在 `for await` 循环内部——**片段一到就往外发**，不是等整条消息结束了再发。这是"界面三十秒不动"这个问题的解。

**决定二：`tool-call` 只被收集，不被执行。**看循环体——它推入 `pendingToolCalls`，仅此而已。执行发生在流结束之后：

```ts
if (messageStarted) {
  yield events.create({ type: 'message.completed', messageId, content });
  messages.push({ id: messageId, role: 'assistant', content, ...(pendingToolCalls.length > 0 ? { toolCalls: pendingToolCalls } : {}) });
}

if (pendingToolCalls.length === 0) {
  yield events.create({ type: 'run.completed', finalContent: content });
  return;
}
```

**为什么必须等流结束才能执行？**因为第 3 章讲过：工具参数是分片传输的。**流没结束，参数就可能还没凑齐。**在第 3 片的参数上执行工具，等于用半截 JSON 去调用。

**决定三：助手消息里带着 `toolCalls`。**这一条不是为了让你读的，是为了**下一轮请求的协议正确性**——模型需要看到自己上一轮的调用决定和随后的结果，才能理解现在的处境。

### 4.3.3 `messageStarted` 这个标志在处理什么

`messageStarted` 是个小标志，但它对应一个真实的协议情况：**有一轮模型只产出了工具调用，没有产出任何文本**。

如果不加这个标志，你会产出一个 `message.started` / `message.completed` 的空消息对。加了之后：

```ts
if (!messageStarted)
  messages.push({ id: messageId, role: 'assistant', content: '', toolCalls: pendingToolCalls });
```

**消息还是会被推进去**——因为协议要求助手消息必须存在——但不会产生一对空事件给界面。

**这类"为了协议正确性而必须留下、为了界面干净而不能展示"的东西，在智能体系统里到处都是。**处理它们的正确方式是分两层：**协议层保留，展示层过滤**。而不是二选一。

## 4.4 边界算术：`maxToolRounds` 到底限制了什么

这是本章最需要动手算一遍的地方。**先把答案写出来，再看推导。**

```ts
const maxToolRounds = input.maxToolRounds ?? 20;
...
for (let round = 0; round <= maxToolRounds; round += 1) {
  // 1) 模型调用
  // 2) 无事可做 → 完成
  if (pendingToolCalls.length === 0) { ...completed...; return; }
  // 3) 轮次用完 → 失败
  if (round === maxToolRounds) throw new Error(`Tool round limit exceeded: ${maxToolRounds}`);
  // 4) 执行本轮的调用
}
```

### 4.4.1 取 `maxToolRounds = 1` 手工推一遍

| 轮次 | 模型调用 | 有工具调用吗 | 判定 |
|---|---|---|---|
| round 0 | 第 1 次 | 有 | `round(0) !== 1`，**执行工具** |
| round 1 | 第 2 次 | 没有 | → **完成** |
| round 1 | 第 2 次 | 有 | `round(1) === 1` → **失败**（第 2 个工具轮次被拒绝） |

**结论可以写成三句：**

1. **最多 `maxToolRounds + 1` 次模型调用**（这里是 2 次）。
2. **最多 `maxToolRounds` 个工具轮次**（这里是 1 个）。
3. **上限只限制"工具轮次"**，不限制单轮里的调用个数，也不限制模型调用总数。

第 3 条最容易被误解。**一轮里可以请求多个工具调用**，而上限对它们一视同仁。所以：

> **数据卡**：轮次上限不等于调用数上限
>
> **口径**：`maxToolRounds` 计的是"可以执行工具的轮数"。一轮内可以请求多个调用；需要控制"总调用次数"的应用必须**另外**加策略
> **时点**：参考实现当前版本（锚定提交 `2d8a79f`）
> **来源**：`packages/agent-core/src/agent-engine.ts` 与其测试 `agent-engine.test.ts`
> **局限**：这不是一个缺陷，是一个**需要被知道的边界**。把它当成"总调用预算"用，会导致实际调用数远高于预期

<div align="center"><img src="images/fig-4-1-boundary-arithmetic.png" alt="图 4-1 轮次上限的边界算术与三种终态" width="1150"/></div>

**读图指引**：左侧看 `maxToolRounds = 1` 时的两条路径——"round 1 给出最终答案"是成功，"round 1 再要一轮工具"是失败。**同一个轮次、同一个模型调用次数，因为请求内容不同而走向两个终态。**这就是"边界在内容上，不在计数上"。

### 4.4.2 为什么它同时也不是成本上限

一个自然但错误的推论是："轮次有限，所以成本有限。"

不成立。因为：

- **单轮内可以请求多个调用**；
- **单次模型调用的 token 消耗不确定**（上下文越长越贵）；
- **单个工具可能很贵**（一次联网检索、一次大模型摘要）；
- **重试策略在循环之外**（参考实现里的重试上限也明确"不属于通用安全预算"）。

**成本必须由独立的预算机制管**，这是第 13 章的内容。轮次上限管的是"决策次数"，它和"花了多少钱"没有换算关系。

## 4.5 三种终态，一个都不能少

```ts
} catch (error) {
  if (input.signal.aborted || isAbortError(error)) {
    const reason = typeof input.signal.reason === 'string' ? input.signal.reason : undefined;
    yield events.create({ type: 'run.cancelled', ...(reason ? { reason } : {}) });
    return;
  }
  yield events.create({ type: 'run.failed', error: describeError(error) });
}
```

| 终态 | 触发 | 语义 |
|---|---|---|
| `run.completed` | 模型不再请求工具 | 执行周期正常结束 |
| `run.cancelled` | 用户或系统触发了中止信号 | **有人主动让它停** |
| `run.failed` | 其他任何不可恢复错误 | **它自己出错了** |

**三种必须分开，不能合并。**理由很直接：**它们的处理方式完全不同。**

| 终态 | 用户看到的应该是 | 该不该报警 | 能不能重试 |
|---|---|---|---|
| 完成 | 结果 | 否 | 不适用 |
| 取消 | 一个"已停止"的提示 | **否** | 用户可以再发起 |
| 失败 | 错误信息与原因 | 是 | 视错误类型 |

<div align="center"><img src="images/fig-4-2-two-forks.png" alt="图 4-2 两处分岔：工具结果与三类终态" width="1150"/></div>

**读图指引**：左右两半分别是"工具这一层"和"运行这一层"的分岔。注意左边第三行是**唯一会让整轮运行静止失败**的工具层情况（4.7 节讲原因）；右边三行是运行结束的三种方式，它们必须分开对待。

把"取消"和"失败"合并，会得到一个非常常见的产品缺陷：**用户点了一次"停止"，界面上出现一条红色的错误提示。**用户会以为系统坏了，而实际上是他自己操作的。

参考实现把这件事写成了一条硬规范：

> 取消语义只有一处定义。任何地方都不允许再手写一个名字叫 `AbortError` 的错误——**写错名字会让取消被当成失败上报。**

### 4.5.1 判定顺序是刻意的

注意 catch 里的顺序：**先判 `signal.aborted` 和 `isAbortError`，再判其他。**

不能反。因为用户取消的时候，底层往往还会抛出一个别的错误（连接被中断、读取失败），如果先判"是不是别的错误"，取消就会被归到失败里去。

同时注意 `isAbortError(error)` 这个**双重判定**：既看信号状态，也看错误本身的名字。这样两种情况都能覆盖——信号已经触发但错误还没来得及包装的情况，以及错误名字对但信号状态没来得及更新的情况。

### 4.5.2 一个必须提前处理的例外：引擎之外的失败

引擎自己会收口失败与取消。但**编排层在进入事件循环之前或写库过程中抛错时，引擎不会产出任何终态事件**——因为它根本还没开始产出事件。

参考实现的做法是"兜底合成"：

> `RunService.consume` 必须有 `catch`。兜底靠 `RunRepository.forceFailure`，它**只在 Run 仍为 `running` 时**合成 `run.failed`，因此重复调用安全，也不会与引擎的终态冲突。

这里面有三个设计点值得抄：

1. **兜底存在**——不假设"引擎一定能收口"。
2. **兜底是幂等的**——有条件判断，只在还没终态时才写。
3. **兜底不与正常路径冲突**——两个来源写终态不会打架。

还有一条配套的不变量：

> **每个 Run 都必须有明确终态。**启动时会把上次进程被强杀留下的 `running` 收归为 `failed`。

**"上次进程被强杀留下的记录"**——这句话本身就说明了为什么必须有这条不变量：**进程会死，而且不会给你机会善后。**

## 4.6 事件序列：`sequence` 为什么必须连续

```ts
// 参考实现源码（BetterWork · packages/agent-core/src/agent-engine.ts）
class RunEventFactory {
  private sequence = 0;
  constructor(private readonly runId: string) {}
  create(input: AgentRuntimeEventInput): AgentRuntimeEvent {
    return { ...input, id: randomUUID(), runId: this.runId, sequence: this.sequence++, createdAt: Date.now() };
  }
}
```

三条性质被这个 10 行的类钉死了：

| 性质 | 保证什么 |
|---|---|
| **单调递增的 `sequence`** | 消费方可以断言"事件没有缺号"，从而判断"我是不是收全了" |
| **每个事件都有 `runId`** | 多个运行并发时事件不会串 |
| **每个事件都有 `id` 与 `createdAt`** | 去重与排序有依据 |

**测试里应该有一条断言：每次普通运行都恰好有一个终态事件，且序号连续。**参考实现的实验要求里就明确写着这一条。

**为什么序号连续这么重要？**因为事件流是**异步消费**的。如果中间丢了一条，界面上的表现是"某个工具卡片一直转圈"。没有序号，你无法区分"它还在跑"和"那条完成事件丢了"。

## 4.7 可恢复错误与不可恢复错误

这是循环里最有"判断含量"的一处设计。

```ts
if (outcome.type === 'completed') {
  yield events.create({ type: 'tool.completed', toolCallId: toolCall.id, output: outcome.output });
  messages.push({ /* role: tool，内容是 JSON.stringify(output) */ });
} else {
  const message = describeError(outcome.error);
  yield events.create({ type: 'tool.failed', toolCallId: toolCall.id, error: message });
  messages.push({ /* role: tool，内容是 JSON.stringify({ error: message }) */ });
}
```

**工具失败不会让运行失败。**它被转成一条**观测结果**回到对话里。这就是"可恢复错误"。

为什么要这样设计？因为**模型能利用这条信息**：

- 文件不存在 → 它可以换一个文件；
- 参数格式错 → 它可以改正参数重试；
- 服务暂时不可用 → 它可以试另一个来源。

如果工具一失败就掐掉整个运行，这些恢复能力全部丧失。

但有另一种情况必须严格区分：

```ts
const tool = tools.get(toolCall.name);
if (!tool) throw new Error(`Unknown tool: ${toolCall.name}`);
```

**未知工具 → 立即让整轮运行失败，不进恢复路径。**

理由只有一句，但它是本章第二个核心判断：

> **核心判断 3**
>
> **不要根据名字动态创建工具。**
> 一个"模型说要调用 foo，系统就去造一个 foo"的设计，等于把工具注册表交给模型决定。而工具注册表就是**权限清单**——你刚刚把权限清单交给了不可信来源。
> 代价是模型偶尔会因为拼错工具名而让整轮失败。**这个代价必须付**，因为它换来的是"模型无法扩张自己的能力范围"这个不变量。

这条区分可以用一句话记住：

**"我允许你做这件事，但你做失败了"是观测结果；"你想做一件我没允许的事"是运行失败。**

## 4.8 串行还是并行：一个不该被"优化"掉的决定

参考实现在一轮之内**顺序执行**所有工具调用。文档里明确解释了为什么不并行：

> 参考实现在模型轮次内顺序执行调用。**并行化不是一个自动的优化**：调用之间可能互相依赖、可能消耗共享预算、也可能产生相互冲突的副作用。**先从你能解释的顺序开始。**

这三条理由值得展开，因为它们是人最容易犯的乐观错误：

| 风险 | 具体场景 |
|---|---|
| **相互依赖** | 第二个调用要用的路径，是第一个调用返回的 |
| **共享预算** | 两个调用各消耗一半的配额，并行时你无法在中间判断"还够不够" |
| **冲突副作用** | 两个调用同时写同一个文件 |

第三条尤其危险：**并行下的冲突写入，结果取决于调度顺序，因此不可复现。**

**顺序执行是可解释的。**当你需要优化它的时候，你必须先证明这三条都不成立——而不是先并行起来，出问题再回退。

## 4.9 长任务期间保持"活着"

一个纯顺序循环有个问题：**工具执行可能很久**，而这段时间循环什么事件都产不出来，界面看起来像卡死。

参考实现用一个值得学的机制解决它——**在等待工具执行的同时，把工具主动上报的进度转发出去**：

```ts
// 参考实现源码（BetterWork · packages/agent-core/src/agent-engine.ts）
const progress: AgentRuntimeEvent[] = [];
let wakeForProgress: (() => void) | undefined;
const onAbort = (): void => wakeForProgress?.();
input.signal.addEventListener('abort', onAbort, { once: true });
const execution = tool.execute(toolCall.input, {
  runId: input.runId,
  toolCallId: toolCall.id,
  workspacePath: input.workspacePath,
  signal: input.signal,
  reportProgress(message) {
    progress.push(events.create({ type: 'tool.progress', toolCallId: toolCall.id, message }));
    wakeForProgress?.();
  },
})
  .then((output) => ({ type: 'completed' as const, output }), (error: unknown) => ({ type: 'failed' as const, error }));
```

关键在于 `reportProgress` 这个回调**同时做两件事**：把事件推进队列，并且**唤醒正在等待的那个 Promise**。

```ts
const progressSignal = new Promise<void>((resolve) => { wakeForProgress = resolve; });
const result = await Promise.race([execution, progressSignal]);
wakeForProgress = undefined;
if (input.signal.aborted) throw abortError();
if (result) outcome = result;
```

`Promise.race([执行结果, 进度信号])` 的含义是：**谁先来就等谁**。

- 工具执行完了 → 拿到结果，结束等待；
- 工具报了一次进度 → 唤醒，回到循环顶部把队列里的进度事件 `yield` 出去，然后**继续等**。

注意 `finally` 里的清理：

```ts
} finally {
  input.signal.removeEventListener('abort', onAbort);
  wakeForProgress = undefined;
}
```

**监听器必须摘掉。**这类"在循环里反复挂监听"的代码如果忘了摘，会在长任务里累积到触发 `MaxListenersExceededWarning`——参考实现在另一处（假提供方的 `pause` 函数）专门为这个问题写了注释，说明它踩过。

> **一条可以固化成习惯的规矩**：**任何 `addEventListener` 都要在同一个函数里找到它的 `removeEventListener`。**找不到就是泄漏。

## 4.10 故意失败：一直成功却永远完不成

现在做本章最重要的实验。

构造两个东西：

1. **一个永远成功的工具**：无论输入是什么，都返回 `{ ok: true }`。
2. **一个永远请求它的提供方**：每一次被调用，都产出同一个工具调用。

然后跑循环，观察：

```text
round 0: 请求工具 → 执行 → { ok: true }
round 1: 请求工具 → 执行 → { ok: true }
round 2: 请求工具 → 执行 → { ok: true }
...
```

**每一次局部动作都成功了。整个任务永远不会完成。**

这就是 4.1 里那个问题的实验形态。它证明的是：

> **工具执行成功 ≠ 任务有进展。**

这两件事在日志里的表现几乎一样（都是绿色的 `tool.completed`），但含义完全不同。**能区分它们的只有一个东西：硬性的轮次上限。**

### 4.10.1 修复，以及修复的边界

修复方式是硬上限，并**保留一条断言上限触发的回归测试**。测试要断言的正是"运行在到达上限时失败"，而不是"运行成功了"。

**一条重要的实现纪律**：你**可以**加"重复等价调用检测"作为改进（同样的工具、同样的参数，连续出现就提前终止）。但它**必须是在硬上限之上**的补充，不能替代硬上限。

原因：重复检测是一种**启发式**。它可能误判（两次看起来一样的调用其实是必要的重试），也可能漏判（每次参数差一点点）。**启发式的失效模式是"在某个边界情况上不再生效"，而硬上限的失效模式不存在——它是计数，不是判断。**

### 4.10.2 第二个实验：取消一个长工具

在工具执行中途触发取消，观察两件事：

1. 引擎是否产出了 `run.cancelled`；
2. **工具是否真的停了。**

第 2 件事的答案通常是"不一定"。参考实现把这句话写得很直白：

> 引擎产出的"已取消"结果，**不证明**一个不配合的工具已经物理停止。宿主必须自己管理未完成的工作。

这个区别在第 12 章会变成一个完整的设计问题：**谁负责等待那些已经收不到信号的工作？**现在只需要记住：**"我通知了"和"它做到了"是两件不同的事实，你不能把后者写成断言。**

## 4.11 这一章在整本书里的位置

到这里，你有了一个**有界、可取消、有明确终态**的循环。它已经能完成第 3 章做不了的事：多步、自适应、可能失败但能恢复。

但循环本身不知道"什么时候该多用一步、什么时候该早点停下来问人"。

**循环里的自由度应该给多少？**——哪一步必须固定下来，哪一步可以交给模型临场决定？

第 5 章回答它。

---

**本章小结**：循环由消息列表、工具注册表、轮次计数、终止判定四件东西构成，缺一不可。`maxToolRounds` 的上限落在**工具轮次**上：最多 `maxToolRounds + 1` 次模型调用、`maxToolRounds` 个工具轮次，**它既不是单轮调用数上限，也不是成本上限**。"没有工具调用"是唯一正常出口，"到达上限"必须判失败。工具执行失败是**观测结果**（可恢复），未知工具是**运行失败**（不可恢复）——这条区分守住了"模型无法扩张自己权限"这个不变量。而**局部动作全部成功，不等于任务有进展**。

**行动清单**

1. 把你的循环上限手工推一遍：给它一个具体的上限值，写出"最多几次模型调用、最多几个工具轮次"。
2. 断言你的循环**恰好产出一个终态事件**，并断言事件序号连续。
3. 加一条**"到达上限必须失败"**的回归测试，并构造一个"永远成功的工具 + 永远请求它的提供方"来触发它。
4. 检查你的工具失败处理：**工具抛错时，整轮运行是否被错误地掐掉了？**如果掐掉了，改成可恢复观测。
5. 检查你的工具解析：**未知工具名会不会被动态创建？**如果是，改成直接失败。
6. 给每个长任务工具加上进度上报；检查所有 `addEventListener` 都有配对的 `removeEventListener`。
