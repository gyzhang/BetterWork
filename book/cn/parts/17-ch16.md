# 第 16 章 可编辑 PPT：最后一页的数字要和第一页对得上

**本章承诺**：读完这一章，你能把一个已复核的报告变成一份**别人能改、每个数字都能追到指标 ID、且改一个输入时所有重复数字同步更新**的演示文稿。

**读完后你能回答**

- 为什么"把每段话放上一页"必然失败？演示和文档的本质差别在哪？
- "可编辑"在技术上有确切定义吗？一张图能算可编辑页的一部分吗？
- 同一个数字出现在四个地方（第 2 页正文、第 2 页图表、第 3 页表格、第 5 页行动项，跨三页），改一个输入后怎么保证四处一致？
- 为什么应用界面的浅色/深色设置**不能**影响公司演示文稿的颜色？

---

先看一次失败。

一份报告被"变成"了演示文稿。做法很直接：把报告里的每一段话，按顺序放进一页幻灯片。

结果是**一份有人打开、没有人使用的 PPT**：

| 问题 | 具体表现 | 根本原因 |
|---|---|---|
| **字太小** | 为了让一段话塞进一页，字号降到了 9pt | **用缩小字号解决内容过多**——错误的方向 |
| **数字不一致** | 图表里显示 16.7%，表里显示 16.67% | 两个元素**各自格式化**，没有共同的源 |
| **改不了** | 每一页是一张整页图片 | 收件人**连一个字都改不了** |

三处问题里，第一处是**设计错误**，第二处是**数据错误**，第三处是**交付错误**。它们是三种不同性质的问题，需要三种不同的修法。

> **核心判断 1**
>
> **演示文稿是一种不同的沟通格式，不是"更小的 Word 页"。**<br>
> 它必须**保住事实**，同时**改变信息的量与排列**。把一篇报告的段落原样搬上幻灯片，等于既没有保住可读性，也没有保住事实——因为搬的过程中字号被压小了、数字被重新格式化了。

## 16.1 从受众的决策开始，不从内容开始

这是整章的方向性决定，也是它和上一章最根本的差别。

写文档时你问的是："我要说清什么？"做演示时你要先问：**"听众要做什么决定？"**

一页幻灯片需要四样东西：

| 要素 | 回答什么 | 缺失时的症状 |
|---|---|---|
| **目的** | 这一页让听众做什么 | 变成"顺便提一下"的一页 |
| **主信息** | 一句话结论 | 听众自己找重点，通常找不到 |
| **支撑证据** | 数字、来源、约束 | 结论没有依据 |
| **版式** | 让前两者的关系可读 | 信息堆在一起，关系看不出来 |

**"目的"这一项是最容易被跳过的，也是最能救命的一项。** 一份五页的演示，每一页都应该能写出一个**动词**——"确认"、"了解"、"决定"、"行动"。写不出来的那一页，就是不该有的一页。

### 16.1.1 一个五页的例子

用第 14、15 章那套已核验的 P1 指标：

| 页 | 目的 | 主要内容 | 可追溯性 |
|---|---|---|---|
| 1 | **陈述决策** | 在批准下期工作前，先复核异常 | 复核者简报 |
| 2 | **汇总支出** | 实际 250；预算 300；偏差 -50 | 整体指标 ID |
| 3 | **说明分布** | A：200 / 220；B：50 / 80（实际 / 预算） | 分项指标 ID |
| 4 | **暴露不确定性** | 工时整体吻合，但分项偏差方向不同；效率**未被证明** | 工时指标 + 明确标注的假设 |
| 5 | **要求行动** | 确认项目完成状态、调查异常 | **建议**，不是已测定的事实 |

<div align="center"><img src="images/fig-16-1-five-slides.png" alt="图 16-1 五页演示的目的、内容与可追溯性" width="1150"/></div>

**读图指引**：注意最右一列。**每一条内容都挂着一个可追溯的东西**——要么是指标 ID，要么是被明确标注的假设。**没有第三条路。**

第 4 页和第 5 页值得单独看。

第 4 页是**唯一一页说"不知道"的页**，而它是整份演示里最重要的一页。工时整体吻合（30 = 30）但 A 偏 -2、B 偏 +2 —— 这两个偏差**互相抵消了**。一份只看合计的报告会得出"工时完全按计划"的结论，**而这是错的**。

第 5 页是**建议而不是事实**。这一页不能出现"（数据支持：建议确认项目完成状态）"这种写法——**建议不是被数据支持的，它是被数据启发的人的判断。** 区分这两者，是这一章在语言上的硬要求。

### 16.1.2 关于颜色的一条具体规则

第 5 页提到"低于预算"，第 2 页的柱状图会用颜色表示。这里有一条必须写明的规则：

> **不要把"有利"仅仅编码成绿色。**

原因很实际：**支出低于预算，可能意味着项目没做完。**

在颜色语义上把它标成"好"，等于在数据层面加了一个**源数据里没有的判断**。这在第 8 章"检索到不等于为真"之后又多了一层：**呈现方式也会引入判断，而呈现方式通常不经过复核。**

正确的做法是：颜色只编码**方向**（高/低、多/少），或者配上文字标注。方向的语义在不同文化里还有差异——本书按中文财务阅读习惯采用**涨红跌绿**，这一点必须在图例里写明，不能假设所有人都知道。

## 16.2 可编辑性有确切定义

"可编辑"不是一种感觉，它有可以逐条检验的定义：

<div align="center"><img src="images/fig-16-2-single-source.png" alt="图 16-2 改一个输入：重算路径与重复数字的核对点" width="1150"/></div>

**读图指引**：看上面第二步"重算受影响指标"——**它是整条链里最容易漏的一步。**再看下面那一行四处位置：**同一个数字出现在几处，就有几个核对点**，这是"最后一页对得上第一页"的机械含义。

| 元素 | 合格 | 不合格 |
|---|---|---|
| 必需的文本 | **真正的文本框对象** | 页大小的图片 |
| 必需的表格 | **真正的表格对象**（单元格可编辑） | 截图、或整页图片 |
| 图表 | **有可编辑的图表数据**，或有一张**已登记的、可编辑的源数据表** | 只有一张渲染好的图 |
| 装饰性插图 | 可以是图片 | —— |
| **整份必需交付物** | 不得压平成图片 | **整册转图即失败** |

第四行是对第一行到第三行的松绑：**图片不是被禁止的。** 一张装饰性插图、一张产品截图，用图片完全没问题。被禁止的是**用图片替代必需的可编辑内容**。

第三行值得展开。为什么图表必须"有可编辑的图表数据，或有一张已登记的源数据表"？

因为**图表是最容易藏数字的地方**。一个柱子的高度、一个数据标签的四舍五入、一条趋势线的斜率——这些东西在视觉上看起来"就是这样"，而**没有人在复核它**。

而参考实现给了这条要求一个非常实在的技术理由：

```ts
// 参考实现源码（BetterWork · apps/desktop/src/main/infrastructure/office-parser.ts，MIT）
if (names.some((name) => name.startsWith('ppt/charts/'))) warnings.push('unsupported-feature');
```

**解析器看到 `ppt/charts/` 目录时，只产出一条"不支持的特性"告警就结束了。** 它**读不出图表里的数值。**

这意味着什么？意味着**如果你的数字只存在于图表里，那么你的自动化校验永远看不到它们。**

> **核心判断 2**
>
> **每一个关键数字都必须存在于一个校验能读到的地方。**<br>
> 图表是**呈现**，不是**存储**。把数字只放在图表里，等于把它从可核验的范围内移出去了。<br>
> 正确的形态是：**数字存在实体表格（或指标记录）里，图表从它渲染而来。** 于是校验程序比对的是表格，人看的是图，两者同源。

## 16.3 主题属于交付物，不属于应用

这一节短，但它拦下的是一类很尴尬的现场事故。

> **一份演示文稿的主题，是这份交付物的属性，不是宿主应用的属性。**<br>
> **改变宿主应用的浅色 / 深色外观，不得意外地改变一份公司演示文稿的颜色。**

为什么会有这个问题？因为很多实现图省事，**把文档样式和应用界面主题共用同一套变量**。于是用户为了自己看着舒服把应用切到深色模式，导出的 PPT 就成了深色底——**而公司模板是白底深字**。

正确的做法是**两份独立的契约**：

| 契约 | 管什么 | 谁改它 |
|---|---|---|
| **应用界面令牌** | 应用自己的按钮、面板、菜单 | 用户偏好 |
| **文档样式** | 交付物里的字体、颜色、间距 | 模板 + 内容模型 |

这两份契约**不得共用一个变量**。这是第 12 章"状态要活过进程"的同构要求：**交付物的属性不能被一个与之无关的会话状态改变。**

## 16.4 改一个输入，不是改一个文本框

这一节回答本章标题的最后半句。

假设复核者说："本期实际支出应该是 270，不是 250。"（**沿用第 14 章的口径**：金额以整数最小单位存储，1 个货币单位 = 100 个最小单位；本节与图 16-1 里写的都是**显示值**，即 250.00，也就是存储值 25000。）

**错误的做法**：找到写着 250 的那个文本框，改成 270，保存。

为什么错？因为 250 可能出现在**四个地方**：第 2 页的正文、第 2 页的图表、第 3 页的表格、第 5 页的行动项。改了一个，剩下三个就是**新旧混杂**的一份文件。而这份文件**看起来完全正常**。

**正确的做法是一条链**：

```
复核过的源修订（270）
  → 重算受影响的指标
  → 更新内容模型
  → 重新生成受影响的那一份演示文稿版本
  → 核对每一个重复出现的数字
```

注意第一步：**改动发生在源修订上，不是发生在输出上。** 这是本章与上一章共同的纪律，也是第 12 章"状态必须活过进程"在交付层的体现。

第二步"重算受影响的指标"是这条链里最容易漏的一步。改一个支出数字，会影响：实际合计、偏差、偏差比例、分项偏差、可能的图表刻度、以及第 4 页那句"效率未被证明"的措辞是否还成立。**"受影响的"这四个字需要一次真正的分析，而不是一次搜索替换。**

第四步"核对每一个重复出现的数字"是可机械化的。本章把它变成一条可执行规则：

> **在生成之后，抽取全部文本、表格与指标引用，与内容模型逐条比对。**<br>
> **任何一处不一致就拒绝发布。**

### 16.4.1 旧版本仍然是有效的历史产物

这条规则容易被误解成"旧版本作废了"。不是的。

> **旧的那一份演示，仍然是它自己那套输入的**有效历史产物**。**

这句话有两个后果：

- **不要删掉它。** 它是"当时我们基于什么做决定"的证据。
- **不要改写它。** 改了就抹掉了历史。

还有一条操作性的区分：**人工可编辑性测试的那份副本，是一次独立的演示，不是"可重现生成"的替代品。**

意思是：你为了验证"这份文件真的能改"，打开它、改了一个字、存了。**这份被改过的文件不能当作交付物**——因为它已经和内容模型不一致了。**测试用过的文件要和正式交付物分开保存，并且明确标注。**

## 16.5 参考实现的边界：能借用什么，不能借用什么

上一章出现过一次的主张，这一章以更强的形式再出现一次。

参考实现里有一段代码，作用是核验"只有成功的执行才能登记产物"：

```ts
// 参考实现源码（BetterWork · file-artifact-service.ts，MIT）
if (execution.status !== 'succeeded') {
  throw new Error('Only succeeded executions can register artifacts');
}
if (!execution.outputIds.includes(input.outputId)) {
  throw new Error('Output is not registered for this execution');
}
```

加上它周围的逻辑，这一段覆盖了：运行归属、结构报告身份、**实际字节的哈希**、授权是否仍然有效、重复登记。

**这些是"登记与来源"的能力。** 它们回答的问题是：**"这份文件是从哪来的、它验过没有、它有没有被换过。"**

它们**不回答**的问题是：**"这份文件的内容对吗。"**

下表的分界线就是这一节的结论。**左列是登记能给的保证，右列是它给不了的。**

| 登记与来源**能**证明 | 登记与来源**不能**证明 |
|---|---|
| 文件来自哪一次执行 | **业务正确性** |
| 它注册时的字节是什么 | 数字算得对不对 |
| 它的哈希有没有变过 | **原生可编辑性** |
| 它属于哪一次运行 | 版式有没有问题 |
| 预览图与渲染器版本的关系 | 受众能不能看懂 |

右边那一列里的每一项，都需要**别的检查**。这就是 16.2 节那四个维度存在的理由。

还有一句必须说清的话：**缩略图和"注册成功"都不能证明业务正确或原生可编辑。** 缩略图是**派生缓存**，它随版本产生、可随时删除重建，**不参与成果真实性校验**。参考实现的实现里这个区分很清楚——缩略图放在单独的目录里，还有一个渲染器语义版本的标记文件：

```ts
// 参考实现源码（BetterWork · file-artifact-service.ts，MIT）
/** 派生缓存目录：随版本产生、可随时删除重建，不参与成果真实性校验。 */
private thumbnailDir(versionId: string): string {
  return path.join(this.artifactFilesRoot, versionId, 'thumbnails');
}
```

这个细节值得学：**把"不可变的真品"和"可以随时生成的派生品"放在不同的位置，用不同的生命周期管。** 混在一起，迟早会有人拿派生品当证据。

## 16.6 三种做法的取舍

| 做法 | 适合 | 代价 |
|---|---|---|
| **手工做幻灯片** | 一次性工作 | 不能重复，不能复现，第 14 章的"可复核"直接不成立 |
| **截图式幻灯片** | 只需要"看一遍"的场合 | 不能有意义地修订，不能被程序检查 |
| **结构化渲染器** | 需要可编辑、需要一致格式、需要复现 | 要维护版式规则与质检 |

第二行的代价值得补一句：**截图式幻灯片不只是"不能改"，它还让"一致性"这件工作失去了落点。** 当数字只存在于像素里，你既不能自动比对，也不能自动重算。

第三行的"要维护版式规则与质检"不是小事。**PPT 的版式质量是这本书里最需要机械检查的一环**——本书自己的配图生产线就用了三道闸门（配色、版式适配、数据几何）来拦下人工容易漏掉的问题。而**机械闸门仍然拦不住全部**：箭头画反、文字压在半透明色块上、表头写"五道"而实际四行——这三类只有**逐张目视**才能发现。第 16 章的验收要求因此必须包含**人工目视**这一项，它不能由解析器替代。

**PPTX 生成的候选实现**：`PptxGenJS` 是 TypeScript 教学适配层的候选之一。它**不是**参考实现的生成后端，也**未经本书验证**。任何发布都必须自行固定版本、并做**具体模板特性**的测试。见附录 C 的 P13。

## 16.7 行业视角：汇报材料的"口径链"

在需要逐级汇报的场景下，演示文稿的问题往往不在技术层，而在**口径链**上。

一份部门月报，可能会经过这样的路径：

```
部门内部分析 → 部门负责人 → 分管领导 → 经营分析会 → 上报材料
```

每一层都会**摘要**上一层的结论。于是出现一个很实际的问题：**摘要到第几层，数字还算数？**

| 层 | 典型做法 | 风险 |
|---|---|---|
| 部门内部分析 | 完整指标 + 口径 + 局限 | 无 |
| 部门负责人汇报 | 摘出关键数字 | **丢掉口径**，数字被单独引用 |
| 分管领导汇报 | 再摘一次 | 数字开始出现在**没有分母**的句子里 |
| 上报材料 | 数字 + 一句结论 | **结论被当成了数据** |

这个链条上有两件事必须由本书的方法兜住：

**第一，口径要跟着数字走，而不是跟着文档走。** 第 14 章要求"每个数字带分母、单位、期间、源坐标"——这个要求的意义就在这里。**当数字被单独摘出来引用时，它身上的口径标签是唯一的防线。**

**第二，"建议"和"事实"必须在每一层都分开。** 第 16.1.1 节第 5 页的规则（建议不是被数据支持的）在每一层摘要后都要重新检查。**到了上报材料那一层，"建议确认项目完成状态"很容易被简化成"项目已完成"，因为后者读起来更像一个结论。**

这一节的工程结论只有一句：**演示文稿的生成流程要把"口径"和"事实/建议的区分"当作必须随数字一起传播的字段**，而不是当作可以事后补的说明。

**本章小结**<br>
一份好的演示**改变的是呈现，不是事实**。原生对象让修订成为可能；带版本的内容与输入映射让它可以被解释；**结构、事实一致性、可编辑性、可见版式**是四个独立且不能互相替代的判断（同第 15 章）。

**六道自检题**：

1. 一张图片能不能是"可编辑演示"的一部分？在什么条件下可以？在什么条件下绝对不行？
2. 为什么"来源注"也需要**目视**检查，而不是只做文本比对？
3. 当 V2 的输入变化影响了出现在四个位置上的同一个数字，会发生什么？正确的处理顺序是什么？
4. 为什么"应用切到深色模式"会影响一份公司 PPT 的颜色？这是设计缺陷还是使用问题？
5. 一份缩略图能证明什么？不能证明什么？
6. 复核者说"实际支出应改为 270"。你的第一个动作应该是"找那个文本框"吗？如果不是，应该是什么？

**想得更远一点**：这一章处理的是**一次性**的交付。第 17、18 章处理的是**重复**的交付——一份报告每个季度都要出一次，而且每期的数据都不同。到那时你会发现，本章的"重复数字核对"会膨胀成"跨期数字核对"，而第 14 章那个缺失预算的问题会以一个全新的形态回来。

**行动清单**

1. 为你手上的演示稿**逐页写一个动词**。写不出动词的那一页，先删掉或改写，不要先调字号。
2. 把每一页的数字**绑定到指标 ID**，把每一句实质陈述**绑定到证据**。绑定不上的，标成"未验证"或删除。
3. 检查所有图表：**它有没有可编辑的图表数据，或者一张已登记的源数据表？** 没有就先补上，因为你的自动校验看不到图里的数。
4. 做一次**改输入的实验**：改一个源数字，走完整条重算链，然后核对每一个重复数字。记下你漏掉了几处。
5. 打开交付物**逐页目视**：看长标签、看来源注、看有没有文字压在色块上。**不要只检查标题。**
6. 检查你的样式实现：**有没有把应用界面主题和文档样式共用变量？** 有就拆开。
