# 第 13 章 观测、评估与预算：可度量的才可交付

**本章承诺**：读完这一章，你能设计出一套可复现的评估，并用它回答"这次改动到底让系统变好了，还是只是运气好"。

**读完后你能回答**

- 三类评估分别需要什么证据？为什么"脚本化的假模型跑通了"不能证明线上质量？
- 为什么评估要看 pass^k（k 次全成功），而不是 pass@1（至少一次成功）？
- 一个评测基准的分数，在什么条件下才可以被引用？

---

先看一次改动。

团队把检索的 top-k 从 5 调到了 12，理由是"多给一些材料，模型应该能答得更全"。改完之后，他们挑了一个任务跑了一遍——**结果变好了。**

于是改动被合并了。

三周后，用户开始抱怨"回答变罗嗦了，而且经常引一些不相关的段落"。

**那次"验证"错在哪？**三个地方，每一个都是独立的：

| 错处 | 问题 |
|---|---|
| **样本量 1** | 一个任务跑一次，**模型本身带随机性**，你分不清是改动起效还是运气 |
| **只看了好的一面** | 它"变好了"的那个任务，恰好是一个**需要更多材料**的任务——这不是随机抽样 |
| **没有量成本** | top-k 从 5 到 12，上下文变成原来的 2.4 倍。**成本的变化没有被记录，所以也从未进入决策** |

三处错处的共同点是：**它们都不是"技术能力不足"，而是"没有把判断变成可测量的"。**

> **核心判断 1**
>
> **没有测量的改动，不是"改进了"，是"换了一种做法"。**<br>
> 而"换了一种做法"在短期看起来通常是变好的——因为你是在看了结果之后才决定要改的。<br>
> 代价是你要在改之前就准备好测量方式。**这个顺序不能颠倒**——先跑一遍看看再决定怎么测，等于让结论来选择证据。

## 13.1 追踪：不是日志，是事件

"记日志"和"可观测"的差别在结构上：

| | 日志 | 追踪 |
|---|---|---|
| 形态 | 文本行 | 结构化事件 |
| 能不能被程序消费 | 勉强（要解析） | **能** |
| 有没有顺序保证 | 没有 | **有**（单调递增的序号） |
| 能不能关联到一次运行 | 靠字符串 | **有运行标识** |

第 4 章那个事件工厂给出了追踪的最小形态：

```ts
// 参考实现源码（BetterWork · packages/agent-core/src/agent-engine.ts）
create(input: AgentRuntimeEventInput): AgentRuntimeEvent {
  return { ...input, id: randomUUID(), runId: this.runId, sequence: this.sequence++, createdAt: Date.now() };
}
```

`id` + `runId` + `sequence` + `createdAt` —— 四个字段构成"可被程序处理的事件"的最小集合。

参考实现的运行时事件词汇表恰好是 **13 种**：

```text
run.started
message.started / message.delta / message.completed
reasoning.delta
tool.requested / tool.started / tool.progress / tool.completed / tool.failed
run.completed / run.failed / run.cancelled
```

**这 13 种事件就是"可观测"的全部内容。**它回答了：这次运行开始了、说过什么、想过什么、请求了什么工具、工具跑得怎么样、最后怎么结束的。

### 13.1.1 两个必须遵守的纪律

**纪律一：原始事件不进主界面。**

参考实现把这条写成了规范：

> 原始 Run 事件不得出现在主界面。工具卡片显示阶段名与一句摘要，原始载荷只在过程面板的折叠区里。

**为什么？**因为原始事件是**给机器和排障看的**，它的字段名、嵌套结构、时间戳对用户毫无意义。直接展示它，会让界面变成一份调试输出。

**纪律二：追踪必须脱敏。**

结构化追踪里不能出现密钥（第 0 章）、不能出现完整的敏感路径、不能出现用户未授权的材料内容。

**这两条纪律的方向相反**——一条要求"别给用户看"，一条要求"别记录敏感内容"。**它们的交集是：追踪记录是一份"给内部用的、经过脱敏的、结构化的东西"。**三个限定词缺一不可。

## 13.2 三类评估，必须分开

这是本章最重要的一张表。三类评估的**证据来源完全不同**，混在一起会让所有结论都不可信。

| 类型 | 用什么跑 | 能证明 | **不能**证明 |
|---|---|---|---|
| **① 确定性检查** | 断言、单元测试、结构校验 | 代码逻辑正确；格式合法；边界被拒 | 输出内容是否**有意义** |
| **② 线上模型评估** | 真实模型 + 固定任务集 | 在**这批任务**上的行为质量 | 在其他任务上的表现；生产环境的稳定性 |
| **③ 人工文档审阅** | 人读产物 | 可读性、专业判断、是否可用 | 规模化（人读不完） |

**三条最容易被混淆的边界：**

| 有人说 | 实际上 |
|---|---|
| "测试全过了，所以系统是好的" | 测试只证明了① |
| "我跑了 20 个任务都成功了，所以可以上线" | 那 20 个是你的任务，不是生产的任务 |
| "用户看了说还行" | ③ 不能覆盖①和②，读过一份文档不代表边界有效 |

参考实现自己的实践正好体现了①和②的分离——**它用脚本化的假提供方做确定性测试**：

```ts
// 参考实现源码（BetterWork · packages/agent-core/src/fake-provider.ts）
/**
 * 教学用 Provider：不联网、输出可预测，用于稳定复现事件顺序与工具行为。
 */
```

而这个假提供方**不能**证明线上质量。参考实现把它写进了规范要求里：

> **脚本化提供方不是线上模型质量的证据。**

同一句话在参考实现的依赖准备里也有对应版本（第 0 章）：**"mock 通过、真实库失败"**。

**它们都是同一类错误：用①的证据去支持②的结论。**

## 13.3 评估集从失败里来，不从想象里来

怎么构造②的任务集？一个常见做法是"想一些有代表性的任务"。这个做法有一个系统性缺陷。

> **你想象出来的任务，带有你想象时的分布。**

而真实工作的分布是另一回事：输入被截断了、需求是含糊的、工具返回了 500、用户中途改了主意。

**正确做法：从生产失败里抽任务。**

| 来源 | 为什么好 |
|---|---|
| **一次真实失败** | 它带着真实的分布：那个被截断的输入、那个含糊的请求 |
| **一次用户抱怨** | 它带着"你没考虑到的那件事" |
| **一次人工返工** | 它带着"为什么产出不可用" |

一条公开的分析把这个差别量化过：

> **数据卡**：基准任务与真实工作之间的"表示差距"
>
> **口径**：公开分析引用的一项对比指出，模型在基准任务上的表现与在真实工作分布上的表现之间存在显著落差，文中给出的读法是"表示差距在 **26% 与 1% 以下**之间"——即模型已经"注意到"基准是一个可被识别的分布<br>
> **时点**：2026 年（第三方分析，原始测量方法与样本以原始材料为准）<br>
> **来源**：公开的智能体评估分析，见附录 C<br>
> **局限**：**这两个数字来自特定分析，不可外推为普遍规律。**它们的用处是支持一条方法论：**用生产的失败做评估集**，因为一份"自己想出来的"任务集，其形状本身就是被你想出来的

### 13.3.1 评估集还要保持"私有 + 轮换"

一条容易被忽略的操作建议：

> 如果你的评估集最终进了公开仓库、支持工单、或者一个会保留数据的上游提示里，**它就获得了与公开基准一样的污染风险**——只是慢一点。

**做法**：留一部分评估集不公开，并定期轮换。轮换的节奏取决于你的任务变化速度，不是日历。

## 13.4 看 pass^k，不看 pass@1

这是一条会改变你对"成功率"理解的纪律。

| 指标 | 含义 | 什么时候用 |
|---|---|---|
| **pass@1** | 单次尝试成功 | 一次性任务，或成本不重要 |
| **pass^k** | **k 次尝试全部成功** | 任何会被重复执行、且失败有代价的场景 |

为什么必须看 pass^k？因为**概率会乘**。

假设单次成功率是 90%。看起来不错。那么：

| k | pass^k = 0.9^k |
|---|---|
| 1 | 90% |
| 3 | 72.9% |
| 5 | 59.0% |
| 10 | 34.9% |

**一个"单次成功率 90%"的系统，连续跑十次全部成功的概率只有三分之一。**

而"连续跑十次"在生产里完全正常——一个每天跑一次的任务，十天内不出问题的概率就是 34.9%。

**这就是为什么"我试了一下，好像可以"这句话在工程上毫无价值。**

> **核心判断 2**
>
> **智能体的可靠性不是一个数，是一个关于次数的曲线。**<br>
> 报告"成功率"时必须带上 k——**或者至少说明"这是单次尝试的成功率"。**<br>
> 代价是你的评估成本至少是 k 倍。而"不评估"的代价，是把样本量为 1 的实验放在生产环境里做。

### 13.4.1 一个立刻能用的最小评估

不需要框架，只需要一个循环：

```text
准备：同一批任务（至少 10 个），每个任务有明确的成功判据
对每个任务：
  跑 k 次（k ≥ 3）
  记录：每次是否成功、耗时、token、失败原因
输出：
  pass@1 = 至少成功的任务数 / 任务数
  pass^k = k 次全成功的任务数 / 任务数
  + 失败分类表（见 13.5）
```

**这个表跑一次，你对系统的了解会超过读十篇框架文档。**

## 13.5 失败要分类，不能只有一个"失败"

评估的价值大部分在**失败分类**里。一个只说"失败了 4 个"的报告，帮不上任何忙。

四类必须分开：

| 类别 | 定义 | 修哪一层 |
|---|---|---|
| **模型错误** | 输入没问题、工具没问题，模型判断错了 | 提示、模型选择、任务定义 |
| **数据错误** | 输入本身有问题（缺字段、单位不一致、重复行） | 数据校验、口径确认 |
| **工具错误** | 工具实现有 bug，或外部服务不可用 | 工具代码、外部依赖 |
| **运行时错误** | 超时、取消、进程中断、权限被拒 | Harness（第 11、12 章） |

**为什么必须分开？**因为它们指向完全不同的修复动作。把它们合在一列里，你会得到一个"失败率 20%"的数字，然后只能靠猜去改。

而且这四类有一个**优先级**：

```text
先修运行时错误 → 再修工具错误 → 再修数据错误 → 最后才是模型错误
```

**理由**：前三类是"确定的缺陷"，修一次就少一类；模型错误往往是"需要长期调优"的那种。**先做能一次解决的事。**

## 13.6 token、时延与成本：参考实现没有的那一块

这一节要先把一件不体面的事说明白。

> **参考实现当前没有 token 与成本的计量。**

这不是猜测。它的运行时事件词汇表里**没有任何 usage 或 cost 事件**——13 种事件全部是行为事件，没有一种是计量事件。

**所以第 13 章的这部分，不是"可以参考现成实现"，而是"你必须自己补"。**

本书的处理方式是明确的：**缺失的功能标注为待补，而不是降级为可选，也不是假装它已经在了。**

需要补的第一件事是**在模型适配器里把用量读出来**。大多数兼容接口在流式响应的最后会带一段用量信息；适配器要做的是把它变成一个事件，而不是丢掉。

```text
需要新增的事件（示例形状）
  { type: 'usage.reported', runId, model, inputTokens, outputTokens, cachedInputTokens? }
```

有了它，三样东西才成立：

| 指标 | 需要什么 |
|---|---|
| **单次运行的 token** | 用量事件求和 |
| **时延** | 事件之间的时间差（已有 `createdAt`，所以这一项**现在就能算**） |
| **成本** | 用量 × 单价（单价是配置，不是代码） |

**注意第二项**：时延**现在就能算**，因为事件里已经有 `createdAt`。**这是一个可以立刻做、不需要任何新基础设施的评估指标。**

## 13.7 无数据即未知

这一节是第 0 章那条纪律在评估层的完整形态。

**没有用量数据时，成本是"未知"，不是 0，也不是"估算"。**

| 做法 | 后果 |
|---|---|
| 报 0 | 报告看起来完整，但它是错的 |
| 按平均值估算 | 把一个编出来的数字写进报告 |
| **报"未知"** | **正确**——它会让"补上计量"变成一个待办 |

**为什么这一条在评估里格外重要？**因为评估表是**用来做决策的**。一份填满了估算值的评估表，会让决策者以为自己看到了全貌。

**一个"未知"格子的价值，远高于一个"看起来合理"的估算值。**前者会被追问，后者不会。

## 13.8 基准：它是分布，不是结论

2026 年的公开评测图景值得完整看一遍——**目的不是记住分数，而是学会怎么读分数。**

> **数据卡**：2026 年 8 月的公开评测快照
>
> **口径**：各基准官方榜或发布方公布的最高分（同一时点不同榜单口径不可比）：SWE-bench Verified 79.2%（2025-12 条目）；SWE-bench Pro 公开 split 61.5%；Terminal-Bench 2.0 84.7% ± 2.1；Terminal-Bench 2.1 83.8%；τ²-bench 87.9%（pass@1）；GAIA 74.5%（成本受控榜）；OSWorld 人类基线 72.36%；METR 时间跨度指标显示"50% 可靠完成的任务时长"约每 7 个月翻一倍<br>
> **时点**：2026 年 8 月（各条目发布日期不同，逐条见附录 C）<br>
> **来源**：各基准官方榜与发布方材料、第三方汇总分析，见附录 C<br>
> **局限**：**这些分数之间不可横向比较**——不同基准测不同的轴，不同榜单的采样与预算口径不同。更要紧的是：**一条没有发布日期的分数不是可核查的**。引用任何分数时必须带上**发布日期 + 评测执行方 + 采样方式（pass@1 还是 pass^k、有没有预算限制）**

### 13.8.1 基准已经分裂成六个轴

2026 年的一个重要变化是：**没有"下一个 SWE-bench"了，因为问题分裂了。**

| 轴 | 代表基准 | 测什么 |
|---|---|---|
| 编码 | SWE-bench Pro / SWE-rebench | 仓库级缺陷修复；抗污染 |
| 终端 | Terminal-Bench | 端到端终端任务 |
| 工具 + 人 | τ²-bench | 工具调用 + 策略遵从的**一致性** |
| 图形界面 | OSWorld | 桌面 GUI 长程任务 |
| 长程耐力 | METR 时间跨度 | 可靠完成的任务时长 |
| 经济价值 | Agents' Last Exam 等 | 专业工作流的可验证产出 |

**"六个轴"这件事本身就是一条方法论**：它说明**没有一个单一分数能代表"智能体能力"**。任何把六个轴压成一个数的排名，都在隐藏信息。

### 13.8.2 六个必须知道的读法陷阱

公开分析把厂商"美化数字"的手法归纳成了六条，值得逐条记住：

| 陷阱 | 表现 | 应对 |
|---|---|---|
| **用 best-of-N 当头条** | 大字写 pass@8，pass@1 藏在脚注 | 问"这是 pass@1 吗" |
| **匿名脚手架** | "内部智能体框架"——调过基准，但你拿不到 | 问"分数是模型还是 harness 的" |
| **子集选择** | "在 300 个任务的子集上" | 问"怎么选的、谁选的" |
| **无界预算** | 不报 token、时长、重试上限 | 问"花了多少" |
| **不报污染** | 不说任务发布时间 vs 训练截止 | **沉默就是答案** |
| **小数位剧场** | 把 93.4 比 93.1 当排名 | 问"运行间方差是多少" |

**第二条（匿名脚手架）在 2026 年变得特别重要**，因为它有一个量化的公开证据：

> **数据卡**：脚手架对分数的影响可能大于模型
>
> **口径**：公开分析引用的一项对比显示，**同一个 Claude Opus 4 模型在两个不同的编排脚手架下，GAIA 分数为 64.9% 与 57.6%**（相差 7.3 个百分点）；另有公开表述称框架选择可使同模型上的基准表现相差最多约 30 个百分点<br>
> **时点**：2026 年（第三方分析引用，原始测量以 Princeton HAL 等材料为准）<br>
> **来源**：公开的智能体框架对比与基准分析，见附录 C<br>
> **局限**：**这两个数字来自特定评测设置，不可外推。**它们的用处是支撑一条判断：**基准分数是"模型 + 脚手架"的联合结果，不是模型属性。**所以"换个更强的模型"未必改善你的系统——**而"改你的 Harness"往往可以**（这条正是第 11 章那个 Harness 结论的定量侧证）

## 13.9 预算：可度量的才有上限

第 4 章说过一句：**轮次上限不是成本上限。**这里补上成本上限怎么做。

预算要管四样东西，它们**互相独立**：

| 预算 | 单位 | 拦住的失败 |
|---|---|---|
| **轮次** | 决策次数 | 死循环 |
| **token** | 模型用量 | 上下文膨胀导致的成本爆炸 |
| **时间** | 墙钟 | 外部服务慢导致的"挂着不动" |
| **调用数** | 外部请求次数 | 检索/工具被反复调用 |

**为什么必须四样都有？**因为任何一样都可以被另一样绕过：

- 只有轮次上限：一轮里可以做 100 次检索（轮次是 1）；
- 只有 token 上限：可以做无限次不耗 token 的本地操作；
- 只有时间上限：可以在这段时间里烧掉巨额 token；
- 只有调用数上限：可以让单次调用极慢。

**任何一项触顶都应该触发同一个动作：停止，并报告已经完成到哪一步。**

参考实现在依赖准备里给出了一个相关的实现细节——**取消要留一个"汇合超时"**：

```ts
new Promise<void>((resolve) => { setTimeout(resolve, cancelJoinTimeoutMs); })
```

即：发取消之后，**只等一个有限的时间**去收敛，不无限等。

**这条值得抄。**一个"发取消然后等它结束"的实现，会在对方不配合时永远等下去（第 4 章那个"不配合的工具"）。**取消之后必须有第二个超时**，这是唯一能保证"一定会停"的做法。

### 13.9.1 熔断：失败次数本身也是一个预算

第 5 章讲过"无进展重复"。它在预算层的对应物是：**连续失败 N 次就停止**。

参考实现在一个公开的工程实践总结里被表述为设置迭代上限作为"熔断器"——超过若干次（公开讨论中给出的经验值是 3–5 次）就强制终止，而不是无限重试。

**熔断的上限值和轮次上限是两种不同的预算**：

| | 轮次上限 | 熔断 |
|---|---|---|
| 计什么 | 所有轮次 | **失败的轮次** |
| 触发语义 | 用完了配额 | **重复失败说明方向错了** |

## 13.10 故意失败：三个必须能检测的失败

### 13.10.1 流畅但无依据的输出

**构造**：一个任务，输入里明确缺少某个事实，而任务要求解释"原因"。

**期望的检测**：输出里出现因果表述，但该原因在输入里没有任何对应字段。

**检测方式**（第 2 章、第 8 章已经给过工具）：

```text
A7：凡涉及因果的表述，必须满足其一：
    · 该原因在输入数据中有对应字段，并给出字段名与取值
    · 明确标注为「待验证的假设」
违反即失败。
```

**这个检测的价值在于它是机器可执行的。**不需要人去读——只要它没给出字段名，就判失败。

### 13.10.2 注入的回归用例

**构造**：把第 11 章那个注入材料做成一条固定的回归用例。

**期望**：每次改动之后重跑，**越界读取仍然被拒绝**。

**为什么注入要进回归集？**因为它防的是一个**会随重构而失效**的控制。一句边界判断被重构掉、或者一个默认值被改成"允许"，都不会导致任何显式测试失败——**除非你有一条专门的注入用例。**

### 13.10.3 一次"改坏了"的注入

**实验**：故意把 top-k 从 5 调到 20，然后跑完整的评估集。

**期望**：评估报告里三项同时变化——

| 指标 | 变化方向 |
|---|---|
| 质量 | 可能略升 |
| **成本（token）** | **明显上升** |
| **时延** | **明显上升** |

**如果报告里只有质量、没有成本和时延，这次实验就白做了。**

**"故意注入一次回归"是评估能力是否成立的检验**：一个无法检测出你人为制造的退化的评估，也不能检测出真实发生的退化。

一条值得知道的行业动态：

> **数据卡**：智能体可观测正在收敛到 OpenTelemetry
>
> **口径**：公开分析指出，行业正在以 OpenTelemetry 作为智能体遥测的通用标准：其 GenAI 特别兴趣组已发布面向智能体与框架的语义约定，定义了 `invoke_agent`、`create_agent` 等操作，以及模型名、输入/输出 token 数、结束原因等标准属性，使一条追踪能同时展示顶层的智能体跨度与嵌套的模型调用、工具执行跨度<br>

## 13.12 这一章在整本书里的位置

第四篇到这里结束。你的系统现在能：

| 章 | 得到什么 |
|---|---|
| 第 11 章 | 有边界，且边界有执行者 |
| 第 12 章 | 有身份、有终态、能恢复、能安全重试 |
| 第 13 章 | **能证明自己做得对不对** |

**"可度量"这件事是第四篇的收口。**因为它把前三篇的成果变成了可以判断的东西：边界有没有被绕过（负向用例）、恢复有没有奏效（中断回归）、质量有没有变化（评估集）。

第五篇换一个角度：前三篇讲的是"过程"，第五篇讲**结果**——**系统跑得再稳，它交出来的东西得是对的、能用的、别人能改的。**

那一篇从最硬的一类开始：数据。

---

**本章小结**：追踪不是日志，是**带身份与顺序的结构化事件**（参考实现有 13 种）；原始事件不进主界面，且必须脱敏。**三类评估必须分开**——确定性检查、线上模型评估、人工审阅，各自只能证明自己那一层，**脚本化提供方不是线上模型质量的证据**。评估集要**从生产失败里抽**，并保持私有与轮换。**看 pass^k 而不是 pass@1**——90% 的单次成功率在 10 次里全成的概率只有 35%。失败必须分成模型/数据/工具/运行时四类，并有修复优先级。**参考实现没有 token 与成本计量**——这是你必须补的部分；缺数据时报告"未知"，不报 0、不估算。**基准测的是分布，不是结论**：引用任何分数必须带发布日期、评测执行方与采样方式；脚手架对分数的影响可能大于模型。

**行动清单**

1. 检查你的追踪：事件有没有**身份与序号**？能不能断言"我收全了"？
2. 把三类评估分开列成三张表，**在每张表上写明它不能证明什么**。
3. 从最近的真实失败里抽任务，搭出你的评估集（**至少 10 个**；一次失败通常能贡献多个任务，不必限于几次失败）。
4. 给评估加 pass^k 指标（k ≥ 3），并记下 k 是多少。
5. 给失败加上四分类，并按"运行时 → 工具 → 数据 → 模型"的优先级排序修复。
6. 补上用量事件；暂时没有的地方，报告里写"未知"。
7. 把 token、时间、轮次、调用数四个预算都实现，**并在取消之后加一个汇合超时**。
8. 故意注入一次退化（比如调大 top-k），确认评估能同时报出质量、成本、时延三项变化。
