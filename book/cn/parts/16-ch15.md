# 第 15 章 Markdown 与 Word：内容模型决定文档能不能改

**本章承诺**：读完这一章，你能设计一条从"已确认的结论"到"一份别人能改、能核、能追溯的文档"的转换链，并且说得清这条链上哪一环出问题会导致什么后果。

**读完后你能回答**

- 为什么"文件能打开"不足以说明文档是对的？一个合法的 Office 包还能错在哪里？
- 内容模型到底是什么？它和"一份 Markdown 文件"的差别在哪里？
- 一个模板**被允许**改变什么、**不允许**改变什么？
- 怎么证明"这份校验报告属于我交付的这一份字节"？

---

先看一次失败。

分析师在对话里逐条确认了结论。其中一条是：**本期支出比预算低 16.67%。**

他点了"导出 Word"。

收到的文件打开正常，页数对，字体也对。但有三处问题，**每一处单独看都不严重，合起来让这份文件不能交付**：

| 问题 | 表面现象 | 实际后果 |
|---|---|---|
| **数字不一致** | 文档里写的是 **16.6%**，对话里确认的是 **16.67%** | 两个数来自两次独立的格式化。**哪一个是"确认过的"？** |
| **标题是假标题** | "一、支出分析"是用加粗的普通文字做的 | 导航窗格是空的，目录生成不了，读屏软件读不出层级 |
| **表格是图片** | 表格是截图粘贴进去的 | 收件人**改不了任何一个数**，也没法把数据取出来 |

> **核心判断 1**
>
> **文档生成不是"把答案截个图存起来"，是一次有契约的转换。**
> 文件**不是**答案的呈现形式，它是**另一个交付物**——它有自己的正确性要求，而且这些要求和对话里的正确性要求**不是同一套**。

## 15.1 内容模型：把"意思"和"样子"拆开

这一章的核心只有一个动作：**把文档的含义和文档的呈现分开。**

前者叫**内容模型（content model）**，后者交给**渲染器（renderer）**。

一个内容模型里装的是：标题、受众、章节结构、段落、表格、**主张（claim）**、来源引用、以及**带类型的指标引用**。它不装字号、不装颜色、不装边距。

```
已核验的结果 + 证据登记表
  → 大纲与复核者决定
  → 已校验的内容模型            ← 事实在这里，只在这里
  → Markdown 渲染器 / DOCX 渲染器
  → 结构与内容检查
  → Office 应用中的可编辑性与目视复核
  → 带输入血缘的不可变输出版本
```

**为什么这个拆分是必须的？** 因为一旦数字出现在两个地方，你就会有两个数字。上一节的 16.67% 与 16.6% 就是这么来的——不是有人手抖，是**同一个事实被写了两遍**。

正确做法是：**内容模型持有唯一的指标记录，所有格式的渲染都从这一条记录取值。**

第 14 章那个已核验的结果，在内容模型里长这样：

| 字段 | 值 |
|---|---|
| 数值 | `25000`（最小单位） |
| 币种 | 币种甲 |
| 显示金额 | `250.00` |
| 预算 | `30000` |
| 偏差 | `-5000` |
| 比例 | `-1/6`（保留完整精度） |
| 期间 | `P1` |
| 来源 | 指向总账与预算的计算记录 |

**注意"保留完整精度"这一项。** 内容模型里存的是 `-1/6`，不是 `-16.67%`。四舍五入只在**渲染的最后一步**发生。

于是同一段正文在 Markdown 和 Word 里是：

> P1 期支出为 250.00，比 300.00 的预算低 50.00（低于预算 16.67%）。**这本身不构成"效率更高"的证据**；项目是否完成需要独立的证据。

第一句是**数值事实**。第二句**阻止了一个没有支撑的解释**。

这两句话在两种格式里必须逐字相同，因为**它们取自同一条记录**。渲染器不允许"自己算一个更漂亮的百分比"。

### 15.1.1 内容契约的字段定义

把上面的想法写成一张可校验的表。这是一份**教学约定的契约**，不是参考实现里现成的 API：

| 元素 | 必须携带的字段 | 校验什么 |
|---|---|---|
| 标题 | 稳定 ID、层级、文本 | 层级合法、文本非空 |
| 段落 | 文本、**主张 ID 列表** | 每一个实质性事实主张要么被映射、要么被明确标为"未验证" |
| 指标表 | 列定义、单位、指标 ID | 引用的指标必须存在；各行宽度一致 |
| 引用 | 来源版本、定位符、摘录身份 | 来源必须是被允许且当前可用的 |
| 修订 | 父版本、复核者要求、输入 | 父版本存在；**改动内容是显式的** |

第四行和第五行最容易被低估。

**"来源必须当前可用"** 意味着：正文里能引用一份材料，前提是这份材料**在生成这一刻确实存在、且版本可指认**。第 17 章会把这一条推到极端——一份编造了合理书名的参考文献表，**即使文笔流畅，也是失败**。

**"改动内容是显式的"** 意味着：不接受 `final-final2.docx` 这种命名。它没有说清改了什么、依据是什么。**版本号的作用不是区分先后，是记录理由。**

## 15.2 加粗的字不是标题

这是最容易被技术人员低估、被非技术人员最先发现的一类问题。

在 Word 里，"标题"有两种做法：

| 做法 | 实现 | 导航窗格 | 生成目录 | 读屏软件 | 换模板时 |
|---|---|---|---|---|---|
| **真标题** | 使用 `Heading 1` / `Heading 2` 段落样式 | ✅ 显示层级 | ✅ 可生成 | ✅ 播报层级 | 跟随模板 |
| **假标题** | 普通段落 + 加大字号 + 加粗 | ❌ 空 | ❌ 不能 | ❌ 播报为正文 | 逐个手改 |

**用字号做出"看起来像标题"的东西，不建立任何结构。** 这不是审美问题，是**能力问题**——文档失去了被程序处理的能力，而"能被程序处理"正是本书从第 6 章开始就一直在要求的东西。

同样的道理适用于表格：

- 表格必须是**真的表格单元格**，带表头、带单位、带来源注。
- 长表格需要**分页行为**与**跨页重复表头**，而且必须在你实际使用的**渲染器 + 阅读器组合**上测过。"理论上支持"不算测过。

> **一条具体的操作建议**
>
> 交付前打开导航窗格。**如果导航窗格里是空的，你的文档就没有结构。** 这个检查只需要三秒，能拦下一大类"看起来正常"的文档。

## 15.3 四个维度必须分别验证

这是这一章最重要的一节。文档的验收不是一个"通过/失败"，而是**四个互相独立的判断**：

<div align="center"><img src="images/fig-15-1-content-model.png" alt="图 15-1 内容模型与两条渲染链：四个独立验收维度" width="1150"/></div>

**读图指引**：看四张卡片最下面那一行（标着"易漏"或"必须"的那一行）。**注意后两张——可编辑性与可见版式只能由人和 Office 应用完成，纯解析器检查不到它们。**

| 维度 | 验什么 | 怎么验 | 谁最容易漏 |
|---|---|---|---|
| **结构** | 标题层级、表格单元格、段落完整性 | 解析器抽取后比对 | 用字号造假标题 |
| **事实** | 每个显示数字与内容模型一致 | 抽取**全部**数字，与记录逐条比对 | 只比对第一页 |
| **可编辑性** | 打开 Office 应用，改一个段落和一个单元格，存、关、重开、检查改动还在 | **必须人工操作** | 用图片代替表格 |
| **可见版式** | 长段落有没有截断、长表格有没有破版、来源注有没有溢出 | **必须目视** | 只看第一页 |

**为什么"文件是一个合法的 ZIP / Office 包"完全不充分？**

因为 Office 文件的本质是一个 ZIP 压缩包，里面是 XML。一个包可以是**结构完全合法**的——能被 `unzip` 出来、能被解析器打开、没有格式错误——同时内容全错、文字被裁掉、表格是图片。**"能读"和"读对了"是两个不同的问题。**

这个区分在本书里出现过一次，第 11 章：**"检查了路径"不等于"跑在沙箱里"。** 这里的形态是：**"包合法"不等于"内容对"。** 是同一个形状。

> **核心判断 2**
>
> **结构有效性、事实一致性、可编辑性、可见版式，是四个独立维度。**
> 任何一个通过都不能替代另一个。尤其是：**前两个可以自动化，后两个不能。** 后两个漏掉，就会有一份"自动化检查全绿、人一看就退回"的文档出去。

## 15.4 版本与血缘：产物是持续的工作，版本是一次交付

这一节处理一个很容易被当成行政问题、实际上是技术问题的事情：**版本怎么记。**

先区分两个概念：

| 概念 | 含义 | 例子 |
|---|---|---|
| **产物（artifact）** | 一份**持续的工作**，跨多次修订存在 | "P1 期支出分析报告" |
| **版本（version）** | 一次**具体的交付状态** | "第 3 版的报告字节" |

一个版本要记录的东西：

| 记什么 | 为什么 |
|---|---|
| 内容模型修订号 | 内容改了什么 |
| 源 / 输入修订号 | 数据换过没有 |
| 模板版本 | 版式约定是否变过 |
| 渲染器版本 | 生成逻辑是否变过 |
| 文件哈希 | **交付的是哪一串字节** |
| 校验状态 | 这份字节验过没有、结论是什么 |
| **被修订的是哪个版本** | 血缘：它是从哪儿来的 |

最后一行是血缘的核心。`final-final2.docx` 之所以不合格，不是命名难看，而是**它没有记录它修订的是谁、为什么改。**

<div align="center"><img src="images/fig-15-2-four-checks.png" alt="图 15-2 一个事实、两条渲染链：四个验收维度与版本血缘" width="1150"/></div>

**读图指引**：看三张版本卡片里第三行起的内容——**每一张都明确记着"父版本"**，而不是覆盖上一个。再往下那三条规则，全部要求在"写入之前"生效。

还有一个必须说清的规则：

> **素材源文件不得被输出覆盖。**
> 用修订版去覆盖原始输入路径，必须在**改到源之前就被拒绝**。哪怕这次改动"看起来很小"。

这条规则的实现方式在参考实现里能看到形态——输出被复制到一个**不可变存储**目录，用只写模式落盘：

```ts
// 参考实现源码（BetterWork · apps/desktop/src/main/services/file-artifact-service.ts，MIT）
mkdirSync(destDir, { recursive: true });
writeFileSync(destPath, fileBuffer, { flag: 'wx', mode: 0o400 });
```

三个细节，每一个都在说同一件事：

| 写法 | 含义 |
|---|---|
| `destPath` 在 `artifactFilesRoot/<versionId>/` 下 | 每个版本**独立的目录**，不共享路径 |
| `flag: 'wx'` | **排他创建**——文件已存在就失败。**不允许静默覆盖** |
| `mode: 0o400` | 只读。**落盘之后就不能被这个流程改写** |

## 15.5 一个事实，两种渲染

这一节把前面的原则落成一个可执行的动作。

**同一个指标记录，供给所有格式的每一个显示数字。** 这句话有三个直接推论：

| 推论 | 做法 |
|---|---|
| 正文里出现的数字，必须是**指标 ID 的引用**，而不是抄写 | 写 `{metric: spend_p1}`，不写 `25000` |
| 两种格式的**规范化抽取结果**必须一致 | 抽取标题、段落、表格单元格、指标值、来源 ID，逐项比对 |
| 两种格式的**字节不必相同** | 二进制相等**既不期望也不需要** |

第三条很重要，防止一个常见的过度要求：Markdown 和 DOCX 是两种不同的封装，字节不可能一样。**要比的是语义可抽取物，不是字节。**

### 15.5.1 一条值得复用的发布不变式

参考实现里有一段代码，它的作用范围是 PPTX 登记，但**它表达的原则适用于所有格式**：

```ts
// 参考实现源码（BetterWork · file-artifact-service.ts，MIT）
const fileHash = hashBytes(fileBuffer);
if (fileHash !== output.fileHash || fileBuffer.length !== output.fileSize)
  throw new Error('Output hash does not match its validation report');
```

这段代码在执行一件事：**确认"被登记的字节"就是"宿主核验过的字节"。**

它防的是什么？防的是**张冠李戴**——一份通过校验的报告，被贴到了另一份没有通过校验的文件上。

> **核心判断 3**
>
> **不要把一份通过的报告挂到另一份字节上。**
> 报告和它描述的对象之间必须有一条**基于内容本身**的绑定——哈希就是这条绑定的最小形式。

回到本章开头的问题："怎么证明这份校验报告属于我交付的这一份字节？"

答案就是这一行：**在交付前重新算一次哈希，和报告里记的比一遍。** 不比，你就只有一个"曾经验过"的说法，而没有"这次交付的这份是验过的"这个事实。

**必须如实说明的边界**：`FileArtifactService` 的登记路径**明确绑定 PPTX 的 MIME 类型**，它**不是一个通用的 DOCX 渲染器**。这一章借用的是它的**校验与登记模式**，不是它的生成能力。DOCX 的渲染实现属于必须自行准备的教学适配层——这一点在第 16 章的边界里还会再出现一次。

## 15.6 三种做法的取舍

这一章的主线是"渲染验证过的内容模型"，但它不是唯一做法。把三种放在一起看：

| 做法 | 适合 | 代价 |
|---|---|---|
| **直接写 Markdown** | 短的、纯文本的、不需要版式的交付物 | 一旦需要 Word 的样式、目录、分页就断了 |
| **让模型直接输出 Office XML** | 看起来"最直接" | **包结构与文档内容混在一起**，无法分别校验。这是最不该走的路线 |
| **渲染验证过的内容模型** | 需要结构、需要引用、需要多次修订 | 要维护内容契约与渲染器，但**版式可控、事实可核、结构可验** |

第二行值得单独说一句：**让模型生成原始 Office XML，是把两个不同的问题——"文件格式对不对"和"内容对不对"——混成一个。** 混成一个之后，你既无法可靠地验格式，也无法可靠地验内容。第 2 章讲模型边界时的结论在这里再次生效：**不需要它做的，就别让它做。**

### 15.6.1 模板：它能改什么，不能改什么

"支持模板"是一句需要被证明的话。分开看：

| 模板**可以**决定 | 模板**不可以**决定 |
|---|---|
| 字体、字号、颜色、间距 | **任何事实内容** |
| 页边距、页眉页脚 | **任何数字** |
| 标题样式的具体外观 | **章节的层级结构**（层级来自内容模型） |
| 可复用的版式骨架 | 引用的来源与定位符 |

第三行是个关键区分：**模板决定标题"长什么样"，内容模型决定它"是几级"。** 反过来就变成了"靠字号判断层级"，也就是 15.2 节那个假标题问题。

还有一条现实约束：**一个能创建文档的库，不会自动导入某个 Word 模板的全部特性。** "这个库支持模板"和"这个库支持你正在用的这个模板的这些特性"是两件事。后者需要针对**具体模板特性**做测试。

**许可与兼容性也要单独处理**：公司模板、字体、图片有各自的授权与兼容约束。教学与公开交付场景需要的是**可再分发的素材**。

## 15.7 行业视角：受控文档比一般文档多一层

这一章的要求在受监管场景下会多一层约束，而不是换一套逻辑。

| 维度 | 一般文档 | 受控文档（银行、医药、公共部门） |
|---|---|---|
| 模板 | 用公司模板即可 | 模板本身是**受控资产**，有版本号与发布记录 |
| 修订 | 记录改了什么 | 记录改了什么**+ 谁批准的 + 依据哪条规则** |
| 引用 | 来源可定位 | 来源需**在提交时仍然有效**，过期文件不能作为依据 |
| 保留 | 保留历史版本 | 保留期限由制度规定，**删除也需要依据** |
| 输出 | DOCX 即可 | **必须是可编辑的原生格式**，不接受 PDF 或截图替代 |

最后一行是本节的要点。**PDF 不是"更正式的 Word"。** 它是**已经完成编辑的终点格式**。当某个流程要求"提交可修改的 Word 文档"时，用 PDF 提交不是偷懒，是**没有交付**。

这条在银行的报告、报送、审批链上尤其刚性——**接收方需要有修改和批注的能力**，而这个能力只能由原生格式提供。

**本书给的一条通用判据**：当你不确定该交哪种格式时，问一句 **"收件人接下来要拿它做什么？"** 要读 → PDF 可以；要改 → 必须是原生格式；要取数 → 表格必须是真表格而不是图片。

**本章小结**
文档渲染器的工作是把**已复核的内容**转换成**可用的格式**。要分别验证的是：输入模型、输出结构、事实一致性、可编辑性、可见版式——**五件事，不是一个"通过"。**

原文件与每一次修订之间的关系必须被保留。

**六道自检题**：

1. 为什么一个合法的 ZIP / Office 包不足以证明内容正确？
2. 模板**应该**被允许改变什么？**不应该**被允许改变什么？
3. 你怎么证明"这份校验报告属于我交付的这一份字节"？
4. 为什么"两个格式的字节必须相同"是一个不该提的要求？该比什么？
5. 一篇文档的导航窗格是空的，说明什么？为什么这是能力问题而不是审美问题？
6. 接到"提交可修改的 Word"这个要求时，交 PDF 算不算交付？

**想得更远一点**：本章提到"幻灯片可以概述内容，但不能改变事实"。第 16 章会把这个约束变成一条硬规则，并且会发现一个更麻烦的问题——**同一个数字出现在四页幻灯片上**，其中一页改了，另外三页怎么办？

2. 把正文里所有的数字换成**指标 ID 引用**。一个直接抄写的数字都不留。
3. 打开导航窗格，**如果你看不到层级，就先修结构**，不要先改外观。
4. 做一次**可编辑性实测**：改一个段落、改一个单元格、保存、关闭、重开、确认改动还在。这份实测副本要**单独保留**，不能和正式交付物混。
5. 实现**哈希绑定**：交付前重算一次文件哈希，和校验报告里记的比一遍，不一致就拒绝发布。
6. 在生成之前挡住**写回源路径**的尝试。哪怕改动很小。
