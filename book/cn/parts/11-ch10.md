# 第 10 章 Skill 与专家：把工作方法做成可复用资产

**本章承诺**：读完这一章，你能把一个团队的工作方法固化成一个可版本化、可校验、可组合的资产，并能算出一次运行"实际生效的能力范围"到底有多大。

**读完后你能回答**

- 工具、Skill、专家这三层各承担什么职责？为什么把它们混成一层会出问题？
- 一个 Skill 声明要用某个工具，运行时怎么保证它真的用得上、且只能用这些？
- 为什么"专家"不应该是一个独立的智能体进程？

---

先看一个反复发生的场景。

一个团队做经营分析有一套自己的方法：

1. 先确认期间、对比期间、预算口径和单位；
2. 只从本次已选定并实际读取的材料里取数；
3. 每一项指标都用确定性工具算，不许心算、不许补缺失值；
4. 输出保留原始值、变化额、变化率、预算偏差；
5. 遇到零基数、缺失期间、单位不一致，明确标记并请人确认。

这套方法很清楚。问题是它现在被写在三个地方：

- 三个人的提示词模板里，措辞略有不同；
- 一份团队 Wiki 里，已经半年没更新；
- 还有一份在某次对话记录里，只有当时在场的人知道。

三份都不一样。于是同一个人做的分析，换个人做，结果的口径就开始漂。

**这不是纪律问题，是资产问题。**方法没有被做成一个东西——所以它只能靠人的记性传递。

> **核心判断 1**
>
> **工作方法要被当成资产对待：有版本、有校验、有归属、可组合。**
> 一份写在提示词模板里的方法，改一次要通知所有人；一份做成资产的 Skill，改一次所有人都拿到新版本。
> 代价是——**你必须先把方法写清楚**。含糊的方法做不成资产，它只会变成一个含糊的 Skill。

---

## 10.1 三层，各管一件事

第 1 章那个"工具"是能力的最小单位。这一章补上另外两层。

| 层 | 是什么 | 回答的问题 | 变化频率 |
|---|---|---|---|
| **工具（Tool）** | 一个带结构化契约的可执行能力 | "能做什么动作" | 低（改了要重新测试） |
| **Skill** | 一套可复用的**工作方法**（说明 + 可选的脚本与资源） | "这件事按什么步骤做" | 中 |
| **专家（Expert）** | 一个**配置化的角色**：方法 + 材料范围 + 工具范围 | "这个角色在什么约束下做事" | 高 |

三层的粒度是递进的：**动作 → 方法 → 角色约束。**

<div align="center"><img src="images/fig-10-1-tool-skill-expert.png" alt="图 10-1 工具、Skill、专家三层的职责与混淆后果" width="1150"/></div>

**读图指引**：看最后一列。三层里任何一层被放到错误的位置，后果都不是"不好用"，而是**结构性失效**——工具爆炸、无法保证执行、或开销失控。

### 10.1.1 最容易犯的错：把它们混成一层

三种混淆，以及各自的后果：

| 混淆 | 后果 |
|---|---|
| **把方法写成工具** | 每换一个场景就要写一个新工具。工具的数量爆炸，而且每个工具里都硬编码了场景假设 |
| **把工具写成 Skill** | 一段"说明"试图描述可执行的动作，模型只能靠理解去"照着做"——**而它不能保证做对** |
| **把专家做成独立智能体** | 一个角色预设被实现成一个独立进程，于是要处理进程间通信、状态同步、权限传递——**成本上升一个数量级，收益为零** |

第三条值得单独说。参考实现对"专家"的定义非常克制：

> **专家**：一个配置化的角色与工作方法/能力预设。**它不必是一个独立的自主智能体进程。**

**这句话在 2026 年不算过时，反而更重要。**后面会看到，主流运行时的公开对比正在把焦点从"能做什么"转向"默认谁拥有循环"——**而"每加一个角色就加一个进程"恰好是把循环分裂开，是反方向的做法。**

## 10.2 一个 Skill 长什么样

参考实现里的 Skill 就是一个目录，核心是一份带 frontmatter 的 Markdown 文件：

```markdown
---
name: "经营分析方法"
description: "用确定性工具计算期间变化和预算偏差，再把结论写成可审阅的经营分析。"
version: "0.1.0"
---

# 经营分析方法

先确认当前期间、对比期间、预算口径和单位。只从本次 Run 已选择并实际读取的材料提取数值。

对每项指标调用 `analyze_business_metrics`，把当前值放入 `current`，对比值放入 `previous`，
预算值放入 `budget`。不要在提示词中自行心算或补齐缺失值。

输出时保留原始数值、变化额、变化率和预算偏差；遇到零基数、缺失期间、单位不一致或异常值，
明确标记并请求用户确认。
```

**全文不到 400 字。**这个长度本身就是一条设计结论：

> **一个 Skill 超过一屏，通常说明它把不该它管的东西写进来了。**

那些东西通常是：具体的数据（应该在材料里）、具体的场景（应该在任务描述里）、具体的工具实现（应该在工具里）。

### 10.2.1 拆开这 400 字，每一句都在防一类失败

| 原文 | 在防什么 |
|---|---|
| "先确认当前期间、对比期间、预算口径和单位" | **定义类错误**——口径没定就开算，后面全是精致的错 |
| "只从本次 Run 已选择并**实际读取**的材料提取数值" | **越界取材**——读到没被选定的文件；"已选择"和"实际读取"是两个条件，不能只满足一个 |
| "不要在提示词中自行心算或补齐缺失值" | **把算术交给模型**（第 6 章的死敌） |
| "保留原始数值、变化额、变化率和预算偏差" | **输出不完整**——只给一个百分比，读者无法核对 |
| "遇到零基数、缺失期间、单位不一致或异常值，明确标记并请求用户确认" | **静默处理**——把所有异常都"平滑"掉 |

**第二句的两个限定词值得特别注意。**

"已选择"是**用户侧**的动作：用户勾选了哪些材料。
"实际读取"是**系统侧**的事实：这些材料真的被读进上下文了吗？

两个条件缺一不可：

| 情况 | 问题 |
|---|---|
| 选了但没读 | 模型可能凭记忆"以为"看过——而它没有 |
| 读了但没选 | **越界**——读了不该读的东西 |

**这个双重限定，把"证据来自哪"这个问题变成了可检查的事实。**第 8 章的证据映射和它是同一个思路。

### 10.2.2 description 是给模型看的，所以要写"什么时候用"

frontmatter 里的 `description` 不是给人看的注释，它参与**能力选择**——模型会看到这些描述，然后决定用哪个 Skill。

所以它也必须遵守第 6 章那条规则：**说清什么时候不该用。**

对比两种写法：

```text
❌ "经营分析方法"
✅ "用确定性工具计算期间变化和预算偏差，再把结论写成可审阅的经营分析。"
```

第二种多了"用确定性工具"与"可审阅"两个限定，直接排除了两类误用：

- 想让它"顺手估一下"的请求——它用的是确定性工具，估不了；
- 想要一份内部草稿的请求——它的产出目标是"可审阅"。

## 10.3 从"一份说明"到"一个资产"：还要加什么

一份说明文件还不是资产。参考实现的发布清单给出了资产需要的最小字段集：

```json
{
  "skillId": "builtin-business-analysis",
  "resourceName": "business-analysis",
  "name": "经营分析方法",
  "description": "...",
  "contentHash": "8ec64936...",
  "originalVersion": "0.1.0",
  "profileHash": "7b1d4898...",
  "dependencyFingerprint": "e3b0c442...",
  "scopeHash": "5b9db745...",
  "profile": {
    "commands": [],
    "environmentRequirements": [],
    "outputContract": { "outputPaths": [] }
  }
}
```

逐个解释这些字段在防什么：

| 字段 | 防什么 |
|---|---|
| `contentHash` | **内容被改过而版本号没动**——改了内容哈希就变，可被检测 |
| `originalVersion` | 版本号本身（与哈希互补：版本号给人看，哈希给机器比） |
| `profileHash` | **能力声明被改过**（profile 变了，适用条件就变了） |
| `dependencyFingerprint` | **依赖环境被换过**——第 10.4 节展开 |
| `scopeHash` | **适用范围被扩大过**——这是权限相关的字段 |
| `commands` | 它需要执行哪些命令 |
| `environmentRequirements` | 它需要什么运行环境 |
| `outputContract.outputPaths` | **它会写到哪里**——输出契约 |

**最后一个字段（`outputPaths`）最容易被忽略，也最重要。**

一个"声明了会写到哪里"的 Skill，让宿主可以在执行前就建立边界：**只允许它写这些路径。**反过来，一个没有输出契约的 Skill，宿主只能选择"要么不给写权限，要么放开全部写权限"——两条路都不好。

> **一条可推广的规则**：**凡是需要权限的动作，都必须有等价的"声明"。**
> 没有声明的权限只能整体授予，而整体授予等于没有边界。

### 10.3.1 四个哈希放在一起，是一份"可审计的能力清单"

这四个哈希对应四个可以独立变化的东西：

```text
contentHash          → 它写了什么（方法内容）
profileHash          → 它要求什么（能力与输出契约）
dependencyFingerprint → 它依赖什么（运行环境与依赖集）
scopeHash            → 它作用于哪（适用范围）
```

**它们分开存储，是为了让"变了哪一样"可被区分。**

如果只有一个总哈希，你能知道"它变了"，但不知道变的是内容还是权限。而这两种变化的处理方式完全不同：

| 变了什么 | 应触发的动作 |
|---|---|
| 内容 | 重新阅读一遍方法 |
| **权限 / 依赖 / 范围** | **重新授权**（因为授权是基于旧版本的） |

**"权限变了必须重新授权"这一条，是整组字段存在的理由。**

## 10.4 依赖：为什么一个"方法说明"会需要环境

这一节可能让初学者意外：**一个 Skill 为什么需要装依赖？**

因为"可复用资产"里包含**脚本**。一个真正好用的分析 Skill 可能带一个 Python 脚本做格式转换；一个文档 Skill 可能带一个渲染器。这些脚本需要运行环境。

参考实现的做法值得完整看一遍，因为它把"依赖"这件事做成了一个**可管理、可失败、可恢复**的流程。

### 10.4.1 环境标识：为什么是三元组

```ts
const environmentKey = computeEnvironmentKey(resolved.base, resolved.platform, lockHash);
```

一个环境由三样东西唯一确定：

| 维度 | 例子 |
|---|---|
| **基础解释器** | 某个受管 Python 的版本与路径 |
| **平台** | `darwin-arm64` |
| **锁定依赖集** | `lockHash`——依赖清单的哈希 |

**为什么必须三个一起？**因为任何单独一个都不能确定环境：

- 只按解释器版本分：升级依赖后会复用旧环境，跑的是旧包；
- 只按平台分：不同 Python 版本会撞在一起；
- 不含 `lockHash`：**这是最关键的一项**——依赖集变了就是另一个环境，必须重建，而不是"就地升级"。

**"就地升级依赖"是环境类问题的常见源头**：一个包被换了版本，之前跑得好好的东西开始坏，而两边都没有"我改了什么"的记录。

### 10.4.2 先探测缺什么，再决定做什么

```ts
const missingWheels: string[] = [];
for (const entry of ...) {
  ...
  if (!present) missingWheels.push(entry.name);
}
```

**先算清单，再做操作。**

这个顺序看起来理所当然，但很多实现是反过来的：先创建环境、装包、撞上错误、再回滚。**代价是每次都做一遍可能失败的操作。**

先探测的好处有三个：

1. **幂等**：什么都不缺时，直接成功返回，不做任何写操作；
2. **报错可读**：错误信息能列出"缺的是哪几个包"，而不是"安装失败"；
3. **可恢复**：中断之后重跑，探测结果会告诉你还差什么。

### 10.4.3 操作要落库，中断的必须收口

参考实现给依赖操作建了记录，并且有一条与 Run 一样的不变量：

```ts
const operations = this.store.dependencyOperations.failInterruptedOperations(now);
```

**进程被强杀时留下的"进行中"记录，在下次启动时被收口为失败。**

我们在第 4 章见过同一条不变量（"每个 Run 都必须有明确终态"）。**它在依赖准备里再次出现，说明这不是某一个模块的做法，而是一条通用纪律。**

> **通用纪律**：**任何有"进行中"状态的长操作，都必须在启动时把残留状态收口。**
> 否则界面会永远显示一个转圈的进度条，而那个操作早就不存在了。

### 10.4.4 失败原因要分类，不能只说"失败了"

参考实现给依赖问题定义了一组明确的错误码：

```ts
| 'interpreter-missing-venv'
| 'wheel-missing'
| ...
```

以及一条具体的错误信息：

```ts
'interpreter-missing-venv',
`${resolvedPath} 缺少 venv 或 ensurepip，无法创建算台专属环境`,
```

**错误码让机器能分类（第 13 章的评估需要它），错误信息让人能行动。**

对比"依赖准备失败"这一句：它既不能统计，也不能行动。

## 10.5 信任状态：Skill 是外来代码

一个 Skill 目录里可以有脚本，脚本会被执行。**所以 Skill 在安全上等价于外来代码。**

参考实现给 Skill 加了信任状态，并在依赖准备时先检查：

```ts
if (skill.trustStatus === 'untrusted') { ... }
```

**这条检查的位置是刻意的**：它在"装依赖"之前，也就是在**任何一行 Skill 代码被执行之前**。

| 检查放在哪 | 效果 |
|---|---|
| **执行前** | 不受信任的 Skill 连环境都不会为它准备 |
| 执行中 | 已经跑了一部分代码才拦下来——太晚 |
| 执行后 | 没有意义 |

**"不受信任就不给准备环境"这个设计，把"不执行"变成了一个物理事实，而不是一个判断。**这是第 11 章"权限优于提示"的又一次出现：**能落到实处的不执行，优于"检查过了所以应该不会执行"。**

## 10.6 专家：一个配置，不是一个进程

现在回答本章开头那个问题：专家是什么。

参考实现对专家的处理集中在"配置"上。看它对一个声明的校验：

```ts
parsed.builtinToolPolicy.toolNames.some((name) => !BUILTIN_TOOL_NAMES.has(name))
```

以及同一个校验在版本层面的重复：

```ts
expert.revision.builtinToolPolicy.toolNames.some((name) => !BUILTIN_TOOL_NAMES.has(name))
```

**两处做同一件事，说明它是一条不变量，而不是一次校验。**

一个专家声明了自己要用哪些内置工具。这个声明的处理流程是：

```text
① 声明：专家配置里写 toolNames
② 校验：每个名字必须在内置工具名集合里   ← 不认识的直接拒绝
③ 求交：与本次运行实际可用的工具取交集
④ 生效：只有交集里的工具能被这个专家使用
```

**第 ③ 步是"有效能力范围"的来源。**它必须是交集，不能是并集：

| 求法 | 后果 |
|---|---|
| 声明 ∩ 实际可用 | **正确**——两边都满足才生效 |
| 声明 ∪ 实际可用 | **越权**——专家能用到它没声明的工具 |
| 只用声明 | 声明的工具可能这次根本没提供，运行到一半才失败 |
| 只用实际可用 | 专家能用到所有工具，声明形同虚设 |

<div align="center"><img src="images/fig-10-2-scope-intersection.png" alt="图 10-2 有效能力范围是三层求交" width="1150"/></div>

**读图指引**：三个圆分别是"专家声明"、"任务阶段允许"（第 5 章）、"本次实际可用"。**只有三者相交的那一小块是真正能用的。**任何一个圆单独扩大，都不会让可用范围变大——这是"最小权限"能被自动维持的原因。

### 10.6.1 专家也是版本化的

注意 `expert.revision` 这个结构。专家配置有修订号，这和 Skill 的 `contentHash` 是同一个思路：

**"这个角色的约束被改过"必须是一个可检测的事实。**

因为专家配置直接决定权限范围。一个被悄悄改了 `toolNames` 的专家配置，会让同一个角色在某一天突然拥有了更多能力——**而使用者看到的还是同一个名字。**

## 10.7 组合，而不是分裂：一个引擎，多套配置

这是本章最重要的一条架构主张。

一个自然的、但有代价的想法是：**每个专家一个独立的智能体。**

它的代价：

| 代价 | 具体表现 |
|---|---|
| 进程与生命周期 | 每个进程要自己的启动、健康检查、退出、日志 |
| 状态同步 | 会话状态、记忆、产物归属要在进程间同步 |
| 权限传递 | 一个专家把任务交给另一个专家时，权限怎么传 |
| 可观测性 | 追踪要跨进程拼接 |
| **资源** | 每个进程一份运行时开销 |

而它换来的收益是什么？**"角色之间的隔离"**——但角色隔离用配置就能做到：

```text
同一套引擎 + 同一个循环 + 同一套工具实现
  + 不同的（专家配置 + Skill 组合 + 材料范围 + 工具范围）
  = 不同的角色行为
```

**参考实现里那个"专家"根本没有自己的循环。**它只是一组配置，被装配进同一个循环。

> **核心判断 2**
>
> **在单智能体的循环**通过评估之前**，不要引入第二个进程。**
> 因为多智能体引入的通信、同步、权限传递问题，会掩盖掉真正的问题——而那真正的问题，通常在单循环里就能测出来。
> 代价是你要在设计时想清楚"角色差异能不能用配置表达"。绝大多数情况下能。

### 10.7.1 什么时候真的需要多个智能体

有一条被公开讨论过的判断标准值得抄：

> 公开的工程实践总结里有一条明确的反面清单：**不要在单个智能体循环还没通过可测量评估之前，就设计多智能体系统。**

也可以从正面给一个判据——**两个条件同时成立时**才考虑：

1. 两个角色的**工具集合不重叠**（而不是"职责不同"）；
2. 两个角色的**上下文几乎完全不同**（共享上下文会让双方互相污染）。

**只满足第一条，用阶段化就够了**（第 5 章）；只满足第二条，用子智能体的上下文隔离就够了——但那已经是另一个话题了。

**"职责不同"不是理由。**同一份职责可以用不同配置表达；不同的职责也可以在一个循环里分阶段完成。

## 10.8 故意失败：三种必须显式失败的配置错误

### 10.8.1 引用了不存在的方法 / 被禁用的方法

**实验**：把专家的 `toolNames` 里写一个不存在的工具名。

**期望**：**在加载配置时就拒绝**，而不是在执行到那一步时才失败。

参考实现的做法正是前者——那个 `.some(...)` 判断发生在**解析阶段**。

**为什么必须早失败？**因为晚失败的代价是"运行到一半"：任务已经做了三步，用了两分钟，然后卡住。而早失败是一个加载期的错误，用户可以立刻改。

**判断一个校验该放在哪个时机，用这个问题：**"这个错误能不能在更早的、不消耗资源的时刻被发现？"能，就放更早。

### 10.8.2 缺失依赖

**实验**：让一个 Skill 声明一个不在依赖集里的包。

**期望**三层：

| 层 | 期望 |
|---|---|
| **准备阶段** | 探测出缺哪些包（`missingWheels` 非空） |
| **状态** | 操作记录为失败，带明确错误码（`wheel-missing`） |
| **运行阶段** | Skill 不被执行——**而不是执行了之后抛 ImportError** |

**第三层是这一节的重点。**"先执行再撞上 ImportError"和"执行前就拦住"，对用户是两种完全不同的体验：后者能告诉他"缺一个包，需要装"，前者只能给他一段 Python 堆栈。

### 10.8.3 不受信任的 Skill

**实验**：把一个 Skill 的信任状态标为不受信任，然后尝试运行它。

**期望**：**在任何代码执行之前被拦下。**

**判据不是"报错了"，是"它的代码没有跑"。**验证方法：在 Skill 的脚本里放一行写文件的代码，运行后检查那个文件是否存在。**不存在才算通过。**

**这是"负向测试"的又一个实例**（第 2 章、第 11 章）：一个安全控制是否有效，不由"正常情况通过"证明，而由"越界被拦"证明——而且"被拦"必须以**可观测的副作用缺席**为准，不能以"看到了报错"为准。

## 10.9 行业视角：方法资产化在企业里的三个硬要求

| 要求 | 对应机制 |
|---|---|
| **方法要能追溯版本** | `contentHash` + `originalVersion` |
| **能力变化要重新授权** | `profileHash` + `scopeHash` + 专家 `revision` |
| **依赖要可复现** | `lockHash` 组成的环境标识 + 受管依赖池 |

第三条在一个受监管环境里尤其重要。**"上次跑出来的结果这次跑不出来"**在审计场景里是致命的——因为它意味着"你无法复现自己的结论"。

而"可复现"的技术基础非常具体：

```text
同一个基础解释器 + 同一个平台 + 同一个锁定依赖集 → 同一个环境 → 同样的行为
```

**这三样少一样，复现就没有保证。**这也是为什么本书反复强调"把隐含假设变成显式契约"——在依赖这件事上，隐含的假设就是"我机器上装的东西和别人机器上的一样"。

## 10.10 这一章在整本书里的位置

第三篇到这里结束。你现在有：

| 章 | 得到什么 |
|---|---|
| 第 6 章 | 能算对（确定性工具） |
| 第 7 章 | 能连上，权限可控（MCP 与绑定） |
| 第 8 章 | 能找到，能被核对（检索与证据映射） |
| 第 9 章 | 放得下、记得住、删得掉（上下文与记忆） |
| 第 10 章 | 可复用、可版本化、可组合（Skill 与专家） |

**能力齐了。**

但这一章最后留下的那个问题还没有答案：**谁保证这些能力各自待在自己的边界里？**

一个不受信任的 Skill、一个声明了更多工具的专家、一次被注入的网页内容——它们都需要一个**执行者**来拦住，而不是一个**提示词**来说服。

第四篇讲的就是这个执行者。第 11 章从最基础的一层开始：**信任边界。**

---

**本章小结**：工具、Skill、专家是三层递进——**动作、方法、角色约束**；把它们混成一层会带来工具爆炸、无法保证执行、或进程开销失控。Skill 是一份带 frontmatter 的说明文件，**超过一屏通常说明它写进了不该它管的东西**；`description` 是给模型看的，必须写清什么时候不该用。资产化的最小字段集是内容哈希、能力哈希、依赖指纹、范围哈希——**分开存储是为了区分"变的是内容"还是"变的是权限"，后者必须重新授权。**依赖环境由"基础解释器 + 平台 + 锁定依赖集"三元组唯一确定，先探测再操作，中断的操作必须收口。**不受信任的 Skill 在任何代码执行之前就被拦下**，这个"拦下"必须用副作用缺席来验证。专家是配置不是进程：**有效能力范围 = 声明 ∩ 阶段允许 ∩ 实际可用**，必须是交集。

**行动清单**

1. 挑一套你现在口口相传的工作方法，写成一个 Skill：说明 + frontmatter，**控制在 400 字以内**。
2. 给每个 Skill 补上四样：`contentHash`、能力声明、依赖清单、输出路径契约。
3. 把输出路径契约接进权限：**一个 Skill 只能写它声明过的路径。**
4. 检查你的专家配置：`toolNames` 里有没有笔误？校验发生在加载期还是执行期？**挪到加载期。**
5. 依赖准备改成"先探测缺什么，再操作"，并给失败原因加错误码。
6. 检查你的不受信任拦截点：它在依赖准备之前吗？**用"脚本里的写文件动作没有发生"来验证它。**
7. 如果你正在设计多智能体：**先确认单循环的评估已经通过。**
