# 第 19 章 打包与迁移：职责边界决定可迁移性

**本章承诺**：读完这一章，你能把一个在你机器上能跑的应用，变成**别人能在声明好的环境里装上、跑起来、停下来、查得清、改得动**的东西。

**读完后你能回答**

- "交付"这个词的确切含义是什么？它在哪一刻才算完成？
- 换一个界面（比如从终端换成 API），哪些职责必须原封不动地跟着走？
- 2026 年的几个主流运行时之间，真正的差别是什么？为什么"能力清单"已经不是有效的比较方式？
- 一个缺配置的安装，正确的行为是什么？为什么"编一个答案"是最坏的一种？

---

先看一次失败。

你的智能体在你的笔记本上跑得挺好。你把仓库地址发给了同学。

**他启动不了。** 三个原因，每一个都是独立的：

| 原因 | 实际发生了什么 | 它属于哪一类问题 |
|---|---|---|
| **依赖装在全局** | 有一个包是用 `-g` 装的，仓库里没有记录 | **环境**问题 |
| **输入路径指向你的 home 目录** | 配置里写的是 `/Users/你/...` | **配置**问题 |
| **唯一的说明是"用我的配置"** | 没有安装步骤，没有环境矩阵 | **文档**问题 |

三类问题，一个共同点：**它们都不是"代码有问题"。** 代码完全正常——**在你的机器上。**

> **核心判断 1**
>
> **交付的意思是：另一个人能在你声明的环境与权限范围内，安装、配置、运行、停止、检查和修订这个应用。**
> 注意这句话里有**六个动词**。"能跑起来"只是第二个。少了"能停"、"能查"、"能改"，你交出去的不是应用，是**一个演示**。

## 19.1 打包的是契约，不是你的机器

第 0 章那个"能写程序不等于能建系统"的问题，到了这一章变成了它的最后形态：**能建系统不等于能交出系统。**

这一节给出结构上的答案：**保留一个无头核心，放在一个由宿主拥有的应用接口后面。**

<div align="center"><img src="images/fig-19-1-layering.png" alt="图 19-1 交付分层：界面、宿主与核心各自拥有什么" width="1150"/></div>

**读图指引**：看右侧那一栏"宿主独占拥有"——**关键在第二层（宿主）：它独占拥有权限、生命周期与持久化**，而第一层无论换成 CLI 还是 API，都不能自己实现这些。

```
CLI / 提供的薄 UI
  → 已校验的应用请求
  → 宿主：身份、范围、配置、生命周期、持久化
  → 核心循环 + 提供方 + 有界工具
  → 持久事件与带版本的产出
  → 呈现适配层
```

**这一节最重要的一句话是**：

> **CLI 和 API / UI 调用的是同一组应用操作。它们不得各自重新实现权限检查，也不得各自计算报表指标。**

为什么这句话是硬要求？因为**一旦有两份实现，就会有两份行为**。

| 如果各自实现 | 会发生什么 |
|---|---|
| 各自做权限检查 | 两条路径的权限规则**必然分叉**，其中一条会出现漏洞 |
| 各自算指标 | 同一个指标在两个入口给出**不同的数**，而且**都对**（按各自的实现） |
| 各自管生命周期 | 一条路径取消了，另一条不知道 |
| 各自记事件 | 追踪断裂，第 13 章的可观测不再成立 |

第 15 章出现过一次同构的问题：**同一个事实被写了两遍，就会变成两个数字。** 这里的形态是：**同一个权限规则被实现在两个地方，就会变成两套权限。**

### 19.1.1 无头核心与薄适配层

为什么推荐"先交无头，再配薄适配"？

| 形态 | 优点 | 代价 |
|---|---|---|
| **CLI** | 对技术用户是最小的可用交付面 | 非技术用户用不了 |
| **薄 UI** | 不要求学习者重搭一个桌面框架 | 需要维护一层界面 |
| **完整桌面应用** | 文件集成与打包体验更好 | **这些关注点会盖住智能体的学习目标** |

第三行不是"不好"，而是"**顺序错了会失焦**"。参考实现提供了一个对照用的桌面架构——渲染层 → 带类型的 preload API → 应用层 → 核心/基础设施/工具。**它的源码展示了分层，但本书要求的第一次可运行交付仍然是"无头 + 薄适配"。**

> **一处必须说清的边界**
>
> **产品级的打包支持，不会自动定义你的教学环境矩阵。**
> 一个产品能在某个平台上打包，说明这个产品的作者测过那个平台；**不说明你的应用在那个平台上能被别人装上。**

## 19.2 一份发布包需要什么

这一节是清单，但每一条都对应一类真实的失败。

| 项 | 为什么需要 | 缺了会怎样 |
|---|---|---|
| **源修订号** | 交付的是哪一版代码 | 别人拿到的是"某个时间的某个分支" |
| **依赖锁文件** | 依赖的确切版本 | "在我这儿是好的" |
| **支持的运行时 / 操作系统矩阵** | 声明在什么上测过 | 别人在没测过的平台上跑，出问题无法归因 |
| **安装命令** | 能照着做 | —— |
| **非机密的配置模板** | 知道要填什么 | 见 19.6 |
| **断言输入（fixture）** | 有一个已知答案的输入 | 无法验证安装是否成功 |
| **启动 / 停止 / 测试命令** | 六个动词里的三个 | 别人不知道怎么停 |
| **数据与输出位置** | 知道读写发生在哪 | 找不到产出，或者写进了不该写的地方 |
| **已知限制** | 知道什么不做 | 会被当成 bug 反复报 |

**最关键的一句**：

> **作者必须在干净环境里测试这些说明。**
> **一串看起来合理的命令，不是可复现性的证据。**

这句话的意义在第 13 章已经立过：**没有测量，就不是"验证过了"。** 这里的形态是：**没有在干净环境里跑过，就不是"能装"。**

### 19.2.1 本地教学 API 的边界

如果要提供一个本地 API，有两条必须写进文档的规则：

| 规则 | 原因 |
|---|---|
| **默认绑定回环地址（loopback）** | 一个未认证的本地服务暴露到网络上，是一个可被远程利用的入口 |
| **写明谁可以调用它** | "本地"不等于"可信"——同机上其他进程也能调 |

还要做三件事：

| 做 | 为什么 |
|---|---|
| 校验请求与响应的**边界** | 输入校验是第 6 章的老规则 |
| **限制载荷大小** | 与第 14 章的 50 MiB / 200 MiB 上限同一个道理 |
| **取消走同一套宿主操作** | 否则又变成"两份实现" |

**最后一句话要记住**：

> **远程部署会引入身份、传输安全、资源隔离与运行责任人——这些是一个本地实验不能确立的。**

把本地实验说成"已经可以做生产部署"，是这一章最严重的一类错误。

## 19.3 2026 年的框架地图：差别在"谁拥有循环"

这一节回答一个问题：**如果我要用现成的框架，我到底在选什么？**

先把一个过时的比较方式淘汰掉：

> **到 2026 年，"能力清单"已经不再是有区分度的比较方式了。**
> 公开分析指出，2026-04-15 之后主流运行时在持久执行、沙箱执行、长时运行、子智能体等能力上已高度收敛。**三家的能力差距被抹平了。**

那么现在有效的比较轴是什么？**"谁拥有循环"。**

<div align="center"><img src="images/fig-19-2-who-owns-loop.png" alt="图 19-2 谁拥有循环：三种运行时默认值的差别" width="1150"/></div>

**读图指引**：**这不是一张能力对照表，是一张默认值对照表。** 能力可以叠加，默认值不会因为你加了功能而改变。

| 运行时 | 谁拥有循环 | 它的"一句话心智模型" | 最适合 |
|---|---|---|---|
| **Claude Agent SDK** | **模型拥有循环** | "给它一台电脑，它自己开" | Claude 在仓库/文件系统里干活 |
| **LangGraph** | **你拥有循环**（作为显式状态图） | "我画流程图，它执行并持久化" | 需要可检查、可恢复、人在环中的机器，且跨模型 |
| **OpenAI Agents SDK** | **你拥有路由，模型拥有每个节点** | "智能体之间用类型化移交委派" | 已知的专家智能体图，用手工接线 |

**这个比较轴的实用价值在哪里？**

它告诉你：**选型不是选"谁更强"，是选"你愿意把控制权交给谁"。**

| 你更在意 | 更适合的方向 |
|---|---|
| 快速得到可用的编码/文件智能体 | 模型拥有循环 |
| 每一步都可检查、可恢复、可插入人工审批 | 你拥有循环 |
| 已想清流程，只需模型填节点 | 你拥有路由 |

**一条必须自己走完的边界**：

> **框架的线程 ID / 检查点 ID，不会自动等同于你系统里的任务 / 会话 / 运行身份。**
> 在做迁移之前，先固定框架版本，再**证明**边界与生命周期测试仍然通过。
> **这一章给的是职责对照，不是一次已执行的迁移。**

### 19.3.1 一个不要顺手做的事：多智能体

在想要"重构一下"的时候，一个很常见的想法是：**拆成三个智能体——研究员、撰写员、复核员。**

先问一个问题：**它解决了哪个失败？**

多智能体带来的额外成本是具体的：

| 增加 | 后果 |
|---|---|
| 协调 | 需要新的编排逻辑与其自身的失败模式 |
| 共享状态 | 谁的上下文是权威的？ |
| 预算 | 成本与轮次的乘法 |
| **权限冲突** | 两个智能体对同一资源有不同的授权范围怎么办 |

而**一个确定性的核查器加一个人类复核者，可能更简单也更可审计。**

> **多智能体架构是一个可选的比较项，不是毕业要求。**
> 这个判断与第 10 章一致：在单循环的评估通过之前，不要引入第二个进程。

## 19.4 交接工作表

把"交付完成"这件事变成一张必须填满的表：

| 问题 | 必须给出的答案 |
|---|---|
| **什么在离线状态下运行？** | 具名命令与固定输入，**安装之后不再有外部请求** |
| **什么会用到外部服务？** | 选定的提供方/集成、已批准的数据、配置、预算 |
| **输入和输出在哪？** | 声明为只读的输入范围，以及可写的产出范围 |
| **怎么停？** | 取消命令 / 界面动作、清理语义、终态结果 |
| **失败怎么查？** | 已脱敏的日志、运行标识、状态与恢复步骤 |
| **谁维护？** | 代码、依赖、数据定义、模板，各自的负责人 |

**第一行和第四行是最常被跳过的。**

第一行决定的是**可离线复现性**。"安装之后不再有外部请求"意味着别人可以在飞机上、在有网络限制的环境里验证它。这一条不成立，你的"可复现"就依赖于对方的网络条件。

第四行决定的是**可操作性**。一个不知道怎么停的系统，在出问题时会**继续产生副作用**。

**最后一行决定的是可交接性。** 一个没有维护责任人的交付物，会在第一次依赖更新时变成废品。第 20 章会把这一条变成明确的归属清单。

## 19.5 故意失败：缺配置必须报错，不能编

这一节讲一个具体的失败模式，它是本章最实用的一节。

**实验**：从一个受控的安装里**移除模型配置**。应用应该怎样？

| 必须做到 | 为什么 |
|---|---|
| **说明配置缺失** | 让人知道该填什么 |
| **把机密留在错误信息之外** | 报错不能泄露凭据 |
| **不要声称任务完成** | 见下 |

**绝对不能做**：

> **它不得静默地用一个假提供方顶替真实评估，也不得使用一个非预期的服务。**

这是本节的核心。三种错误行为的严重性递增：

| 错误行为 | 严重性 | 后果 |
|---|---|---|
| 报一个看不懂的错 | 低 | 浪费排查时间 |
| 静默失败，什么都不输出 | 中 | 用户以为任务在跑 |
| **静默换一个假提供方，然后输出结果** | **最高** | **输出看起来像真的** |

第三种为什么最严重？因为它产出了一个**看起来正常的、完全没有依据的产物**。这个产物会进入下一步——**它会被当成真实结果使用。**

第 4 章讲过"到达上限必须是失败"，第 13 章讲过"没有测量就不是改进"。这里是同一条纪律的第三次出现：**一个不知道自己没在干活的系统，比一个明确报错的系统危险得多。**

**第二个实验**：**移除一个文档渲染依赖。**

| 期望行为 | 不允许的行为 |
|---|---|
| 在预检查或运行时以**可操作的方式失败** | 生成一个**扩展名正确但内容为空的文件** |

**"一个空文件"不是"合理的降级"。** 它会让下游流程以为文档生成成功了。

**把这两个案例都加进交接冒烟检查。** 交接检查不能只测成功路径——**成功路径几乎总是能过，它证明不了什么。**

## 19.6 行业视角：选一个场景做适配简报

这一节给一个练习，也给出它在真实行业里的形态。

从这几个场景里选一个：**校园项目进度**、**银行流程对照**、**能源工单分析**、**制造质量报告**。

然后回答这五个问题：

| 问题 | 为什么它决定了架构 |
|---|---|
| **源定义变了吗？** | 字段、口径、粒度是否还是原来那套 |
| **有哪些敏感字段？** | 决定了数据流向与脱敏要求 |
| **决策所有者是谁？** | 决定了停车位设在哪 |
| **哪些动作是被禁止的？** | 决定了权限边界的形状 |
| **部署义务是什么？** | 决定了能不能用某些服务、日志要留多久 |

**只使用合成输入。**

> **一句话必须写在每一份适配简报里**：
> **一次成功的本地演练，不构成对生产安全、监管合规或运行适宜性的认证。**

这句话不是免责声明，是**准确的描述**。本地能跑、数据是合成的、没有接入真实身份系统、没有做过安全评估——这些条件同时成立时，"能跑"和"能上线"之间的距离就是**那五项部署义务**。

在机构场景下，第五节"部署义务"通常是最先被问到的。**数据分级、隔离网要求、日志留存期限、审计接口、投产评审流程**——这些不是技术细节，它们是**方案能不能被采用的先决条件**。第 17 章讲过"部署形态不能混用"，这里给出的是落地形态：**把它写成清单，逐条给出责任人与证据要求。**

**本章小结**
一份交付出去的应用是**可复现且可操作**的——**由别人**。框架可以提供机制；**策略与领域正确性仍然归宿主所有**。迁移改变的是上下文与适配器，**不能丢掉证据与边界**。

**六道自检题**：

1. 检查点**不**解决哪些职责？
2. 一个绑定回环地址的 API，为什么还需要声明"谁可以调用"？
3. 什么样的证据才能让"迁移后等价"这个主张变得可信？
4. "能力清单"为什么在 2026 年不再是有区分度的框架比较方式？有效的比较轴是什么？
5. 缺配置时静默换一个假提供方，为什么比直接报错**更**严重？
6. 一份发布包缺了"怎么停"，最坏情况是什么？

**想得更远一点**：这一章让你把系统交给了别人。第 20 章问的是更难的一件事：**别人拿到之后，能不能解释它为什么这样工作、能不能在一个没见过的输入上改对它。**

---

**行动清单**

1. 在**干净环境**里照着你自己写的说明装一次。**记录第一个失败的步骤**——那才是别人会遇到的第一个问题。
2. 检查界面层：**有没有任何权限检查或指标计算写在 CLI / UI 里？** 有就搬回宿主。
3. 把发布包清单变成一张**打勾表**，缺任何一项都不发布。
4. 确认离线路径："安装之后不再有外部请求"这句话，**用一次断网运行来证明**。
5. 做两次"破坏性冒烟"：删掉模型配置、删掉一个渲染依赖。检查它们是否**明确失败**，而不是产出空文件或假结果。
6. 明确写出**四个责任人**：代码、依赖、数据定义、模板。写不出来的那一项，就是第一个会烂掉的地方。
