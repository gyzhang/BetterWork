# 第 0 章 能写程序不等于能建系统

**本章承诺**：读完这一章，你能用四道出口题判断自己是否已经具备"建一个系统"的底子——以及如果不具备，缺的到底是哪一块。

**读完后你能回答**

- 为什么"能写一个函数、一个循环、一个条件"和"能建一个系统"之间，隔着的不是更多语法，而是四类完全不同的东西？
- 一个命令明明失败了，为什么你的自动化流程会报告成功？
- "缺失"和"零"在数据处理里为什么必须分开？混了会怎样？

---

先看一段真实经历。

一个人写了三年脚本，熟练使用变量、循环、函数，逻辑很清楚。他第一次接一个"小系统"：读两个 Excel，算出对比，生成一份报告。他花了两天写完，本地跑通了。

上线第三天出问题。原因有四个，各自独立：

1. **表头变了。**业务方在第二张表里把"金额（元）"改成了"金额(元)"，全角括号换成了半角。他的代码按下标取列，所以没崩——但它取到了错的那一列，静默算出了错的结果。
2. **路径是他自己电脑上的绝对路径。**换台机器就找不到文件。
3. **有一个表是空的。**他算"增长率"时除以零，得到一个 `Infinity`，然后这个 `Infinity` 被写进了报告，显示为 `∞%`。
4. **他的测试"通过了"。**因为他验证的方式是看终端最后一行有没有输出——而那行输出是管道里最后一个命令的。

四件事，一件都不是"语法不熟"造成的。它们分别落在这一章的四节上：**程序与工程基础**（环境与配置）、**数据与接口**（把"大概是这样"变成契约）、**异步与错误**（把慢、失败、被打断分开）、**测试与数据素养**（从"我觉得对"到机器能判定）。

这一章就补这四件事。它不讲新语法，讲的是**从"程序能跑"到"系统能被别人接着用"之间缺的那几层**。

> **定义**：系统
>
> 一个能在**别人的机器**上、在**预计之外的输入**下、**被检查过失败路径**之后仍然给出可判断结果的程序。
>
> **它不是什么**：不是"代码更多"的程序，也不是"用了框架"的程序。一个 80 行的脚本可以是一个系统；一个 8000 行的项目也可以不是。
>
> **本书中的用法**：判定标准只有一条——**换个人、换个环境、换份输入，它还能不能用。**

> **核心判断 1**
>
> 从"能写程序"到"能建系统"，缺的不是知识量，而是**把隐含假设变成显式契约的习惯**。<br>
> 这个习惯有个代价：你会比现在写得慢。慢下来的那部分时间，全花在写你现在不写的东西上——校验、错误路径、测试、文档。

## 0.1 先做四道题：这章你要不要读

不要凭感觉判断自己需不需要读这一章。做四道题，**做得出就不用读**。

| # | 出口题 | 交付物 | 对应能力 |
|---|---|---|---|
| F01 | 跑通一个别人写好的项目，改掉其中一个函数，并说清这次改动会影响到谁 | 一段改动说明 + 实际跑通的证据 | 程序与工程基础 |
| F02 | 解析一份本地响应数据；面对缺失字段与非法字段，在不泄露密钥的前提下给出可读错误 | 一段处理代码 + 错误样例 | 数据与接口 |
| F03 | 追踪一个带延时的操作，中途取消它，并**区分"失败"与"合法的空结果"** | 一份事件时序记录 | 异步与错误 |
| F04 | 为一个表格计算补一条回归测试，并用给定的预期值验证它 | 一个测试文件 + 通过记录 | 测试与数据素养 |

F03 的第二半句是这四道题里最容易翻车的：**"失败"和"合法的空结果"必须分开**。查一个知识库，没查到东西，这是**空结果**，是成功；查一个知识库，服务连不上，这是**失败**。把前者当后者报错，用户会以为系统坏了；把后者当前者放过，用户会以为真的没有。

如果你四道题都做得出来，直接翻到第 1 章。做不出哪一道，就读对应的小节——**不需要从 0.2 顺序读到 0.5**。

## 0.2 程序与工程基础：你的机器不是别人的机器

### 0.2.1 三件必须显式声明的东西

一个"在我这儿能跑"的程序，至少有三件事是靠运气：

| 靠运气的东西 | 后果 | 正确的做法 |
|---|---|---|
| **当前目录** | 用相对路径读写文件，换目录就找不到 | 路径从**显式传入的根目录**解析，不在代码里 `process.cwd()` |
| **已安装的依赖** | 你机器上有，别人机器上没有 | 依赖写进 `package.json`，版本锁进 lockfile |
| **环境变量** | 你的 shell 里配过，别人的没有 | 启动时**校验必需变量**，缺失就报错退出，不要给默认值 |

第三条最容易被做错。给环境变量设默认值是**善意的错误**——它让错误从"启动时明确报错"变成"运行到一半时行为诡异"。看一段真实代码里怎么处理这类问题：

```ts
// 参考实现源码（BetterWork · packages/agent-core/src/openai-compatible-provider.ts）
const endpoint = (baseUrl: string): string => {
  const url = new URL(baseUrl);
  const normalizedPath = url.pathname.replace(/\/+$/, '');
  if (!normalizedPath.endsWith('/chat/completions')) {
    url.pathname = `${normalizedPath}/chat/completions`;
  } else {
    url.pathname = normalizedPath;
  }
  return url.toString();
};
```

这段代码在解决一个很小但很真实的问题：**用户填的地址有三种写法**——`https://host/v1`、带若干尾斜杠的同一地址、以及已经写全的 `https://host/v1/chat/completions`。三种都必须落到同一个端点。

值得学的不是这段逻辑，是它的态度：**不假设输入是规范的，而是把用户可能怎么填想清楚，然后在入口处归一化一次**。归一化做一次，后面所有代码都能假设"我拿到的已经是规范地址"。

### 0.2.2 Git 不是备份工具，是"这次改动影响了谁"的答案

初学 Git 的人把它当"保存按钮"。它在系统开发里的真正用途是**改变的可解释性**：

- 一次提交应该能回答"为什么改"。`fix: reject traversal in read-text tool` 这样的信息，三个月后还能救你一次。
- 一个文件的历史应该能回答"这行为什么长这样"。找不到原因，说明当时没写清楚。
- 一个分支应该能回答"这次改动的边界在哪"。边界不清的改动，review 时无法判断风险。

**具体一点**：本书涉及的参考实现用一句命令作为交付门禁：

```bash
npm run verify   # lint → format:check → typecheck → test → build，任一失败即中止
```

这不是"跑个测试"，这是**把'改坏了'这件事变成一个可自动判断的事实**。一个仓库如果连这条命令都没有，它的"质量"就只能靠人的记性。

### 0.2.3 一条你现在就该记下的教训

> **数据卡**：管道会吞掉退出码
>
> **口径**：`cmd | tail` 的退出码是 `tail` 的退出码，不是 `cmd` 的<br>
> **时点**：2026-09（参考实现工程规范当前版本）<br>
> **来源**：参考实现 `docs/12-engineering-standards.md` §1<br>
> **局限**：这不是一条理论风险。参考实现把它写进规范正文，说明它已经真实发生过

正确的写法有两种：

```bash
npm run verify > log 2>&1; echo $?     # 写法一：不接管道，先落盘再取退出码
set -o pipefail && npm run verify | tail   # 写法二：让管道返回第一个失败命令的退出码
```

**这条教训的普适形式是**：**当你为了看清输出而做了一次"加工"，你必须检查加工有没有顺手把结论改掉。**后面你会反复遇到它的变体——第 13 章的"脚本化提供方不是模型质量的证据"，第 15 章的"渲染成功不等于内容正确"，都是同一个错误在不同层次上的重现。

## 0.3 数据与接口：把"大概是这样"变成契约

### 0.3.1 JSON 里没有"应该有的字段"

JSON 是一份**关于数据的文本**，不是一个"结构已知的对象"。区别在于：前者可能在任何一个字段上失效。

```json
{ "period": "2026-06", "amount": "1,234.50", "currency": null }
```

这一行里有三个陷阱，每一个都在真实项目里出过事故：

| 陷阱 | 现象 | 后果 |
|---|---|---|
| 数字被写成了**字符串** | `"1,234.50"` | `amount + 0` 会变成字符串拼接，得到 `"1,234.500"` |
| **千分位逗号** | `1,234.50` | 直接 `Number()` 得到 `NaN` |
| **`null` 与缺失** | `currency: null` 和没有 `currency` 键 | 不做区分时，两者会走进同一个分支 |

**处理规则只有一条**：**在系统边界上校验一次，之后内部就只处理已知合法的形状。**不要在每个使用点都写 `if (x.amount != null)`——那说明校验位置错了。

看参考实现里怎么把"外部给的杂数据"变成"内部可以相信的形状"：

```ts
// 参考实现源码（BetterWork · packages/tool-runtime/src/business-metrics.ts）
const numbersSchema = z
  .record(z.string().trim().min(1).max(100), z.number().finite())
  .refine((values) => Object.keys(values).length <= 100, '最多同时分析 100 个指标');
```

四件事在一行半里全部说清了：

1. **键**：字符串，去掉首尾空格后不能为空，长度 ≤100。
2. **值**：必须是**有限数**（`.finite()`）。这一条挡掉了 `NaN`、`Infinity`、`-Infinity`——它们都是 `number`，但都不是可以参与业务计算的数。
3. **规模**：最多 100 个指标。防止有人传一个十万键的对象把内存打满。
4. **不宽容**：非法形状直接报错，而不是被悄悄忽略——键不合法、值不是有限数、指标超过 100 个，三条都会让 `.parse()` 抛出。

第 2 点和第 3 点值得单独记：

> **核心判断 2**
>
> **校验的目的不是"拦住坏人"，而是"让错误在离它产生最近的地方暴露"。**<br>
> 一个 `NaN` 如果在入口就被拒绝，你会看到一行明确的报错；如果放进去，它会在二十步之后变成报告里的"∞%"。

### 0.3.2 HTTP：状态码是结论，正文是证据

调一个 HTTP 接口，最常被写错的一行是：

```ts
const data = await (await fetch(url)).json();   // 错
```

`fetch` **不会**在 404 或 500 时抛异常。它会给你一个 `response.ok === false` 的响应，而 `.json()` 可能仍然解析成功（很多错误响应返回的是 JSON 格式的错误体）。于是你的代码拿着一份错误信息，当成正常数据往下走。

正确的最小写法：

```ts
const response = await fetch(url, { signal });
if (!response.ok) throw new Error(`请求失败（HTTP ${response.status}）`);
if (!response.body) throw new Error('没有返回体');
```

这两行在参考实现里是逐字存在的（见 `openai-compatible-provider.ts`）。注意第二行：**`response.ok` 为真也不代表有 body**——流式接口返回 200 但正文为空的场景是会发生的。

### 0.3.3 密钥：不是"别打印"，而是"让它根本流不到日志里"

初学者对密钥的处理通常是"小心点，别打印出来"。这在工程上不成立，因为**你控制不了所有打印路径**——错误信息、堆栈、第三方库、用户截图，任何一处都可能带出去。

工程做法是**在构造字符串的那一刻就把密钥排除掉**：

```ts
// 参考实现源码（BetterWork · packages/agent-core/src/openai-compatible-provider.ts）
const displayBaseUrl = (baseUrl: string): string => {
  try {
    const url = new URL(baseUrl);
    url.username = '';
    url.password = '';
    url.search = '';
    url.hash = '';
    return url.toString();
  } catch {
    return '配置的模型地址';
  }
};
```

注意它做的是**四件事**：清掉用户名、清掉密码、清掉查询串、清掉锚点。查询串（`?api_key=xxx`）是最常被漏掉的一处——很多人只记得清密码。

它的第二个作用是错误信息里**只出现"配置的模型地址"**这种可读占位，而不是原始字符串。所以这个函数的调用点长这样：

```ts
return new Error(`无法连接模型服务（${displayBaseUrl(this.config.baseUrl)}）：${detail}`, {
  cause: error,
});
```

**这条纪律在参考实现里被写成规范**：密钥只允许在主进程内部流转，对外接口一律只回"是否已配置"这个布尔值；日志、错误信息、测试输出绝不出现密钥。第 11 章会讲这条纪律如何放大成信任边界。

## 0.4 异步与错误：三件被混为一谈的事

初学者常把三件事当成一件：**慢、失败、被打断**。它们在代码里必须分开。

| 概念 | 表现 | 谁触发 | 正确处理 |
|---|---|---|---|
| **慢** | 还没返回，但没出问题 | 网络、磁盘 | 设超时，超时是**失败** |
| **失败** | 出错了 | 对方的服务、数据、代码 | 显式抛出，让上层看见 |
| **被打断** | 用户点了取消、程序要关闭 | 你这一侧 | 走**取消**路径，不是失败路径 |

### 0.4.1 超时和取消必须能同时生效

看参考实现怎么把两者合起来：

```ts
// 参考实现源码（BetterWork · packages/agent-core/src/openai-compatible-provider.ts）
const timeout = AbortSignal.timeout(this.streamTimeoutMs);
const signal = AbortSignal.any([request.signal, timeout]);
```

`AbortSignal.any([...])` 的含义是：**任意一个被触发，合并后的信号就触发**。于是：

- 用户点取消 → `request.signal` 触发 → 请求中止；
- 服务端一直不返回 → `timeout` 触发 → 请求中止。

但两者**不能走同一个出口**，因为它们的含义完全不同。看它怎么区分：

```ts
private streamError(error: unknown, requestSignal: AbortSignal, timeout: AbortSignal): Error {
  if (requestSignal.aborted) return abortError();
  if (timeout.aborted) {
    return new Error(`模型流响应超时（超过 ${this.streamTimeoutMs / 1000} 秒）`, { cause: error });
  }
  return error instanceof Error ? error : new Error('模型流请求失败', { cause: error });
}
```

**顺序是刻意的**：先判断"是不是用户取消的"，再判断"是不是超时了"。因为用户取消时，超时信号通常也快到了——**先判取消，才能保证取消不会被误报成超时**。

> **这条纪律在参考实现里同样被写进规范**：取消语义只有一处定义，任何地方都不允许再手写一个名字叫 `AbortError` 的错误。原因很具体——**名字写错，取消就会被当成失败上报。**用户在界面上看到的是"运行失败"，实际上是他自己点的取消。第 12 章会展开这一点。

### 0.4.2 取消是"请求"不是"命令"

一个必须早点建立的认识：**取消是协作式的**。

你发一个中止信号，不等于对方那件事已经停了。它可能：

- 正在一个不支持中断的系统调用里；
- 已经把请求发出去了，正在等服务端返回；
- 是第三方进程，根本不读你的信号。

所以"我调用了取消接口"和"它已经停了"是**两件不同的事实**。参考实现把这件事写在注释里，作为一句提醒：

> 引擎产出的"已取消"结果，**不证明**一个不配合的工具已经物理停止。宿主必须自己管理未完成的工作。

这句话在第 4 章和第 12 章会各出现一次。现在只需要记住它的形状：**别把"我通知了"当成"它做到了"。**

## 0.5 测试与数据素养：先能证伪，再谈正确

### 0.5.1 测试的最小形态是一个断言

不需要框架也能开始测试：

```ts
if (result !== expected) throw new Error(`期望 ${expected}，实际 ${result}`);
```

一行代码，就把"我觉得对"变成了"机器判定"。

参考实现把它们组织成文件——**一个实现文件对应一个同目录同名的测试文件**（`calculator.ts` ↔ `calculator.test.ts`）。这个约定让"这段代码有没有测试"变成看一眼文件名就知道的事，不需要维护一份测试清单。

三条来自真实教训的测试纪律：

| 纪律 | 原因 |
|---|---|
| **用真实的数据库，不要 mock 仓储** | 参考实现明确记录："本仓已有多次『mock 通过、真实库失败』的教训，来源是 schema 与约束" |
| **外部 HTTP 必须注入 `fetch`，测试绝不触网** | 触网测试会因为对方服务抖动而随机失败，最后没人再信任它 |
| **有一个实现就必须有一个对应测试文件** | 落单的实现文件是"还没有被验证过"的标记 |

第二条的做法就是第 3 章会讲的**注入**：把 `fetch` 当参数传进来，测试传一个假的，生产传真的。这不是为了测试方便，它是**把"依赖外部世界"这件事变成显式的**。

### 0.5.2 表格数据的四个概念，错一个后面全错

案例 B 全篇都在处理表格，所以这四个概念必须在这里钉死。

| 概念 | 含义 | 典型错误 |
|---|---|---|
| **键（key）** | 唯一标识一行的字段组合 | 以为"日期"是键，其实"日期 + 项目"才是 |
| **颗粒度（grain）** | 一行代表什么 | 一行是"一笔明细"还是"一天的汇总"，混了会重复计数 |
| **合计** | 对某列求和 | 对"已经是汇总值"的列再求和 |
| **比例** | 分子/分母 | 分母为零时输出一个数字，而不是报错 |

**颗粒度错了，后面全错**——这是第 14 章的说法。原因很直白——如果一张表里既有明细行又有小计行，你把它们一起求和，得到的就是一个既不是明细也不是汇总的第三个数。

### 0.5.3 缺失与零：本书反复强调的第一条数据纪律

> **定义**：缺失与零
>
> **缺失**表示"这个值不存在，或者我们不知道"；**零**表示"这个值是 0，而且我们知道它就是 0"。
>
> **它不是什么**：不是同一件事的两种写法。缺失可以填零，但填了之后**你就再也分不出它原来是缺失的了**。
>
> **本书中的用法**：任何"从缺失值推导出来的数字"，都必须带上一个显式的警告标记，不能直接给出结果。

看参考实现遇到"分母为零"时的处理：

```ts
// 参考实现源码（BetterWork · packages/tool-runtime/src/business-metrics.ts）
if (previous !== undefined) {
  result.previous = previous;
  result.change = current - previous;
  if (previous === 0) warnings.push('comparison-zero-baseline');
  else result.changeRate = (current - previous) / Math.abs(previous);
}
```

三件事同时发生了：

1. **绝对变化额照算**：`change` 永远可以算，它不涉及除法。
2. **相对变化率不算**：分母为零时**干脆不产生这个字段**，而不是给一个 `Infinity` 或 `0`。
3. **但明确标记**：往 `warnings` 里推一条 `comparison-zero-baseline`。

这就叫"**显式的缺失**"。它的对立面是很多系统的实际做法——悄悄把 `0/0` 写成 `0%`，报告上看起来一切正常。

还有一个细节值得注意：`previous !== undefined` 这个判断。**如果上一期数据本身就是缺失的，那么"变化"这件事根本不该被算出来**——不是算出 0，而是不算。这是与"分母为零"并列的第二种缺失形态，第 14 章会再遇到它。

## 0.6 从"我的写法"到"这套代码的写法"

进入一个已有代码库，第一件该看的不是业务逻辑，是**它把规矩写在哪、以及机器怎么保证这些规矩被遵守**。

参考实现的做法值得抄：它把工程规范分成三层，每一层都有明确的执行者。

| 层 | 载体 | 管住什么 |
|---|---|---|
| 单文件写法 | `eslint.config.mjs`、`.prettierrc.json` | 一个文件内部的类型、异步、命名与排版 |
| 跨文件结构 | `standards/coding-standard.test.ts` | 配置唯一性、零豁免、分层边界、Token 与动效纪律 |
| 门禁 | `npm run verify` | 上面两层，加类型检查、全部测试与构建 |

关键在于第二层。**"跨文件的结构约定"是 ESLint 表达不了的**——它管不了"`packages/*` 不许依赖 `apps/*`"这种规则，因为那不是单个文件的语法问题。所以参考实现把它写成**一个测试文件**，随 `npm test` 一起跑：

```text
它断言的都是 ESLint 表达不了的约定：
  · ESLint / Prettier / tsconfig 各只有一份且严格开关全开
  · 源码里没有任何豁免注释
  · packages/* 不依赖 apps/*
  · Agent Core 不依赖宿主运行时
  · Renderer 不导入 node:*
  · ipcMain.handle 只在一处
  · 取消词汇只在一处
  · 硬编码色值与写死的动效时长只出现在白名单里
```

**这套做法的核心思想是：把"架构约定"降级成"可执行的断言"。**文档会过期、会被绕过、会被新人忽略；一个失败的测试不会。第 11 章讲信任边界时，你会看到同一个思想被推到极致——**规则写在文档里靠自觉，写在代码里才靠得住。**

还有一条同样值得抄：**源码里不接受单点豁免**。

```text
eslint-disable、@ts-ignore、@ts-expect-error、prettier-ignore 一律为零，由结构护栏强制。
真要放宽某条规则，改 eslint.config.mjs 并在配置注释里写清理由——
这会迫使例外可见、可评审，而不是藏进一行注释。
```

以及一条给测试文件的、按**角色**而不是按文件给的豁免：

```text
需要构造非法输入、按下标取断言目标时直接用 ! 与 any，
测试文件按角色放宽了这几条规则。这是按文件角色划定的单一策略，
不是逐文件例外；生产代码不享受。
```

**"按角色放宽"和"逐文件例外"的区别，是团队能不能长期维持规范的分水岭。**前者是一条能被记忆和审查的策略（"测试文件可以这样"），后者是几十条只存在于当事人脑子里的特例。

## 0.7 故意失败：一个会报告成功的失败

这一章最好用的一次实验，只需要两行命令。

先制造一个必定失败的命令：

```bash
node -e "process.exit(1)"
echo $?          # 输出 1 —— 失败被正确报告
```

现在给它加一个"为了让输出更好看"的管道：

```bash
node -e "process.exit(1)" | tail -1
echo $?          # 输出 0 —— 失败消失了
```

**你的自动化流程刚刚把一个失败读成了成功。**

这就是 0.2.3 里那条规范要防范的东西。但真正值得停下来想的是它的**结构**：

> **你为了看清输出做了一次加工，加工顺手改掉了结论。**

现在把它换成第 13 章的形状——**同样的错误，换了一层皮**：

| 层次 | 加工动作 | 被改掉的结论 |
|---|---|---|
| Shell | `cmd \| tail` | 命令的退出码 |
| 测试 | 用脚本化的假模型提供方跑通了 | 真实模型上的质量 |
| 文档 | 渲染成功了 | 内容对不对 |
| 数据分析 | 用另一套口径的近似算法验算了 | 原计算的正确性 |

**四行的结构完全一样。**这也是为什么这一章值得放在最前面：它给的不是知识，是一个**形状**，你会在后面每一篇里重新认出它。

### 0.7.1 第二个实验：把"缺失"变成"零"，看它去哪了

拿 0.5.3 那段代码做一次反向实验。把 `if (previous === 0)` 这条判断删掉，改成：

```ts
result.changeRate = previous === 0 ? 0 : (current - previous) / Math.abs(previous);
```

现在跑一份合成数据：上一期支出为 0，本期支出为 12,000 元。

- 改之前：结果里**没有** `changeRate` 字段，`warnings` 里有 `comparison-zero-baseline`。
- 改之后：`changeRate = 0`。

**改之后的结果看起来更"完整"——这就是它危险的地方。**因为下游代码看到 `changeRate = 0`，会认为"和上期持平"。而真实情况是"上期没有支出，无法比较"。这两个结论在报告里长得几乎一样，但一个是对的，一个是编的。

> **核心判断 3**
>
> **缺失值被填成默认值的那一刻，错误就完成了。**它此后的每一跳都会显得更合理，直到出现在某个人做决策的那一页 PPT 上。<br>
> 代价是有时候你必须在报告里写"此项无法计算"——这比写一个数字难看，但它是唯一诚实的写法。

## 0.8 行业视角：机构里没有"我的机器上跑通了"这句话

第 0 章讲的是"你的机器不是别人的机器"。在机构里，这句话要再往前推一层：**你的机器、你的网络、你的依赖来源，都不是别人能直接复用的。**

| 环节 | 个人项目里 | 机构场景里 | 对系统的要求 |
|---|---|---|---|
| 装依赖 | 从公网直接装 | 只能从内部制品库取，且要登记来源 | 依赖固定版本，并记录**它是从哪来的** |
| 配置 | 写在自己的环境变量里 | 来自配置中心或已审批的变更单 | 配置可校验；**缺失时显式失败**，不取默认值 |
| 时区与编码 | 通常一致 | 不同机房、测试与生产常常不一致 | 时间一律带时区；编码在解析前确认 |
| 出错 | 自己在控制台看 | 要能定位到"哪一次变更之后开始出错" | 运行必须带**环境标识与版本号** |

四行里第三条最容易被忽略，因为它在你自己的机器上永远不会出问题。**而它恰恰是"结果不对却找不到该负责的环节"的一个常见来源**——同一份数据在两台机器上被解析成了两个东西。

机构里的"跑通"，定义不是"在我这里能跑"，而是**"在别人审批过的环境里能跑"**。这是本书后面两条纪律的起点：**依赖要有来源（附录 B），环境要能被别人重建（第 19 章）。**

## 0.9 这一章在整本书里的位置

到这里，你应该能判断自己缺哪一块了。缺的补上，不缺的跳过——**这一章的目的只是把入口闸门放下，它不是本书的论点。**

从下一章开始，进入真正的问题：**在动手之前，怎么判断一件事该不该做成智能体。**

---

**本章小结**：从"能写程序"到"能建系统"，缺的是四件事——把环境和配置显式化（程序与工程基础）、把隐含假设变成显式契约（数据与接口）、把慢/失败/被打断分开（异步与错误）、把"我觉得对"变成机器判定，并学会把缺失和零分开（测试与数据素养）。这四件事有一个共同的形式：**把原来藏在人脑子里的判断，搬到代码和机器能检查的地方去。**

**行动清单**

1. 做 §0.1 的四道出口题，把做不出的那一道记下来，只读对应小节。
2. 在你手上任意一个脚本里，找到所有 `process.cwd()` 和相对路径，改成从显式传入的根目录解析。
3. 检查你所有的环境变量读取点：**任何一个给了默认值的必需变量，都改成缺失即报错退出**。
4. 找出你项目里所有对 `fetch` 结果直接 `.json()` 的地方，补上 `response.ok` 与 `response.body` 两道检查。
5. 在 Shell 里跑一次 `set -o pipefail`，然后重跑你常用的验证命令，看有没有哪个"一直成功"的命令其实是失败的。
