# 第 9 章 上下文与记忆：上下文是有限资源，不是仓库

**本章承诺**：读完这一章，你能把上下文装配画成一张有额度的预算表，并为每条记忆写出它的作用域、生命周期和删除路径。

**读完后你能回答**

- 一次模型请求里，有哪几样东西在抢同一块空间？它们各自应该分到多少？
- "知识"和"记忆"的差别是什么？为什么这个差别决定了一个功能该不该被做出来？
- 一条被用户删除的记忆，为什么可能在下一次运行里重新出现？

---

先看一个很典型的故障。

系统被要求"按上次确认过的口径算一下这个月的费用"。它算完了，数字也对，格式也对。唯一的问题是：**它用的是三个月前确认的口径。**

三个月前，口径是"含折旧"；两个月前，用户把它改成了"不含折旧"，并在同一轮对话里明确说过。

**但那个"明确说过"发生在一个已经结束的会话里。**而这次运行，系统装配上下文时：

- 系统提示：有（今天的日期）；
- Skill 说明：有（经营分析方法）；
- 检索回来的材料：有（本月的表格）；
- **历史记忆：没有。**

于是它按"默认"口径算了。而"默认"口径是它自己从系统提示的措辞里推出来的——**不是任何人确认过的那个。**

这个故障的形状值得我们记住：

> **它不是"记错了"，是"根本没记"。**而"没记"的表现，和"记对了"在输出层面完全一样。

> **核心判断 1**
>
> **上下文不会自动包含你需要的东西。它只包含你显式放进去的东西。**
> "它会记住"是一个**不存在的能力**：模型没有跨请求的记忆，只有"这一次你给了它什么"。
> 代价是你要为每一类信息设计"它该怎么进入上下文"——这个设计工作没有捷径。

## 9.1 上下文是一张有额度的预算表

把它想象成一份预算表。总额是**上下文窗口**，而下列每一类信息都在申请额度：

| # | 槽位 | 内容 | 谁写的 |
|---|---|---|---|
| 1 | **运行环境** | 当前日期、时区、平台事实 | 系统 |
| 2 | **角色与方法** | 专家配置、Skill 说明 | 用户配置 |
| 3 | **本次任务** | 用户这一次的诉求 | 用户 |
| 4 | **对话历史** | 本轮会话之前的相关轮次 | 历史 |
| 5 | **工具定义** | 每个可调用工具的名称、描述、参数 schema | 系统 |
| 6 | **外部材料** | 检索结果、选定的文件、上传的表格 | 检索 / 用户选择 |
| 7 | **记忆** | 被确认过、且作用域匹配的长期事实 | 记忆库 |

参考实现的装配顺序把这七类摆得很清楚：

```ts
// 参考实现源码（BetterWork · packages/agent-core/src/agent-engine.ts）
const messages: AgentMessage[] = [
  { id: randomUUID(), role: 'system', content: SYSTEM_PROMPT() },          // 1 运行环境
  ...(input.expertInstruction ? [ /* 2 专家配置 */ ] : []),
  ...skillMessages,                                                        // 2 Skill 说明
  ...(input.messages ?? []),                                               // 4 对话历史
  { id: randomUUID(), role: 'user', content: input.prompt },               // 3 本次任务
];
```

<div align="center"><img src="images/fig-9-1-context-budget.png" alt="图 9-1 上下文预算的七个槽位" width="1150"/></div>

**读图指引**：看"变化频率"一列。**它同时决定了两件事**——排序位置（稳的在上）和缓存命中率（变的不该在最前面）。而"工具定义"和"Skill 说明"是最容易被忽略的两笔大额支出。

### 9.1.1 三个容易被忽略的事实

**第一：工具定义也占额度，而且很占。**

一个 40 个工具的系统，每个工具的描述加 schema 平均 400 token，**光是"告诉模型它有哪些工具"就要花掉约 16,000 token**——在还没开始干活之前。

**这直接推出一个实践**：不要给一个任务挂上它不需要的工具。第 5 章讲过"阶段化同时是权限划分"，这里补上第二条理由：**它同时是上下文预算的划分。**

**第二：Skill 说明有溢出。**

参考实现给 Skill 指令设了一个明确的预算，并在超限时**截断 + 提示**：

```ts
// 参考实现源码（BetterWork · packages/agent-core/src/agent-engine.ts）
export const SKILL_INSTRUCTION_BUDGET = 16_000;

const OVERFLOW_HINT =
  '（部分 Skill 指令因长度被截断，可通过 skill_read_resource 工具按需读取完整内容。）';
```

注意它做了三件事，缺一不可：

| 动作 | 作用 |
|---|---|
| **去重** | 同一个 Skill 被重复引用时只放一次（按 `skillId` 去重） |
| **按序填充** | 累加长度，放得下就放，放不下就进入截断分支 |
| **截断并留提示** | 截断处加一句"被截断了，可以用工具读全文"——**给模型一条补救路径** |

**第三：这个"16,000"是字符还是 token？**

它是 `.length`，也就是**字符数**，不是 token 数。这个区别很重要：**中文的 token/字符比与英文不同**，所以同一个字符预算对中文和英文的实际效果不一样。

这不是缺陷，是**一个必须被知道的近似**。工程上可行的做法是：用它作为**粗略闸门**（防止某个 Skill 意外膨胀到十万字符），真正的精确计量交给第 13 章的 token 统计。

## 9.2 稳定性排序：会变的东西放下面

七个槽位怎么排？参考实现的顺序给出了一个可推广的规则：

```text
稳定的（很少变）  →  上
会变的（每次都变）  →  下
```

| 位置 | 内容 | 变化频率 |
|---|---|---|
| 最上 | 运行环境、角色与方法 | 几乎不变 |
| 中间 | 对话历史 | 逐轮增长 |
| 最下 | 本次任务 | 每次都变 |

**为什么这样排？**两个理由，第二个比第一个重要：

1. **注意力分布**：靠近末尾的内容对模型的影响更强，所以"这一次要做什么"应该在最下面。
2. **前缀缓存**：多数模型服务对**请求前缀**做缓存计费。前缀越稳定、命中率越高，成本越低。**把每次都变的内容放在最前面，会让缓存完全失效。**

第二条在很多实现里被忽略。一个"把时间戳放在系统提示开头"的实现，会让每次请求的前缀都不同——**缓存命中率归零，成本可能翻几倍**。

> **一条立刻能用的检查**：**把请求的第一个字符到最后一个字符看一遍，问"这一段里有多少是每次都变的？"**
> 答案应该是"只有最末尾的一小段"。

## 9.3 装配结果必须被记录下来

第 8 章说过"检到了不等于被读到"。要把这句话变成可检查的，唯一的办法是**把装配结果留下来**。

> **核心判断 2**
>
> **上下文装配的产物本身，必须成为一个被记录的对象。**
> 否则你永远无法回答"这次为什么没用到那份材料"——因为材料在检索结果里出现了，你看不出它有没有进入模型。
> 代价是存储量上升（每次运行多存一份完整的请求体），以及**脱敏要求变严**（这份记录里可能含敏感内容）。

记录什么？至少四样：

| 项 | 为什么 |
|---|---|
| **槽位清单** | 每一类信息放了什么（文件名、记忆 ID、Skill ID） |
| **额度占用** | 每个槽位花了多少（字符或 token） |
| **被排除的项** | **放了哪些东西被挤掉了**——这一列最有价值 |
| **装配版本** | 用哪一版规则装的（配置变了要能区分） |

第三列是排障的关键。当一个用户说"它好像没看到我上传的表"时，你要能一眼看出：**表被检索到了吗？被排进去了吗？还是被 Skill 说明挤掉了？**

## 9.4 压缩：什么时候压，压掉了什么

上下文会满。满了就要处理。三种做法：

| 做法 | 机制 | 丢掉什么 |
|---|---|---|
| **截断尾巴** | 丢掉最早的历史 | 早期的决策依据 |
| **摘要历史** | 用模型把旧轮次压成一段 | 细节与原文 |
| **重写工作台**（scratchpad） | 让模型定期重写"当前进展与待办" | 过程细节 |

公开的工程实践给出的经验阈值是：**当历史达到窗口约 50% 时开始压缩**，而不是等到满了再压。理由很直接——**压缩本身也要消耗额度**（摘要是一次模型调用），等满了再压，你没有空间做这件事。

### 9.4.1 压缩有一条绝对不能碰的底线

**有些东西不能被摘要替换。**列成一个清单：

| 不能压掉的 | 为什么 |
|---|---|
| **审批状态** | "用户是否已经确认了这个口径"——压掉了就会重新问，或者更糟：忘掉已经确认过 |
| **当前计划** | 模型正在执行的步骤序列 |
| **已加载的规则** | Skill 约束、专家配置 |
| **已被改动产物的清单** | 改了哪些文件、哪个版本 |
| **删除与排除** | **用户明确排除掉的记忆，不能因为压缩而回到上下文里** |

最后一条正是章首那个故障的另一种形态。**摘要会"忘记"否定信息**——因为摘要倾向于保留"讲了什么"，而"明确排除掉什么"是反事实，很容易被压掉。

> **一条硬规则**：**把"不能被摘要的内容"做成一份结构化对象，与摘要并列存放，不走摘要通道。**
> 摘要通道只处理"对话文本"，不处理"状态"。

## 9.5 知识与记忆：两种不同的东西

这两个词在很多产品里被混用，而它们的差别决定了功能该怎么做。

| | **知识** | **记忆** |
|---|---|---|
| 是什么 | 参考资料 | 保留下来、有作用域的协作上下文 |
| 来源 | 用户导入的文档、外部检索 | 对话中被确认的事实、偏好、口径 |
| 可变性 | 相对稳定 | 会被修订 |
| 是否需要"确认" | 不需要（导入了就在） | **需要**（未经确认的不该生效） |
| 删了会怎样 | 检索不到 | **必须彻底不再出现** |
| 谁负责准确性 | 材料作者 | 系统 + 用户 |

最本质的差别在第四行：**记忆在被确认之前，只是一个候选。**

参考实现把这个差别做进了数据模型——记忆有状态，而且是**包含"候选"状态的**：

```ts
// 参考实现源码（BetterWork · apps/desktop/src/main/services/memory-service.ts）
const records = this.store.memories
  .list({ includeCandidates: true })
  .filter((record) => record.status !== 'deleted' && record.status !== 'candidate');
```

两行代码表达了两个规则：

1. **候选状态存在**（否则不需要 `includeCandidates` 这个开关）；
2. **候选不进投影**——它还没被确认，不该被当成事实使用。

而投影时也滤掉了 `deleted`。**这两个过滤是"记忆不会自己回来"的第一道防线。**

## 9.6 记忆的四个作用域

一个记忆属于谁？参考实现给出了四类：

```ts
// 参考实现源码（BetterWork · apps/desktop/src/main/services/memory-service.ts）
const scopeLabel = (record: MemoryRecord): string => {
  switch (record.scope.kind) {
    case 'user': return '用户';
    case 'workspace': return `工作空间 ${record.scope.workspaceId}`;
    case 'expert': return `专家 ${record.scope.expertId}`;
    case 'expert-workspace': return `专家 ${record.scope.expertId} · 工作空间 ${record.scope.workspaceId}`;
  }
};
```

| 作用域 | 含义 | 例子 |
|---|---|---|
| **用户** | 跨全部工作空间生效 | "我的名字是……""我一律用简体中文" |
| **工作空间** | 只在这个资料库里生效 | "本项目的成本口径含折旧" |
| **专家** | 只在这个角色配置下生效 | "作为财务分析角色，金额一律以万元呈现" |
| **专家 × 工作空间** | 两者同时满足才生效 | "在这个项目的财务分析角色下，折旧按月摊" |

**为什么需要四类，而不是一类？**

因为**作用域是防串味的唯一机制**。只有"用户"级别的记忆，会让 A 项目的口径污染 B 项目；只有"工作空间"级别的记忆，会让每次换一个资料库都要重新交代基本偏好。

第四类（交叉）看似多余，实际最常用：**"这个角色在这个项目里的特有约定"。**

<div align="center"><img src="images/fig-9-2-memory-scope.png" alt="图 9-2 记忆的四个作用域与生命周期" width="1150"/></div>

**读图指引**：左半是"这条记忆属于谁"，右半是"它什么时候生效、什么时候必须消失"。**作用域是防串味的唯一机制，生命周期是防复活的唯一机制**——两者缺一，记忆就会变成污染源。

### 9.6.1 生效还要加两个条件

作用域匹配只是第一个条件。参考实现的读取方法签名给出了完整的四个：

```ts
// 参考实现源码（BetterWork · apps/desktop/src/main/services/memory-service.ts）
getApplicable(
  workspaceId: string,
  expertId?: string,
  now = Date.now(),
  excludedMemoryIds: readonly string[] = [],
): MemoryRecord[] {
  const excluded = new Set(excludedMemoryIds);
  return this.store.memories
    .listApplicable(workspaceId, expertId, now)
    .filter((memory) => !excluded.has(memory.id));
}
```

四个条件：

| 条件 | 参数 | 拦住的失败 |
|---|---|---|
| **作用域匹配** | `workspaceId`, `expertId` | 别的工作空间/角色的记忆串进来 |
| **时间有效** | `now` | **过期的事实继续被使用** |
| **未被排除** | `excludedMemoryIds` | 用户在本次任务里明确说"这次别用这条" |
| **状态可生效** | （查询内部） | 候选、已删除的进来 |

**第二个条件（时间）是最容易被忽略的**。记忆必须有有效期——因为**事实会过期**。"这个项目的负责人是张三"在半年后可能已经不成立，而它作为一条记忆会一直"有效"到有人去改它。

**第四个参数 `excludedMemoryIds` 的设计值得单独说。**它把"这条记忆这次别用"变成了一个**每次运行都可以带上的参数**——而不是要求用户去删除它。

这两件事必须分开：

| 动作 | 语义 | 可逆 |
|---|---|---|
| **排除** | 只对本次运行生效 | 是（下次自动失效） |
| **删除** | 永久移除 | 否 |

**只提供"删除"不提供"排除"的产品，会逼用户做不可逆的操作来完成一次临时需求。**

## 9.7 真相源与投影：为什么记忆要写两份

参考实现把记忆同时写在两个地方，但**地位完全不同**：

```ts
/**
 * 记忆的产品服务层：SQLite 保存可审计真相，Markdown 仅作为可重建的只读投影。
 */
export class MemoryService {
```

| | SQLite | Markdown 投影 |
|---|---|---|
| 地位 | **真相源** | 派生视图 |
| 能不能改 | 通过接口改 | **不能改**（改了会被覆盖） |
| 丢了怎么办 | 数据丢失 | **重建** |
| 为什么存在 | 查询、审计、事务 | 让用户/其他工具**能读**，让记忆可被人审阅 |

投影文件自己的头部就写着这句话：

```text
# BetterWork 记忆（受管投影）

> 此文件由算台根据 SQLite 记忆记录自动生成。请通过算台管理记忆，不要手工编辑。
```

**为什么必须把这句话写进文件里？**因为一个 Markdown 文件天然会被人编辑。写清楚它是投影，是唯一的防止方式。

投影的重建过程有三处值得学的细节：

```ts
// 参考实现源码（BetterWork · apps/desktop/src/main/services/memory-service.ts）
const previous = await this.readManifest();
for (const relativePath of previous) {
  await rm(path.join(this.projectionRoot, relativePath), { force: true });
}
...
const destination = path.join(this.projectionRoot, relativePath);
const temporary = `${destination}.tmp`;
await mkdir(path.dirname(destination), { recursive: true });
await writeFile(temporary, `${lines.join('\n')}\n`, 'utf8');
await rename(temporary, destination);
generated.push(relativePath);
```

| 细节 | 作用 |
|---|---|
| **先按上次的清单删除旧文件** | 否则被删掉的记忆会留下一份孤儿投影文件——**而那个文件看起来还像真的** |
| **写 `.tmp` 再 `rename`** | `rename` 在同一文件系统内是原子的。**避免"写到一半崩溃留下半个文件"** |
| **写完之后把新清单落盘** | 清单是下一次删除的依据；它必须与磁盘状态一致 |

**第一行是这一节的核心。**试想如果不删除旧的投影文件：用户删掉一条记忆，SQLite 里没了，投影里那份旧文件**还在原地**。任何人（或工具）读到它，都会以为那条记忆仍然有效。

> **删除必须删两处，而且必须删干净。**这类"真相源删了、派生视图还在"的 bug 在很多系统里存在，而且极难被发现——因为派生视图通常不在主流程的关键路径上，只在有人去读的时候才暴露。

### 9.7.1 清单本身也要防篡改

```ts
// 参考实现源码（BetterWork · apps/desktop/src/main/services/memory-service.ts）
private async readManifest(): Promise<string[]> {
  try {
    const parsed: unknown = JSON.parse(await readFile(this.manifestPath, 'utf8'));
    if (!Array.isArray(parsed)) return [];
    return parsed.filter(
      (value): value is string =>
        typeof value === 'string' &&
        value.endsWith('/index.md') &&
        !value.includes('..') &&
        !path.isAbsolute(value),
    );
  } catch {
    return [];
  }
}
```

这是一个**清单文件的路径校验**。三个条件缺一不可：

- `endsWith('/index.md')` —— 只删它自己生成的那种文件；
- `!includes('..')` —— 不许向上逃逸；
- `!isAbsolute(value)` —— 不许是绝对路径。

**为什么一份你自己写的清单也要校验？**因为它是一个**磁盘上的文件**——可能被手工编辑、被其他程序改写、被损坏。而它的用途是"决定删除哪些文件"。

**一个决定删除的文件，永远值得多检查一次。**这是"最小权限"原则在文件系统操作上的实例：**投影服务只需要删除 `memory/` 下自己生成的 `index.md`，那就只允许它删这个。**

## 9.8 故意失败：三个必须构造的实验

### 9.8.1 删掉的记忆又回来了

**实验**：创建一条记忆 → 让它进入投影 → 删除它 → 重建投影 → 搜索投影目录。

**合格表现**：投影目录里再也找不到它。

**不合格的表现**（两种）：

1. 旧的投影文件还在（因为没按清单删除旧文件）；
2. **它出现在摘要里**——因为某次上下文压缩把"曾经有过这条记忆"概括进去了。

第 2 种更难查，也更危险。防它的办法就是 9.4.1 那条硬规则：**删除与排除信息不走摘要通道。**

### 9.8.2 别的工作空间的事串进来

**实验**：在资料库 A 里创建一条工作空间级记忆，切到资料库 B，问一个会用到它的任务。

**合格表现**：B 里完全看不到它。

**不合格的表现**：B 里能看到——通常是因为装配时只传了 `userId` 没传 `workspaceId`，或者作用域判断写成了"或"而不是"与"。

**这个实验值得在每次改动记忆相关代码后重跑。**因为"作用域判断"是一处很容易在重构中被写错、而写错后**没有任何报错**的逻辑。

### 9.8.3 过期的记忆继续生效

**实验**：创建一条带有效期的记忆，把系统时间调过有效期，看它还会不会被装配进去。

**合格表现**：不生效。

**不合格的表现**：继续生效。而用户看到的现象是"它还在用我三个月前改掉的口径"——**这正是章首那个故障**。

## 9.9 行业视角：为什么"记忆"在受监管场景是一个合规问题

个人应用里，"记住用户偏好"是个便利功能。在机构场景里，同一件事会被问三个问题：

| 问题 | 需要的能力 |
|---|---|
| **这条记忆从哪来？** | 每条记忆必须有来源（`sourceType` + `sourceId`）与确认状态 |
| **谁能看见它？** | 作用域必须可枚举、可审计 |
| **怎么彻底删掉它？** | 必须有删除路径，且删除必须可验证（含投影与备份） |

参考实现的数据模型对第一问给了答案——每条记忆带 `sourceType`、`sourceId`、`confidence`、`revision`。投影文件里也把这些写了出来：

```text
## <kind> · <作用域标签>
- 状态：<status>
- 来源：<sourceType> · <sourceId>
- 置信度：<confidence>
- 修订：<revision>
```

**"来源 + 置信度 + 修订号"这三样，是"记忆可被追责"的最小集合。**

- **来源**回答"它从哪来"；
- **置信度**回答"它有多确定"（用户明确确认的 vs 系统推断的，不该同级）；
- **修订号**回答"它被改过几次"——当两个人对同一条记忆有不同印象时，修订号能定位到是谁在什么时候改的。

第三项还有一个技术用途：**修订号是并发写入的检测手段**。两个人同时改同一条记忆，后写的如果不知道前一次的修订号，就会**静默覆盖**。要求"基于某版本修改"，把覆盖变成冲突——而冲突是可以被处理的。

**本章小结**：上下文是一张有额度的预算表，七类信息在抢同一块空间，其中**工具定义**和 **Skill 说明**这两项最容易被忽略地吃掉大额预算。装配要按"稳定的放上面、会变的放下面"排布——这同时改善了注意力分布与前缀缓存。**装配结果本身必须被记录**，否则"检到了没被读到"永远无法排查。压缩有一条底线：**审批状态、当前计划、已加载的规则、删除与排除信息，不能走摘要通道**。知识是参考资料，记忆是需要确认的协作上下文；记忆有四个作用域、四个生效条件（作用域 / 时间 / 未排除 / 状态），并且**SQLite 是真相源、Markdown 只是可重建的只读投影**——删除必须同时删掉投影，否则记忆会"复活"。
