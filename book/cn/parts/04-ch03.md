# 第 3 章 一次工具交换：提示词的尽头是代码

**本章承诺**：读完这一章，你能独立走通一次完整的"模型请求 → 工具执行 → 结果回填"，并能说清这条链上每一个标识符为什么必须存在。

**读完后你能回答**

- 从"模型说要算 60"到"60 这个数真的被算出来"，中间必须经过哪几个环节？每个环节谁负责？
- 工具调用的参数为什么会分成好几片传来？分片带来的后果是什么？
- `toolCallId` 这个看起来多余的字段，去掉会发生什么？

---

先说一个很容易被忽略的事实。

当模型回复"计算结果是 60"时，**没有人算过 60。**

数值可能是对的，因为 `(12 + 8) * 3` 太简单了，模型在训练数据里见过足够多类似的式子。但请注意：这个"对"不是**算出来的对**，是**猜出来的对**。

现在把式子换成 `1284.6 * 0.0731 - 47.28`。

模型仍然会给你一个数字，仍然是"60"这样的格式，仍然流畅。**这个数字可能错，而且错得看不出来。**

这一章要做的事只有一件：**把"猜"换成"算"。**

> **核心判断 1**
>
> 模型的职责是**决定调用什么**，代码的职责是**保证调用的结果是对的**。
> 这两件事不能由同一个东西承担。一旦你把算术交给模型，你就失去了对正确性的判断能力——因为你没法独立验算它的答案，只能再问它一遍。

---

## 3.1 一次交换的完整形状

先看全貌，再拆细节。一次工具交换有五个环节：

```text
① 你发起请求     messages + tools + signal  →  模型服务
② 模型返回流     text-delta / tool-call ...  →  你的代码
③ 你校验并执行   解析参数 → 校验 → 执行工具  →  你的代码
④ 你回填观测     role: tool 的消息            →  messages
⑤ 下一轮请求     messages（含观测）           →  模型服务
```

注意 ③ 和 ④ **全部发生在你的代码里**。模型在 ② 之后就不动了——它只产出了一个"我想调用这个工具，参数是这样"的**意图**。

<div align="center"><img src="images/fig-3-1-exchange.png" alt="图 3-1 一次工具交换的完整时序" width="1150"/></div>

**读图指引**：看中间那条竖线两侧的分工。**左侧（你的代码）是唯一能产生副作用、唯一能做校验、唯一能拒绝的地方。**右侧（模型）只产生文本与意图。这条分界线在第 11 章会变成"信任边界"。

## 3.2 提供方边界：一个只有九个方法的接口

参考实现把一个"模型提供方"抽象成极小的三组类型。

```ts
// 参考实现源码（BetterWork · packages/agent-core/src/types.ts）
export type ModelStreamChunk =
  | { type: 'reasoning-delta'; delta: string }
  | { type: 'text-delta'; delta: string }
  | { type: 'tool-call'; toolCall: ToolCall }
  | { type: 'done' };

export interface ModelRequest {
  messages: AgentMessage[];
  tools: ModelToolDefinition[];
  signal: AbortSignal;
}

export interface ModelProvider {
  readonly id: string;
  stream(request: ModelRequest): AsyncIterable<ModelStreamChunk>;
}
```

**只有四个 chunk 类型、一个方法。**这四行值得逐项解释，因为它们划定了整本书后面所有抽象的边界。

| 类型 | 含义 | 为什么单独列出来 |
|---|---|---|
| `reasoning-delta` | 模型的思考过程片段 | 可以让用户看到"它在想什么"，但**不应作为判断依据**（第 5 章解释） |
| `text-delta` | 面向用户的回答片段 | 界面渲染增量用 |
| `tool-call` | 一次工具调用的完整意图 | 与文本分开，因为它的**去向不同**——它要进执行器，不是进界面 |
| `done` | 流结束 | 必须显式存在，否则"流断了"和"流正常结束"无法区分 |

**这个接口最重要的性质是它没有的东西：**

- 没有 `chat()`（只有 `stream()`）。因为流式是刚需——一个三十秒不动的界面是不可用的，而增量输出让用户知道系统还活着。
- 没有会话管理。**提供方不管历史**，历史由调用方拼好传进来。这样"上下文怎么组织"就是你的决定，不是提供方的黑盒（第 9 章的主题）。
- 没有重试。重试是**策略**，属于编排层。提供方只负责"这一次请求"。

> **定义**：提供方（Provider）
>
> 一个把"消息 + 工具定义 + 中止信号"变成"一串流式片段"的适配器。
>
> **它不是什么**：不是智能体，不管循环，不管工具执行，不管历史。它是一个**翻译层**：把不同厂商的接口差异翻译成统一形状。
>
> **本书中的用法**：换一个模型只应该替换这一层。如果换模型需要改循环和工具，说明抽象做错了。

## 3.3 工具契约：四个字段，各有各的职责

```ts
// 参考实现源码（BetterWork · packages/agent-core/src/types.ts）
export interface AgentTool {
  name: string;
  description: string;
  inputSchema: Record<string, unknown>;
  execute(input: Record<string, unknown>, context: ToolExecutionContext): Promise<unknown>;
}
```

| 字段 | 给谁看 | 作用 |
|---|---|---|
| `name` | **模型** | 调用时用的标识符，必须唯一 |
| `description` | **模型** | 决定**要不要**用、**什么时候**用这份工具 |
| `inputSchema` | **模型 + 你的代码** | 告诉模型参数的形状；同时作为第一层校验 |
| `execute` | **只有你的代码** | 真正执行。模型永远看不到它 |

**第三行和第四行是这一章最容易做错的地方。**

`inputSchema` 是"声明"，它跑在模型那一侧（作为提示的一部分）和你这一侧（作为校验依据）。但**声明不等于校验**：

> **定义**：声明与校验
>
> **声明**是"我告诉模型参数长什么样"；**校验**是"拿到参数时我实际检查它符不符合"。
>
> **它不是什么**：不是同一件事的两种说法。声明是**建议性的**（模型可能不听），校验是**强制性的**（不符合就拒绝执行）。
>
> **本书中的用法**：两者必须同时存在，且**校验必须在执行之前**。

看参考实现怎么让这两件事落在同一处：

```ts
// 参考实现源码（BetterWork · packages/tool-runtime/src/calculator.ts）
const inputSchema = z.object({ expression: z.string().min(1).max(500) });

export const calculatorTool: AgentTool = {
  name: 'calculator',
  description: 'Perform deterministic arithmetic with +, -, *, / and parentheses.',
  inputSchema: {
    type: 'object',
    properties: { expression: { type: 'string' } },
    required: ['expression'],
    additionalProperties: false,
  },
  async execute(rawInput, context) {
    if (context.signal.aborted) throw abortError();
    const { expression } = inputSchema.parse(rawInput);
    context.reportProgress(`正在计算 ${expression}`);
    return { expression, result: new Parser(expression).parse() };
  },
};
```

**同一个参数形状写了两遍。**这不是冗余，是刻意的：

- 上面那份（`inputSchema` 字面量）是**给模型的**——必须是 JSON Schema 格式，因为那是协议要求的形状。
- 下面那份（`inputSchema` 这个 Zod 对象）是**给你的代码的**——`.parse()` 会在参数不合法时抛出，并且 Zod 的 `.strict()`、`.finite()` 这些能力比手写 `if` 强得多。

这两份定义要**分开维护、不要试图合成一份**：读者不同（一份给模型，一份给你的代码），能表达的约束也不同——JSON Schema 是协议要求的形状，而 Zod 能表达"长度上限""必须是有限数"这类更强的检查。

<div align="center"><img src="images/fig-3-2-contract-layers.png" alt="图 3-2 工具契约的四层职责" width="1150"/></div>

**读图指引**：看第二列"谁看得到"。**执行层（第 ③ 层）永远只有你的代码能看到，模型看不到 `execute` 里的任何一行。**这四层的可见性不同，正是"提示词不能当权限系统"的结构原因。

### 3.3.1 一个必须现在就建立的判断：不要用 `eval`

看 `calculatorTool` 返回的那一行：

```ts
return { expression, result: new Parser(expression).parse() };
```

`Parser` 是什么？是一段**手写的递归下降解析器**，支持 `+ - * /` 和括号。整个文件 87 行。

为什么不用 `eval(expression)`？因为 `eval` 会把 `expression` 当成**代码**执行，而它来自**模型输出**。模型输出是不可信的（第 2 章已经确立），所以 `eval` 等价于"让一个不可信来源在你的进程里执行任意代码"。

`Parser` 还做了两件 `eval` 不会做的事：

```ts
// 参考实现源码（BetterWork · packages/tool-runtime/src/calculator.ts）
if (this.cursor !== this.expression.length)
  throw new Error(`Unexpected token at position ${this.cursor + 1}`);
if (!Number.isFinite(result)) throw new Error('Result is not finite');
```

- **第一个**：解析完之后必须已经吃掉整个输入。否则 `1+2 恶意内容` 会被解析成 `3` 然后放过剩下的一半。**"解析成功"必须包括"输入被完整消费"。**
- **第二个**：结果必须是有限数。这挡住了整数溢出到 `Infinity`、以及 `0/0` 产生的 `NaN`。同时 `parseTerm` 里对除数做了零检查：

```ts
if (this.take('/')) {
  const divisor = this.parseFactor();
  if (divisor === 0) throw new Error('Division by zero');
  value /= divisor;
}
```

**注意这里选择的是"抛错"而不是"返回 Infinity"。**这与第 0 章的缺失/零纪律是同一条原则：**宁可明确失败，不要给出一个看起来正常的数字。**

> **核心判断 2**
>
> 工具的价值不在于它能算什么，而在于**它不能做什么**。
> `Parser` 不能执行代码、不能读文件、不能联网——这三条"不能"才是它安全的原因。**评估一个工具时，先列出它的禁止集，再看它的功能集。**

## 3.4 调用身份：`toolCallId` 为什么不能省

```ts
// 参考实现源码（BetterWork · packages/agent-core/src/types.ts）
export interface ToolExecutionContext {
  runId: string;
  toolCallId: string;
  workspacePath: string;
  signal: AbortSignal;
  reportProgress(message: string): void;
}
```

五个字段，每个都对应一个具体的失败场景：

| 字段 | 少了它会怎样 |
|---|---|
| `runId` | 无法把这次执行关联回是哪一次运行，日志里全是无主记录 |
| `toolCallId` | **一轮里模型可以请求多个工具调用**，结果回填时无法知道哪个结果对应哪个请求 |
| `workspacePath` | 工具只能去猜工作目录在哪，或者干脆用进程当前目录（第 0 章的坑） |
| `signal` | 无法取消，长任务只能等死 |
| `reportProgress` | 长任务期间界面一片空白，用户以为卡死了 |

### 3.4.1 一轮多调用：这个场景必须提前想到

模型**可以在一轮里同时请求多个工具调用**。参考实现明确记录了这一点：

> `maxToolRounds` 限制的是**工具轮次**，不是模型调用总次数，也不是单个工具调用次数。一轮里可以请求多个调用；需要"总调用数"预算的应用要另外加策略。

于是回填出现了一个新要求：**每条结果必须带着它对应的 `toolCallId` 回到消息里。**

```ts
// 参考实现源码（BetterWork · packages/agent-core/src/agent-engine.ts）
messages.push({
  id: randomUUID(),
  role: 'tool',
  toolCallId: toolCall.id,
  toolName: toolCall.name,
  content: JSON.stringify(outcome.output),
});
```

去掉 `toolCallId` 会得到什么？三条结果堆在消息列表里，模型只能靠**顺序**猜哪条对应哪个请求。在一个一轮三个调用的场景里，顺序对不上就会让模型把 A 的结果当成 B 的——**而且它依然会流畅地给出回答**。

> **这类失败的特征是"静默"。**它不会抛异常，不会让测试变红，只会在某一次复杂任务里产生一个说不通的结论。所以处理规则很简单：**凡是"用来对齐两件事"的标识符，一个都不能省。**

## 3.5 传输细节：工具参数是分成几片传过来的

这是全章最技术性、也最容易漏掉的一节。

模型服务用 Server-Sent Events 把结果流式发回来。你的适配器要做的事看起来很简单：读行、解析 JSON、取 `delta`。但**工具调用的参数在协议层是被切片传输的**：

```ts
// 参考实现源码（BetterWork · packages/agent-core/src/openai-compatible-provider.ts）
for (const call of delta?.tool_calls ?? []) {
  const index = call.index ?? 0;
  const current = toolCalls.get(index) ?? { id: call.id ?? `tool-${index}`, name: '', arguments: '' };
  current.id = call.id ?? current.id;
  current.name += call.function?.name ?? '';
  current.arguments += call.function?.arguments ?? '';
  toolCalls.set(index, current);
}
```

循环体里四次更新字段，处理了三件不同的事（其中 `name` 与 `arguments` 用 `+=` 累加，`id` 用 `=` 兜底）：

1. **函数名也是分片的**（`current.name += ...`），不是只在第一片里出现。
2. **参数 JSON 字符串是分片的**——你可能先收到 `{"expres`，下一片接着 `sion":"1+2"}`。**必须累加完整之后才能 `JSON.parse`。**
3. **用 `index` 作为聚合键**，而不是数组位置。因为多路调用是交错的：第 1 片给调用 0，第 2 片给调用 1，第 3 片又回到调用 0。

### 3.5.1 关键设计：工具调用在流结束后才产出

注意代码里的顺序：整个 `while` 循环把流读完之后，才做这件事：

```ts
// 参考实现源码（BetterWork · packages/agent-core/src/openai-compatible-provider.ts）
if (!completed) throw new Error('模型流在收到完成信号前结束');
for (const call of toolCalls.values()) {
  const input = JSON.parse(call.arguments || '{}') as Record<string, unknown>;
  yield { type: 'tool-call', toolCall: { id: call.id, name: call.name, input } };
}
yield { type: 'done' };
```

**这一句 `if (!completed) throw` 是这一节最重要的一行代码。**

它在处理什么？**流在完成信号之前就结束了。**

> **定义**：不完整流
>
> 连接正常建立、数据正常到达、然后**在收到协议约定的完成标记之前，连接结束或被切断**。
>
> **它不是什么**：不是"网络错误"（那会直接抛连接异常）。它表现得完全像一个正常结束的短响应。
>
> **为什么危险**：如果适配器不检查完成标记，一个被切断的半截 JSON 会走到 `JSON.parse` 那里——运气好会抛解析错，运气不好会解析出一个**合法但缺少字段的对象**，然后这个不完整的意图被当成完整意图执行。

### 3.5.2 两种完成信号都要认

协议的完成标记有两个来源，参考实现两个都认：

```ts
if (data === '[DONE]') { completed = true; return []; }   // 流结束标记
...
const choice = chunk.choices?.[0];
if (choice?.finish_reason) completed = true;              // 正常结束原因
```

**为什么要认两个？**因为不同服务端实现、不同兼容层可能只发其中一个。只认一个的适配器会在另一种实现上报告"流被截断"——而实际上没有。

### 3.5.3 缓冲与行边界

```ts
buffer += decoder.decode(result.value ?? new Uint8Array(), { stream: !result.done });
const lines = buffer.split('\n');
buffer = lines.pop() ?? '';
for (const line of lines) yield* emitLine(line.trim());
```

这里有一个必须做对的动作：**`buffer = lines.pop()`**。

网络分片和行边界**没有任何关系**。一个 chunk 可能包含 2.5 行，下一片接着那半行。所以必须：

1. 把新到的字节**追加**到缓冲区；
2. 按换行切分；
3. **把最后一段（可能不完整）留着**，等下一片到了再拼。

如果直接对每个 chunk 的完整内容按行处理，那半行会被当成一整行解析——**得到一条格式错误、内容合法的记录**。

`decoder.decode(..., { stream: !result.done })` 里的 `stream: true` 同理：**一个 UTF-8 汉字占 3 个字节，可能被切在两片里**。不开流式解码会解出乱码。

## 3.6 观测结果回填：把"发生了什么"变成"模型能读的文本"

工具执行完之后，结果要变成一条消息回到对话里。参考实现统一用 JSON：

```ts
content: JSON.stringify(outcome.output)
```

**为什么是 JSON 而不是自然语言描述？**因为下一轮读取它的是模型。JSON 有两个好处：结构明确（模型能精确定位字段），以及**你的代码也能读**（可以写断言）。

但这里有一个设计选择值得停下来想：**回填的内容，是"原始结果"还是"给模型看的摘要"？**

| 做法 | 优点 | 风险 |
|---|---|---|
| 回填原始结果 | 信息无损 | 一个返回 5 万个字的工具会直接吃掉上下文预算 |
| 回填摘要 | 省 token | 摘要可能丢掉模型真正需要的那一项 |

参考实现在另一处给出了一个务实的答案——它对不同工具做**专门的摘要**：

```ts
// 参考实现源码（BetterWork · packages/agent-core/src/fake-provider.ts）
if (toolName === 'calculator') {
  const result = readNumberOrText(output?.result);
  return `计算结果是 ${result || rawContent}。`;
}
if (toolName === 'knowledge_search' || toolName === 'web_search') {
  const heading = toolName === 'knowledge_search' ? '已检索个人资料库。' : '已完成联网搜索。';
  const lines = listResults(output).map((result) => {
    const title = readText(result.title);
    const excerpt = readText(result.excerpt) || readText(result.snippet);
    return title ? `- ${title}：${excerpt}` : '';
  });
  return `${heading}${readText(output?.message)}\n\n${lines.filter(Boolean).join('\n')}`.trimEnd();
}
```

**"按工具定制摘要格式"是一条设计原则，不是实现细节。**回填格式属于工具契约的一部分——因为**下游看到的是这段文本，不是原始 JSON**。

## 3.7 故意失败：三种畸形输入

### 3.7.1 参数畸形

构造一个工具调用，参数是 `{"expression": 123}`（数字而不是字符串）。

会发生什么取决于你的校验在哪一层：

| 校验位置 | 结果 |
|---|---|
| 没有校验，直接 `new Parser(123)` | `expression.slice` 报类型错，**错误信息里带着内部实现细节** |
| Zod `.parse()` 在 execute 开头 | 抛出结构化的校验错误，指明字段与期望类型 |
| 只在 JSON Schema 里声明 | **什么都不会发生**——那只是给模型看的建议 |

**第三种情况是最常见的实际状态**：开发者写了 `inputSchema`，以为那就是校验。跑正常输入永远发现不了问题，因为模型在正常输入下通常会给对类型。

**所以必须构造这个负向用例**：手工喂一个类型错误的参数，断言它被拒绝。手工喂，不要指望模型会替你产出它。

### 3.7.2 不完整流

把上面 `if (!completed) throw` 这一行**注释掉**，然后构造一个"发了一半就断"的响应。

结果通常是两种：

- 半截 JSON 让 `JSON.parse` 抛错 → 这次是运气好，你看到了错误；
- 半截 JSON 恰好解析成一个合法对象（比如少了 `expression` 字段）→ 工具被调用，`inputSchema.parse` 拒绝它 → 你以为是模型的参数给错了，**而真正的原因是流被截断了**。

**第二种情况就是"错误报告指向错误的位置"。**这种错误的修复成本远高于它本身的复杂度：你会去调提示词、去调工具描述、去换模型，而真正要改的是那三行流处理代码。

### 3.7.3 未校验的标识符

给 `toolCallId` 传一个空字符串，观察会发生什么。

在一个单调用、单轮的场景里，**很可能什么都不会发生**——所有东西照常工作。这就是它危险的原因：**它的失败需要"一轮多调用"这个条件才会出现**，而大多数人的测试用例里没有这个条件。

> **核心判断 3**
>
> **静默失败比显式失败贵一个数量级。**
> 显式失败要求你在场、看日志、修代码；静默失败要求你在某一天发现一份报告的数字不对，然后回查三天的日志——而日志里可能什么都没记，因为"没有异常"。

## 3.8 行业视角：在机构里，一个工具是一次变更，不是一个提交

第 3 章讲工具契约的四个字段。加上机构这一侧之后，每个字段都多了一个读者：

| 契约字段 | 工程上给谁看 | 机构里还给谁看 |
|---|---|---|
| `name` / `description` | 模型 | **审计**：它变了要不要走变更 |
| `inputSchema` | 调用方 | **数据分级**：入参能不能带客户信息 |
| 返回结构 | 模型 | **回显约束**：哪些字段绝不能进日志与错误信息（第 0 章） |
| 禁止集 | 模型、"什么时候不该用它" | **评审重点**：禁止集比功能集更该被人看过 |

最后一行是本节最想说的：**在机构里评审一个工具，应该先看它不能做什么，再看它能做什么。** 功能集出错的后果是"做错了"；禁止集出错的后果是"越界了"——**后者的责任不在工程师身上，在批准它的人身上。**

所以：**新增一个工具要留痕**（谁提的、谁批的、什么时候生效）。这不是繁文缛节，它是**责任能被追溯的最小单位**（第 12 章）。

## 3.9 这一章在整本书里的位置

现在你有了：

- 一次请求怎么发（消息装配、系统提示、角色）
- 一次工具调用怎么被解析出来（分片聚合、完成信号、缓冲区）
- 一次执行怎么被约束（运行时长校验、路径边界、取消信号）
- 一次结果怎么回填（按工具定制的格式、调用身份对齐）

**但这一切只发生了"一次"。**

真实的科研任务不是一次交换能完成的：读完第一篇材料会发现问题定义不对，读了第二篇会发现和第一篇矛盾，某个工具会失败，需要换一个来源。

于是下一个问题自然出现了：**这个动作怎么重复、什么时候停。**

第 4 章回答它。

---

**本章小结**：一次工具交换的实质是"模型产出意图，代码执行意图"。提供方只暴露一个 `stream()`，把厂商差异翻译成四种片段；工具契约由 `name`/`description`/`inputSchema`/`execute` 四部分组成，其中声明是给模型的、校验是给自己的、两者必须都在且校验必须在执行之前；`toolCallId` 这类"对齐用的标识符"一个都不能省，因为它的失效条件是"一轮多调用"，而那个条件你的测试里通常没有。**工具的价值不在它能做什么，而在它不能做什么。**

**行动清单**

1. 给你现有的每个工具，把 `inputSchema` 的声明与运行时的校验分开写，**并手工构造一个类型错误的参数，断言它被拒绝**。
2. 找到你的流式响应处理，检查三件事：完成标记有没有检查两个来源、行缓冲有没有保留半行、UTF-8 解码有没有开流式模式。
3. 检查工具定义里的 `name` 与 `description`：`name` 是否全局唯一？`description` 是否说清了**什么时候不该用**？
4. 为每个工具写一条**负向测试**，构造一个必须被拒绝的调用。
5. 检查你的工具执行入口：`signal.aborted` 在开头查了吗？执行完之后再查一次吗？
