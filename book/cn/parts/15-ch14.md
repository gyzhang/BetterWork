# 第 14 章 Excel 分析：颗粒度错了，后面全错

**本章承诺**：读完这一章，你能把一份工作簿变成一份**可复核的数字结论**——每一个汇总数都能说清它是从哪些行、按什么口径、经哪几步算出来的。

**读完后你能回答**

- "读取成功"和"分析正确"之间隔了几道关？为什么一个查得出结果的 SQL 仍然可能是错的？
- 为什么"缺失"和"零"必须分开处理？把它们合并会造成什么后果？
- 一个指标该由谁来定义、谁来计算、谁来解释？这三件事能不能由同一个角色做？

---

先看一次失败。

一份社团的支出工作簿打开了。智能体读了它，然后报出了一个预算总额：**520.00**（单位与口径见 14.3 节）。

数字是干净的两位数小数，格式规范，还附了一段看起来很专业的说明："本期支出低于预算，执行率良好。"

**这个数是错的。**错在三处，而三处**都不在模型身上**：

| 错处 | 发生了什么 | 为什么会这样 |
|---|---|---|
| **重复口径** | 预算表里"项目 A 预算 220.00"这一行，被**按项目 A 的每一笔总账各连接了一次** | 连接的时候没有声明"这是一对多" |
| **重复主键** | 维度表里项目 A 出现了两次，连接后实际支出被放大 | 没有校验维度表主键唯一 |
| **缓存缺失** | 有一个单元格是公式，但文件里没有缓存值，读取器把它当成了空 | 解析器**不重算公式**，它只读存在的值 |

把三处叠起来：**重复口径把预算从 300.00 虚高到 520.00，重复主键又把实际支出放大，而缓存缺失那一处被读成了空、相当于压小。**放大与压小混在一起，净差额看起来还算"合理"——**这才是它最危险的地方：单看差额，你判断不出它对不对。**

> **核心判断 1**
>
> **读取工作簿只是分析的第一步，不是分析。**<br>
> 后面还有四步：确定每一行**是什么意思**（颗粒度）、确定行与行**怎么关联**（键与基数）、确定哪些计算**是被许可的**（口径）、确定结果**能和源数据对上**（对账）。<br>
> 这四步里任何一步被跳过，你得到的都不是"差一点的结果"，而是**一个看起来正常的错误结果**。

## 14.1 表格不是数值，是"带坐标的断言"

先把最基础的层次说清。在读完这本书的前十三章之后，你需要重新认识一个你以为了解的东西：单元格。

一个工作簿包含工作表；一个工作表包含由行列定位的单元格。像 `A1:G4` 这样的**区域（range）** 命名一块矩形。**单元格的外观不等于它的值**——格式可以把一个数字显示成货币或百分比，底层仍然是同一个数。而一个**公式**是一个表达式，一个**缓存结果**是某个计算应用存下来的值。

参考实现对这个边界的处理很克制。看它的 Excel 读取核心：

```ts
// 参考实现源码（BetterWork · apps/desktop/src/main/infrastructure/office-parser.ts，MIT）
const raw = cell.value;
if (raw && typeof raw === 'object' && 'formula' in raw) {
  const formula = String(raw.formula);
  const result = 'result' in raw ? raw.result : undefined;
  cells.push({
    address: cellAddress(rowNumber, columnNumber),
    formula,
    ...(result === undefined ? {} : { value: result }),
  });
  if (result === undefined) warnings.push('formula-without-cached-result');
  return;
}
cells.push({ address: cellAddress(rowNumber, columnNumber), value: raw ?? null });
```

这段代码做了三个决定，每一个都值得单独拿出来看：

| 决定 | 代码位置 | 它意味着什么 |
|---|---|---|
| **不重算公式** | 只读 `raw.result`，不调 evaluate | 解析器**不声称**自己能算这个公式。它把公式原样保留，把结果留空 |
| **缺失要留痕** | `warnings.push('formula-without-cached-result')` | 这不是"读不到就算了"，而是**主动产出一条结构化告警** |
| **位置即身份** | `address: cellAddress(rowNumber, columnNumber)` | 每个值都带着自己的源坐标，后面可以回溯到"这个数来自 M7" |

第三条是这一章后面所有能力的基础。`cellAddress` 自己也是个值得一写的函数：

```ts
// 参考实现源码（BetterWork · office-parser.ts，MIT）
const cellAddress = (row: number, column: number): string => {
  let value = column;
  let letters = '';
  while (value > 0) {
    const remainder = (value - 1) % 26;
    letters = String.fromCharCode(65 + remainder) + letters;
    value = Math.floor((value - 1) / 26);
  }
  return `${letters}${row}`;
};
```

第 27 列要写成 `AA` 而不是 `A1`。这个"看起来是常识"的换算，正是**你的数据能不能被指认**的最小实现。第 12 章那个"报告的可信度不能由报告自己证明"的道理，在这里以最朴素的形式出现：**一个数字如果没有坐标，它就无法被复核。**

还有一件容易被忽略的事：读取是**有预算的**。参考实现给每一层都设了上限——

| 限制 | 值 | 为什么要设 |
|---|---|---|
| 压缩包大小 | 50 MiB | 防止一个恶意的、声称很小但实际很大的文件 |
| 解压后总大小 | 200 MiB | **压缩炸弹**：压缩率可以是 1000:1，只看压缩包会被绕过 |
| 单页/单文本字节 | 20 MiB | 单点超限也要拦 |
| Sheet 数量 | 200 | 结构爆炸 |

> **定义框：压缩炸弹**
>
> 一个几 KB 的 zip 文件，解压后可以是几十 GB。**如果你的检查只发生在解压之后，检查本身就成了攻击目标。**所以上限必须在**解压过程中累计判定**，而不是解压完再数。参考实现正是这么写的：`expanded += ...; if (expanded > MAX_EXPANDED_BYTES) throw`。这个模式在第 11 章信任边界里出现过一次，在这里以数据入口的形式再出现一次。

## 14.2 五道关：从"读到了"到"算对了"

把这一章的机制画成一条线，它长这样：

<div align="center"><img src="images/fig-14-1-grain-pipeline.png" alt="图 14-1 从工作簿到可复核结论的五道关" width="1150"/></div>

**读图指引**：看五个阶段方框——**①②③ 检查结构与类型，④ 检查关系，只有 ⑤ 检查语义。**注意最下面那一行：前三道关失败时你会立刻知道，而第五道关的对账，是唯一一道能抓住"语法全对但结果错了"的关。

逐关说：

### 第一关：检视（inspect）

把工作簿当**结构**读，而不是当**数字**读。要拿到的是：有哪些工作表、每张表的有效区域是哪里、哪些单元格是公式、哪些公式没有缓存值、列的**类型**是什么。

这里有个反直觉的点：**"这一列是数字"本身就是一个需要验证的假设。** 一个支出列里混进一个 `#N/A`，一个金额列里有三行写着 `-`，一个日期列里有两行是文本。这些在 Excel 里看起来"就是那样"，但在聚合时会静默出错——`#N/A` 参与加法得到的是 `NaN`，而 `NaN` 通过校验、通过比较，最后显示成一个空。

### 第二关：归一化（normalize）

把源字段映射到一个**规范模式**。为什么必须做这一步？因为源数据的符号约定和字段命名**不可信**。

同一笔支出，有的系统记正数，有的记负数；有的叫 `amount`，有的叫 `金额`，有的叫 `AMT_CNY`；有的金额单位是元，有的是分。**你把这些当作"差不多"处理的那一刻，你的汇总就变成了一个混合单位的数。**

> **核心判断 2**
>
> **归一化不是把数据变整齐，是把隐含假设变成显式映射。**<br>
> "项目 A 的 2000 代表什么"——这个问题的答案必须写下来、由人确认，而不是由代码猜。<br>
> 本章最后会给出这三件事的分工：**模型可以提议映射，宿主只执行已经确认过的映射。**

### 第三关：校验（validate）

键的唯一性、期间的合法性、单位和符号的一致性、数值范围。具体到这一章的例子上：

| 校验项 | 检查什么 | 失败了怎么办 |
|---|---|---|
| 条目唯一 | `entry_id` 有没有重复 | **阻断**，不静默去重 |
| 维度唯一 | 项目表主键有没有重复 | **阻断**——这正是把 25000 放大成 45000 的那个原因 |
| 复合键 | 预算表的（期间, 项目, 指标, 币种）是否唯一 | **阻断** |
| 币种一致 | 有没有把两种币种混在一列 | **阻断**，且**禁止隐式汇率换算** |
| 符号一致 | 同一列的正负号约定是否统一 | 阻断或按已确认规则统一 |
| 数值范围 | 单个值是否在安全整数区间；**累加后**是否仍在 | 阻断，见 14.4 |

注意"阻断"这个词。校验失败的行，**不能悄悄从一份本来合理的合计里消失**。它必须作为**带原因排除**被记录下来。一份报告说"合计 25000，另外有 3 行因币种不一致被排除"，比一份"合计 25000"要诚实得多——因为后者让读者以为 25000 涵盖了一切。

### 第四关：聚合与连接（aggregate & join）

**先把总账按需要的颗粒度聚合，再与已经唯一化的维度表和预算表连接。** 顺序不能反。

这条顺序是本章最技术性的一句话，也是 14.3 节整个例子的全部内容。

### 第五关：对账（reconcile）

对账是**把结果和源数据对起来**：接受的行数、排除的行数、聚合后的合计，三者之间要有可解释的关系。

> **对账不是可选的记账，它是唯一的语义正确性检查。**

前面四关都能在"语法完全正确"的前提下通过——你写不出一个会报错的查询，但你能写一个错的查询。**只有对账能抓住它。** 因为对账用的是**独立的算术**：如果连接真的把一行变成了三行，行数会告诉你。

## 14.3 一个手算的例子：25000 是怎么变成 52000 和 45000 的

下面三张表全部是合成的。`P1` 是期间标识，不是真实的客户报告期。这个例子里 1 个货币单位等于 100 个最小单位（分）。

**总账（ledger）：一笔一行**

| entry_id | period | project_id | metric | amount_minor | currency |
|---|---|---|---|---|---|
| e1 | P1 | A | spend | 12000 | 币种甲 |
| e2 | P1 | A | spend | 8000 | 币种甲 |
| e3 | P1 | B | spend | 5000 | 币种甲 |

**项目表（projects）：一个项目一行**

| project_id | label | planned_hours | actual_hours |
|---|---|---|---|
| A | 研究 | 20 | 18 |
| B | 活动 | 10 | 12 |

**预算表（budget）：期间 / 项目 / 指标 / 币种 一行**

| period | project_id | metric | currency | budget_minor |
|---|---|---|---|---|
| P1 | A | spend | 币种甲 | 22000 |
| P1 | B | spend | 币种甲 | 8000 |

正确的做法是：**先聚合总账**，得到 A = `20000`、B = `5000`、合计 `25000`；**再把这两行**连接到唯一的项目行与预算行。结果是：

| 指标 | A | B | 合计 |
|---|---:|---:|---:|
| 实际支出 | 20000 | 5000 | 25000 |
| 预算 | 22000 | 8000 | 30000 |
| 实际减预算 | -2000 | -3000 | -5000 |
| 预算执行率 | -1/11 | -0.375 | **-1/6** |

现在看两个错误版本，**两个都能无语法错误地执行完**：

**错误一：先连接预算，再求和。** 把 A 的预算 22000 按 A 的**两笔总账**各连接一次：

```
22000（跟随 e1）+ 22000（跟随 e2）+ 8000（跟随 e3）= 52000
```

预算从 30000 变成 52000。**"预算超了"变成"预算还富余很多"**——方向完全反了。

**错误二：维度表里项目 A 重复了一行。** 连接时 A 的每一笔总账都匹配到两条 A 行：

```
A 的实际支出 20000 × 2 = 40000，加上 B 的 5000 → 45000
```

实际支出从 25000 变成 45000。

**这两个错误的共同特征是：它们的算术都对，语法都对，类型都对。** 错的是**关系**——是一个一对多连接被当成了一对一。

> **核心判断 3**
>
> **颗粒度（grain）不是数据自带的属性，是你必须声明并验证的假设。**<br>
> "总账一笔一行"、"项目一个项目一行"、"预算一个期间×项目×指标×币种一行"——这三句话不是观察，是**声明**。声明之后你才能验证：如果实际数据违反了这个声明（出现了重复主键），它就是错的，而不是"数据就是这样"。<br>
> 检验颗粒度最实用的方法：**问你的连接会不会放大行数。** 会放大，就说明你还没做完聚合。

还有一个细节值得单挑出来：**合计数为 `-5000 / 30000`，不是各项目比例的算术平均。**

```
各项目比例：-1/11 ≈ -9.09%，-0.375 = -37.5% → 平均 ≈ -23.3%
正确合计：  -5000 / 30000 = -1/6 ≈ -16.67%
```

**加权平均不等于平均**。一个占总预算 73% 的项目和一个占 27% 的项目，它们的比例怎么能等权相加？这个错误在任何汇总报告里都极其常见，而它同样**不会报任何错**。

## 14.4 缺失不是零，单位不是标签

### 14.4.1 四种伪装成"正常"的缺失

这一章开始时那个"预算虚高"的例子里，有一个公式单元格没有缓存值。它被读成了空。**空在后续计算里通常会被当成 0。** 这就是第一个致命的等价替换。

| 缺失的表现 | 实际发生了什么 | 后果 |
|---|---|---|
| 填成零 | 缺的数据被当成 0 参与计算 | 合计偏小，且**看不出来** |
| 静默跳过 | 缺的行被丢弃 | 合计的**分母**变了，比例失真 |
| 取默认值 | 用上期或同类值补上 | **造出一条源数据里不存在的"事实"** |
| 用近似值代替 | 用公式算出个接近的数 | 看起来精确，实际是估算 |

**它们的共同效果是：报告看起来更完整，而错误已经完成。**

正确做法只有一条，而且很简单：**缺失就是缺失，它必须随着结果一起被报告出来。**

上一章（第 13 章）立过一条规则："没有测量的改动，不是改进了，是换了一种做法。"这里有个完全同构的规则：**没有数据的地方，不能给出结论。**

一份这样的报告是合格的：

> 实际支出为 25000 最小单位。**完整的预算对比暂不可用**，因为项目 B 的本期预算缺失。在预算覆盖范围明确之前，不给出整体的预算执行结论。

一份这样的报告是**不合格**的——即使它字句通顺：

> 实际支出为 25000 最小单位，低于预算，执行情况良好。

### 14.4.2 整数最小单位与"安全整数"

这个例子里金额用**整数最小单位**（分），而不是浮点。原因很实在：`0.1 + 0.2` 在浮点里不等于 `0.3`。金额用浮点，误差会随行数累积。

但用整数也有它自己的边界，而这个边界很容易被忽略：

> **JavaScript 的安全整数范围是 `Number.MAX_SAFE_INTEGER = 9007199254740991`（约 9×10¹⁵）。**<br>
> 单个值在这个范围内，**不代表它们的和也在**。两个 9×10¹⁵ 相加就溢出了。

所以校验要检查两次：**输入值**和**累加后的总和**。参考实现里的比较工具用 `z.number().finite()` 做输入校验——这只保证"有限"，不保证"安全"。**这是教学实现需要自行补上的一层**，本书把它明确列在附录 B 的缺口清单里。

### 14.4.3 不要把币种和单位当标签

那条"禁止隐式汇率换算"的规则，值得单独说一次。两个币种的金额**不能相加**，这一点没有争议。有争议的是那些"看起来只差一点"的情况：

| 情况 | 能不能直接算 | 为什么 |
|---|---|---|
| 币种甲 + 币种乙 | **不能** | 需要汇率，而汇率是**带时点的外部事实** |
| 小时 + 分钟 | **不能** | 单位不同，先统一到同一单位 |
| 计划工时 + 实际工时 | **特别不能** | 这两个**量纲相同但含义不同**，加起来的数没有意义 |
| 百分比 + 百分比 | 看分母 | 分母不同则不能加权 |

最后一行是这一章那个 `-16.67%` 的教训在单位层面的再现：**一样的东西才能加，而"看起来一样"是一个需要验证的判断。**

## 14.5 三个角色：谁定义、谁计算、谁解释

<div align="center"><img src="images/fig-14-2-three-roles.png" alt="图 14-2 指标的三权分立：定义、计算、解释" width="1150"/></div>

**读图指引**：看每张卡片标题的后半句"由谁拥有"，再往下看那三行"强项 / 弱项 / **不能**"。**三条"不能"合起来才是这个分工的全部意义**——它们正好把三种失败模式分别关了起来。

| 角色 | 拥有什么 | 由谁承担 | 不能做什么 |
|---|---|---|---|
| **定义** | 口径：指标怎么算、分母是什么、缺失怎么处理、排除规则 | **人（复核者）** | 不能由模型自己决定口径 |
| **计算** | 算术：按已确认的口径执行确定性运算 | **代码（工具）** | 不能猜缺失值，不能自己编公式 |
| **解释** | 陈述：把算出来的数讲成一句人话 | **模型** | 不能把假设说成结论，不能改数字 |

为什么这个分工是硬的？因为**三者的失败模式正好互补**：

- **模型** 的强项是理解语义、提出映射、写出可读的解释；弱项是算术和确定性。第 2 章已经说过：**它只会产生猜测。**
- **代码** 的强项是确定性、可重复、可测试；弱项是"这个口径对不对"——**代码不知道业务含义。**
- **人** 的强项是判断口径、承担签字责任；弱项是慢、贵、不能对每笔交易都亲自看。

所以"模型提出映射，人确认映射，代码执行映射"不是流程繁琐，**它是把三种不同的失败模式分别关进了各自的笼子。**

参考实现里的比较工具正是"计算"这一角色的样子：

```ts
// 参考实现源码（BetterWork · packages/tool-runtime/src/business-metrics.ts，MIT）
if (previous !== undefined) {
  result.previous = previous;
  result.change = current - previous;
  if (previous === 0) warnings.push('comparison-zero-baseline');
  else result.changeRate = (current - previous) / Math.abs(previous);
}
```

三个值得注意的点：

1. **`if (previous === 0) warnings.push(...)`**——零基数时**不算比例**，而是产出一条告警。这正是 14.4.1 那条规则的实现：**说不清的地方，不给结论，给告警。**
2. **`if (current === undefined) throw new Error(...)`**——当前期缺指标直接抛错。**不补、不猜、不跳。**
3. **`Math.abs(previous)`**——这里有一个必须说清的口径差。参考实现用**绝对值**作分母；本章的手算例子用的是**带符号分母**。对正基数两者一致；对负基数两者会给出不同的比例。

第 3 点不是缺陷，是一个**真实的口径选择**，而且它恰好演示了本节的主张：**代码不知道哪个口径对。** 你必须在定义阶段做出选择、写下来，并知道你的工具用的是哪一种。

> **一处必须如实说明的边界**
>
> `analyzeBusinessMetrics` 是一个**比较辅助工具**，不是这一章的完整分析管线。它接受"已经算好的数字"，输出确定性比较；而**模式映射、连接校验、对账、独立核验**这四件事它都不做。<br>
> 本书不把它当作完整的分析实现。第 14.2 节的五道关里，它只覆盖第四关末尾和第五关的一小部分。

## 14.6 行业视角：为什么银行的口径问题更尖锐

这一章的内容对任何行业都成立，但在**银行业**它有一个额外的维度。

在本章的例子里，`spend` 这个指标的定义、科目到指标的映射、成本归集的口径，都是**可以由一个部门自己定**的。而在银行，这三件事**外部给定**：

| 项 | 通用场景 | 银行业场景 |
|---|---|---|
| 指标口径 | 部门内部约定 | 受**监管报送口径**约束，口径变更需留痕并同步 |
| 数据来源 | 单一内部系统 | 总账系统、管会系统、其他系统，**同一指标在不同系统里口径可能不同** |
| "排除一行" | 记录原因即可 | 排除可能构成**数据质量事件**，需要登记与说明 |
| 交付物用途 | 内部参考 | 可能进入**报送、审计或对外披露**链条 |

带来两个直接的工程后果：

**第一，机构类型不能混用。** 国有大行、城商行、农商行在总账结构、科目体系、监管约束和内部审批链上**真实存在差异**。同一份分析模板跨类型套用时，会造出一条**源材料里根本不存在的"合格线"**。这是本书在案例中一直用机构类型代称、并且不把不同类型混写的原因——**脱敏脱的是主体，不是证据。**

**第二，"可复核"在银行业的最小定义更高。** 通用场景下，"每个数字能回溯到单元格坐标"就够了。在银行业场景下，最低要求通常还要加上：**口径来源、数据快照时点、计算过程版本、复核人**。

这四项其实不复杂，它们就是这一章五道关在受监管场景下的显式化。**你现在搭的这套流程不做改造就能承载它们，前提是第一步就别跳过。**

---

**本章小结**<br>
可信的分析同时保住五样东西：**颗粒度、键、单位、缺失性、来源**。工具负责计算；人负责确认定义；模型负责解释**已有支撑的结果**，并把假设明确标成假设。

对账是正确性检查，不是可选的记账。一个能执行完的查询和一个正确的查询，中间隔着的正是这一章的五道关。

**六道自检题**（答案在正文里，遮住上一节再答一遍）：

1. 为什么整体预算偏差不是各项目比例的算术平均？
2. `52000` 这个数算术上完全正确，为什么它是错的？
3. 公式的缓存值可能是**过时**的吗？解析器为什么选择不重算它？
4. 为什么"解压后的总大小上限"必须累计判定，而不能解压完再数？
5. 一个连接看起来正常，但把 25000 变成了 45000。最可能漏掉了哪一步校验？
6. 一个指标谁来定义、谁来计算、谁来解释？把三者合并到一个人身上，最先出问题的会是什么？

**想得更远一点**：把本章的 25000 换成一份两期对比报告——第 18 章会让 `e3` 这一笔发生变化，届时请你回头找出**所有受影响的报告字段与幻灯片字段**。你会发现受影响的地方比你第一眼想到的多。

**行动清单**

1. 打开你手上任意一份工作簿，**用一句话写出每张表的颗粒度声明**（"这张表一个 X 一行"）。写不出来的表，就是还没搞清的表。
2. 对每一个将要使用的连接，**问一次"会不会放大行数"**。会放大，就先聚合再连接。
3. 列一份**阻断清单**与**告警清单**：哪些问题必须停止流程，哪些只需记录。这个划分要和人确认。
4. 在你的结果结构里，为**每一个数字**附上：分母、单位、期间、源坐标。
5. 写一个**独立的核验**：用另一种方式（手算、另一条查询、另一个工具）算出至少一个汇总数，和主流程对比。
6. 检查你的代码里有没有 `|| 0`、`?? 0`、`Number(x) || 0` 这类写法出现在**数据字段**上。有，就说明你正在把缺失静默地变成零。
