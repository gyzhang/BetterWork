# 第 20 章 独立交付、评估与复述

**本章承诺**：读完这一章，你能判断"这个系统是真的被人接手了，还是只被人复现了一次"——并且你能给出一个**不依赖身份、不依赖印象**的判断方法。

**读完后你能回答**

- "能复现一个打磨好的例子"和"能独立工程"之间，差的是什么？
- 为什么"把例子跑通"这件事，连一半都证明不了？
- 一个漂亮但有关键缺陷的交付，能不能通过？
- 系统交付之后，哪些东西必须被指派责任人？

---

先看一次失败。这一次失败的人不是初学者。

一个学习者能**完整复现**一个打磨好的例子。步骤记得很熟，输入输出都对得上。

**但问他三个问题，他就卡住了**：

| 问题 | 他答不上来的原因 |
|---|---|
| 为什么那次工具调用被允许？ | 他知道**它被调用了**，不知道**是哪一条规则放行的** |
| 把输入模式改一下会怎样？ | 他改不了，因为他不清楚哪些字段是必需的、哪些是装饰 |
| 这个合计为什么是重复的？ | 他能看到合计**不对**，但不知道**从哪一层开始错的** |

**这个例子证明了一份产物存在。它还没有证明独立工程能力。**

> **核心判断 1**
>
> **独立能力的判据是四个动词：能解释、能改、能评估、能迁移。**
> "能复现"不在这四个里面。它是**入门门槛**，不是能力。
> 原因很实际：**复现走的是别人已经为你排除了错误的那条路。** 那条路上没有你要做的判断。

## 20.1 三角验证：为什么要用多种观察

单一的观察方式都有它测不到的东西：

| 观察方式 | 它能测 | 它测不到 |
|---|---|---|
| **笔试 / 问答** | 词汇与概念 | **能不能实现** |
| **单一综合案例** | 深度 | 另一条必须掌握的路径 |
| **只有口头答辩** | 表达能力 | **有没有可操作的证据** |
| **只看代码** | 实现细节 | **能不能解释为什么这样做** |

所以要用**多种观察互相补位**：

<div align="center"><img src="images/fig-20-1-triangulate.png" alt="图 20-1 三角验证：六种观察各自测什么" width="1150"/></div>

**读图指引**：看每张卡片第二行的"建立："——六项各自建立什么，**不能互相替代**。注意第三项和第四项：它们分别测"概念所有权"和"迁移"。

```
作品集复核 → 受让人复跑 → 学习者解释
  → 未见过的输入 / 需求 → 受控缺陷
  → 有依据的修正与回归检查 → 迁移讨论
```

| 环节 | 它建立什么 | 为什么不能用别的代替 |
|---|---|---|
| **作品集** | 广度 | 只看一个案例测不出覆盖 |
| **受让人复跑** | 交付 | 你自己复跑成功**不代表别人能** |
| **学习者解释** | 概念所有权 | 讲解能背，**但变更行为不能靠背** |
| **未见输入** | 迁移 | 见过的输入测的是记忆 |
| **受控缺陷** | 从证据推理的能力 | 测的是**诊断**，不是**修复已知步骤** |
| **迁移讨论** | 边界判断 | 测的是他知道什么变、什么不变 |

### 20.1.1 关于使用编码助手

这一节在 2026 年必须写清楚，而且要写得诚实。

| 场景 | 规定 |
|---|---|
| 日常练习 | **允许**，但**必须如实说明** |
| 最终评估 | 按声明好的规定执行，**并且仍然必须建立学习者本人的理解** |

**关键的一句**：

> **一份背下来的解法说明，如果学习者无法改变它的行为，就是不够的。**

这句话很重要，因为它排除了一种看起来"理解了"的状态：**能流利地复述架构图，但改一个字段就不知道怎么动。**

判断标准很实用：**不看他说了什么，看他改了什么、以及改完之后知不知道为什么。**

## 20.2 一次复核：从作品集里发现问题

看一个具体的复盘，它演示了"有针对性的补救"是什么样子。

一个学习者提交了：Markdown 与 DOCX 两份有支撑的研究方案、一份可编辑的研究演示、两份分期运营演示、数值与检索测试、一份脱敏追踪、一份交接指南。

**复核者发现了一处具体缺口**：第二期的演示数据用对了，但"取消"这件事**只有一张截图**，没有任何持久状态证据。

注意复核者的处理方式：

| 做 | 不做 |
|---|---|
| 精确指出缺的是什么 | 不重问所有章节 |
| 要求演示"在受控点取消、检查终态、证明没有不完整产出被提升" | 不要求重做整份作品集 |
| 只对缺口做补救 | 不降低标准 |

> **针对性的补救既保住了标准，又避免了无关的工作。**

这句话看着简单，做起来需要判断力：**你要能分清"这个人的理解不够"和"这个人少采集了一项证据"。** 前者需要重学，后者只需要补一次。**把后者当成前者，是评估里最常见的不公平。**

### 20.2.1 评分维度

一份可共用的评分表：

| 维度 | 分值 |
|---|---:|
| 场景设计与任务边界 | 15 |
| 智能体机制与工具集成 | 20 |
| 数据 / 证据正确性 | 20 |
| Harness 可靠性与控制 | 20 |
| 可用交付物 | 15 |
| 可复现性与复述 | 10 |
| **合计** | **100** |

**把这六个维度的分值加一遍，看权重压在哪。** 数据正确性 20 分、Harness 可靠性 20 分——**这两项合起来 40 分**；而"智能体机制与工具集成"只占 20 分。也就是说：**权重最高的两项，一项都不考"会不会用工具"，只考"会不会出错"。**

### 20.2.2 及格线之上仍然可以不及格

这一节是整张评分表的关键。

> **高于 80 分，不能补偿以下任何一项：**
> - 未授权的执行
> - **编造的支撑**
> - 覆盖了输入
> - **虚假的完成**
> - 缺少必需格式
> - 缺少独立能力

**为什么要有这一条？** 因为如果只有总分，就会出现"用 95 分的技术水平掩盖一次编造引用"这种情况。而编造引用的性质**不是扣分问题**，它是**整个交付可信度归零**。

**"分数是证据判断，不是提交文件数量的加总。"** 提交了十个文件而每个都不能被复核，不如提交三个都能被复核的。

### 20.2.3 两个看起来很好但必须失败的提交

**第一个**：幻灯片很漂亮，但有一个重复连接把实际支出放大了。

**它不能通过。**

> **已验证的数值正确性是一项关键义务。**
> 正确的修法是**修颗粒度与连接基数，并重新生成受影响的产出**——**不是把幻灯片上的措辞放软。**

这句话值得反复看。"把措辞放软"是一个极其自然的反应：既然数字有问题，那我把它说得含糊一点行不行？

**不行。** 因为含糊的措辞**不会让错误的数字消失**，它只是让错误更难被发现。第 14 章那句"报告看起来更完整，而错误已经完成"，在这里的形态是"**措辞看起来更谨慎，而数字还是错的**"。

**第二个**：把一次**被取消**的运行报告成**已完成**。

同样不能通过。**视觉质量不能补偿。**

修法也一样具体：**演示真实的终态，并在重新评估前修好报告与发布的逻辑。**

### 20.2.4 一句话要说清"课程资产坏了"和"学习者没学会"

这是一个很实际的判断：

> **不要因为作者提供的教学材料坏了而惩罚学习者。**
> 应该把受影响的交付或评估标为**未完成**，修好课程材料，并提供一次重试。

这条规则的技术意义在于：**它区分了两类失败。** 一类是"你的系统在某个层出问题"（要修），另一类是"你基于的材料本身是错的"（要改材料）。**把后者归给前者，会得到一个永远修不好的循环。**

还有一条具体的例子：**缺少 Word 支持，不是把必需的 DOCX 产出换成 PDF 或截图的理由。** 材料坏了就修材料，**标准不因材料坏了而降低。**

## 20.3 一次简短的复述

这一节给一个可用的复述练习。**用你自己的话，说清这三个概念各自的边界**（尤其是每张表最右一列那条）：

| 概念 | 通俗解释 | **本书要求你注意的边界** |
|---|---|---|
| **ReAct** | 推理 / 行动 / 观测的交替模式 | **本书检查的是可观察的决定、调用与观测结果，不是模型私有的推理过程** |
| **Agent Loop** | 有界的执行循环：请求模型决策、执行被允许的工具、返回观测结果、停止 | **"有界"和"能停止"是它的定义的一部分**，不是附加条件 |
| **Harness** | 围绕循环的运行时控制：上下文、访问、生命周期、持久化、可观测、评估 | **框架可以提供机制，策略仍归宿主** |

第二行和第三行里加粗的部分，是整个复述的重点。

**ReAct 那一行**排除了一个看起来很有价值的检验方式："看看模型的推理过程对不对。"第 5 章已经说过：**可以展示推理，不能把推理当判断依据。** 原因是**你看不到它私有的推理**——你看到的是一段被生成的文本，它可能准确描述了决策依据，也可能是一段事后编好的解释。**能检验的只有决策、调用和观测结果。**

**Harness 那一行**排除了一个很贵的误解："我用了某个框架，所以我的 Harness 有了。"框架给的是机制（图、检查点、流式、中断恢复），**职责归属不变**——权限、范围、生命周期、数字正确性仍然归你。

### 20.3.1 追踪一个真实案例

然后做这件事：**追踪一次真实运行**，回答六个问题。

| 问题 | 你要指出的证据 |
|---|---|
| 选定了哪个输入？ | 输入清单与快照 / 版本身份 |
| 请求了哪次调用？ | 运行时事件里的调用记录 |
| **在哪里被校验的？** | **校验发生的位置——不是"模型说它会检查"** |
| 返回了什么观测结果？ | 工具返回的结构化结果 |
| **为什么停下来了？** | 终态：完成 / 取消 / 失败 / 达到上限 |
| 产出了哪个输出版本？ | 产物版本标识 + 文件哈希 |

**第三行和第五行是能否过关的分界线。**

第三行：如果被问"在哪里校验的"，回答是"提示词里写了要校验" ——**这不成立**。第 11 章已经确立：**提示注入只能被边界解决**；同理，**校验只能由代码执行**。提示词负责"想对"，代码负责"错不了"（第 2 章）。

第五行：如果被问"为什么停下来了"，回答是"结果看着差不多了" ——**这也不成立**。终态必须是一个**被显式判定并记录的值**。第 4 章立过规则：**到达上限必须是失败。** 这里要求的是它的对偶：**每一个终态都必须能被指出。**

> **没有这次追踪，词汇只能得到部分的证据。**

## 20.4 交付之后：责任必须被指派

系统交付了，这**不是**终点。有一件事必须在这一刻做完：**把维护责任指派出去。**

| 需要责任人的事项 | 如果没人管会怎样 |
|---|---|
| 依赖更新 | 某个依赖出现安全问题或破坏性变更，系统静默失效 |
| 模型 / 配置变更 | 提供方换了模型快照，行为漂移，无人知晓 |
| 固定输入（fixture）刷新 | 输入过期，测试失去意义 |
| **指标定义** | 口径被悄悄改动，历史数据不可比 |
| 模板变更 | 版式漂移，产出不合规范 |
| **保留策略** | 该留的删了，或者该删的越积越多 |
| 事件处理 | 出问题没有人负责响应 |

**最后一条纪律**：

> **当以上任何一项变更可能影响行为时，重跑相关的评估。**
> **一份曾经通过的报告，不能为一个持续变化的系统作永久担保。**

这句话是第 13 章"没有测量就不是改进"的最终形态。它的反面是一种很常见的状态：**半年前做过一次评估，一直引用那次结果。** 半年里模型换过、依赖更新过、数据口径调过——**而"通过"这两个字还挂在墙上。**

## 20.5 行业视角：接手的人不止工程师

第 20 章给的是一套"不依赖身份、不依赖印象"的判断方法。机构场景把这个方法的读者扩大了：**接手的不只是下一个工程师。**

| 验证项 | 机构里的接手方 | 他们会问的问题 |
|---|---|---|
| 概念所有权 | 内审 | 这条规则谁定的、依据是什么 |
| 迁移 | 运维 | 换台机器要带什么、缺什么会失败 |
| 已知限制 | 合规 | 哪些数据不能进、哪些场景不能用 |
| 现场复述 | 业务 | 它出的数，我能不能拿去用 |

四行的共同点：**它们都不是技术问题，但它们都只能靠技术产物来回答。** 一份只有架构图的交接，会让这四类人各自去猜一次——**而猜错的成本由你承担。**

机构里还要多问一句：**这套东西停下来的时候，谁负责说停？** 这正是第 19 章那七项维护责任人里最容易空着的一项。**而它空着的后果，是没人敢停。**

## 20.6 全书收束：四个问题

现在回到第 0 章。

第 0 章说，能写程序的人离"能建系统"差的是**把隐含假设变成显式契约**的习惯。全书给了这个习惯的具体形态——**它在四个问题上**：

<div align="center"><img src="images/fig-20-2-four-questions.png" alt="图 20-2 全书的四个问题与它们在各章的落点" width="1150"/></div>

**读图指引**：看每个问题下面列出的章节编号。**注意四个问题各自反复出现在多个篇章里**——这正是这本书的组织逻辑：不是"一章讲一件事"，而是**四个问题被反复追问、逐层加深**。

| 问题 | 落点 |
|---|---|
| **什么被允许？** | 第 5 章（自由度与阶段）、第 10 章（能力范围 = 声明 ∩ 允许 ∩ 可用）、第 11 章（信任边界）、第 19 章（部署义务） |
| **什么支撑这个结果？** | 第 8 章（检索到的 ≠ 为真）、第 14 章（颗粒度与对账）、第 15 章（来源与版本）、第 17 章（主张—证据登记） |
| **失败时会发生什么？** | 第 4 章（到达上限必须是失败）、第 12 章（进程会死且不会善后）、第 18 章（取消与重启的终态）、第 19 章（缺配置不许编） |
| **别人能复现并修改吗？** | 第 15–16 章（可编辑与血缘）、第 17–18 章（可复核的方案与期报）、第 19–20 章（打包、交接、复述） |

**一个完成的智能体应用，对这四个问题都有具体的答案——而且有证据说明这些答案在变化之下仍然成立。**

### 20.5.1 关于数字时效的一点说明

这本书里有一批数字会过期：协议版本、基准分数、漏洞统计、政策文件编号、框架特性。

**它们全部有明确的快照时点（2026 年 9 月 18 日），全部在附录 C 里逐条标注了口径、时点与局限。**

**而这本书主张的主要价值不在那些数字上。** 在四个问题、在数据纪律、在边界设计、在交付标准——**这些不随版本失效。**

半年后你回头看附录 C，会发现其中几行已经过时了。**那是正常的，而且是有意如此设计的**：一本声称"引用必须可核查"的书，必须让自己的引用**可以被一眼看出是哪天的事实**。

**本章小结**
独立能力意味着：**你能解释系统为什么这样工作、能认出它在哪里会失败、能做一次有界的改动、并验证改动后的结果。**

最终的交付物必须包含**两条生产线和全部必需格式**，而不是最上镜的那一个例子。

**六道自检题**：

1. 哪一个关键义务可以否掉一个 95 分？
2. 受让人复跑能揭示什么，是你自己的复跑**一定**看不到的？
3. 你怎么区分"教学材料本身出了问题"和"学习者理解错了"？
4. 为什么"我看过模型的推理过程，它是对的"不是一个有效的检验？
5. 一个被取消的运行被报告成"完成"，正确的修法是改报告措辞还是改逻辑？
6. 为什么"一份通过的报告"不能长期为系统担保？

**最后一问**（也是全书的问题）：**你的系统，现在对那四个问题都有答案了吗？**

**行动清单**

1. 建一份**按成果索引的作品集**：每一项能力指向确切的运行记录、文件与测试。
2. 找一个**没参与过的人**，只给交接指南，让他在没有额外帮助的情况下走一遍完整流程。**记录每一次你忍不住要开口帮忙的地方。**
3. 演示三件事：**一次正常运行**、**一次受控失败**、**一次被复核的修订**。
4. 拿一个**你没见过的输入**，在动手之前先说明需要改什么。
5. 用一个**你自己没写过的缺陷**做一次诊断：从"期望行为 vs 实际行为"出发，定位**最早被违反的那个契约**，然后为修正加一条回归检查。
6. 写下**七项维护责任人**：依赖、模型配置、固定输入、指标定义、模板、保留策略、事件处理——比第 19 章那"四类产出责任人"更细一层。
