# 前言与全书地图

## 1. 一段看起来完全正确的回答

先看一个场景。

某学生社团的财务负责人拿到三张表：一张是总账导出，一张是项目费用明细，一张是上半年的预算表。他想知道一件事——**为什么 6 月的支出比 5 月高了那么多**。

他把三张表丢给一个助手，助手很快回了一段话：

> 6 月支出较 5 月增长约 23%，主要由市场活动费用上升所致。增长与社团成员规模的扩大基本一致，属于良性增长。

这段话读起来很顺，甚至很有条理。但它有四件事是错的或者无法成立的：

1. **三张表里没有任何成员规模数据。**"成员规模扩大"这个原因，是模型自己补上去的。
2. **有一个项目被重复统计了。**两处口径重叠，23% 这个数字根本不是真实增幅。
3. **预算表是上半年的累计数，不是 6 月单月数。**拿累计比单月，算出来的偏差没有意义。
4. **这份回答是纯文本，不能改。**财务负责人想调一下口径重算，只能从头再来一遍。

现在问一个问题：**这个助手完成任务了吗？**

大多数人的第一反应是"没完成，因为它算错了"。但更值得注意的不是"算错了"，而是**它错在了哪些地方，以及这些错误为什么不归模型管**。

第 1 条错在"输入里没有这个事实"，这是**信息边界**问题。<br>
第 2、3 条错在"口径没定义清楚"，这是**计算边界**问题。<br>
第 4 条错在"产出不能被继续使用"，这是**交付边界**问题。

三条全都不在模型的推理能力范围内。一个更聪明的模型不会自动解决它们——它只会把那段话说得更流畅。

再看第二个场景。

某研究小组要让助手帮忙整理参考文献。助手检索到一篇相关页面，读了它，然后**照着页面里的一行字，去读了一个小组从未选定的文件**。它最后的建议可能是对的。但系统已经越过了自己的权限边界。

这个失败无法靠"把提示词写得更明确"来修复。因为问题不在提示词，而在**谁有权决定可以读哪些文件**。

> **核心判断 1**
>
> 智能体的可靠性，主要不取决于模型有多聪明，而取决于模型之外那层系统设计得有多严密。<br>
> 这句话有个代价：它意味着换一个更强的模型，通常不会让你的系统变可靠；你得改系统。

上面两个场景，一个是**结果错了，却找不到该负责的环节**；一个是**过程越界了，却没有东西拦得住**。它们共同定义了这本书要解决的问题。

## 2. 这本书要教的，是一件完整的事

市面上讲智能体的材料，大多只讲一件事：**模型怎么调用工具**。给你一个循环、几个函数、一段示例代码，跑通了就结束了。

但那不是"交付"。真正的交付链条要长得多，而且每一环都有它自己的失败方式：

| 环节 | 会出的问题 | 责任落在哪一层 |
|---|---|---|
| 决定要不要做 | 把简单的事做复杂，把该写脚本的事做成智能体 | 需求判断 |
| 想清楚做什么 | 目标不可度量，做完无法判断成功 | 任务定义 |
| 与模型打交道 | 看起来对但没根据的回答 | 提示与结构约束 |
| 让模型动手 | 工具参数畸形、调用不存在的工具、循环停不下来 | 运行时 |
| 给模型能力 | 检索到无关材料、算术算错、上下文被撑爆 | 能力层设计 |
| 限制模型 | 读了不该读的文件、执行了不该执行的动作 | Harness |
| 管住整个过程 | 进程重启后状态全丢、重试导致重复扣款 | 生命周期设计 |
| 出结果 | 数字对不上、文档改不了、图和文互相矛盾 | 交付工程 |
| 交出去 | 换个人跑不起来，没人能解释为什么这么写 | 打包与文档 |

**这本书从头到尾讲这条链，而不是讲其中的某一环。**

> **核心判断 2**
>
> 智能体工程的产出单位不是"一段能跑的代码"，而是"一份别人能复核、能修改、能接着用的交付物"。<br>
> 判断一段智能体代码值不值得留下的唯一标准，是它交到另一个人手里之后还能不能用。

## 3. 起点：你能写一个函数、一个循环、一个条件

这本书的起点设得很低，但设得很明确。

**最低要求**：你能写并解释一个小程序，里面有一个函数、一个循环、一个条件判断。

如果你能做到，你就够了。你不需要事先知道：智能体、机器学习、TypeScript、React、Electron、数据库、线性代数、模型训练、会计、客户交付。

如果这条线你都还够不着——比如你不能解释自己写的循环为什么会停在某个位置——那么请先完成一门编程入门课再回来。**"有编程经验"和"会建软件系统"是两件不同的事**，中间的那段路本书第 0 章会补，但它补不了"完全没写过程序"。

第 0 章覆盖四件事：程序与工程基础、数据与接口、异步与错误、测试与数据素养。如果你已经有实际工程经验，请直接跳过去做它的四道出口题——**做得出就不用读**。

## 4. 两个贯穿全书的案例

书里的例子不是零散的代码片段，而是两个从头走到尾的完整任务。

### 案例 A：从问题到一份可辩护的方案

```
问题与选定材料 → 研究计划 → 本地与外部证据 → 对比与综合
  → 经审核的方案 → Markdown / Word / PPT → 按反馈修订
```

它关心的是：研究范围划没划清、证据质量够不够、材料互相矛盾时怎么办、不确定性怎么表达、人在哪一步必须介入、产出能不能被下一轮复用。

### 案例 B：从运营数据到一份可复用的期报

```
总账与项目系统的导出 → 模式与质量检查 → 商定的指标定义
  → 确定性计算 → 解读 → 演示 → 下一期用新数据重跑
```

它关心的是：期间与单位一致不一致、关联做对了没有、缺失值和零是不是被混为一谈、数字能不能被独立复核、事实与因果假设有没有分开。

**两个案例都包含一个"低领域入口"和一个"行业变体"。**低领域入口是校园场景（研究提案、社团预算），它不要求你懂任何行业；行业变体换成机构场景（业务方案、部门经营分析），用的是同一套技术标准。

> **这里有一条纪律，全书都遵守**：行业熟悉度不影响技术通过标准。你在银行干过十年，不会让你的代码自动变得更对；你没进过银行，也不该因此被降低要求。案例中的机构一律以**机构类型**指代，而且**类型不可混淆**——大型国有银行、城商行、农商行在数据口径、监管约束、交付流程上的差异是真实存在的，混着写会造出一条源材料里根本不存在的"合格线"。

> **代称约定（配合上面那条纪律）**：为了让读者能跨章对照，**主线机构固定为「某城商行」**——凡需要落到"某一家机构的具体数据、具体约束"的地方，都用它，**跨章沿用同一代称**。其他行业只作**对照**，用行业名代称（如"某制造企业""某券商"），**不与主线机构混写**。泛称"机构""受监管场景"的地方不受此限。
>
> **为什么必须固定成一个**：不固定，同一批数字在不同章就会落到规模不同的机构上，读者无法横向对照；而且这本身就是本书反复强调的那类错误——**在数据层面偷偷加了一个源材料里没有的判断**（第 14 章）。

## 5. 这本书不承诺什么

写技术书最容易犯的错，是把"我读过"说成"我验证过"，把"设计上应该"说成"实际能跑"。这里把边界先说清楚：

| 书里出现的代码 | 它到底是什么 |
|---|---|
| 标注为**参考实现源码**的片段 | 来自公开的 BetterWork 仓库（MIT 许可），锚定到具体提交号。片段所在的完整文件还包含导入、周边校验与集成细节，**片段本身不是一个能单独跑起来的应用** |
| 标注为**工作示例**的片段 | 合成输入 + 手工推导的预期结果。**不是**某次真实模型运行或客户部署的观测记录 |
| 标注为**教学设计 / 伪代码**的片段 | 一个要在隔离实验里自己实现并测试的机制，**不是**现成的 API |

另外三件事必须说在前面：

1. **不写市占率、排名、增长率这类"合理推测"出来的数字。**源材料里没有的，一律留空或删掉。删掉一个说不清的数字，比留下一个说不清的数字更专业。
2. **时效敏感的数字都带时点。**这本书的事实快照是 **2026 年 9 月 18 日**。智能体领域半年就能换一代，附录 C 会逐条记下每个数字的口径与访问日期。**方法不会过期，数字会。**
3. **不声称教学资产已全部可运行。**参考实现里有测试的部分，附录 B 会告诉你测试在哪个文件；需要另行准备教学实现的部分，书里会明确标注，而不是悄悄把它降级成"可选"。

## 6. 怎么读这本书

### 6.1 七篇的问题链

书的每一篇都在回答上一篇留下的那个问题。这不是装饰性的分类，是**读完一篇你才会真的想知道下一篇在问什么**。

| 篇 | 回答的问题 | 读完的标志 |
|---|---|---|
| 第 0 篇 起步 | 我手上的编程能力，离"能建一个系统"还差哪几步？ | 能跑通四道出口题 |
| 第一篇 认知 | 在动手之前，怎么判断一件事该不该做成智能体？ | 能为一个模糊需求写出一页可判断的场景说明书 |
| 第二篇 技艺 | 既然决定要做，那"一次完整的决策"长什么样？ | 能独立实现一个有终止条件的循环，并说清它为什么一定会停 |
| 第三篇 能力 | 这个循环要真正干活，需要能做什么、能看什么、能记住什么？ | 能设计一个确定性工具、接一个 MCP 工具、评估一次检索 |
| 第四篇 系统 | 能力齐了，谁来保证它不乱跑、不丢状态、不被骗？ | 能画出信任边界图，并为每条边界指出它的执行者 |
| 第五篇 交付 | 系统跑得稳了，怎么产出一份别人能核、能改的交付物？ | 能从一份 Excel 走到三份可编辑的文档产出 |
| 第六篇 综合 | 零件都会用了，能拼成一条完整的生产线吗？ | 两条端到端案例能独立跑完 |
| 第七篇 迁移 | 这东西交到别人手里，还能跑、还能改、还能被解释吗？ | 别人能接手你的系统，你能解释它的每一个决定 |

### 6.2 两种读法

| 读法 | 怎么读 | 适合谁 |
|---|---|---|
| **顺读**（推荐） | 第 0 章 → 第 20 章，一章不跳 | 第一次建智能体系统的人 |
| **定点读** | 先读第 1、4、11 章（任务定义 / 循环 / 信任边界），再按需跳到具体章节 | 已经在做、卡在某一环的人 |

**定点读的唯一要求**：第 1、4、11 章不能跳。它们分别是"该不该做""怎么跑""谁来管"，是后面所有章节的前提。

### 6.3 每一章的固定结构

每章都由同一组积木搭成，位置固定，你读两章之后就能凭位置找信息：

| 积木 | 在哪 | 作用 |
|---|---|---|
| **本章承诺** | 章首 | 一句话说清读完能解释什么 |
| **读完后你能回答** | 章首 | 把承诺拆成 3–4 个能自己检验的问题 |
| **定义框** | 按需——概念首次出现处或容易被误读处 | 钉死术语，全书一词一义 |
| **核心判断** | 章中 1–3 处 | 这一章最不能被稀释的那句话 |
| **数据卡** | 按需——有硬数据处 | 数字 + 口径 + 时点 + 来源 + 局限，同屏给出 |
| **本章小结** | 章末 | 收束，不复述 |
| **行动清单** | 章末 | 5–8 条马上能做的动作 |
| **延伸阅读** | 章末 | 让读者能自己去核 |

注意章末是**行动清单**不是"思考题"。工具书要给动作，不给练习题。

**其中章首两块 + 章末三块是每章必备**（共 5 块，可用脚本机械校验）；**定义框、核心判断、数据卡按需出现**——它们只在真的有东西要钉住时才放，不放就是这一章没有需要钉住的东西。

### 6.4 四个一直要摆在桌面上的问题

读任何一章、写任何一段代码，都拿这四个问题过一遍：

1. **这个系统被允许做什么，是谁批准的？**
2. **支撑这个结果的证据是什么？**
3. **这一步失败或者被打断，会发生什么？**
4. **换一个人，能复现并修改这份交付物吗？**

这四个问题会反复出现。它们不是口号——**全书都在回答它们**：每一问都被反复追问、逐层加深，各自的落点见第 20 章那张四问对照图（图 20-2）。**不要把"回答过一次"当成"回答完了"**：同一问在第 5 章和第 11 章的答案不在同一个层次上。

## 7. 术语与约定

### 7.1 怎么决定一个词用中文还是用英文

判据只有一条：**这个英文词在中文技术语境里有没有一个稳定、无歧义的译法？**

- 有 → 用中文。`tool` → 工具，`retrieval` → 检索，`sandbox` → 沙箱，`prompt injection` → 提示注入，`idempotency` → 幂等。
- 没有，或者译出来会误导 → **保留英文原词**，第一次出现时给定义。

保留原词的只有这几个，全书统一：

| 保留原词 | 为什么 |
|---|---|
| **token** | "词元"没有被普遍接受，硬译反而增加理解成本 |
| **Harness** | 中文社区译作"外壳""挽具""套具"都不稳定；2026 年它已成为专名 |
| **Agent Loop** | 直译"智能体循环"会与编程语言里的循环混淆 |
| **ReAct** | 论文原名 |
| **Skill** | 参考实现中的产品概念，译成"技能"会与泛义混淆 |
| **MCP** / **A2A** | 协议专名 |
| **Expert** | 只在指代参考实现中的"专家配置"这一概念时保留原词，其余场合用"专家" |

其余全部用中文。**不是越英文越专业**——一句话里塞五个英文词，读者只会觉得你在掩饰。

### 7.2 排版约定

- 章节号用阿拉伯数字：`## 1. 标题`，子节 `1.1`、`1.2`。数字后有空格。
- 中文与拉丁字母之间**加一个空格**：`真实 coding agent`，不是 `真实coding agent`。
- 代码块里不遵守这条（代码就是代码）。
- 引用外部来源时给出**可查证出处**；时效敏感的数字另附时点与口径。

### 7.3 常用术语速查

完整术语表见附录 A，这里给最常用的十二个。**先看一眼，读到正文时不会卡**。

| 术语 | 本书中的意思 | 它**不是**什么 |
|---|---|---|
| **智能体** | 由模型决策、工具、上下文、状态与控制共同构成，去追求一个任务的**有界系统** | 不是"任何聊天机器人"，也不是"任何工作流" |
| **模型** | 产生预测与回答的组件 | **不会**自己执行工具，**不会**自己执行权限判断 |
| **Agent Loop** | 协调模型调用、工具执行、观测回填与停止判定的执行周期 | 不是"一个提示词"，也不是"没有上限的 while 循环" |
| **工具** | 带结构化契约的**可执行能力** | 不是"用文字描述的一个期望动作" |
| **Harness** | 模型之外的运行时与全部控制：上下文装配、能力准入、生命周期、可观测、评估 | 不是某一个标准化组件的名字，也不只是一个系统提示词 |
| **MCP** | 连接宿主/客户端与工具、资源的**协议** | 不是智能体引擎，不是授权策略，更不保证数据可信 |
| **Skill** | 可复用的工作方法（说明 + 必要时带脚本与资源） | 不是新引擎，也不自动获得执行授权 |
| **上下文** | 一次请求里模型能看到的**有界**信息 | 不是"无限的历史记录"，也不会被自动记住 |
| **检索（RAG）** | 从外部选信息来支撑生成 | 检索质量与答案质量是**两个**要分别检查的东西 |
| **证据** | 可追溯的支撑材料 | 不是"看起来像引用的字符串" |
| **产物** | 可用的、带版本的**工作产出** | 不是"脚本吐出来的任意一个文件" |
| **检查点** | 一个可恢复的状态落点 | 一次落盘**不等于**能恢复被中断的模型调用 |

## 8. 关于怎么使用 AI 助手

**你可以用编程助手。**这本书不打算假装你不该用。

但请记录三件事：它给了你什么、你验证了什么、你**能独立解释**什么。助手能加速实现，但它有三件事做不了：

1. 它不能当你的独立数值裁判——它算的和它说的可能一样错。
2. 它不能为它没读过的来源提供证据——你让它引用，它会给你一个格式正确的假引用。
3. 它不能替你完成最后的复述——你能把 ReAct、Agent Loop、Harness 讲清楚，才算真的学会了。

## 9. 学习方式：每一步都先预测

这本书的每一章都按同一个节奏推进：**先讲清楚问题 → 讲机制 → 走一遍具体输入输出 → 故意让它失败 → 你自己动手做**。

有三个动作能显著提高你的收获，成本极低：

- **读到结果之前先预测。**看到一个"预期输出"表格，先遮住，写下你认为会是什么，再对。
- **读完一段代码，合上书重建关键决定。**不是复述代码，是说清"为什么这里必须是这个顺序"。
- **改坏它，看它怎么坏。**每章都有一个"故意失败"小节，别跳过。**一个成功的响应告诉你的信息，远少于一次被拒绝的动作。**

## 10. 现在，从哪一页开始

- 你写过实际项目、用过 API、写过测试 → 直接翻到**第 1 章**。
- 你写过语法练习但没建过系统 → 先做**第 0 章**的四道出口题，做不出就读第 0 章。
- 你已经在做智能体、卡在某一环 → 读**第 1、4、11 章**，再按目录跳。
