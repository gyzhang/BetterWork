# 第 7 章 MCP：发现能力不等于获得权限

**本章承诺**：读完这一章，你能接一个外部工具系统进你的智能体，并且能准确说出"协议替你解决了什么、又绝对没有替你解决什么"。

**读完后你能回答**

- MCP 的 host / client / server 三层各自负责什么？哪一层负责授权？
- 服务端声明了一个工具，为什么你的代码还要再校验一遍它给的 schema？
- 2026 年 7 月的协议大改把会话砍掉了，这对你的连接管理意味着什么？

---

先看一个很常见的搭建过程。

有人想让智能体接上公司内部系统，于是装了四个 MCP 服务端：文件系统、工单、数据库、搜索。装完之后，界面上出现了三十七个可用工具。

他试了一下，很好用。**这个系统此刻没有任何安全边界。**

问题不在某个服务端有漏洞，而在一个更基础的地方：

> **"我把能力接进来了"这件事，和"我允许谁在什么情况下用哪个能力"是两件事。**

前者靠协议解决，后者**协议一点忙都帮不上**。

而事故往往发生在一个看起来很自然的动作之后："既然工具已经有了，不如让所有任务都能用。"

> **核心判断 1**
>
> **协议负责"能连上"，宿主负责"允许用"。**<br>
> 一个把"发现到的工具"直接变成"可调用的工具"的实现，等于把权限清单交给了**外部服务端**——而那个服务端不是你的。<br>
> 代价是你要替每一批工具做一次显式的绑定决定，不能"全选"。

参考实现的这条判断，写在了一个函数签名里：

```ts
// 参考实现源码（BetterWork · apps/desktop/src/main/services/mcp-client-service.ts）
async createAgentTools(bindings: readonly McpToolBinding[]): Promise<AgentTool[]> {
```

注意参数名：**`bindings`（绑定），不是 `connections`（连接）。**

**发现是发现，绑定是绑定。**中间那一步是人的决定。这个方法不会去遍历所有连接，它只把**被显式绑定的**工具变成智能体可用工具。

## 7.1 三层角色：谁在跟谁说话

MCP 的名字容易让人以为它是"模型调工具"的协议。**它其实不直接管模型。**

| 角色 | 是谁 | 负责 |
|---|---|---|
| **宿主（host）** | 你的应用程序 | 决定给模型看哪些工具、执行哪些调用、记录什么、拒绝什么 |
| **客户端（client）** | 宿主里的一个连接器 | 与**某一个**服务端保持 1:1 的连接，负责连接建立与协商（2026-07-28 起不再有 `initialize` 握手）、请求与响应 |
| **服务端（server）** | 外部能力提供方 | 声明自己有哪些工具与资源，接受调用并返回结果 |

**关键在第二行那个"1:1"。**一个宿主可以同时连多个服务端，但每个客户端只对一个服务端。

于是"命名冲突"这件事必须由宿主解决——这就是第 6 章那个 `mcp_<connectionId>_<name>` 前缀的由来。

**读图指引**：看宿主那一层里的两个方框——"发现的工具"和"绑定的工具"。**它们之间那条线是**人**画的，不是协议画的。**所有关于权限的讨论，都发生在这一条线上。

## 7.2 协议解决的问题，和它明确不解决的问题

MCP 的定位可以用一句话描述：**把"M 个宿主 × N 个外部系统"的适配工作，变成"M + N"。**

| 没有协议 | 有协议 |
|---|---|
| 每个宿主为每个系统写一套适配 | 每个系统写一个服务端，每个宿主写一个客户端 |
| 工具描述格式各家自定义 | 统一的工具声明与调用形状 |
| 认证、发现、超时各写一遍 | 协议层抽象 |

**它不解决的问题**（这一段比上面那张表重要）：

| 不解决 | 谁来负责 |
|---|---|
| **授权**：这个工具该不该给这个任务用 | 宿主 |
| **数据可信性**：服务端返回的内容可不可信 | 宿主（默认不可信，见第 11 章） |
| **资源限制**：这次调用花了多少、能花多少 | 宿主（见第 13 章） |
| **审计**：谁在什么时候调了什么 | 宿主 |
| **服务端本身的安全**：它会不会被投毒 | 服务端作者 + 你的接入审查 |

> **图 7-1 的结语只列了前四项**——那四项的责任方全部是宿主，所以可以一句"全部由宿主负责"收掉；**第五项不一样**，它的责任方在服务端作者与你的接入审查，不在宿主，所以没进那句结语。

**把这张表记住，可以避免绝大多数关于 MCP 的误解。**MCP 是接线板，不是保险丝。

## 7.3 2026 年：协议发生了一次大改

英文稿参考的规范版本是 `2025-11-25`。**当前版本已经是 `2026-07-28`，而且这是协议发布以来最大的一次修订。**

> **数据卡**：MCP `2026-07-28` —— 协议层无状态化
>
> **口径**：正式规范于 2026-07-28 发布（发布候选在 2026 年 5 月公布）。核心变更包括：**移除 `initialize` / `initialized` 握手**（由每次请求在 `_meta` 中携带协议版本与客户端能力替代）、**移除 `Mcp-Session-Id` 及协议级会话**、新增 `server/discover` 方法、引入 **Extensions 框架**（MCP Apps、Tasks 移入扩展）、授权加固、**正式废弃策略**、工具使用完整 JSON Schema 2020-12、`list` 类响应支持 `ttlMs` / `cacheScope` 缓存提示<br>
> **时点**：规范 2026-07-28；快照 2026-09-18<br>
> **来源**：MCP 官方规范与官方博客的发布说明，见附录 C<br>
> **局限**：这是一次**含破坏性变更**的修订。以 2025 年教程写的服务端，在新版客户端下**第一步就可能撞墙**。协议版本与实现版本必须逐个核对，不能假定"装了新的就行"

### 7.3.1 "无状态"改了什么，以及它对你意味着什么

改动本身很技术，但它对工程的实际影响只有三条：

| 变化 | 之前的做法 | 现在 |
|---|---|---|
| **跨请求状态** | 服务端记在会话里 | 服务端给出一个显式句柄（类似 `basket_id`），由模型在后续调用中**作为普通参数传回** |
| **横向扩展** | 需要会话亲和 + 共享会话存储 | 任意请求可落到任意实例，普通轮询负载均衡即可 |
| **能力发现** | 握手时一次性宣告 | 新增 `server/discover`，需要时主动探测 |

第二条是运维上的解放。第三条对**你自己写客户端**的人有直接影响：**别再把"握手时拿到的能力清单"当成永久有效的东西。**

第一条其实是一个认知上的收获，官方发布说明里有一句话值得抄：

> 让模型在调用之间**自己传递一个标识符**，不只是会话状态的可行替代，**往往还是一种更有力的做法**。

为什么"更有力"？因为它把状态变成了**显式可见的**：你能在追踪里看到模型什么时候拿到了这个句柄、什么时候传了回去、中间有没有被它丢掉。**藏在会话里的状态，你看不见。**

这和本书贯穿的一个立场一致：**能看见的机制优于隐式的机制。**

### 7.3.2 协议在变，职责不变

`2025-11-25` 到 `2026-07-28` 之间，传输层、会话模型、扩展机制都变了。**但三层角色的划分没变，宿主负责授权这一点没变。**

所以本书在讲 MCP 时，**教的是职责分工，不是 API 细节**——API 细节半年会变一次，职责分工不会。这是本书一贯的立场：**教不会过期的那一层。**

<div align="center"><img src="images/fig-7-2-spec-delta.png" alt="图 7-2 协议在变，职责不变" width="1150"/></div>

**读图指引**：左边是会变的部分（传输、会话、扩展机制、版本号），右边是不变的部分（三层角色、授权在宿主、工具输出默认不可信）。**你的架构应该按右边设计，只把左边当成可替换的实现细节。**

## 7.4 传输方式的安全含义

参考实现只用了 stdio 一种传输：

```ts
// 参考实现源码（BetterWork · apps/desktop/src/main/services/mcp-client-service.ts）
const transport = new StdioClientTransport({
  command: connection.transport.command,
  args: connection.transport.args,
  ...(connection.transport.cwd ? { cwd: connection.transport.cwd } : {}),
  stderr: 'pipe',
});
```

`stdio` 的含义是：**把服务端作为一个子进程启动，用标准输入输出通信。**

它有一个被低估的好处：**没有网络攻击面。**服务端不做监听，不暴露端口，不经过网络栈。想攻击它，得先能在这台机器上执行命令——而那时候问题已经不在协议层了。

对应的代价也很明确：

| 传输 | 攻击面 | 适用 |
|---|---|---|
| **stdio** | 本机进程边界 | 本地工具、开发环境、受控桌面应用 |
| **HTTP** | **网络**（认证、TLS、SSRF、元数据端点） | 远程服务端、多租户 |

**所以第一条工程建议是：能用 stdio 就用 stdio。**

### 7.4.1 HTTP 传输的真实风险

如果必须用 HTTP，2026 年的公开分析给出了很具体的风险形态：

> **数据卡**：MCP 的 HTTP 攻击面
>
> **口径**：2026 年的公开安全分析记录了一条可链式利用的路径——提示注入可驱动工具发起对内部网络的请求（SSRF），进而触及云元数据端点；其中一例是 MCP 服务端 HTTP 传输层的漏洞（编号 **CVE-2026-27826**）。同一批分析引用第三方统计：公共 MCP 服务端中约 **41%** 无需认证；MCP 生态第一年累计披露 40 余个 CVE<br>
> **时点**：2026 年（各 CVE 与统计的原始发布日期见附录 C）<br>
> **来源**：安全厂商的公开分析文章与 CVE 记录，见附录 C<br>
> **局限**：**41% 是第三方对公共服务的抽样统计，不等于你的部署面临的比例**；CVE 编号与影响范围以各厂商公告为准。这条数据的用处不是吓人，是说明"**默认假设服务端是安全的**"这个前提不成立

从这条风险里能直接推出几条硬约束：

| 约束 | 理由 |
|---|---|
| HTTP 传输必须认证，优先 mTLS | 未认证的服务端是可被任意调用的 |
| **对工具里的 URL 参数做白名单校验** | 注入驱动 SSRF 的入口就是"模型给的 URL" |
| 限制服务端进程的网络出口 | 即使被控，也打不到内部网段 |
| 拒绝访问云元数据端点与私网地址 | 这类请求在正常业务里几乎不会出现，一律拒绝损失极小 |

第二条要特别强调：它是**工具实现的职责**，不是提示词的职责。你在工具描述里写"不要访问内网地址"没有任何约束力——**这句在第 2 章已经确立过。**

## 7.5 不该相信服务端给的 schema

接入一个外部服务端，最自然的做法是："它说它的工具要什么参数，我就照它说的传"。

参考实现多做了一步：

```ts
// 参考实现源码（BetterWork · apps/desktop/src/main/services/mcp-client-service.ts）
const toToolSummary = (connectionId: string, tool: SdkTool, discoveredAt: number): McpToolSummary => {
  const inputSchema = schemaRecord(tool.inputSchema);
  try {
    z.fromJSONSchema(inputSchema);
  } catch (error) {
    throw new McpClientError(`MCP 工具输入 Schema 无法验证：${tool.name}`, { cause: error });
  }
  ...
```

**它在接受这个 schema 之前，先试着把这份 schema 本身解析一遍。**

为什么要这样？因为一份"看起来像 JSON Schema"的东西，可能：

- 用了你的校验器不支持的构造；
- 结构本身不合法（比如 `type` 是个数组但你只支持字符串）；
- 嵌套深到构造 zod 对象时爆栈。

如果不先验，会发生什么？**schema 会在第一次调用时才被使用，然后在那里抛出一个谁也看不懂的错误。**而那时你已经登了连接、已经把它展示给了用户、可能已经让模型看见了它。

**"在边界处校验"这条原则适用于所有外来数据，包括元数据。**一份 schema 也是数据。

### 7.5.1 schema 指纹：服务端悄悄改了怎么办

```ts
// 参考实现源码（BetterWork · apps/desktop/src/main/services/mcp-client-service.ts）
const hashSchema = (schema: Record<string, unknown>): string =>
  createHash('sha256').update(JSON.stringify(schema)).digest('hex');
```

每个工具在被发现时都算一次 schema 的哈希，存进 `schemaHash`。

**这解决的是一个真实存在的场景**：服务端升级了版本，某个工具的参数字段悄悄改了。你的绑定还在，工具名还在，但**语义变了**。

没有指纹时会怎样？模型按老参数调用，服务端的 schema 校验拒绝它，于是你看到"这个工具一直调用失败"——**而真正的原因在服务端发布说明里。**

有了指纹，你至少能做一件有价值的事：**在发现到的 schema 与上次不同时，把绑定标记为"需要重新确认"。**

> **一条可推广的做法**：**对外部系统的每一个契约，都存一份指纹。**<br>
> 契约不变时它是噪音；契约变了而你不知道时，它是唯一的线索。

## 7.6 三种上限，以及"拒绝"和"截断"的分工

参考实现里有三个数字：

```ts
const maxOutputChars = 100_000;
const connectionTimeoutMs = 10_000;
const callTimeoutMs = 60_000;
```

第一个是体积，后两个是时间。注意体积那一个的处理方式是**抛错**，不是截断：

```ts
if (serialized && serialized.length > maxOutputChars) {
  throw new McpClientError(`MCP 工具输出超过 ${maxOutputChars} 字符上限。`);
}
```

**为什么这里选抛错，而第 6 章的读文件工具选截断？**

因为两者的下游不同：

| | 读文件工具 | MCP 工具 |
|---|---|---|
| 输出形态 | 纯文本，截断后**语义仍然完整**（前 2 万字还是前 2 万字） | 可能是结构化数据，截断会**让 JSON 不合法** |
| 截断后果 | 模型看到的信息变少，知道（`truncated: true`） | 可能得到一个语法错误的载荷 |
| 选择 | 截断 + 显式标记 | 拒绝 |

**这条对比给出了一个通用的判断方法**：

> **问自己：截断之后的产物，还是一个合法的、能被下游理解的东西吗？**<br>
> 是 → 截断 + 显式标记是合理的。<br>
> 否 → 必须拒绝。

### 7.6.1 超时必须分两层

`connectionTimeoutMs`（10 秒）和 `callTimeoutMs`（60 秒）分开设置，是因为它们是两类操作：

| | 连接 | 调用 |
|---|---|---|
| 正常耗时 | 亚秒级 | 可能很慢（查询、批量操作） |
| 超时含义 | "这个服务端起不来" | "这次操作太久了" |
| 合理阈值 | 短 | 长 |

**用一个统一超时是最常见的简化，也是最容易出问题的简化**：短了会把正常的慢调用误判为失败，长了会让起不来的服务端拖住整个运行。

第 12 章会把超时和取消放到生命周期里统一处理。这里先记住：**超时不是"参数"，是"策略"，不同层的策略不该共用一个数字。**

### 7.6.2 取消和进度要透传

```ts
// 参考实现源码（BetterWork · apps/desktop/src/main/services/mcp-client-service.ts）
const result = await state.client.callTool(
  { name: tool.name, arguments: input },
  {
    signal: context.signal,
    timeout: callTimeoutMs,
    onprogress: (progress) => {
      if (progress.message) context.reportProgress(progress.message);
    },
  },
);
```

三行参数，三件必须做的事：

1. **`signal`**：把宿主的取消信号传进外部调用。**不传，用户点了停止也没用。**
2. **`timeout`**：调用级超时（与连接级分开）。
3. **`onprogress`**：把外部服务的进度转发成宿主事件——**这是第 4 章那个"长任务期间保持活着"的机制在协议层的延伸。**

第 1 条尤其重要。一个不透传取消信号的外部调用，会让"取消"变成一个**假的**功能：界面上显示已停止，后台还在跑，还在计费。

## 7.7 连接生命周期：那个容易被忽略的竞态守卫

```ts
// 参考实现源码（BetterWork · apps/desktop/src/main/services/mcp-client-service.ts）
this.active.set(id, state);
transport.onclose = () => {
  if (this.active.get(id) !== state) return;
  this.active.delete(id);
  this.store.mcpConnections.updateDiscovery(id, {
    status: 'disconnected',
    tools: [],
    lastCheckedAt: Date.now(),
  });
};
```

**第二行那个 `if` 是整段代码的关键。**

它在防什么？这个场景：

1. 连接 A 建立，`onclose` 里捕获了 `state = A`；
2. 用户改了配置，代码关闭 A、建立连接 B；
3. 这时 A 的 `onclose` **姗姗来迟**地触发了；
4. 如果没有守卫，它会**把 B 的状态改成"已断开"**——而 B 活得好好的。

**这类 bug 的特征是"偶发、不可复现、且报错信息指向错误的对象"。**用户会说"连接有时候莫名其妙就断了"，而你去看日志会发现断开时间点对不上任何真实事件。

> **一条可以固化成习惯的规矩**：**在异步回调里操作共享状态之前，先确认"这个回调对应的对象还是当前那个"。**<br>
> 做法就是捕获一个局部引用，然后与当前值比较。一行代码，换来的是一整类 bug 的消失。

### 7.7.1 其他几处细节

| 代码 | 在做什么 | 不做的后果 |
|---|---|---|
| `transport.stderr?.on('data', () => undefined)` | 把子进程的 stderr **排空** | 管道写满时子进程会**阻塞**，表现为"服务端卡死" |
| `await this.shutdown()` 里用 `Promise.allSettled` | 关闭所有连接，**不因单个失败而中断** | 一个连接关不掉会让整个退出流程挂住 |
| 连接失败时 `this.active.delete(id)` + `client.close()` | 失败路径也要清理 | 残留的半开连接会让下一次重连拿到一个坏对象 |
| `updateDiscovery(id, { status: 'connecting' / 'failed' / 'ready' / 'disconnected' })` | **状态被显式落库** | 界面上只能显示"不知道在不在" |

**最后一行是给用户看的。**一个有四个状态（连接中/就绪/失败/已断开）的实现，和一个只有"连上/没连上"的实现，在排障时的差别是巨大的——前者能让用户自己看出问题在哪一段。

## 7.8 故意失败：两个必须被拒绝的场景

### 7.8.1 请求一个未被绑定的工具

构造一个调用，`toolId` 指向一个**已经发现但没有被绑定**的工具。

期望行为：**拒绝**，并且错误信息说明"这个工具不存在或尚未发现"。

参考实现的那一行：

```ts
const tool = state.tools.get(binding.toolId);
if (!tool) throw new McpClientError(`MCP 工具不存在或尚未发现：${binding.toolId}`);
```

**注意它只查 `bindings` 里的项。**没被绑定的工具，根本不会进入这个循环——它在更早的地方就不存在了。

这个实验要证明的是：**"已经发现"和"已经授权"是两件事，且后者在代码里有明确的位置。**

如果你的实现里找不到"授权"这一步——如果工具一旦被发现就能被调用——那这个实验会失败，而失败的方式是**成功执行**。

### 7.8.2 服务端不可用

把服务端进程换成一个不存在的可执行文件，然后发起调用。

期望行为有三层：

| 层 | 期望 |
|---|---|
| **连接层** | 在 `connectionTimeoutMs` 内失败，错误信息说明是连接失败 |
| **状态层** | 连接状态落库为 `failed`，带 `failureMessage` |
| **调用层** | 抛出 `McpClientError`，**不吞掉**底层的真实原因（`cause` 链保留） |

**第三层最容易被做错**：很多实现会把它包装成一句"调用失败"，把真正的 `ENOENT: no such file or directory` 丢掉。于是排障的人只能去猜。

参考实现的包装方式值得抄：

```ts
throw new McpClientError('MCP 连接失败。', { cause: error });
```

**保留 `cause`**，让"给人看的摘要"和"给机器看的细节"同时存在。这条在参考实现的工程规范里被写成硬规则：重新抛出的错误必须带 `cause`。

## 7.9 行业视角：为什么"连上就能用"在受监管场景走不通

在个人项目里，"装个服务端就能用"是合理的便利。但在需要向合规部门解释的场景里，这套说法过不了三个问题：

| 会被问到的问题 | 只有"能连上"时的回答 | 需要补的东西 |
|---|---|---|
| **谁能调用这个外部系统？** | "智能体" | 服务端凭据的作用域与生命周期 |
| **它被允许做什么？** | "它声明的工具都能用" | 显式绑定清单 + 每次变更的记录 |
| **出了事怎么查？** | "看日志" | 结构化追踪：谁、何时、调了什么、结果是什么（第 13 章） |

这三问的答案都不在协议里。它们全部落在**宿主**这一侧——也就是第 11 章的主题。

顺便说一个 2026 年的政策背景，它解释了为什么这套要求正在从"合规部门的要求"变成"行业惯例"：

> **数据卡**：智能体的身份与能力声明进入了标准体系
>
> **口径**：2026 年发布的《人工智能 智能体互联》系列 **7 项国家标准**，覆盖总体架构、身份码、身份管理、智能体描述、智能体发现、智能体交互、智能体工具调用等环节；同期的《智能体规范应用与创新发展实施意见》提出构建分类分级治理框架，并探索建立"智能体注册平台"（提供数字身份管理、检索发现与能力声明等服务）<br>
> **时点**：2026 年（标准以国家标准化指导性技术文件形态发布）<br>
> **来源**：国家标准发布说明与政策文件答记者问，见附录 D<br>
> **局限**：**这是国家标准体系与治理框架的框架性部署，不构成对你具体系统的合规结论。**它在本节的用处只有一个：说明"**能力声明 + 身份 + 发现**"这套三件套，在协议层（MCP / A2A）和治理层（国家标准）同时出现了——**这不是巧合，是同一个问题在两个层面的映射**

## 7.10 这一章在整本书里的位置

到这里，你的智能体已经能接外部能力了——**并且只有你显式允许的那些。**

但外部能力解决的是"做事"，不解决"知道"。

一个研究任务的瓶颈通常不是"能不能查"，而是"查回来的东西对不对、够不够、有没有矛盾"。**这就是检索要解决的问题**——它也是全书最容易被做错的一块，因为它有一个非常诱人的错误方向：**把"检索到了"当成"是真的"。**

第 8 章回答它。

---

**本章小结**：MCP 是接线板，不是保险丝——它标准化"怎么连"，完全不决定"允许用哪个"。三层角色里，**授权只发生在宿主**；参考实现用 `createAgentTools(bindings)` 这个签名把"发现"和"绑定"显式分开。协议在 2026-07-28 经历了一次含破坏性变更的大改（无状态化、握手与会话移除、Extensions 框架），**但三层职责没有变**——按职责设计，把传输与会话当作可替换的实现细节。外来数据一律在边界校验，**包括服务端给的 schema 本身**；每个外部契约存一份指纹。上限处理要问一句"截断之后还是合法的东西吗"：是就截断并标记，否则必须拒绝。

**行动清单**

1. 检查你的 MCP（或任何外部能力）接入代码：**有没有一个显式绑定步骤？**如果没有，补上，并让默认值是"零个绑定"。
2. 核对你的 MCP 服务端与客户端各自声明的协议版本，确认它们能对上（`2026-07-28` 含破坏性变更）。
3. 优先使用 stdio 传输；确需 HTTP 时，补上认证、TLS、以及对工具里 URL 参数的**白名单校验**。
4. 为每个外部契约存一份 schema 指纹，并在发现到变化时把绑定标记为"需重新确认"。
5. 检查所有"包装错误"的地方：**`cause` 保留了没有？**丢掉底层错误等于把排障线索扔掉。
6. 检查所有异步回调里对共享状态的写入：**有没有"这个回调还是当前那个对象吗"的守卫？**
