# 第 5 章 ReAct 与工作流：自由度只能给在固定阶段之内

**本章承诺**：读完这一章，你能把一个任务画成"固定阶段 + 段内自适应"的结构，并为每一处自由度写出它的边界和它的升级规则。

**读完后你能回答**

- ReAct 论文说的是"推理与行动交替"，为什么本书不要求你展示模型的私有推理过程？
- 一个全自由循环和一个全固定工作流，各自会在什么情况下崩掉？
- 两份互相矛盾的材料摆在一起，系统应该怎么处理——选一个、都报出来、还是停下来问人？

---

先看一段失败的样子。

系统被要求"比较两个方案并给出建议"。它读到两份材料：

- 材料 A 说这套方案的实施周期是 **12 周**；
- 材料 B 说同一套方案的实施周期是 **20 周**。

系统在思考过程里写了一句话：

> 两份材料的实施周期表述不一致，我以材料 A 的数字为准，因为它更早发布，可能更接近基准方案。

然后它按 12 周写了比较，给出结论。

**问题在哪？**

问题不在它选错了。"以更早发布的为准"这个推理，听起来甚至是有道理的。问题在于：**它擅自引入了一条材料里根本不存在的裁决规则。**

材料里没有说"更早发布 = 更接近基准"。这条规则是它自己造的。而这条规则的引入过程，被藏在了一段**只有模型自己能看到**的文本里。

> **核心判断 1**
>
> **你可以让模型展示推理，但不能把推理当作判断依据。**<br>
> 判断依据必须是**可观测的东西**：它调用了什么、读到了什么、写了什么、拒绝了什么。推理过程是**给人看的解释**，不是**给机器验的证据**。<br>
> 代价是你需要花力气设计"过程可观测"，而不是省事地打印一段"思考过程"就交差。

---

## 5.1 ReAct：论文说的和工程要做的

### 5.1.1 论文的原始表述

ReAct 来自一篇 2022 年提出、2023 年在 ICLR 发表的论文（*ReAct: Synergizing Reasoning and Acting in Language Models*）。它的核心主张是**把推理与行动交错起来**：模型先产生一段推理，据此采取一个行动，看到行动的结果，再产生下一段推理。

这个模式打开了一个新的可能性：模型不再是"一次性回答"，而是"边做边想"。

### 5.1.2 本书对它的处理，有一处必须讲清的差别

> **本书与论文表述的差别**
>
> 论文的表述是**交错推理与行动**，推理是显式产生、可以写在提示里的一部分。<br>
> 本书把它落成**可观测的工具调用循环**：不要求模型把推理写出来，只要求它的**行动**可被记录和检查。
>
> 这个选择是刻意的，理由是工程性的而不是学术性的：**推理文本不可验证，行动序列可验证。**

参考实现里的对应关系很直白。它产出的流式片段里既有推理片段也有文本片段：

```ts
// 参考实现源码（BetterWork · packages/agent-core/src/types.ts）
export type ModelStreamChunk =
  | { type: 'reasoning-delta'; delta: string }   // 模型的推理片段
  | { type: 'text-delta'; delta: string }        // 面向用户的回答
  | { type: 'tool-call'; toolCall: ToolCall }    // 行动
  | { type: 'done' };
```

**注意 `reasoning-delta` 和 `tool-call` 是并列的两个类型。**这个结构本身就在表达本章的立场：**推理和行动是两种不同的东西，各有各的去向**——推理进界面（可折叠、可关闭），行动进执行器（必须被记录、被校验）。

### 5.1.3 一个反直觉的推论：不展示推理也能算 ReAct

由此得到一条对工程实践很实用的结论：

> **你可以完整实现 ReAct 模式，而完全不向用户展示一段"思考过程"。**

因为 ReAct 的实质是"**行动之后看到结果，据此决定下一步**"——这个"据此"可以发生在模型内部，看不见也没关系。你真正需要观测的是：**它上一步做了什么，看到了什么，下一步做了什么。**

这也解释了为什么有些系统把"思考过程"关掉之后反而更好用：**当一段不可验证的文本被摆在用户面前时，用户会倾向于相信它。**而它恰恰是全书最不应该被当成依据的东西。

## 5.2 自由度光谱：给多少，给在哪

"要不要用 ReAct"这个问法是错的。正确的问法是：**这个任务的哪些部分必须固定，哪些部分可以自由？**

把自由度画成一条光谱：

| 位置 | 形态 | 谁决定下一步 | 崩掉的方式 |
|---|---|---|---|
| **最左** | 全固定工作流 | 写流程图的人 | 遇到没覆盖的情况**静默走错** |
| **偏左** | 固定阶段 + 段内自适应 | 人定阶段，模型定段内动作 | 段边界划错，模型在错的位置做对的事 |
| **偏右** | 全自由循环 | 模型 | **花很多步做无用功；越权；停不下来** |
| **最右** | 无限自由 + 无观测 | 模型，且没人看 | 上述全部，并且没人知道发生过 |

**大多数生产任务落在中间两格。**这本书主张的默认结构是**偏左那一格**：

```text
固定阶段（人定） → 段内自由度（模型） → 固定阶段（人定） → ...
```

<div align="center"><img src="images/fig-5-1-freedom-stages.png" alt="图 5-1 自由度光谱与阶段化结构" width="1150"/></div>

**读图指引**：看中间那两格的区别。**"固定阶段 + 段内自适应"的关键约束是：模型只能改变"怎么做"，不能改变"做哪几步"。**阶段序列是权限的一部分，不是建议。

### 5.2.1 为什么会崩：两个方向的具体形态

**全固定工作流崩掉的样子**——第 1 章那个场景可以复用：

```text
步骤 3：按「金额」列求和
【实际数据】表头变成了「金额（万元）」
【结果】找不到该列 → 回退到「按第 4 列求和」→ 第 4 列是「备注」→ 求和得到 NaN
【表现】报告里出现 NaN，或者被静默填成 0
```

**注意这里的失败是静默的。**没有异常，没有报警，只有一份错的报告。

**全自由循环崩掉的样子**——第 4 章 §4.10 的实验已经展示过：一直成功，永远完不成。

### 5.2.2 划阶段的判据

怎么知道该在哪里划一条阶段边界？用三个问题：

| 问题 | 回答"是"的含义 |
|---|---|
| **这一步的产出，会被下游当成不可质疑的输入吗？** | 是 → 这一步结束就是一个阶段边界，产出必须被检查 |
| **这一步之后，需要人来拍板吗？** | 是 → 阶段边界，且带一个检查点（见 §5.4） |
| **这一步的动作集合，和下一步完全不同吗？** | 是 → 阶段边界，**因为工具权限可以收窄** |

第三条最容易被忽略，但它是最实用的：**阶段划分同时也是权限划分。**

在研究阶段，系统只需要"读"的能力：检索、读文件、读材料。<br>
在成稿阶段，系统需要"写"的能力，但**仍然不需要**"发邮件""改源文件"的能力。

**如果你不划阶段，你就只能给一套工具权限。**而一套权限必须按最大需求给——于是研究阶段也拥有了写文件的能力。

> **阶段化的第二个收益是权限最小化。**这是第 11 章"最小权限"原则能在应用层落地的唯一方式。

## 5.3 2026 年的一个行业观测：先问"谁拥有循环"

阶段化不是本书独有的偏好。2026 年主流运行时的一个公开对比，恰好可以用同一个框架来读：

> **数据卡**：主流智能体运行时的能力正在趋同，差异转移到"默认谁拥有循环"
>
> **口径**：2026 年 4 月前后，OpenAI Agents SDK 补齐了沙箱执行、持久状态与子智能体能力；此前这些是 Claude Agent SDK 与 LangGraph 的区分点。公开分析的表述是：**三个 SDK 现在都能做持久、沙箱、长时运行；区别变成了"默认谁拥有循环"**——Claude Agent SDK 由模型拥有循环、LangGraph 由你以显式状态图拥有循环、OpenAI Agents SDK 由你拥有路由而模型拥有每个节点<br>
> **时点**：2026-04 至 2026-09（框架版本持续变化）<br>
> **来源**：公开的框架对比分析，见附录 C<br>
> **局限**：这是**第三方分析的口径**，且框架版本迭代很快，具体能力以各项目当期文档为准。它在这里的用处不是"选哪个框架"，而是**它是同一个问题的另一种问法**

把它翻译成本章的框架：

| 框架默认 | 对应光谱位置 |
|---|---|
| 模型拥有循环 | 偏右（段内自由度高） |
| 你拥有状态图 | 偏左（阶段由你显式画出） |
| 你拥有路由、模型拥有节点 | 偏左（固定阶段，段内自由） |

**本章的建议与第三行一致。**理由也在那条观测里：**当"能不能做持久、能不能沙箱"变成所有人的共同能力之后，剩下的区分点就只有"默认把自由度放在哪"。**这是一个设计选择，不是一个采购决策。

## 5.4 人在环路：哪一步必须停下来

阶段化的最大收益在这里体现：**它给了你一个天然的"停机位置"——也就是本节要讲的检查点。**

> **定义**：检查点
>
> 一次运行**停下来**、并把此刻的状态**落盘**的地方。它有两个面：**"停"**（等一个人做一个决定）与**"存"**（进程死了还能从它恢复）。**两个面缺哪个都不成立**——只停不存，重启后得从头再做一遍。
>
> **它不是什么**：不是"自动保存"——没人要等的落盘，只是一个缓存；也不是"接着上一次跑"——被中断的模型调用不能从中间续上（见 §12.3）。
>
> **本书中的用法**：哪里该设、怎么设（第 5 章）；它保存什么、不保存什么（第 12 章）；在一条真实生产线上落在哪几处（第 17 章）。

阶段边界是唯一一个**此时停下代价最小、信息最完整**的位置。原因是：

- 上一阶段的产出已经完整（不是半截结果）；
- 下一阶段还没开始（停下来的成本只是等待）；
- 检查需要的信息都在手边（不需要回溯）。

### 5.4.1 三类必须设检查点的地方

| 类型 | 判据 | 例子 |
|---|---|---|
| **定义类** | 这一步的产出会锁定后面所有计算的语义 | 指标定义（"支出"含不含折旧）、期间切分规则 |
| **不可逆类** | 这一步之后需要撤销的成本很高 | 覆盖同名文件、对外发送、删除 |
| **结论类** | 这一步的产出会被当成事实引用 | 因果解释、建议、对外结论 |

第一类是最容易被省掉的，也是最贵的。**指标定义错了，后面所有计算都是精致的错误。**而且它有一种特别的隐蔽性：模型不会被"卡住"，它会顺畅地按自己理解的口径算下去，给你一个看起来完整的报告。

### 5.4.2 检查点的实现形态

检查点的最小实现只需要两件事：

1. **一个显式的"等待"状态**（而不是"卡在那里"）；
2. **一份可恢复的状态**（进程死了还能接着做）。

第 12 章会给完整实现。这里先钉死一条纪律：

> **在检查点等待时，不要持有活跃的模型调用。**<br>
> 正确的做法是：把当前状态落盘、结束这一轮运行、把"等待确认"变成一个**可恢复的任务状态**。等确认到了，再发起新的一轮。<br>
> 反过来的做法（让模型调用挂着等人回复）会在用户去吃饭的时候消耗一个长连接，并且进程一重启就全丢。

## 5.5 升级规则：什么时候该交回给人

一个只有检查点、没有升级规则的循环是不完整的。因为**除了"计划中的停"，还需要"意外情况下的停"**。

参考实现的实验要求里有一条很具体的表述：**处理冲突观测与无进展重复，独立解释并修改循环。**

把它拆成可直接实现的四类升级条件：

| 触发条件 | 判据（可编码） | 动作 |
|---|---|---|
| **证据冲突且无法裁决** | 同一事实出现两个不同的值，且没有优先级规则能决定用哪个 | 停下来，把两个值都报给用户 |
| **重复无进展** | 连续 N 次调用同一工具且参数等价，产出也等价 | 停止，报告"卡住了"以及卡在哪 |
| **权限不足** | 完成任务需要一个未授权的动作 | 停止，说明需要什么授权 |
| **超出预算** | token、时间或轮次任一触顶 | 停止，报告已经完成到哪一步（第 13 章） |

**第一条要特别小心。**回到章首那个例子：系统在两份矛盾材料之间擅自引入了一条裁决规则。正确的处理不是"选一个更合理的"，而是：

```text
材料 A：实施周期 12 周（来源：xxx，发布日期 yyy）
材料 B：实施周期 20 周（来源：xxx，发布日期 yyy）

两份材料对同一事实给出不同取值，且没有可用的优先级规则。
【已停止】请确认以哪一份为准，或提供裁决规则。
```

这段输出**比原来那段差得多**——它没有给出建议，读起来像没干活。

**但它是唯一诚实的输出。**因为它把"需要人决定的事"还给了人，而不是替人做了一个自己都说不清依据的决定。

> **核心判断 2**
>
> **遇到无法裁决的冲突时，"停下来问"是正确答案，不是能力不足。**<br>
> 一个总能给出答案的系统，在冲突场景下给出的必然是编的答案。区别只在于编得像不像。<br>
> 代价是系统的"完成率"会下降——如果你把完成率当 KPI，你就是在激励它编。

## 5.6 无进展重复：怎么检测，以及它的边界

### 5.6.1 检测什么

"重复调用"不等于"无进展"。合法的重试看起来也是重复调用。区分点在于**产出是否等价**：

| 情况 | 是重复吗 | 处理 |
|---|---|---|
| 同一工具、同一参数，返回同样的结果 | **是**，无进展 | 计数 +1，到阈值就停 |
| 同一工具、同一参数，第一次失败第二次成功 | 不是，是**有效重试** | 不计数 |
| 同一工具、参数每次差一点点 | 不判定 | 交给轮次上限兜底 |
| 不同工具，但都在做同一件事 | 通常不判定 | 不要试图自动识别，误判代价高 |

### 5.6.2 边界必须写清

> **重复检测是启发式，硬轮次上限是计数。**<br>
> 启发式的失效模式是"在某个边界情况上不再生效"；计数的失效模式不存在。<br>
> 所以**重复检测只能加在硬上限之上，不能替换它**。（第 4 章 §4.10.1）

一个具体的实现建议：把"无进展"定义成**可计数的事实**，而不是可判断的感觉。比如"同一 `(toolName, 规范化参数)` 三元组连续出现 3 次，且三次的产出 JSON 字符串完全相等"。**三个条件都必须是机器能判定的。**

## 5.7 故意失败：两个矛盾的观测

做一个实验。

准备三份材料：两份对同一事实给出不同数值，第三份提供一条**可以裁决它们的规则**（比如"以最新版为准")。然后跑两条路线。

### 5.7.1 路线一：不告诉系统有裁决规则

预期行为：系统**停下来问**。

实际常见行为：它选了一个，并给出一个听起来合理的理由。

**判断这个实验成不成功的方法不是看它选得对不对，是看它有没有在输出里**说明它依据了什么规则**。如果它给出的理由在材料里找不到，那它就是在编——即使结论恰好是对的。

### 5.7.2 路线二：给它裁决规则

预期行为：它按规则裁决，并在输出里**引用这条规则**。

这一步在验证的东西是：**规则是否真的被用上了，还是它又自己编了一条。**

具体做法：写一条验收条件

```text
A8：凡涉及"在多个冲突来源之间做取舍"的表述，
    必须引用裁决规则的原文或给出规则所在位置；
    引用不到即判失败。
```

### 5.7.3 这个实验真正证明的东西

它证明的不是"模型会不会编"，而是：

> **在没有可引用的规则时，"给出建议"和"编造规则"在输出层面长得一模一样。**

所以你的系统必须能在**结构上**区分它们。区分的办法不是让模型诚实一点，而是**在验收条件里要求可引用的依据**——**把"诚实"变成一个可机器检查的形状。**

这条做法会在第 13 章和第 17 章各出现一次，一次是变成评估指标，一次是变成端到端案例的验收条件。

## 5.8 行业视角：机构里的"人在环路"是授权，不是礼貌

第 5 章说"阶段边界同时是权限边界"。在机构里，这句话要补上后半句：**它同时是责任边界——谁按的"继续"，谁对这个决定负责。**

| 检查点类型 | 机构里的对应动作 | 谁有权按"继续" |
|---|---|---|
| 问题的方向会改变 | 方案方向、口径选择 | 业务或方案负责人 |
| 存在越权风险 | 超出既定范围的读取或写入 | **复核人**（双人复核） |
| 不可逆动作 | 对外发送、覆盖历史、登记生效 | 有审批权限的岗位，通常要**单号** |

**关键在这张表的第三列，不在第一列。** 把检查点实现出来并不难；难的是**把"谁有权按继续"写进配置，而不是写进文档**。写在文档里的约定，在系统里不存在。（第 17 章会把这类位置放到一条完整的生产线上——五个阶段里，有三处是这样的检查点。）

一个可验证的做法：**检查点触发时，运行记录里必须留下"是谁按的"**，而不是只留一个布尔值。这条与第 20 章"责任必须被指派"是同一个要求——**只是它发生在运行时，而不是交付时。**

## 5.9 这一章在整本书里的位置

到这里，第二篇结束了。你有了：

- 一个判断该不该用智能体的框架（第 1 章）；
- 一份模型能力边界的清单（第 2 章）；
- 一次完整的工具交换（第 3 章）；
- 一个有界、可取消、有明确终态的循环（第 4 章）；
- 一套把自由度限定在阶段内的方法（第 5 章）。

**这五章合起来回答的是"决策的形状"。**

但骨架不自带能力。这个循环现在已经能重复做决定了，可它手里没有一件真正管用的工具——只有一个算术计算器。

**它需要能做什么、能看什么、能记住什么？**这就是第三篇的问题。第 6 章从最基础的一件开始：**怎样造一个值得信任的工具。**

---

**本章小结**：ReAct 的工程实质是"行动后看到结果，据此决定下一步"，因此**不需要展示私有推理**——推理和行动是两种东西，各有各的去向。自由度应该给在"固定阶段之内"：阶段序列属于权限，不属于建议；模型可以改变"怎么做"，不能改变"做哪几步"。阶段边界同时是权限边界和检查点位置。遇到无法裁决的冲突时，停下来问是正确答案——一个总能给出答案的系统，在冲突场景下给出的必然是编的答案。

**行动清单**

1. 把你手上的任务画成阶段图，标出每一处"看情况"发生在**哪一个阶段之内**。如果某个"看情况"跨越了阶段边界，说明阶段划错了。
2. 为每个阶段列出它需要的工具，然后收窄到最小集合——**研究阶段不该有写文件的能力**。
3. 在定义类、不可逆类、结论类三处各设一个检查点，检查点必须能落盘恢复，**且不持有活跃的模型调用**。
4. 实现四类升级条件（冲突、无进展、权限不足、超预算），为每类写一条可机器判定的判据。
5. 在你的验收条件里加一条"引用依据"要求：**凡涉及取舍的表述必须给出可引用的规则或来源**。
