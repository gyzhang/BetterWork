# 第 12 章 生命周期：状态必须活过进程

**本章承诺**：读完这一章，你能为一次运行设计出完整的身份、状态、中断恢复与幂等策略，并说清"检查点保存了什么、又绝对没有保存什么"。

**读完后你能回答**

- 一次运行被打断后，"恢复"到底恢复了什么？为什么它不可能恢复一个正在进行的模型调用？
- 同一个文件被登记两次，怎么保证产物不会变成两份？
- 为什么"登记产物"这件事要在事务里**再检查一遍**权限？

---

先看一个真实发生过的场景。

用户在等一个长任务。跑了六分钟，完成了三步。这时他关掉了应用——或者更常见的是，应用因为一个内存问题崩了。

重新打开后，界面显示：

> 运行中……

而且它一直显示"运行中"。刷新没用，重启也没用。

**数据库里那个 Run 的状态是 `running`。**而那个 Run 对应的进程，六分钟前就不存在了。没有任何东西会来改这个状态——因为它该做的那个进程，已经死了。

> **核心判断 1**
>
> **进程会死，而且不会给你善后机会。**
> 所有"只在内存里"的状态，在进程消失的那一刻就全部消失了——包括"它正在运行"这个状态本身。
> 代价是：**每次启动都要做一次"清理残局"的动作**，而且这个动作必须假定"上次是不干净地结束的"。

---

## 12.1 三种身份，缺一不可

要管住生命周期，先要分清"这是谁"。参考实现里至少有四层标识：

| 标识 | 代表 | 生命周期 |
|---|---|---|
| **task** | 用户想做的一件**事** | 天到周 |
| **session** | 一次**连续协作** | 小时到天 |
| **run** | 一次**执行**（一次循环的完整跑动） | 秒到分钟 |
| **execution** | 一次**代码执行**（如一个脚本的跑动） | 秒到分钟 |

为什么需要这么多层？

| 少了它 | 后果 |
|---|---|
| 少了 task | 没法把"这件事做过几次"关联起来；产物无处归属 |
| 少了 session | 没法区分"同一件事的两次不同讨论" |
| 少了 run | 一次运行失败后重跑，无法区分是新的一次还是同一次 |
| 少了 execution | 无法把一个产物的**来源**定位到具体哪一次脚本跑动 |

**最后一行是"证据链"的基础。**第 15 章讲文档交付时，每一个产出的文件都要能回答"它是哪一次运行、哪一次执行产生的"——**这个链条的末端就是 execution。**

参考实现的产物登记里，这个链条被完整写进了一条记录：

```ts
return this.store.artifacts.registerFile({
  taskId,
  versionId,
  title: input.title,
  runId: input.runId,
  mimeType: '...',
  fileSize,
  fileHash,
  fileKey,
  executionId: input.executionId,
  validation: output.validation,
});
```

`taskId` + `runId` + `executionId` + `versionId` + `fileHash` —— 五个标识连起来，才是一条**可追溯的线**。

## 12.2 终态不变量：每个 Run 必须有明确终态

第 4 章已经确立过这条不变量。这里给出它的**工程实现**。

```text
启动时：把上次进程被强杀留下的 running 记录，收口为 failed
```

这一条动作被称为**中断收口**。它的实现要点有四条：

| 要点 | 为什么 |
|---|---|
| **只在启动时做** | 运行时做会与正常流程竞争 |
| **只处理 `running`** | 已经有终态的不能改（会覆盖真实结果） |
| **必须是幂等的** | 启动可能发生多次（比如连续崩溃重启） |
| **必须记录原因** | 收口为 `failed` 时要说明"这是因为进程中断"，而不是笼统的失败 |

**第三条最容易被漏。**一个非幂等的收口逻辑，在"启动两次"的情况下会把第二次的合法状态也改掉。

参考实现在另一个地方用了一个更通用的做法——把"收口"做成有条件的：

```ts
const operations = this.store.dependencyOperations.failInterruptedOperations(now);
```

**方法名里的 `Interrupted` 就是条件**：只有"中断的"才失败。这个命名本身就在约束实现。

### 12.2.1 编排层也要兜底

引擎自己会收口失败与取消，但有一个缺口：

> **编排层在进入事件循环之前（读模型配置、构造搜索客户端）或在写库、广播过程中抛错时，引擎不会产出任何终态事件。**

所以参考实现要求编排层必须有 `catch`，并且兜底方式是**有条件合成**一个失败终态——只在 Run 仍为 `running` 时才写，因此重复调用安全，也不会与引擎的终态冲突。

**"兜底合成"这个设计有一个值得学的性质：它不假设上游会正常工作。**

```text
正常路径：引擎产出终态 → 状态落库
异常路径：编排层捕获 → 检查是否已有终态 → 没有则合成 failed
```

两条路径都可能写终态，所以**写入必须是有条件的**。这是"至少一次投递"场景下的常规做法：**幂等的写入 + 状态检查。**

## 12.3 检查点：它保存了什么，没保存什么

这一节是本章最重要的一节，因为它要纠正一个非常普遍的误解。

先看参考实现给出的一个诚实标注：

> **一个持久化的任务检查点，不会恢复被中断的模型请求的调用栈。**

**"恢复调用栈"是个技术术语，它在这里的意思很具体：**

| 检查点保存的 | 检查点**不能**保存的 |
|---|---|
| 任务的当前状态 | 一个正在进行的模型调用的**中间态** |
| 已产出的产物版本 | 那个调用已经流过多少个 token |
| 待确认的事项 | 模型服务端那份请求的上下文 |
| 归属关系 | 它跑到哪一行了 |

**为什么不能？**因为那个调用**不在你这边**。它是另一个进程（模型服务）上的一次请求，你可能已经收到了它的前 300 个 token。**你无法让"从第 301 个 token 继续"。**

<div align="center"><img src="images/fig-12-1-lifecycle.png" alt="图 12-1 三种身份与检查点能恢复什么" width="1150"/></div>

**读图指引**：看中间那条竖线。**线以上是"你自己的状态"（能落盘、能恢复），线以下是"别人的调用"（只能重新发起）。**把这件说清楚，是这个图存在的全部理由——因为"我们有检查点"这句话，太容易被听成"什么都能接着跑"。

### 12.3.1 正确的恢复语义

所以正确的做法是：

```text
中断发生在检查点之后：
  → 从检查点恢复任务状态
  → 重新发起一次新的模型调用（不是"接着上一次"）
  → 这次调用会重新读一遍上下文

中断发生在检查点之前：
  → 回到上一个检查点
  → 从那里重做

中断发生在"一个副作用已经发生、但结果还没落盘"的窗口：
  → 这是最危险的情况，见 12.5
```

**第三种情况是这一章真正要解决的问题。**它有一个专门的名字：**效果已发生、记录未落盘**——第 12.5 节讲它。

## 12.4 归属校验：五个"属于"检查

看参考实现的检查点服务。它只有 43 行，而其中**五行是同一类检查**：

```ts
// 参考实现源码（BetterWork · apps/desktop/src/main/services/discussion-checkpoint-service.ts）
private assertTask(taskId: string): void {
  if (!this.store.tasks.getWorkspaceId(taskId)) throw new Error('Task does not exist');
}

create(taskId: string, input: CreateDiscussionCheckpointRequest): DiscussionCheckpoint {
  this.assertTask(taskId);
  if (input.taskId !== taskId)
    throw new Error('Discussion checkpoint task does not match request');
  if (input.runId && !this.store.runs.belongsToTask(input.runId, taskId)) {
    throw new Error('Discussion checkpoint Run does not belong to Task');
  }
  if (input.supersedesId) {
    const previous = this.store.discussionCheckpoints.get(input.supersedesId);
    if (!previous || previous.taskId !== taskId) {
      throw new Error('Discussion checkpoint to supersede does not belong to Task');
    }
  }
  for (const versionId of input.artifactVersionIds) {
    const version = this.store.artifacts.getVersionDetail(versionId);
    if (!version) throw new Error(`成果版本不存在：${versionId}`);
    const artifact = this.store.artifacts.getDetail(version.artifactId);
    if (!artifact || artifact.taskId !== taskId) {
      throw new Error('讨论节点引用的成果版本不属于当前 Task');
    }
  }
  return this.store.discussionCheckpoints.create(taskId, input);
}
```

**五道检查，全部是"这个东西真的属于这个 Task 吗"：**

| # | 检查的对象 | 拦住什么 |
|---|---|---|
| 1 | Task 本身存在 | 对一个不存在的事挂检查点 |
| 2 | 请求路径里的 taskId 与载荷里的一致 | 参数错配 |
| 3 | Run 属于这个 Task | **跨任务引用**——A 任务的运行被挂到 B 任务下 |
| 4 | 被取代的那个检查点属于这个 Task | 跨任务改写 |
| 5 | 每个产物版本存在，且它所属的产物属于这个 Task | **跨任务引用别人的成果** |

### 12.4.1 为什么这五行如此重要

因为它们防的是一类特殊的错误：**跨边界引用**。

这类错误的形状是：数据看起来完全正常，只是**它属于别人**。

| 场景 | 后果 |
|---|---|
| A 项目的运行被挂到 B 项目下 | B 的报告里出现了 A 的数据 |
| A 的产物被 B 引用 | **数据泄露**（在受监管场景里这是事故级） |
| 一个已删除的检查点被"取代" | 空引用或复活 |

**第 5 行检查写得最细，值得单独看**：

```ts
const version = this.store.artifacts.getVersionDetail(versionId);
if (!version) throw new Error(`成果版本不存在：${versionId}`);
const artifact = this.store.artifacts.getDetail(version.artifactId);
if (!artifact || artifact.taskId !== taskId) { throw ... }
```

**它检查了两层**：版本存在 → **版本所属的产物属于这个 Task**。

为什么不直接检查版本归谁？因为**版本本身不直接持有 taskId**——归属关系在产物上，版本是产物的子对象。所以必须**沿引用链向上追溯一层**。

> **一条可推广的规则**：**归属检查必须沿着引用链走到持有归属的那个对象。**
> 只检查直接引用对象，会在"子对象没有独立归属"时失效。代价是每多一层引用，就多一次查询——**这个开销必须付**，因为一次跨任务引用就是一次数据泄露。

## 12.5 效果已发生、记录未落盘

这是本章最难的一类问题。它的形状是：

```text
步骤 1：工具调用外部服务，成功（钱已经扣了 / 文件已经生成 / 邮件已经发了）
步骤 2：把这一步的结果写入数据库
【步骤 1 和步骤 2 之间，进程死了】
```

重启后，系统看到的是"这一步没做过"。于是它**再做一次**。

**结果是副作用发生了两次。**

### 12.5.1 处理方式有三种，选哪种取决于副作用类型

| 副作用类型 | 例子 | 处理方式 |
|---|---|---|
| **幂等的** | 写一个内容确定的文件 | 直接重做 |
| **可检测的** | 生成一个带固定 ID 的产物 | 重做前先查该 ID 是否已存在 |
| **不可检测、不可逆的** | 扣款、外发邮件 | **不能自动重做，必须人工确认** |

参考实现的产物登记用的是**第二种**：

```ts
const fileKey = `${input.executionId}/${input.outputId}`;
...
const existing = this.store.artifacts.findRegisteredFile(fileKey);
if (existing) {
  if (input.artifactId && input.artifactId !== existing.artifactId)
    throw new Error('Output already belongs to another artifact');
  return existing;
}
```

**`fileKey` 是一个从"执行 ID + 输出 ID"推出的确定性键。**同一个输出被登记两次时，第二次会**返回第一次的结果**，而不是创建一个新版本。

**这就是幂等键（idempotency key）。**它的构造原则是：

> **键必须由"这次操作的确定身份"推出，不能由时间或随机数推出。**

- ✅ `executionId/outputId` —— 同一次执行的同一个输出，无论登记多少次都是同一个键；
- ❌ `randomUUID()` —— 每次都不一样，幂等失效；
- ❌ `时间戳` —— 同上。

### 12.5.2 幂等键不能同时防住"不同 artifact"

注意那个嵌套判断：键已存在，但调用方指定了一个**不同的** `artifactId`——这时**抛错**，而不是合并。

因为"同一个输出被登记到两个不同的产物下"是一个**语义冲突**，不是重复请求。**它必须被明确拒绝，而不是被幂等逻辑悄悄吞掉。**

**这个细节很能说明幂等设计的成熟度**：幂等处理的是"同一个请求重复到达"，不是"两个互相冲突的请求"。

## 12.6 事务里要再检查一次权限

现在看参考实现里最值得学的一段结构。

它的产物登记分两个阶段：

**阶段一（事务外）**：读、校验、算哈希、准备数据

```ts
const execution = this.store.executions.getExecution(input.executionId);
if (!execution) throw new Error('Execution does not exist');
if (execution.runId !== input.runId) throw new Error('Execution does not belong to this run');
if (execution.status !== 'succeeded') throw new Error('Only succeeded executions can register artifacts');
if (!execution.outputIds.includes(input.outputId)) throw new Error('Output is not registered for this execution');
```

**四层校验**：存在 → 归属 → **终态是成功** → 输出句柄被登记过。

第三层（`status !== 'succeeded'`）是一条重要的规则：**只有成功的执行才能登记产物。**否则一个失败的脚本留下的半成品会被登记成"产物"，而它的名字和正常的产物一模一样。

**阶段二（事务内）**：**重新检查一遍时效性**

```ts
return this.store.transaction(() => {
  if (
    this.store.runs.get(input.runId)?.status !== 'running' ||
    !this.acceptsRun(input.runId) ||
    !this.store.executions.isBindingAuthorized(execution.bindingId)
  )
    throw new Error('Run or Skill authorization is no longer active');
  ...
});
```

三个条件：

| 条件 | 拦住什么 |
|---|---|
| Run 仍然是 `running` | **运行已经被取消了**——不要再登记它的产物 |
| `acceptsRun(runId)` | 宿主侧的策略（比如这个运行已被标记为不可接受） |
| **`isBindingAuthorized(execution.bindingId)`** | **授权在登记这一刻是否仍然有效** |

**第三个条件是最容易被忽略的。**

想一下这个场景：

1. 一个 Skill 获得授权，开始运行；
2. 运行过程中，用户**撤销**了这个 Skill 的授权；
3. 那个运行刚好完成了，来登记产物。

**在阶段一检查过了授权（因为它检查了 `execution.status === 'succeeded'` 和归属），但在这一刻授权已经没了。**

**所以检查必须在"动作真正发生的那一刻"再做一次。**

> **核心判断 2**
>
> **权限检查的有效期，就是"从检查到动作"之间的那段窗口。窗口越长，检查越不可靠。**
> 正确的做法是把检查尽量贴近动作：**放在执行动作的那个事务里。**
> 代价是检查要执行两遍（事务外的快速失败 + 事务内的最终判定），代码更长。

**事务外的检查不浪费**：它让绝大多数非法请求在**做任何准备工作之前**就被拒绝（不读文件、不算哈希）。

## 12.7 不可变与真实性：怎么保证"这个文件就是那个文件"

产物登记的另一个核心职责是**真实性校验**。参考实现做了四件事：

```ts
const fileBuffer = readManagedFile(context.workspacePath, path.relative(context.workspacePath, sourcePath));
const fileHash = hashBytes(fileBuffer);
if (fileHash !== output.fileHash || fileBuffer.length !== output.fileSize)
  throw new Error('Output hash does not match its validation report');
const reportPath = `${sourcePath}.report.json`;
const report = readManagedFile(context.workspacePath, path.relative(context.workspacePath, reportPath));
if (hashBytes(report) !== output.reportHash) throw new Error('Validation report hash mismatch');
```

| 动作 | 拦住什么 |
|---|---|
| 读文件并算哈希 | **文件在校验之后被改过** |
| 比对**长度** | 哈希相同但长度不同的情形（理论上不该发生，作为冗余） |
| 读 **`.report.json`** 并校验它的哈希 | **校验报告本身被改过** |

**最后一行很关键。**一个只校验"文件哈希与报告里写的一致"的实现，有一个漏洞：**把文件和报告一起换掉。**攻击者改文件、同时改报告里记录的哈希——两者一致，检查通过。

**要堵住这个漏洞，报告本身的哈希必须来自一个外部来源**（这里是数据库里 `output.reportHash`）。**报告的可信度不能由报告自己证明。**

<div align="center"><img src="images/fig-12-2-registration.png" alt="图 12-2 成果登记的五道校验与不可变落盘" width="1150"/></div>

**读图指引**：看上下两段的分工——**上半是"事务外的快速失败"，下半是"事务内的最终判定"。**权限那一项必须出现两次，因为从检查到动作之间有一段真实存在的窗口。

> **这条规则可以推广**：**校验的信任根必须在你控制的地方。**
> 一个"自证"的校验（文件说自己是好的、报告说文件是好的）不是校验。

### 12.7.1 不可变的实现：两个文件系统标志

```ts
mkdirSync(destDir, { recursive: true });
writeFileSync(destPath, fileBuffer, { flag: 'wx', mode: 0o400 });
```

两个参数各自承担一半的"不可变"：

| 标志 | 含义 | 拦住什么 |
|---|---|---|
| **`flag: 'wx'`** | 只在文件**不存在**时创建，存在就失败 | **覆盖**——同一个版本目录不会被写第二次 |
| **`mode: 0o400`** | 只读（属主可读） | **后续修改**——进程自己也没有写权限了 |

**这两个标志加起来，才是"不可变存储"的实际含义。**很多实现只在文档里写"产物是不可变的"，而没有这两个标志——那就是一句愿望。

### 12.7.2 失败要清理

```ts
try {
  return this.store.transaction(() => { ... });
} catch (error) {
  rmSync(destDir, { recursive: true, force: true });
  throw error;
}
```

**数据库事务失败时，删掉已经复制好的文件目录。**

如果不删：磁盘上留着一份没有任何数据库记录的孤儿文件。它永远不会被引用，也不会被清理——**因为清理逻辑通常按数据库记录来找文件。**

**"先落盘再写库"这个顺序必然产生这个窗口**，所以必然需要这个 `catch`。反过来的顺序（先写库再落盘）会产生另一种孤儿：数据库里有一条记录，文件不存在。**两种都有代价，区别是哪种更容易检测**——文件缺失会被用户立刻看到，文件孤儿只是浪费磁盘。**所以选"先落盘再写库 + 失败清理"。**

## 12.8 派生缓存：失效策略比生成策略重要

参考实现里有一个用得很好的模式：**派生数据带一个语义版本标记，版本不符就整批作废。**

```ts
// 参考实现源码（BetterWork · apps/desktop/src/main/services/file-artifact-service.ts）
private readCachedRevision(versionId: string): number | undefined {
  const marker = path.join(this.thumbnailDir(versionId), '.revision');
  ...
}

listThumbnails(versionId: string): ArtifactThumbnail[] {
  const dir = this.thumbnailDir(versionId);
  if (!existsSync(dir)) return [];
  if (this.readCachedRevision(versionId) !== this.pptxRenderer.previewRevision) {
    // 渲染器换过了：整目录作废，由下一次请求完整重建，不留新旧混用的残页。
    rmSync(dir, { recursive: true, force: true });
    return [];
  }
  ...
}
```

三个设计决定，逐条读：

| 决定 | 效果 |
|---|---|
| **缓存带语义版本标记** | 渲染器升级后，旧缓存自动作废 |
| **不符就整目录删除** | **不留新旧混用**——混用会产生"有的页是旧渲染器画的、有的是新的"这种极难查的问题 |
| **标记文件最后写** | 中途崩溃只会留下无标记目录 → 下次读作废并重建，**不会把半成品当有效缓存** |

**第三条是最好的一条。**它是一个"写入顺序即正确性"的例子：

```text
先写内容，最后写标记
  → 崩溃在写内容过程中：没有标记 → 视为无效 → 重建
  → 崩溃在写标记之后：所有内容已写完 → 有效
```

**如果不这样设计**（比如先写标记再写内容），崩溃的后果是：标记在、内容不全 → **被视为有效缓存** → 界面显示缺页的预览。

**"什么时候写那个标记"这个决定，决定了这个缓存是否可信。**这是一个很典型的"一个写入顺序换一类 bug 消失"的设计。

### 12.8.1 派生功能的失败不能中断主路径

```ts
try {
  slides = await this.pptxRenderer.render(pptxPath);
} catch (error) {
  return { thumbnails: [], error: `幻灯片预览生成失败：${describeError(error)}` };
}
```

**注意它 `return` 一个带 `error` 的结果，而不是 `throw`。**

参考实现的注释写明了理由：**失败以 `error` 返回，让界面保留「打开」通路并解释原因。**

也就是说：**预览生成失败了，用户仍然能打开那个 PPT。**

| 做法 | 用户看到 |
|---|---|
| 抛错 | "操作失败"——用户以为整个产物坏了 |
| **返回带 error 的结果** | 产物可用，预览暂时没有，并说明原因 |

**判断一个功能该 `throw` 还是该"降级返回"，用这个问题**：**这个功能失败时，主功能还能用吗？**

- 能 → 降级返回（派生功能）
- 不能 → 抛出（主功能）

**把派生功能的失败升级成主功能的失败，是一种"过度严苛"，它的代价是用户被挡住了本来能做成的事。**

## 12.9 故意失败：四个必须构造的实验

### 12.9.1 中断恢复

**实验**：在一个运行的中间强杀进程，重启应用。

**期望**：
1. 那条 Run 被收口为 `failed`，并说明是中断导致；
2. 从最近的检查点可以**发起一次新的运行**；
3. **不能**声称"从上次中断的地方继续"。

**第 3 条是判据的关键。**如果你的产品文案写的是"继续上次的运行"，而实现是"发起一次新运行"，那就是一个**承诺与实现不符**的问题。

### 12.9.2 重复登记

**实验**：对同一个 `executionId` + `outputId` 连续登记两次。

**期望**：第二次返回**同一个**版本，**不创建新版本**。

**验证方法**：数一下版本表的行数——一次执行一个输出，只应该有一个版本。

### 12.9.3 篡改校验报告

**实验**：把产物文件改掉，同时把它旁边的 `.report.json` 里的哈希也改成新文件的哈希。

**期望**：**登记被拒绝。**

**理由**：报告本身的哈希与数据库里记录的 `reportHash` 对不上。

**这个实验证明的是"信任根在外部"**：报告自证无效。

### 12.9.4 授权在登记前失效

**实验**：让一个执行在授权有效时完成，然后在登记之前撤销授权。

**期望**：**登记被拒绝**，错误信息说明"运行或 Skill 授权已不再有效"。

**这个实验不容易构造**（需要精确的时序控制），但它的价值最高——**它是"检查必须贴近动作"这条原则唯一的验证方式。**

## 12.10 行业视角：为什么 2026 年的运行时都在补这一层

第 5 章引用过一条框架对比的公开结论："三个 SDK 现在都能做持久、沙箱、长时运行。"这一章讲的正是其中的"持久"与"长时运行"。

把它翻译成本章的语言：

| 公开能力名 | 对应本章的什么 | 对应本书哪一章 |
|---|---|---|
| **持久状态与检查点** | Run 的状态落库 + 中断收口 | 第 12 章 |
| **沙箱执行** | 隔离的执行环境 | 第 11 章 |
| **失败恢复** | 从检查点发起新运行 | 第 12 章 |
| **工具发现** | 能力注册与绑定 | 第 7 章 |
| **人工批准原语** | 检查点 + 升级规则 | 第 5、12 章 |

> **数据卡**：主流运行时把长期运行当作基础能力
>
> **口径**：2026 年的公开技术分析记录了一个方向性转变：早期做法是"模型外面套一个 while 循环"，问题在容器重启后丢状态、生成代码在宿主上跑导致凭据泄露、长任务无法暂停等人批准。到 2026 年 8 月，主流 SDK 在**持久状态与检查点、沙箱执行、失败恢复、工具发现、人工批准原语**这几项上已经收敛。一处被公开引用的描述是：一个真实的长任务"运行几分钟，然后睡一天"，托管运行时在空闲时不产生成本
> **时点**：2026 年 8 月（公开分析时点）
> **来源**：公开技术分析文章与各框架发布说明，见附录 C
> **局限**：这是**方向性判断而非能力对比**，各框架的具体实现与成熟度差异很大，且版本迭代很快。它在本章的用处是提供一个判断：**"持久状态"是 2026 年的基础能力，不是加分项**——如果你的系统在这件事上是空白，那它已经落后于行业基线

**注意那三个"早期问题"**：丢状态、凭据泄露、无法暂停等人批准。

**它们恰好对应本书的第 12、11、5 三章。**这不是巧合——那三个问题就是这一章、上一章和上上章各自要解决的。

**本章小结**：进程会死且不会善后，所以**每次启动都要做中断收口**——只处理 `running`、必须幂等、必须记录原因。四层身份（task / session / run / execution）连起来才是可追溯的线。**检查点保存的是"你自己的状态"，不能保存"别人的调用"**——被中断的模型请求只能重新发起，不能"接着跑"。"效果已发生、记录未落盘"是生命周期里最难的一类问题：靠**由确定身份推出的幂等键**解决，不可检测的副作用必须人工确认。**归属检查必须沿引用链走到持有归属的那个对象**——检查点服务里那五行"属于吗"防的是跨任务引用与数据泄露。**权限检查必须放在执行动作的那个事务里再做一次**，因为从检查到动作之间有一个窗口。**校验的信任根必须在外部**——报告不能自证。派生功能失败要降级返回，不要升级成主功能的失败。

**行动清单**

1. 实现中断收口：启动时把残留的"进行中"状态收口为失败，**只处理运行中的、幂等、带原因**。
2. 列出每一个会重复到达的写操作，为它设计一个**由确定身份推出**的幂等键。
3. 把每一处"权限检查"挪到执行动作的事务里；保留事务外的快速失败。
4. 为所有归属关系写检查，**沿引用链走到持有归属的对象**。
5. 给产物落盘加上 `wx` + 只读模式，并在数据库事务失败时清理文件。
6. 让校验报告的可信根来自数据库而不是报告自身。
7. 给派生缓存加语义版本标记，**标记最后写**；版本不符就整目录作废。
