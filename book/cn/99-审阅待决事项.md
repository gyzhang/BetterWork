### 7.1 作者质疑："预计阅读 约 4 小时 35 分钟"——这个数字不成立

**作者原话**："一本 328 页的技术书籍，为什么会在约 4 小时 35 分钟内完成？我从来没有遇到过看技术书籍这么快的人，就算是看修仙小说也看不到这么快吧！无法预估时间，咱们就不要写这个时间！"

**复核结论：作者完全正确，这是我的缺陷，已修。**

| 项 | 内容 |
|---|---|
| 数字从哪来 | `build_html.py` 的 `mins = 汉字数 / 480` |
| 480 是什么 | 一个**隐含的阅读速度**：480 汉字/分钟 = **每秒 8 个字** |
| 折算 | 132,068 汉字 ÷ 480 ≈ 275 分钟 ≈ 4 小时 35 分；**328 页 ÷ 275 分钟 = 每分钟 1.2 页** |
| 为什么错 | ① 这个速度**对任何书都不成立**，更不用说要停下来看代码、核对 API 名、对照配图的技术书；② 它的**分子分母都交代不清**——"480 字/分钟"没有任何口径来源；③ 按本书自己的纪律（写作纪律第 1 条数据三问），**这类数字根本不该写** |
| 修法 | **不是换个系数重算**（换成 200 字/分钟仍是假的），而是**整条去掉**，换成**可数的结构事实** |
| 替换成什么 | `中文 132,068 字 · 配图 39 张 · 代码 180 段 · 表格 270 个` —— 四个都能用一条命令数出来 |
| 落地范围 | HTML 阅读版统计条、外壳 `<title>` 无关处、控制台输出；**PDF 已从新 HTML 重导**（仍 328 页，三形态同源） |
| 全书复查 | 正文、附录、overview、架构说明**均无其他时间估算**（唯一命中"小时+分钟"的是第 14 章讲单位不能混加的教材例子，正确） |
| 技能修复 | ① 本书 `build_html.py` 已改；② **`md-to-html-book` 技能内的同源脚本也同步修正**（否则下一本书会继承同一缺陷），并新增铁律 10；③ `book-studio` 写作纪律新增第 8 条 |

## 8. 作者质疑触发的勘误（第二轮）：PDF 必须有书签

**作者原话**："我的 pdf 不会只是打印版，很多时候可能是在线阅读版，所以得要有书签。"

**复核结论：作者完全正确。** 命中一个我漏掉的根本认识——**我把 PDF 的交付形态定义错了。**

| 项 | 内容 |
|---|---|
| 缺陷 | 生成的 328 页 PDF **书签 0 条**，元数据只有 Chrome 自动带的一个 title |
| 根因 | 我在概念上把这份 PDF 当成"打印件"，于是只关心纸张相关的事（A4、页码、色带不着色反白）。**而实际使用场景里，读者多数是在在线阅读器/预览器里读它**——那样一份 328 页没有目录树的书，只能一页页翻 |
| 命名也带偏 | 文件名叫 `…·打印版.pdf`，这个命名本身就在暗示"它只用于打印"，进一步固化了错误的形态定位 |
| 修法 | ① 注入 **445 条三层书签**（27 篇/章 + 218 节 + 200 子节）；② 补齐**元数据**（title / author / subject / keywords / creator）；③ **改名 `<书名>.pdf`**，去掉"打印版"三字 |
| 技术要点 | Chrome 的 `--print-to-pdf` **不会**从 HTML 标题生成 PDF 大纲，必须事后注入 |
| 定位方法（不猜页码） | 从 HTML 取标题权威清单 → 在 PDF 里按**字号带**抓候选（L1 15.5–17.5pt / L2 12.70–12.95pt / L3 10.90–11.15pt；正文 10.5pt、表 9.1pt、代码 8.7pt 均不重叠）→ **排除封面页**（封面 SVG 的副标题会落进 L3，制造假标题）→ 两份清单**逐条比对归一化文本 + 层级，对不上就报错退出** |
| 验证 | 书签 445 条 = HTML 标题 445 条；**逐条回查"该页是否真含该标题"，错误 0 条** |
| 脚本 | `add_pdf_bookmarks.py`（已同步并入 `md-to-html-book` 技能，供后续所有书复用） |

**这次的教训比上一次更深一层**：上一次的"预计阅读时间"是**一个算错的数**；这一次是**一个想错的交付形态**——我没有算错任何东西，我把整份产物的用途理解窄了。两个错误的共同点是：**都通过了全部机械校验**（八项校验、闸门、目检、结构校验、实拍复核，一条不落），因为**它们都不在检查项里**。

**由此新增的检查项**：三形态交付时，PDF **必须**核对两项——① 书签条数 = 标题条数；② 每条书签指向的那页确实含该标题。已写进 `book-studio` 与 `md-to-html-book` 两个技能。

**作者原话**："这个文件中的'结果不对接不上责任'是啥意思？你写完书稿后有回读检查吗？"

### 9.1 第一问：那句话的意思，以及它为什么写坏了

**我想表达的**：出了错，却找不到该负责的环节。前面那个助手给了错答案，但三处错误（信息边界、计算边界、交付边界）**没有一处能归到"模型不够聪明"头上**——所以换更强的模型不会解决，你得改系统。这正是紧接着那条「核心判断 1」的引子。

**写坏了两个地方**：① 把一整条逻辑压成 6 个字；②「接不上」在中文里首先会被读成"电话接不通"。**读者要先做一次语义解压才能懂，这就是写坏了。**

**已改为**：「一个是**结果错了，却找不到该负责的环节**；一个是**过程越界了，却没有东西拦得住**。」

### 9.2 第二问：**没有。这是我的真实缺口。**

**我做了什么**（都必须说清，因为它们是真实投入的）：

| 检查 | 覆盖 |
|---|---|
| `check_manuscript.py` | 脱敏 / 图片正反向 / SVG-PNG 配对 / 中英间距 / 体例 / 图号连续 / 合稿漏拼 |
| 配图三道闸门 | 配色 / 版式适配 / 数据几何 |
| 配图目检 | **39 张全量读完，不抽查** |
| HTML 结构校验 | 目录链接、重复 id、残留 img、markdown 残留 |
| HTML 实拍复核 | 首屏 / 表格 / 代码 / 配图 / 夜读，五视角 |
| PDF 核验 | 页数 / 纸型 / 图注 / 页码 / 445 条书签逐条回查 |

**我没做的**：**没有把正文通读一遍。** 读过的正文只有：写每一章时看自己的草稿、以及为修「读图指引」对照图看的那几段。

**后果就是那句话活到了 v1.0**：它不含数字、不涉及图片、不涉及体例、中英间距也正常——**八项校验全部通过，因为它语法完全正确，只是读不懂。**

**三轮质疑的共同点越来越清楚**：
1. 第一轮"预计阅读时间" = **一个算错的数**
2. 第二轮"PDF 无书签" = **一个想错的交付形态**
3. 第三轮"这句话什么意思" = **一句写坏的话**

三轮全部通过了当时**全部**机械校验。结论不是"校验没用"，而是：**机械校验守住的是"已经想到的规则"；没想到的维度，只能靠人或靠作者指出来。**
