## 10:40 同一任务 5 次 Run 的短期上下文回顾（状态：完成）

- 背景：用户根据工作页截图询问“执行记录 5 次”是否等于 5 轮对话，以及后续 Run 是否遗失了前文工作目标。
- 变更内容：只读检查本机 `betterwork.db` 中同一 Task、Session 的 5 条 Run、事件、历史重放记录与 Artifact 登记；按 GATE-0 顺序查看 `/tmp/betterwork-dev.log`，未修改产品数据或代码。
- 关键发现：5 条记录对应 5 次用户提交 / Run（1 次模型连接失败、4 次完成），不严格等于 5 组完整问答，因为每次 Run 内含多条助手消息和工具事件。首次失败 Run 的原始目标没有进入下一次安全历史重放；第二次“请继续”的 Run 因此无历史轮次可重放。第三次长 Run 的历史对在下一轮被 `history-budget` 拒绝；第四次状态查询只被后续 Run 重放，第三次仍因 `history-budget` 被跳过。5 次 Run 的长期记忆选择预算均为 0，且没有记忆读取行。
- 结论：数据支持“同一 Task 跨 Run 的短期对话上下文断续”这一现象。已存储的 Run 记录不等于每次模型请求都能看到全部历史；本例至少有“失败 Run 不重放”和“长历史对超预算”两个可定位断点。日志未包含这几次模型请求的完整上下文，不能仅凭本地记录断定模型服务端收到的确切消息数组。
- 测试证据：SQLite 使用 `-readonly` 查询；`run_memory_contexts.replay_json` 对第二次为空、第四次将第三次标为 `replayed:false / history-budget`、第五次将第四次重放而将第三次标为 `history-budget`；Artifact 表仅有第五次 Run 登记的 PPTX。未运行自动化测试。
- 相关文件：`docs/logs/2026-10-05.md`、`apps/desktop/src/main/services/run-service.ts`、`apps/desktop/src/main/services/run-history-policy.ts`、`apps/desktop/src/main/services/memory-recall-service.ts`、`docs/development/memory-contracts.md`。

### 10:56 关于“5 轮对话”的定义补充

- 纠正口径：5 条 Run 就是同一 Task / Session 下 5 次用户提交各自对应的执行记录；按产品对话理解，可称为一个任务中的 5 轮提交。首轮虽连接失败，仍是一次已提交的轮次。此前“不严格等于 5 组完整问答”只说明首轮无成功回答、Run 内含多个事件，不应让人理解成不是同一任务的多轮对话。
- 设计核对：领域模型把 Task 定义为一项工作、Session 定义为围绕该任务的连续协作上下文、Run 定义为一次 Agent 执行；ADR-0008 明确专家持续承担同一任务，ADR-0014 明确暂停后继续由新 Run 承接。每轮独立 Run 用于记录执行状态、固定本轮上下文与授权并支持取消和审计。
- 发现的设计缺口：本例 `tasks.goal` 保存了完整原始目标；当前 `RunService.buildPreviousMessages` 只装配记忆块、安全重放的历史消息和本次材料清单，没有把 `Task.goal` 作为稳定任务简报单独传入。因此首轮失败、又没有已完成历史可重放时，下一轮模型虽处于同一 Task，却看不到持久化的原始目标。现行安全历史重放契约是在后续补入的受限机制，无法覆盖失败轮和超预算整轮；这属于上下文连续性设计/实现缺口，不是 Task / Session / Run 划分本身错误。
- 下一步判断：应先把“每个新 Run 必须继承哪些任务目标、用户修订、进度和阻塞状态”写成明确产品/架构契约，再评估实现；本次只分析，未改产品设计或代码。
