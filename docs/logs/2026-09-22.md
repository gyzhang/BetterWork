## 12:35 Work-centered memory design discussion (status: complete)

- Background: The user asked for a stronger memory design suited to BetterWork's knowledge-worker audience and artifact-first product goals.
- Changes: Inspected product and memory documents and delegated a read-only assessment of implemented memory capture, persistence, selection, run injection, UI, and feedback sources. No application code, roadmap, or accepted design was changed.
- Findings: Scoped, revisioned storage, manual confirmation, run injection, and management UI exist. Automatic candidate extraction and learning from accepted corrections are absent. Current selection uses scope, validity, recency, and budgets rather than task-content relevance; the accepted ADR's content-matching description is not evidence of implemented retrieval.
- Proposed direction, pending user review: Build a work-continuity loop around preferences, workspace decisions, reusable methods, and source-linked delivery experience. Prioritize correction-to-memory suggestions, a source-backed workspace brief, and relevant, inspectable reuse in subsequent tasks. Reuse existing scopes and revisions; keep temporary task state outside long-term memory.
- Proposed safeguards: Inferred memories remain candidates until confirmed; current instructions and selected materials take precedence; source access and workspace isolation apply before recall; stale or conflicting facts require review. Memory never grants tools or material access. Usage traces demonstrate context inclusion, not guaranteed influence on an output.
- Validation evidence: Static document/code inspection only. No tests, application launch, browser verification, or runtime database inspection was performed. Proposed acceptance scenarios cover a corrected next-period report, current-period material precedence, cross-workspace isolation, and exclusion after memory removal, including historical context replay.
