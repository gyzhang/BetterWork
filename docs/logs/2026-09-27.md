## 05:02 修「抽屉里的下拉点不动」：浮层层级必须高于模态（状态：完成，待光哥窗口回看）

- 背景：光哥回看昨晚四刀（Field／Tabs／Badge／EmptyState）时给出第一个真实缺陷——设置→模型的编辑抽屉里「模型角色」下拉点了没反应。截图里 chevron 已经翻向展开态，说明状态切了，菜单没露出来。
- 变更内容：
  - **层级倒挂**：`--z-popover: 12` 压在 `--z-modal-backdrop: 19` 之下，菜单 portal 到 `document.body` 后被模态面板整个盖住。档位表改成 `--z-modal-backdrop: 19` < `--z-popover-backdrop: 20` < `--z-popover: 21`，`:root` 注释与 docs/10 §9.11 的「两处有意改变」同步改写为「菜单类浮层一档高于模态」。
  - **Esc 双关**：`PopoverMenu` 在菜单里 `preventDefault` 了 Esc，但事件继续冒泡到 window，`Modal` 的订阅照旧关闭模态——按一次 Esc 会连抽屉一起关。改为 `Modal` 见到 `event.defaultPrevented` 就交给上一层。
  - **Tab 抢焦点**：菜单在面板之外，`useOverlaySemantics` 的「焦点被移出面板就拉回」把键盘用户从菜单里拽走。改为焦点落在带 `data-overlay-layer` 的浮层内时不接管；该属性由 `PopoverMenu` 根节点声明，两个基座之间不互相 import 类名。
  - 护栏新增一条：`--z-popover` 与 `--z-popover-backdrop` 都必须大于 `--z-modal-backdrop`（jsdom 算不出层叠，只能在档位表上锁死）。
- 关键决策：**修在基座的交接处，不给抽屉开特例**。页面里再写一遍「这个下拉在模态里要抬高」就等于承认基座之间不能组合；层级、Esc、Tab 三件事全部收在 `Modal` 与 `PopoverMenu` 的接口上（`defaultPrevented` 与 `data-overlay-layer`），页面零改动。
- 教训：**「模态盖住浮层」这条层级直觉在有嵌套交互的表面里是反的**——写档位表时按「谁更重要」排，没按「谁可能被谁调用」排。判断依据应是：模态内允许出现的最上层表面，必须高于模态本身。
- 测试证据：`Modal.test.tsx` 新增「模态内的菜单类浮层」3 条（抽屉里点 `FieldSelect` 能展开且菜单挂在 `document.body`、焦点在菜单里时 Tab 不抢、Esc 只关菜单不关抽屉），三条都做过变异验证——分别删掉 `data-overlay-layer` 早退与 `defaultPrevented` 早退后各自转红，恢复后 14/14 绿；层级护栏把 `--z-popover` 改回 12 立刻转红。护栏 44 条全绿。人工验收：光哥窗口里重试「模型角色」下拉。

## 05:36 圆角与密集高度并档收口：150 处裸值上档，护栏改零容忍（状态：完成，待光哥窗口回看）

## 09:14 知识页反馈通道收口 ＋ 最近作业可清空（状态：完成，待光哥窗口回看）

- 背景：光哥在真实界面里点了一次「检查当前列表来源 (9)」，同一件事出现三个表面——最近作业行、消息中心通知、页面底部一条不会消失的绿色横幅。他只质疑了后两个问题：横幅为什么不消失，以及「最近作业」要是做上 180 次怎么办。查库确认那次作业在 `notifications` 表里确实有一条 `success / 来源检查完成（9/9）`（08:12:59），也就是**落库通知合法、页面横幅非法**。
- 根因：`use-knowledge-library.ts` 用单一 `message` 字符串同时装成功、信息与失败，`KnowledgeView.tsx` 把它渲染成不带 `.error` 的常驻 `.inline-message`——§11.5.1 与知识契约 §12 都明文禁止「列表页顶部的持久结果横幅」；它也没有任何清除路径，只有下一次动作覆盖。全局 `ToastHost` 的「同页抑制」（`App.tsx:1200-1205`）让知识页收不到右下角浮层，于是页面自己补了一条，补错了通道。
- 变更内容：
  - 钩子通道一分为二：`error`（内联、可行动、随下一次动作清）与 `toast`（复用 `useTransientToast`，4s／6s 自消、不落库）。38 处 `setMessage` 逐条判归类——提交作业、集合增删改、分类保存、启用/停用语义检索、取消请求等走 `toast`；检索失败、保存冲突、同名集合等走 `error`。`KnowledgeView` 里页面自建的第二个 toast 状态与 `KnowledgeToast` 类型删除，动作结果统一交给钩子那条通道；`detailError` 补上 `.error` 态。
  - **作业成功不再在页面播报**：结果的两份合法投影是「最近作业」那一行与消息中心的落库通知；部分完成与失败例外，留内联并指向「查看条目／重试」。
  - 最近作业可清空：协议新增 `knowledge:clear-jobs`（无输入、返回 `{ cleared: true }`，与 `notification:clear` 同形），`KnowledgeJobStore.clearTerminal()` 只删已收口作业（条目外键级联、`retry_of_job_id` 置空），排队与运行中的作业不在范围内；服务、IPC、preload 逐层接上。界面在折叠组标题右侧加「清空」（`danger-text`）＋ `ConfirmationDialog`，与消息中心同款交互；确认后本地列表与已展开的条目一起收掉，成功走自消提示。
  - 护栏新增「反馈通道纪律」两条：渲染层出现不带 `.error` 的 `className="inline-message"` 即失败；`.inline-message` 不得长出 `.error` 以外的配色变体。
- 关键决策：**180 次作业不会变成 180 行**——列表本来就只取最近 10 条（`RECENT_JOBS_LIMIT`），要补的是「看过就能清掉」而不是分页；清的是记录，资料、修订、索引与原件一律不动，这条写进确认框文案与契约 §12。
- 教训：文档写「已收口」不等于契约被遵守——`.inline-message` 只保留错误态早在评估里立了条款，但护栏只在 `SkillsView.test.tsx` 里做了一次 DOM 断言，换个页面就长回来了。同类约束必须落在跨文件的结构护栏上，不能留在单页测试里。
- 测试证据：服务层新增 1 条（只删终态、进行中作业与已索引资料不受影响、二次清空返回剩余条数）；钩子新增 2 条（清空走链路并给自消提示、失败留内联且不假装清掉）；界面新增 1 条（标题上的「清空」先出确认框、不切换折叠）；两条新护栏各用探针验证（写回 `className="inline-message"` 与 `.inline-message.success` 后对应断言转红）。`npm run verify` 退出码 0：lint／format:check／typecheck／`npm test` 144 文件 1400 测试／build。人工验收：知识页跑一次来源检查与关键词重建，确认页面不再留常驻横幅、结果看作业行与消息中心，再点「清空」看确认框与进行中作业是否幸存。
