## 01:11 B00-2 指令注入顺序与运行约定解耦（状态：完成）

- 背景：B00-1 让一次 Run 可以绑定多个 Skill，但运行约定段（`算台运行约定：...`）仍是一整段硬编码字符串，里面混着 `svg-export` / `template-merge` / `pptx-validate` 等 PPT 样本专属口径。任何带命令的 Skill 都会被告知一套并不存在的命令，模型照着编造调用。本卡把通用层与预设层拆开。
- 变更内容：

  - `apps/desktop/src/main/services/ppt-generation-preset.ts`：PPT 预设实现 `runtimeConventions`，按命令 id 集合条件输出（svg-export + template-merge 的 attempt 合并口径、template-merge 的 assets/ 公司模板口径、pptx-validate 的 artifact 登记闸门）。
  - `apps/desktop/src/main/services/run-service.ts`：`resolveSkillBindings` 改为按 `snapshot.revision.contentHash` 查适配预设，取回 `runtimeConventions` 后交给 `composeRuntimeConvention` 组装；正文为空的 Skill 不再注入空 system 段。
  - 测试：`skill-runtime-conventions.test.ts`（5 项，含泄漏锁——通用层不得出现 `svg-export` / `template-merge` / `pptx-validate` / `assets/` / `公司模板`）、`ppt-generation-preset.test.ts`（新增 4 项 runtimeConventions 测试）、`agent-engine.test.ts`（新增两技能各一条 system 段、顺序即用户选择顺序、互不串内容）。

- 关键决策：
  - **通用层与预设层拆成两个文件/接口，而不是在 RunService 内部分支。** 前者是唯一持有通用契约的地方，后者由适配预设按 `contentHash` 匹配后提供。这样即使未来新增样本预设，通用层也不会被样本词汇污染；测试可以直接断言「通用层不含样本词汇」作为回归锁。
  - **命令表每项带 `bindingId` 与 `skillName`，而不是只在段落开头说一次。** 多绑定下模型在推理 `skill_execute` 调用时，需要逐条命令寻址到正确 Skill；只在段落开头说一次不够，模型容易拿错 `bindingId`。
  - **正文为空的 Skill 不注入。** `readSkillInstruction` 读 SKILL.md 后 `stripFrontmatter`，若结果为空字符串，agent-core 的 `buildSkillMessages` 仍会产出一条只有标题的 system 段。在 RunService 层过滤更干净。
  - **不在 RunService 加 model seam 做「Fake Provider 断言 messages 结构」。** agent-core 已有 `recordingModel`，B00-2 新增的 agent-engine 测试直接断言两技能各一条 system 段、顺序正确、互不串内容。RunService 到 agent-core 是 plain array pass-through，无分支，纯函数测试已足够。
- 教训：
  - **`indexOf` 跨字符串比较无意义。** 我写 `expect(systemMessages[1]?.content.indexOf('PPT 专属口径')).toBeLessThan(systemMessages[2]?.content.indexOf('研究助手口径'))`，两个 `indexOf` 返回的是各自字符串内的位置，不可比。改为断言数组顺序 + 互不包含对方内容。
  - **`toContain` 不能用在 `undefined` 上。** `adapter.runtimeConventions?.(new Set(['svg-export']))` 返回 `undefined`（因为 `svg-export` 单独不触发任何预设口径），`expect(undefined).not.toContain('attempt')` 报错。改为 `toBeUndefined()`。
