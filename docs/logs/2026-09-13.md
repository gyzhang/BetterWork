- 关键决策：
  - **上限 6 写进协议常量而不是只写文档**：注入预算与 chip 条可读性都是可被绕过的约束，只有 Schema 拦得住。
  - **去重放在 Schema 层**：重复 `skillId` 会让同一份指令注入两次、绑定快照无法回溯，属于协议非法而非业务偏好。
  - **绑定快照不再容忍伪造 ID**：旧 `resolveSkillInstructions` 在 `getBinding` 返回空时静默回退到当前修订，等于允许一个不存在于库里的 `bindingId`；现在缺快照直接失败。两个原先靠伪造 `createBinding` 存活的测试改为委托真实的 `SkillExecutionService`。
  - **不新增 `ActiveRun.bindingIds`**：工具桥接的权威判据是 SQLite 里的 `binding.run_id`；再存一份内存列表只会在长任务中与库漂移。撤销级联只需要 `skillIds`。
  - 隐式继承的删除同时写成了回归测试的正向断言（后续 Run 拿不到绑定、停用技能不连带无关 Run、无绑定 Run 不被误取消），而不是只删代码。
- 教训：
  - **拆「校验」与「建快照」两步会静默丢掉前置检查。** 我先按 `resolveBindingIds` / `resolveSkillInstructions` 拆分，`resolveBindingIds` 用 `if (!execution) return []` 短路，导致没有执行服务时启用/信任检查一个都不跑——两个既有测试立刻红。改为单次遍历内「先整体校验、后逐个落快照」才成立。跨层重构时不能只保证新路径正确，要逐条问「旧代码的每个分支现在由谁承担」。
  - **同一遍历里失败要回滚到零。** 逐个处理时第一个技能已经把 `run_skill_bindings` 写进去了，第二个才报未信任，于是失败的 Run 带着半截授权记录。ADR 的「整个 Run 不启动」必须先校验完再落盘，并补断言 `listBindingsByRun(runId)` 为空。
