# UI/UX 体系与落地计划

## 1. 文档目的

本文定义算台 BetterWork 的界面体验基线，是 Renderer 开发、视觉验收和交互取舍的真相源。

UI Foundation 重构已完成并通过验收：主题 Token 契约、三种外观模式与四套成对色系、统一应用外壳与页面骨架、任务工作区、可完全收起的上下文面板、独立的模型设置空间均已落地。本文自此是**生效中的规范**，而不是待执行的重构计划。

后续界面工作按本文规范增量进行：新增页面必须复用 §8.3 的统一页面骨架，新增颜色必须先进 §9.3 的 Token 契约并当场补齐全套色系 Variant。第 3 节保留为重构前的问题记录，用于说明这些规范的由来，不再描述当前界面。

## 2. 参考与独立性

### 2.1 参考 LobsterAI

重点借鉴：

- 安静、克制、适合长时间工作的桌面视觉气质
- 清楚的应用层导航、任务层操作和上下文层信息分工
- 低学习成本的入口与渐进披露
- 统一的主题变量、组件状态和紧凑但不拥挤的密度
- 设置页面的信息组织与模型配置心智

不复制：

- OpenClaw 的产品概念、引擎结构和历史业务状态
- 与 BetterWork 目标无关的 IM、定时任务和复杂插件入口
- 任何仅凭表面相似而直接搬运的源码或样式

### 2.2 参考 ClawBible Desktop

ClawBible Desktop 继续作为模型接入、Agent、工具、知识和 Office 能力的工程经验来源，不作为 BetterWork UI 的视觉母版。

## 3. 现有界面的主要问题

现有界面的问题属于体系问题，而不是局部美化问题：

1. 三栏长期同时展开，导航、对话和执行时间线互相争夺注意力。
2. 原始运行事件被当成主要内容，界面更像 Agent 调试器，而不是知识工作者的工作台。
3. 左侧深色区域、中间暖色区域与右侧工具面板缺乏统一的表面和层级关系。
4. 字号、间距、圆角、边框和状态色没有稳定标尺，页面密度忽松忽紧。
5. 模型配置挤在临时弹层中，模型列表、编辑表单、角色默认值和连接状态没有清楚分层。
6. 任务结果缺乏足够视觉地位，Artifact 仍像消息附件，而不是可继续工作的成果。
7. 空状态、加载、运行、取消、错误和完成状态缺少完整一致的反馈设计。

因此不能通过继续添加卡片、阴影或渐变解决，必须先重建信息架构和设计系统。

## 4. 产品体验定位

算台的 UI 应呈现为：

> 沉静、可信、克制、有温度的知识工作台。

视觉隐喻取自“纸张、墨色、青玉”：

- 纸张提供适合阅读、分析和创作的安静底色。
- 墨色表达内容和工具的可靠性。
- 青玉色用于激活、选择、进度与关键动作。
- “算盘”只保留在品牌图标和少量秩序感中，不把古典纹样装饰化地铺满界面。

避免通用 AI 产品常见的高饱和蓝紫渐变、发光星芒、大面积玻璃拟态和无意义动态效果。

## 5. 六条设计原则

### 5.1 Task-first

用户首先看到自己正在完成的工作，而不是模型、工具或执行框架。所有技术能力都服务于 Task。

### 5.2 Artifact-visible

研究报告、表格分析、Word 和 PPT 是一等对象。成果应拥有独立预览、版本、导出和继续修改入口。

### 5.3 Progressive disclosure

默认只显示当前决策需要的信息。工具细节、完整过程、模型高级参数和原始事件按需展开。

### 5.4 Calm density

界面紧凑但不拥挤，信息密度来自清楚的结构，而不是缩小字体和压缩点击区域。

### 5.5 State is visible

长操作必须显示正在做什么、已经完成什么、是否需要用户决定，以及如何停止或恢复。

### 5.6 Chinese-first

中文菜单、标点、换行和长文阅读优先设计，同时保证英文资料、数字和文件名的可读性。

## 6. 信息架构

### 6.1 应用级导航

当前固定入口（已落地）：

- 工作：新建与最近 Task
- 成果：Artifact 集合与最近输出
- 知识：本地资料与索引状态
- 设置：模型与能力、搜索、外观、通用

设置分区说明：「搜索」随联网搜索能力新增（见 [ADR-0007](adr/0007-search-engine-config-and-web-search-tool.md)）；「通用」当前为占位，工作目录、语言、数据与更新设置尚未建设，原计划的独立「数据」分区并入「通用」。

后续入口：

- 专家：预置人格、记忆、知识范围和 Skill 的组合
- 能力：Skill 与套件的发现和管理

不把模型、Tool、调试日志作为一级导航。

### 6.2 任务工作区

采用可折叠三层结构：

```text
应用导航 | Task 主工作区 | 上下文面板
```

- 左栏负责去哪里：应用入口、最近任务和设置。
- 中栏负责做什么：任务协作、确认、编辑和主要内容。
- 右栏负责参考什么：过程、资料和成果，默认按场景出现并允许收起。

右栏不是永久执行日志。没有过程、资料或成果需要查看时，应自动收起，把空间还给主工作区。

### 6.3 设置空间

设置是独立页面，不附着在输入框或任务消息中。设置左侧为类别导航，右侧为当前设置内容；编辑复杂配置时使用侧边 Sheet 或对话框。

## 7. 核心页面

### 7.1 首页 / 新建任务

目标设计：

- 一句明确任务输入作为视觉中心
- 提供研究、分析文件、编写文档、制作演示四个意图入口，而不是功能仪表盘
- 最近任务和最近成果位于次级区域
- 模型选择只显示当前工作模型，详细配置跳转设置

当前实现状态：

- 无任务时中栏显示欢迎视图——抽象点线饰条、eyebrow「算台 · 知识工作台」、品牌主张「以我所知，成我所作」（全系统唯一展示字体位置）与一句引导正文。视觉中心是品牌主张，不是任务输入框。
- Composer 固定在中栏底部（与对话列同宽，见 §8.3），含工作区行、多行输入、页脚（当前工作模型 + `⌘/Ctrl ↵` 快捷键提示 + 开始/停止按钮）。
- 意图入口只有两个教学示例按钮（计算一组数据、读取一份资料），点击后填入输入框。研究 / 分析文件 / 编写文档 / 制作演示四个产品意图入口未落地，应在 Phase 1 研究工作流可用时替换教学示例。
- 最近任务在左侧导航栏的「最近任务」区，按 Task 而非 Run 展示；首页内没有独立的次级区域。
- 当前工作模型只在 Composer 页脚以文本呈现，不可就地切换；配置与切换均在设置页。

### 7.2 Task 工作区

目标设计：

- 顶部：任务标题、当前模型、运行状态和少量上下文动作
- 中部：用户目标、Agent 回应、确认点和可编辑内容
- 底部：可扩展 Composer，支持附件、发送和停止
- 运行活动在回复内部以分组摘要呈现，例如“查阅 5 个来源”“分析工作簿”“正在生成报告”
- 右侧可切换“过程 / 资料 / 成果”，并记住用户对当前 Task 的展开状态

当前实现状态：

- 顶部页头带只承载 eyebrow「工作」、状态化标题（无任务时「开始一件工作」，有任务时「继续完成任务」）与右侧「收起/查看上下文」开关。任务标题不在页头带，而在左侧栏「最近任务」中以选中态呈现。
- 当前模型 chip 曾放在页头带，2026-09-04 主动移除：页头带是全局贯通的拖拽区，放易变的状态芯片会破坏各页标题坐标一致性。当前工作模型改在 Composer 页脚呈现。
- 运行状态在右栏「过程」页签的活动摘要中呈现（状态点 + 文案 + 阶段计数），页头带不重复。
- 中部已有用户目标与 Agent 流式回应；确认点依赖尚未定义的审批事件，可编辑内容目前只有成果的修订编辑器（在成果页）。
- 底部 Composer 支持多行输入、`⌘/Ctrl ↵` 提交、发送/停止切换与工作区选择；**不支持附件**。
- 右侧三页签已落地，但展开状态**未按 Task 记忆**：`contextOpen` 只在会话内保持，发起新运行时强制展开，切换任务不恢复该任务上次的展开状态；侧栏折叠状态则已持久化到 `localStorage`。

### 7.3 Artifact 预览

- 成果在任务中以明确卡片出现，点击后进入主区域预览
- 提供版本、导出、继续修改和返回任务
- Word、PPT 和 Excel 使用各自适合的预览工具栏，不强行共用一套聊天卡片

### 7.4 Knowledge 知识库

- 资料集合、文件列表、解析与索引状态
- 资料详情显示来源、摘要、更新时间和可检索状态
- 不把向量、Chunk 等实现术语作为默认用户语言

### 7.5 模型与能力设置

- 模型列表按文本、视觉、嵌入角色筛选
- 每行显示名称、Provider、模型标识、连接状态和默认角色
- 新增与编辑使用 Sheet；常用字段先显示，高级参数折叠
- 明确区分“已保存”“连接成功”“已设为默认”三种状态
- API Key 始终掩码显示，测试连接有独立反馈和重试动作

### 7.6 专家、Skill 与套件

当前只预留导航和组件语言，不在 UI Foundation 阶段实现业务。未来沿用同一对象结构：简介、适用任务、绑定能力、知识范围、最近使用和管理动作。

## 8. 桌面布局规范

### 8.1 尺寸

| 项目 | 规范值 | 实装现状 |
| --- | --- | --- |
| 窗口 | — | 默认 1380×860，最小 980×640 |
| 顶部标题栏 | 不单独设栏 | 无独立标题栏元素。窗口拖拽与双击最大化由两处承担：中栏 70px 页头带（§8.3）、侧栏顶部 40px 拖拽带；设置页与上下文面板另有各自的顶部拖拽区。标题带以下的内容区不承载任何窗口行为 |
| macOS 红绿灯 | 不得与侧栏内容重叠 | `trafficLightPosition` 固定在 (16, 18)，横向占位约 16–68px |
| 左侧导航 | 默认 240px，可在 220–320px 调整，折叠后 **88px** | 默认 240px 已落地；折叠后 88px 已落地。宽度拖拽调整未实现。折叠宽度原为 56px，因装不下 macOS 红绿灯（绿灯溢出到主工作区）于 2026-09-05 改为 88px——按红绿灯实际占位 68px 加边距倒推 |
| 窄屏自动折叠 | 与用户折叠同宽 | **残留不一致**：`max-width: 960px` 的自动折叠仍是 60px，与 88px 的手动折叠宽度不一致，需统一为 88px |
| 中央内容 | 版心统一 860px（§8.3） | 已落地：`min(860px, 100% - 48px)`，窄窗口两侧各留 24px。`body` 最小宽度 760px（窄屏降至 620px），原「最小 640px」的表述以此为准 |
| 右侧上下文面板 | 默认 380px，可在 340–440px 调整，可完全收起 | 默认 380px 已落地；收起后整体卸载、不留残条已落地。宽度拖拽调整未实现；`max-width: 1279px` 时转为 360px 覆盖式浮层 |
| 主要点击区域 | 不小于 32px；高频操作 36–40px | 主 CTA 与页头操作为 32–36px，达标。**未达标处**：Composer 工作区行的文字按钮 25px、上下文页签 29px、模型行内动作与通知面板动作约 25px、证据「原文」按钮约 24px——这些属低频次级动作，如需达标应扩大命中区而不是放大视觉尺寸 |

### 8.2 响应规则

- 大于等于 1280px：允许三栏同时显示
- 960–1279px：右栏作为覆盖式 Drawer，左栏可折叠
- 小于 960px：左栏默认折叠，右栏覆盖显示，保证主工作区优先
- 窗口过窄时不缩小正文换空间，改用折叠与覆盖

实装状态：断点已按 `max-width: 1279px` 与 `max-width: 960px` 落地，正文不随窗口收窄而缩小（版心用 `min()` 收，`body` 有最小宽度）。两处与规范有差距：窄屏是把左栏**强制**变为图标栏，不读取用户的折叠偏好，因此宽屏下手动展开的状态在窄屏不生效；覆盖式右栏没有点击外部关闭的背板，只能通过页头带的「收起上下文」开关关闭。按 §8.3，右栏只在工作视图渲染，成果、知识、设置视图不预留空栏。

### 8.3 统一页面骨架

所有主内容页（工作、成果、知识）共用同一页面骨架，由两个 layout 层组成：

- 页头带（page header）：贯穿中栏的同一横带——高度固定 70px、左缘 28px、同底部分隔线、同一拖拽区行为；左侧固定放「返回键 + eyebrow + 页标题」，右侧固定放本页操作区。标题与返回键在所有页面坐标一致，切换导航时不发生跳跃。右侧上下文面板展开时，其顶部区（面板标题行 + 页签行）总高必须等于页头带高度 70px，分隔线与页头带底边构成同一条贯通横线。
- 版心（page body）：统一 860px、水平居中；窄窗口时两侧各留 24px 最小间距。页内说明文字、内容列表、对话消息与输入框全部落在版心内；工作视图的对话列与输入框同宽。
- 上下文面板按场景出现：右栏只在承载任务上下文的工作视图渲染（过程/资料/成果）；成果、知识、设置等无任务上下文的视图不渲染面板，主工作区占满剩余宽度，布局网格不得预留空栏。面板收起后整体移除、不留残条，重开入口固定为页头带右侧操作区的「查看上下文」开关。

实现上以共享的 layout 样式类（`.page-header` / `.page-scroll` / `.page-body`）为唯一来源，页面不得自定版心宽度、页头结构或标题坐标。设置页因保留二级导航布局作为声明特例，其余新增页面一律套用本骨架。

## 9. 视觉系统

### 9.1 外观模型：模式与色系分离

算台从 UI Foundation 起就支持多外观，但不把“浅色 / 深色”和“青色 / 蓝色 / 暖色”等概念混成一个主题列表。外观由两个独立维度组成：

```text
AppearanceMode = system | light | dark
ColorScheme = jade | ink | ocean | sand | ...
ResolvedTheme = ColorScheme[系统或用户选择后得到的 light/dark variant]
```

- 外观模式决定当前使用浅色还是深色，并支持实时跟随操作系统变化。
- 色系决定品牌强调色、表面温度和中性色倾向。
- 每套正式色系必须同时提供浅色和深色 Variant。切换系统明暗时保留同一色系，不发生风格跳变。
- 用户选择应跨启动持久化，并在 React 挂载前恢复，避免启动时先闪现错误主题。

这比把每个主题直接标记为 light 或 dark 更适合长期产品：新增色系不会改变用户的明暗偏好，系统跟随也不会随机落到另一套视觉风格。

### 9.2 首批内置色系

UI Foundation 首批提供四套成对色系：

| 色系 | 定位 | 浅色倾向 | 深色倾向 |
| --- | --- | --- | --- |
| 青玉 `jade` | 算台默认品牌主题 | 暖灰纸面、克制青绿 | 墨绿黑、低饱和玉色 |
| 纸墨 `ink` | 最安静的阅读与写作主题 | 象牙白、近黑强调 | 中性炭黑、灰白文字 |
| 远洋 `ocean` | 冷静、专业的数据分析主题 | 冷白、深海蓝 | 蓝黑、低亮度青蓝 |
| 暖砂 `sand` | 温和的长时间办公主题 | 米白、暖铜点缀 | 棕黑、暗金铜点缀 |

首批不提供任意取色器。任意颜色很容易破坏对比度和组件状态一致性；后续如开放自定义主题，也必须经过 Token 完整性与可访问性校验。

### 9.3 主题 Token 契约

组件只能消费语义 Token，不直接绑定某套主题的色值。最小契约包括：

- 品牌：`brand`、`brand-hover`、`brand-soft`、`on-brand`
- 画布与表面：`canvas`、`surface`、`surface-raised`、`overlay`
- 文本：`text-primary`、`text-secondary`、`text-muted`、`text-on-dark`
- 边界与输入：`border`、`border-subtle`、`input-border`、`focus-ring`
- 状态：`success`、`warning`、`danger`、`info` 及其柔和背景
- 专用区域：`sidebar`、`composer`、`selection`、`scrollbar`
- 图表：一组经过对比度校准的有序数据色，但不替代状态色

每套 Variant 必须完整实现契约，禁止组件用 `#fff`、`black` 或仅针对 `.dark` 的局部补丁绕过主题系统。圆角、字体和密度属于独立 Design Token，不随色系任意变化。

落地现状：四套色系 × 明暗共 8 个 Variant 已完整定义在 `renderer/src/styles.css` 顶部的 `:root[data-theme][data-scheme]` 选择器组中，由 `appearance.ts` 在 React 挂载前写入 `data-theme` / `data-scheme`，并同步 Electron 标题栏背景与符号色。

契约缺口与已知违规：

- `border-subtle` 尚未定义，当前所有分隔与控件边界共用 `border`。
- 图表数据色尚未定义（无图表 Artifact，属 Phase 2 前置）。
- `text-on-dark` 已在 8 个 Variant 中定义但零消费，属死 Token；应在被使用前删除或找到正确消费点。
- **违规**：通知未读徽标 `.notification-badge` 硬编码 `color: #fff`，违反本节契约。应新增 `on-danger` Token（或复用 `text-on-dark`）并当场补齐 8 个 Variant。
- 阴影与遮罩背板仍写作 `rgba(0, 0, 0, …)` 字面量，未 Token 化；深色 Variant 下阴影强度理想上应低于浅色，当前无法按主题区分。
- 外观模式与色系预览卡（`.mode-preview` / `.scheme-preview`）内的色值是**刻意硬编码**的：它们描绘的是各色系自身的样本，不能跟随当前主题变化，属本节的明确例外。

### 9.4 主题作用域

外观切换覆盖应用外壳、设置、Markdown 阅读、图表和系统标题栏，但不能污染用户成果本身：

- Word、PPT、Excel 与图表 Artifact 保留自身模板和配色。
- Artifact 预览放在中性画布或页面框中，清楚区分“应用主题”和“文档主题”。
- 代码高亮、Markdown、图表和未来第三方组件通过 Theme Adapter 响应明暗变化。
- Electron 标题栏、启动画面、滚动条、系统菜单和浮层必须与当前主题同步。

### 9.5 外观设置交互

“设置 → 外观”包含：

1. 外观模式：浅色、深色、跟随系统，使用三个可识别的布局预览卡。
2. 色系：显示浅色与深色并列的小型色板预览，选择后即时应用。
3. 字号与密度：字号进入 UI Foundation；紧凑密度可以预留但首版不开放。

切换应即时预览并持久化，不依赖“保存全部设置”。如果应用主题失败，恢复上一个有效选择并说明原因。

实装状态：第 1、2 项已落地——三个模式预览卡与四套色系色板预览均为纯 CSS 样本，选择后即时应用并写入 `localStorage`（键 `betterwork-appearance`），跟随系统时监听 `prefers-color-scheme` 变化且保留用户所选色系。第 3 项字号设置**未落地**，紧凑密度按原计划不开放。主题应用失败后的回退与说明也未实现：当前 `parseAppearance` 对非法或损坏的持久化值静默回落到默认外观（system + jade），不向用户说明原因。

### 9.6 色彩语义

青玉（jade）浅色 Variant 的落地基线：

| Token | 色值 | 用途 |
| --- | --- | --- |
| `canvas` | `#F6F7F5` | 应用背景 |
| `surface` | `#FFFFFF` | 内容与浮层表面 |
| `surface-raised` | `#F0F2EF` | 抬升表面与次级容器 |
| `sidebar` | `#EDF0ED` | 导航表面 |
| `text-primary` | `#1D2420` | 主文本 |
| `text-secondary` | `#68736C` | 次要说明 |
| `text-muted` | `#8A948E` | 时间、路径与弱提示 |
| `border` | `#DBE2DC` | 分隔与控件边界 |
| `input-border` | `#CBD6CE` | 输入控件边界 |
| `focus-ring` | `#4D8A78` | 键盘焦点环 |
| `brand` | `#2F6B5D` | 主要动作与选中态 |
| `brand-hover` | `#25594D` | 主要动作悬停 |
| `brand-soft` | `#E1EEE9` | 轻选中与进度背景 |
| `selection` | `#D8EBE3` | 列表与导航选中背景 |
| `success` | `#2F7A58` | 成功状态 |
| `warning` | `#A86E1B` | 警告与待确认 |
| `danger` | `#AD5149` | 错误与危险动作 |
| `info` | `#3D6B8C` | 提示与中性通知 |

四个状态色各自带一个 `*-soft` 柔和背景变体，用于通知、Toast 与内联提示的底色。

深色 Variant 不是浅色的反转：青玉深色以 `#121813` 为画布，用低对比墨绿灰建立表面层级，并单独校准正文、边框与悬停对比度（例如 `brand` 在深色下提亮为 `#65A990` 以保持可用对比度）。

全部 8 个 Variant（4 色系 × 明暗）的完整取值以 `renderer/src/styles.css` 为唯一来源；本文只固定 Token 语义与青玉基线，不重复罗列其余色系色值。

颜色不能单独承担状态含义，必须同时配合图标、文本或形状。

### 9.7 字体

使用系统字体栈，优先适配 macOS 与 Windows 中文字体。正文基线为 14–15px，不允许用 9–10px 字体承载产品信息。全系统唯一使用展示字体的位置是欢迎页口号「以我所知，成我所作」，用 `Georgia + 楷体（Kaiti SC/STKaiti/KaiTi）` 衬线栈；其余所有界面文字（含各级页面标题、成果标题与成果内标题）一律使用系统默认字体栈，不用宋体或其他衬线承载展示文字。

推荐字号层级：

- 12px：时间、路径和非关键注释
- 14px：控件、列表与常规 UI
- 15–16px：正文与对话
- 20px：页面标题
- 28px：欢迎页主标题

正文行高 1.6 左右，长文预览行高 1.7 左右；数字状态可使用等宽数字，不把代码字体用于普通说明。

落地现状与偏差：字号层级中的 15px 正文、20px 页面标题、28px 欢迎页主标题均已按规范落地，展示字体也确实只用在欢迎页口号一处。但小字号一档存在**系统性偏差**：`styles.css` 中有 16 处 `10px`、2 处 `9px`、1 处 `font: 10px`，另有 29 处 `11px`——而本节把 `12px` 定为时间、路径和非关键注释的下限。

按性质区分：

- **可豁免**：格式徽标（成果列表的 `MD`、资料卡的 `MD/PDF/DOC/TXT`）与品牌字标（侧栏 `BETTERWORK` 副标）属图形化标识，不是正文，可保留小字号。
- **属违规**：执行记录时间、证据来源路径与摘录、活动阶段时间、版本历史时间、通知时间、上下文页签等**承载产品信息的次要文本**大量使用 10–11px，违反本节与 AGENTS.md、`.qoder/rules/betterwork-ui.md` 的「禁止用 9–10px 小字号换取空间」铁律。正确解法是按规范提升到 12px 并用折叠、覆盖或响应式重排换空间，而不是继续压字号。
- **属死声明**：成果版本来源列表的图标容器仍写着 `font-size: 9px`，但该处早已改为内联 SVG 图标（尺寸由 `size` 属性决定），声明已无作用，应直接删除。

这项偏差需要一次专项收敛，不应随其他 UI 改动零散修补。

### 9.8 间距、圆角与阴影

- 间距采用 4 / 8 / 12 / 16 / 24 / 32px 标尺
- 控件圆角 6–8px，卡片 10–12px，浮层不超过 16px
- 分组优先使用留白和细分隔线，避免每个对象都套卡片
- 阴影只用于浮层、菜单和拖离画布的对象；普通内容不使用厚重阴影

落地现状：圆角与阴影用途已按规范执行（普通内容不用阴影，浮层与 Toast 才用）；分组以留白和 1px 分隔线为主，未出现「每个对象都套卡片」。间距存在少量偏离标尺的 `3px`（上下文页签、证据列表、执行记录等非导航场景的 `gap`），导航类间距已于 2026-09-05 统一为 4px；剩余 `3px` 应一并对齐标尺。

### 9.9 动效

- 即时反馈：120ms
- 展开与切换：180ms
- Drawer 与大区域过渡：240ms
- 不使用循环发光和无意义等待动画
- 支持 `prefers-reduced-motion`

落地现状：本节**尚未开始实施**——`styles.css` 中没有任何 `transition` 或 `animation` 声明，也没有 `prefers-reduced-motion` 媒体查询。当前所有悬停、选中、页签切换、面板收起与 Toast 出现/消失都是瞬时的。

「不使用循环发光和无意义等待动画」这一条天然满足。补齐动效时应同时落地降级查询，并把时长值提为 Token，避免散落魔法数字；上下文面板与 Toast 属大区域过渡（240ms），按钮与页签属即时反馈（120ms）。

## 11. 关键交互规则

### 11.1 启动与运行

- 发送后输入框保留当前上下文，发送按钮切换为停止按钮
- 第一时间反馈“已开始”和当前阶段，不等待模型首个 token 才响应
- 连续工具事件合并为一个 ActivityGroup，默认显示用户可理解的摘要
- 原始事件只在开发模式或过程详情中查看

当前实现状态：

- 发送后输入框文本被清空，用户目标以消息块形式保留在对话流顶部——「保留当前上下文」指任务上下文而非输入框文本。发送/停止按钮切换已落地。
- 提交即创建 Run、展开右栏并切到「过程」页签，不等首个 token。已落地。
- ActivityGroup 合并已落地（理解任务 / 处理工作材料 / 整理结果 / 任务完成），但阶段标题的工具映射只覆盖 `calculator` 与 `read_text_file`；`knowledge_search` 与 `web_search` 都退化为通用的「调用工作工具」，无法呈现「查阅 5 个来源」这类具体摘要。新增工具时必须同步更新 `renderer/src/activity.ts` 的标签映射。
- **违规**：消息流中的工具卡片用 `code` 元素直接渲染 `JSON.stringify` 后的工具输出，属原始事件进入默认主界面，违反本条与 AGENTS.md「原始 Run 事件不得成为默认主界面的视觉中心」。应改为面向用户的自然语言摘要，原始载荷移到「过程」页签的详情展开中。

### 11.2 确认与错误

- 需要用户决定时，确认块出现在主内容流中，不藏在右栏或 Toast
- 错误说明发生了什么、受影响的对象和可执行的下一步
- 连接失败、模型不可用和工具失败使用各自具体文案，不统一显示“未知错误”

### 11.3 上下文面板

- “过程”按目标阶段分组，不按底层事件类型堆叠
- “资料”显示正在使用和已引用的文件或网页
- “成果”显示当前 Task 的 Artifact 与版本
- 面板关闭后，关键确认和完成状态仍必须在主工作区可见

### 11.4 模型配置

- 模型列表优先，编辑其次；不在同一窄弹层内永久并排
- 创建后不自动宣称连接成功，必须经过实际测试
- 默认角色包括文本、视觉和嵌入；同一模型可以承担多个角色
- Provider 高级兼容参数默认折叠，避免首次配置时产生认知负担

### 11.5 消息中心与通知

同一结果事件以三层呈现，三层是分工而不是三个独立功能：

| 层 | 载体 | 生命周期 | 职责 |
| --- | --- | --- | --- |
| 内联反馈 | 页面内 InlineNotice（`inline-message`、`action-note` 等） | 停留在页面期间 | 操作当时的直接说明（如导入跳过原因） |
| Toast | 右下角浮层 | 自动消失（常规 4s，错误 6s） | 用户可能已切走视图时的即时提醒 |
| 消息中心 | 侧栏铃铛 + 下拉面板 | 持久化，可回溯 | 所有长操作结果的统一留档与回溯入口 |

规则：

- 所有长操作结果一律写入消息中心（SQLite `notifications` 表，200 条滚动上限，超限淘汰最旧）；Toast 是否弹出由「同页抑制」决定：用户正在对应页面时不弹（页面已有内联反馈），在其他视图或查看其他任务时才弹。
- run 取消是用户主动行为，不产生通知。
- 通知条目必须携带可跳转 target（任务 / 成果 / 知识页）；点击条目复用既有导航入口（如最近任务、成果卡片）跳转并标记已读，不另造导航路径，不破坏进行中任务的状态。
- 铃铛固定在侧栏底部、设置入口上方，全局唯一入口；侧栏折叠或窄屏图标栏下退化为图标 + 红点。面板自铃铛向右侧主区展开，宽度约 360px，须挂在与铃铛同级的定位容器内，避免被 `overflow: hidden` 外壳裁剪。
- 未读徽标使用 danger 色圆点加数字，封顶显示 99+；面板内未读条目用 brand 色圆点与加粗区分，支持单条已读、全部已读与清空（清空需确认）。
- Toast 堆叠上限 4 条，hover 暂停消失，可手动关闭，点击可按 target 跳转；位于右下角，短暂覆盖上下文面板属预期行为。
- 窗口失焦时，run 完成 / 失败发送系统通知（Electron Notification）；点击系统通知聚焦窗口并跳转对应任务。导入与导出不发系统通知。
- 通知颜色一律消费语义状态 Token；`warning` / `info` 及其柔和背景是 §9.3 契约的组成部分，引入时必须当场补齐全套色系 Variant，不得先出一套主题再补另一套。

## 12. 无障碍与可用性底线

- 全部主要路径支持键盘操作
- 焦点顺序与视觉顺序一致，焦点环清晰可见
- 正文和控件达到 WCAG AA 对比度目标
- 重要按钮使用文字或可访问名称，不能只靠难以识别的图标
- 界面功能图标一律使用内联 SVG 描边图标（`currentColor`、统一 24 网格与笔画粗细，见 `renderer/src/icons.tsx`）；禁止用 Unicode 字符或 emoji 充当界面图标，品牌字标与格式徽标（MD/PDF）除外
- macOS 无边框窗口：仅窗口顶部标题带（三栏各自的头部区域）承载拖拽与双击最大化，双击遵循系统「双击窗口标题栏」偏好；标题带以下的任何内容区与空白区不得承载拖拽、双击等窗口行为；红绿灯位置不得与侧栏内容重叠
- 空状态必须说明可以做什么，不使用纯装饰插画占位
- 允许系统缩放和较长中文文案，不以裁切作为默认处理

- 多色系边界状态、窗口缩放与可访问性
- 统一空状态、加载状态和错误文案

### UI-5：视觉 QA 与回归

至少验证：

- 1280×800、1440×900、1728×1117 三种桌面尺寸
- 三种外观模式与四套色系的关键页面抽样
- 系统明暗切换后保持当前色系，冷启动无明显主题闪烁
- 应用换肤不改变 Word、PPT、Excel 等 Artifact 自身配色

- 模型新增、编辑、测试、设为默认与失败恢复
- 全键盘主路径和减少动态效果

## 14. 界面工作实施边界

任何实施者（编码智能体或开发者）进行界面工作时，应遵守以下边界：

- UI Foundation 已完成；后续界面工作是在本文规范上的增量，不是再次重构
- 不在界面改动中改写 Agent Core、模型协议和数据库语义
- 允许重构 Renderer 组件结构，但保持现有类型化 IPC 契约
- 先做少量基础组件，不为追求“设计系统”引入过重框架（取舍理由见 [系统架构](03-system-architecture.md) §10）
- 每完成一个阶段都启动真实 Electron 应用进行视觉检查，不能只依赖静态代码判断；启停只用 `scripts/dev-start.sh` 与 `scripts/dev-stop.sh`
- 新增颜色先进 §9.3 的 Token 契约并当场补齐全套色系 Variant；新增图标先进 `icons.tsx` 图标集再使用
- 对照 LobsterAI 时先阅读对应实现，必要时启动观察，但以本文档和 BetterWork 领域模型为最终准则

## 15. 完成标准

UI Foundation 完成后应达到：

1. 首屏一眼能看出这是用于完成知识工作的产品，而不是 Agent 调试 Demo。**已达成**
2. 用户始终知道当前 Task、运行状态和主要成果在哪里。**已达成**
3. 过程信息可见但不喧宾夺主，右侧面板可以完全收起。**已达成**（收起后整体卸载，不留残条）
4. 模型配置具有独立、完整、可理解的操作路径。**已达成**（并扩展出搜索配置分区）
5. 字号、间距、颜色、圆角和组件状态来自统一 Token。**部分达成**：颜色 Token 覆盖 8 个 Variant，圆角与组件状态达标；但小字号一档存在系统性偏差（§9.7），且通知徽标有一处硬编码 `#fff`（§9.3）
6. 浅色、深色与常见桌面尺寸均通过视觉验收。**部分达成**：每轮改动均有真实桌面人工验收记录，但没有 §13 UI-5 要求的三尺寸 × 3 模式 × 4 色系验收矩阵
7. UI 重构没有破坏现有 Agent 教学链路和真实模型链路。**已达成**（Fake Provider 与 OpenAI-compatible Provider 链路的回归测试持续通过）

第 5、6 条的残留缺口应作为独立收敛项处理，不要与功能切片混在一起。
