## 1. 文档目的

2026-09-14 专家交互已确认并已由 E13–E14 接入：专家页卡片/详情以“召唤”为主要操作，直接进入该专家任务对话；编辑配置是独立入口，退出回专家页。对话内查看专家使用可关闭信息面板。默认对话不展开任务准备表单，材料通过“＋”按需补充，完整材料/能力/记忆按需查看。系统预检保持在发送链路中，不能要求用户先完成一次工作依据预览。详见[设计 v0.2](designs/experts-and-task-materials.md) §3–§5。

本文定义算台 BetterWork 的界面体验基线，是 Renderer 开发、视觉验收和交互取舍的真相源。

UI Foundation 重构已完成并通过验收：主题 Token 契约、三种外观模式与四套成对色系、统一应用外壳与页面骨架、任务工作区、可完全收起的上下文面板、独立的模型设置空间均已落地。本文自此是**生效中的规范**，而不是待执行的重构计划。

## 3. 重构前的界面问题（历史记录）

以下记录 UI Foundation 重构前的问题，只解释规范的由来；当前页面不能据此判定有同样缺陷：

1. 三栏长期同时展开，导航、对话和执行时间线互相争夺注意力。
2. 原始运行事件被当成主要内容，界面更像 Agent 调试器，而不是知识工作者的工作台。
3. 左侧深色区域、中间暖色区域与右侧工具面板缺乏统一的表面和层级关系。
4. 字号、间距、圆角、边框和状态色没有稳定标尺，页面密度忽松忽紧。
5. 模型配置挤在临时弹层中，模型列表、编辑表单、角色默认值和连接状态没有清楚分层。
6. 任务结果缺乏足够视觉地位，Artifact 仍像消息附件，而不是可继续工作的成果。
7. 空状态、加载、运行、取消、错误和完成状态缺少完整一致的反馈设计。

因此不能通过继续添加卡片、阴影或渐变解决，必须先重建信息架构和设计系统。

## 4. 产品体验定位

算台的 UI 应呈现为：

> 沉静、可信、克制、有温度的知识工作台。

视觉隐喻取自“纸张、墨色、青玉”：

- 纸张提供适合阅读、分析和创作的安静底色。
- 墨色表达内容和工具的可靠性。
- 青玉色用于激活、选择、进度与关键动作。
- “算盘”只保留在品牌图标和少量秩序感中，不把古典纹样装饰化地铺满界面。

避免通用 AI 产品常见的高饱和蓝紫渐变、发光星芒、大面积玻璃拟态和无意义动态效果。

## 5. 六条设计原则

### 5.1 Task-first

用户首先看到自己正在完成的工作，而不是模型、工具或执行框架。所有技术能力都服务于 Task。

### 5.2 Artifact-visible

研究报告、表格分析、Word 和 PPT 是一等对象。成果应拥有独立预览、版本、导出和继续修改入口。

### 5.3 Progressive disclosure

默认只显示当前决策需要的信息。工具细节、完整过程、模型高级参数和原始事件按需展开。

### 5.4 Calm density

界面紧凑但不拥挤，信息密度来自清楚的结构，而不是缩小字体和压缩点击区域。

### 5.5 State is visible

长操作必须显示正在做什么、已经完成什么、是否需要用户决定，以及如何停止或恢复。

### 5.6 Chinese-first

中文菜单、标点、换行和长文阅读优先设计，同时保证英文资料、数字和文件名的可读性。

## 6. 信息架构

### 6.1 应用级导航

**一级导航与页面称呼只有一张表。** 导航标签取 `apps/desktop/src/renderer/src/App.tsx` 的 `PRIMARY_NAV_ITEMS`，页头称呼取各页 `PageHeader` 的 `eyebrow`／`title`；两侧由 `standards/coding-standard.test.ts`「导航与页面称呼纪律」比对，改任一侧必须同轮改本表。

| 一级导航 | 页面正式称呼 | 页头 eyebrow | 列表页标题（`title`） | 备注 |
| --- | --- | --- | --- | --- |
| 工作 | 工作页 | 「工作」 | 「开始一件工作」／「继续完成任务」（按有无运行分两档） | §7.1 的「首页」是工作页的**空态**，不是另一个页面 |
| 成果 | 成果页 | 「成果」 | 「可继续工作的交付物」 | 详情态 eyebrow 由 `headerEyebrow` 按成果类型给 |
| 知识 | 知识页 | 「知识 · 个人资料库」 | 「让资料成为下一次工作的起点」 | 「知识库」指 vault 与索引，不是页面名 |
| 技能 | 技能页 | 「技能」 | 「管理可复用的工作方法」 | 详情态标题是 Skill 名称 |
| 专家 | 专家页 | 「专家」 | 「召唤固定的工作方式」 | 编辑态是 eyebrow「专家配置」＋标题「新建专家」／「编辑专家修订」 |
| 设置 | 设置页 | —（侧栏底部项，不在 `PRIMARY_NAV_ITEMS` 里） | 分区标签：模型／搜索／MCP／记忆／外观／通用 | 俗称的「记忆页」是**设置 → 记忆**那一分区，不是第七个一级导航 |

**操作名词同理只有一套**（写在代码里，引用时按字面）：技能页「导入 Skill」；Skill 详情「信任」「启用」「环境」「来源」「试运行」；依赖面板「准备环境」（环境已就绪时是「重新准备（修复）」）、「取消准备」、「确认依赖授权」；专家页「召唤」；输入区「开始工作」与运行中的「停止」（占位文案「告诉算台你想完成什么工作…」）；空间入口「选择工作空间」，其菜单内「搜索工作空间」与「新建工作空间」。

设置分区顺序按配置动作分组：模型与搜索都是填 API Key 即可用，MCP 是连接外部工具，记忆属于我的数据，外观与通用属于偏好。「搜索」随联网搜索能力新增（见 [ADR-0007](adr/0007-search-engine-config-and-web-search-tool.md)）；「通用」当前为占位，工作目录、语言、数据与更新设置尚未建设，原计划的独立「数据」分区并入「通用」。

「能力」是模型、技能、MCP 与搜索的**总称**，只用于设置面板标题和文档描述，**不作为任何页面的名字**。「能力页」是已退役叫法：2026-09-30 全仓改准为「技能页」共 **7 处**（`docs/logs/2026-09-08.md` 1 处、`docs/logs/2026-09-09.md` 5 处、`docs/acceptance/2026-09-14-b0-two-skill-restart.md` 1 处）；唯一有意保留的是 `docs/prototype/skills-view/index.html` 的 `<title>` 与 `<h1>`——那是 2026-09-09 拍板时的评审快照，改掉它等于改掉当时被批准的那件东西。Skill 管理只有「技能」一级导航一个入口：2026-09-08 为发现性把 Skill 提升为主导航时临时保留的「设置 → Skill」兼容入口已于 2026-09-21 收敛删除，同一页面不设第二扇门。

不把模型、Tool、调试日志作为一级导航。

### 6.1.1 Skill 配置信任与本地来源（管理与授权已实现，分发验收见任务板）

Skill 列表分别展示来源（内置/用户）、启用状态、信任状态和依赖状态，不能用单一开关混同「启用」「信任」「可运行」。详情页提供「受信任：允许在已授权范围内执行脚本」选项，附简短提示「脚本以本机用户权限运行，信任不提供沙箱隔离」。

内置项默认信任、可撤销；用户导入项允许在导入完成时选择信任，不默认勾选。未信任项可以查看和编辑，试运行说明缺少授权并进入信任设置。缺依赖进入环境准备，不显示误导性的「已就绪」。授权范围变化时展示差异。

已满足运行条件的 Skill 点击「试运行」后进入新任务对话，清空旧任务消息，显示已选择的 Skill 并聚焦任务输入框；此时不创建 Run、不调用模型或脚本。用户输入非空要求并点击「开始工作」（或 `⌘/Ctrl ↵`）后，才创建 Task / Session 并携带 Skill 绑定启动 Run。新建普通任务或切换历史任务时清除草稿中的 Skill 选择；提交失败保留要求与选择供重试。

内置编辑入口为「复制并编辑」；显示新副本来源和未信任状态。升级不覆盖副本或用户的停用/撤销选择。撤销或停用后若存在活跃脚本，立即显示正在停止，清理后更新结果，不谎报已经停止。

首版使用现有技能入口承接 Skill 管理，不因目录分发额外增加一级「安装中心」。开发/安装/用户三个目录是宿主实现，正常使用无需理解；高级详情可查看来源位置。详见 [ADR-0011](adr/0011-skill-trust-and-local-distribution.md)。


### 6.1.2 专家召唤与材料协作（已确认，E1–E2 已实现）

专家页负责发现与配置：卡片和详情的主要操作是“召唤”，直接进入所选专家的新任务对话，沿用当前工作空间并聚焦输入框；不自动发消息，不进入准备表单。编辑配置独立打开，保存/取消回专家页；对话内查看专家使用可关闭简要面板，关闭回原对话且保留草稿。

对话默认只显示当前专家、能力/材料简要信息和 Composer。常用能力与适用参考由系统带入，可在详情中查看和调整；“＋”按需添加文件、引用知识或成果。材料用途有默认判断，有歧义在对话中询问，不要求用户逐个附件填写用途。无本期数据时允许澄清，缺项在对话中提供对应添加入口；模型、授权、依赖和无效绑定仍在发送边界校验。

右侧资料面板按需区分本次材料、已查阅来源与适用记忆，默认收起，允许完全关闭；不将工具、MCP 开关和记忆列表常驻为任务设置表。系统预检/快照在用户发送后执行，没有强制“工作依据预览”或第二次开始。

从成果开始新任务引用精确版本并沿用专家，清空本期输入与期间；用户直接表达下一期目标，缺材料再补，不复制整段历史对话。首次运行后切换专家采用新任务，普通导航不改变任务执行者。实施与验收见[开发计划](development/tasks-experts.md) E13/E14/E25。

### 6.1.3 工作型记忆界面（WM，已实现）

[工作型记忆产品设计](designs/work-centered-memory.md) §3 与 [ADR-0026](adr/0026-work-centered-memory.md) 规划的四处界面已落地，组件与 Hook 有自动化测试（[WM 任务板](development/tasks-memory.md) §15），真实桌面人工验收仍待确认；本节不改变上面已确认的导航规则，也不新增一级导航：

- **记忆页（扩展）**：在现有设置分区「记忆」内完成人工保存表单（内容/分类/适用范围/可选议题/可选有效期/来源说明）、候选批次、冲突「可能冲突」并列呈现与裁决、有效期 set/clear、来源复核状态与投影重建入口。正文与常规控件不用小于 12px 的字号换取空间。
- **上下文面板（复用现有可关闭面板）**：按需区分「下次运行可用」（候选范围预览）、「本次运行记忆」（精确修订、顺序、选择理由、请求阶段）与「历史上下文调整」（被截断轮次及可解释原因）。阶段文案只用 `selected`/`request-prepared`/`dispatch-attempted`/`legacy_unknown` 的对应措辞，禁止显示「模型已收到/已阅读」或声称因果影响；面板必须允许完全收起。
- **工作空间简报**：复用 WorkspaceSelector 的空间入口与上述可关闭面板，展示已确认目标/约束/决策/方法、未决讨论节点和用户指定的参考成果版本；每条可跳转来源，不整体自动注入模型，不设启动表单。
- **参考成果标记**：成果版本详情提供「指定为本空间参考版本」「取消参考」「引用到当前任务」；标记只表示参考选择，**不表示内容正确、审批通过或已被本期读取**，固定精确版本与哈希、不跟随 latest。

反馈继续按 §11.5.1 决策表归类：局部短时成功用 `TransientToast`，表单可处理错误用内联 `InlineError`（原文写的 `.inline-message.error` 已于 2026-09-28 连同基础规则一并删除并登记「不得复活」，见 §10.1 台账），只有确需跨页回看的长操作结果进消息中心 + 全局 `ToastHost`；候选结果本身可见时不重复通知，禁止逐条全局 Toast 或自造成功提示计时器。IPC 调用收在 hooks/ 并按 §11.5.1 的二选一走「让用户看见」或「只记录」两类处置（缺省实现是 `reportAction`／`trackAction`，形状清单见 [工程规范 §5](12-engineering-standards.md) 的 Renderer 小节），视图不出现 `window.betterwork`。字段与通道见[记忆实施契约](development/memory-contracts.md)，界面落地卡片为 WM07/WM11/WM14，见 [WM 任务板](development/tasks-memory.md)。

### 6.1.5 定时任务界面（已确认入口，设计 Proposed，未实现）

光哥已确认独立“定时任务”入口位于“专家”下方、业务主导航最后；消息中心与设置仍保留底部位置。创建先选已有专家、长期工作目录，再按需添加知识或知识库来源；不内嵌专家定义编辑，专家新修订必须提示，应用只改变调用绑定。详见[设计 v0.3](designs/scheduled-tasks.md)与 [SC 待办](development/tasks-schedules.md)，具体技术和原型仍需收口，不视为已实现。

同一目录长期使用，生成物持续积累、人可增减资料；各次工作分别留档，历史月/季/半年资料仍可供对比，不把多期工作显示成多个新项目。后台不抢焦点、不切走任务或清空草稿，状态、取消和来源可主动查看；复用统一页面骨架与通知反馈。Workspace 将来的“项目”文案另行统一，本轮不改页面代码。

### 6.1.6 记忆治理页的检索与滚动区（2026-09-25 光哥拍板）

记忆条数上去以后，「四个分组串成一条长纸带、整页滚动」不再成立。两项决定：分组收成横向页签、一次只看一组，页面唯一的滚动区落在该组列表上，滚动条因此贴版心右缘而不是窗口右缘；记忆多了必须能搜，搜索走后端全库检索，而不是过滤已加载的那一页。

- **页签**：待确认 / 已确认 / 已过期 / 历史与已停用 收成一组按钮并带条数，默认落在第一组有记录的页签；分组标题与说明固定在滚动区之上，不随列表滚动。
- **滚动边界**：设置页外层在「记忆」分区改为不整页滚，列表用 §8.3 的 `ScrollRegion`；窗口过矮时先保住列表可读高度，再由分区兜底滚动。「页面不得自定滚动边界」的约束不变，滚动区仍只有一个。
- **搜索**：工具条（`PageToolbar`）内一个搜索框，输入停顿即发请求、可「清除」；命中为 0 时说明「没有匹配」，不谎报成「还没有记忆」。搜索框与知识页共用同一组输入样式，不新建第二套视觉。
- **不翻页**：本页只显示最近一页（`LIST_PAGE_DEFAULT_LIMIT`），命中超出一页时在列表尾部说明并引导用搜索定位；检索与分页口径见[契约 §9.1](development/memory-contracts.md)。

### 6.1.7 工作空间身份与侧栏分组（已实现，ADR-0029）

**命名口径**：Workspace 的中文一律「工作空间」（一个本地文件夹＋可改别名＋图标与颜色）；§6.2 的中栏继续叫「任务工作区」。此前「工作区」同时指这两件事，侧栏分组标题一旦叫「工作区」就会与中栏同名不同义，因此 2026-09-28 起收口：默认空间叫「我的工作空间」，材料来源叫「工作空间文件」，选择器与对话框一律「工作空间」。

侧栏从「一条不分组的最近任务」改为「工作空间分组＋组内任务」：

- 一次列出最近活跃的前 12 个空间（含新建后还没有任务的空空间），按各空间最近一次任务活动排序，没有任务时退回登记时间。空间与更多条目靠输入区那个工作空间选择器的搜索定位，侧栏不另开第二扇浏览门。
- 每个空间默认**只有当前那一个展开**，其余折叠；展开偏好是界面状态，按「默认值＋例外」存 `localStorage`（只落用户手动改过的那几档，新出现的空间仍按默认摊开）。
- **点空间行只展开收起**：不切换当前空间、不清草稿、不打断运行中的任务。切换当前空间只有两条路——打开别的空间里的任务（这是「打开任务」的必然结果），或在输入区的选择器里选。
- 组内折叠时给 3 条任务，「展示更多（k）」就地展开到已加载的 20 条，`k` 来自仓储统计的真实总数；一页装不下时在尾部说明「另有 N 项未列出」，不假装能翻页。
- 任务行是 `RunSummaryRow` 的 `compact` 档：meta 只报相对时间，只有进行中／失败仍带状态词——十几个空间并列时「已完成」在每个空间里都是多数派，报出来是噪声。
- 身份（别名／图标／颜色）在新建对话框里一次定好，之后从空间行的「更多」菜单改。菜单里**没有删除**：`tasks / artifacts / input_snapshots / run_context_snapshots / memory_records` 全部 `ON DELETE CASCADE`，删一个空间会带走整棵子树，因此只提供「从侧栏隐藏」；恢复走选择器（它列全部空间，选中即解除隐藏）。
- 「新建工作空间」与「打开本地文件夹」此前是两颗做同一件事的按钮，现合并为一个对话框入口；对话框第一步就是选目录，**选目录不再顺手登记一个空间**（`workspace:pick-directory` 只回路径），取消时不会留下半行数据。
- 折叠成 88px 窄栏时这一组换成着色图标网格（最多 6 枚），点图标先展开侧栏再展开那一组。

### 6.2 任务工作区

采用可折叠三层结构：

```text
应用导航 | Task 主工作区 | 上下文面板
```

- 左栏负责去哪里：应用入口、工作空间分组（组内是该空间的最近任务）和设置。
- 中栏负责做什么：任务协作、确认、编辑和主要内容。
- 右栏负责参考什么：过程、资料和成果，默认按场景出现并允许收起。

右栏不是永久执行日志。没有过程、资料或成果需要查看时，应自动收起，把空间还给主工作区。

### 6.3 设置空间

设置是独立页面，不附着在输入框或任务消息中。设置左侧为类别导航，右侧为当前设置内容；编辑复杂配置时使用侧边 Sheet 或对话框。

## 7. 核心页面

### 7.1 工作页空态 / 新建任务

目标设计：

- 一句明确任务输入作为视觉中心
- Composer 提供 `+` 能力菜单：技能（多选，带搜索与可用状态）、专家、添加文件、引用知识与引用成果；已选项以 chip 条显示在输入框上方，可逐个移除或调整材料用途
- `+` 菜单及其他 Popover 浮层必须进行视口碰撞处理：下方空间不足时向上展开；上下都不足时选择空间较大的一侧并在浮层内部滚动，同时保持左右边界与安全间距。窗口缩放或滚动后重新计算位置。
- 提供研究、分析文件、编写文档、制作演示四个意图入口，而不是功能仪表盘
- 最近任务和最近成果位于次级区域
- 模型选择只显示当前工作模型，详细配置跳转设置

当前实现状态：

- 无任务时中栏显示欢迎视图——抽象点线饰条、eyebrow「算台 · 知识工作台」、品牌主张「以我所知，成我所作」（全系统唯一展示字体位置）与一句引导正文。视觉中心是品牌主张，不是任务输入框。
- Composer 固定在中栏底部（与对话列同宽，见 §8.3），含工作区行、多行输入、页脚（当前工作模型 + `⌘/Ctrl ↵` 快捷键提示 + 开始/停止按钮）。
- 意图入口只有两个教学示例按钮（计算一组数据、读取一份资料），点击后填入输入框。研究 / 分析文件 / 编写文档 / 制作演示四个产品意图入口未落地，应在 Phase 1 研究工作流可用时替换教学示例。
- 最近任务在左侧导航栏的「最近任务」区，按 Task 而非 Run 展示；首页内没有独立的次级区域。
- 当前工作模型只在 Composer 页脚以文本呈现，不可就地切换；配置与切换均在设置页。
- 历史记录（B00-4 前）：当时 Composer 没有能力入口，技能只能从 Skill 详情页「试运行」带入新任务草稿，界面只有一行「已选择 Skill：名称」纯文本提示，不能在对话内增删。2026-09-13 B00-4 已落地 `+` 菜单与 chip 条（现状见 §7.1 与 [ADR-0012](adr/0012-composer-capability-binding.md)），主进程同时取消隐式延续同任务历史绑定：绑定完全由界面 chip 集合显式决定。

### 7.2 Task 工作区

目标设计：

- 顶部：任务标题、当前模型、运行状态和少量上下文动作
- 中部：用户目标、Agent 回应、确认点和可编辑内容
- 底部：可扩展 Composer，支持能力绑定（`+` 菜单与 chip 条）、附件、发送和停止
- 运行活动在回复内部以分组摘要呈现，例如“查阅 5 个来源”“分析工作簿”“正在生成报告”
- 右侧可切换“过程 / 资料 / 成果”，并记住用户对当前 Task 的展开状态

当前实现状态：

- 顶部页头带只承载 eyebrow「工作」、状态化标题（无任务时「开始一件工作」，有任务时「继续完成任务」）与右侧「收起/查看上下文」开关。任务标题不在页头带，而在左侧栏「最近任务」中以选中态呈现。
- 当前模型 chip 曾放在页头带，2026-09-04 主动移除：页头带是全局贯通的拖拽区，放易变的状态芯片会破坏各页标题坐标一致性。当前工作模型改在 Composer 页脚呈现。
- 运行状态在右栏「过程」页签的活动摘要中呈现（状态点 + 文案 + 阶段计数），页头带不重复。
- 中部已有用户目标与 Agent 流式回应；确认点依赖尚未定义的审批事件，可编辑内容目前只有成果的修订编辑器（在成果页）。
- 底部 Composer 支持多行输入、`⌘/Ctrl ↵` 提交、发送/停止切换、工作区选择、技能绑定和材料选择；文件会先形成受管输入快照，知识与成果按具体修订/版本加入任务。PPTX/XLSX 输入仍显示为不可读取，留待 E51 解析。
- 右侧三页签已落地，但展开状态**未按 Task 记忆**：`contextOpen` 只在会话内保持，发起新运行时强制展开，切换任务不恢复该任务上次的展开状态；侧栏折叠状态则已持久化到 `localStorage`。

### 8.2 响应规则

- 大于等于 1280px：允许三栏同时显示
- 960–1279px：右栏作为覆盖式 Drawer，左栏可折叠
- 小于 960px：左栏默认折叠，右栏覆盖显示，保证主工作区优先
- 窗口过窄时不缩小正文换空间，改用折叠与覆盖

实装状态：断点已按 `max-width: 1279px` 与 `max-width: 960px` 落地，正文不随窗口收窄而缩小（版心用 `min()` 收，`body` 有最小宽度）。两处与规范有差距：窄屏是把左栏**强制**变为图标栏，不读取用户的折叠偏好，因此宽屏下手动展开的状态在窄屏不生效；覆盖式右栏没有点击外部关闭的背板，只能通过页头带的「收起上下文」开关关闭。按 §8.3，右栏只在工作视图渲染，成果、知识、设置视图不预留空栏。

### 8.3 统一页面骨架

所有主内容页（工作、成果、知识、技能、专家）共用同一页面骨架，由两个 layout 层组成：

- 页头带（page header）：贯穿中栏的同一横带——基准高度 70px、左缘 28px、同底部分隔线、同一拖拽区行为；左侧放「返回键 + eyebrow + 页标题」，右侧放本页操作区。返回键始终单行且不压缩；长标题单行省略，完整名称可通过 title 查看。标题与操作不能并排容纳时，操作区换到下一行，页头按内容增高，禁止把中文返回键或操作文字挤成竖排。该响应由 `PageHeader` 基座拥有，页面不覆盖页头几何。工作页的上下文开关可并排容纳，页头与上下文面板顶部仍以 70px 对齐。
- 版心（page body）：统一 860px、水平居中；窄窗口时两侧各留 24px 最小间距。页内说明文字、内容列表、对话消息与输入框全部落在版心内；工作视图的对话列与输入框同宽。
- 上下文面板按场景出现：右栏只在承载任务上下文的工作视图渲染（过程/资料/成果）；成果、知识、设置等无任务上下文的视图不渲染面板，主工作区占满剩余宽度，布局网格不得预留空栏。面板收起后整体移除、不留残条，重开入口固定为页头带右侧操作区的「查看上下文」开关。

实现上以 `components/layout/` 下的 `PageHeader`、`PageToolbar`、`ScrollRegion`、`ViewContainer` 与共享 Token/样式为唯一来源；页面不得自定版心宽度、页头结构、滚动边界，也不得替骨架容器补纵向间距——间距机制必须由骨架自己拥有（§9.8）。设置页因保留二级导航布局作为声明特例，其余新增页面一律套用本骨架。数据加载、搜索和删除等业务编排留在页面对应的 hook，不在布局组件中复制 Cloud 的通用 CRUD 控制器。

详情与密集管理页的阅读顺序（2026-10-02，真实产品走查 V03–V08）：

- 成果详情首屏优先正文或演示预览；参考设置、声明采用依据和版本说明放入 `Disclosure`，版本历史与实际访问记录仍可回看。声明采用与运行访问不能合并成同一种来源语义。
- Markdown 表格在 `MarkdownPreview` 内提供可聚焦的横向滚动区，表头单行；宽表不迫使页面横滚，也不缩小字号或改写成果内容。滚动区虽是 div，焦点仍复用全局控件规则的主题 Token 与盒内环，不依赖浏览器默认外扩环；`RING_OUTLETS` 同步登记这条组合选择器，仍保持五个出口。
- 知识详情以资料标题、来源状态、保存文本为主；资料库搜索、集合筛选、导入和总量说明留在列表态。详情中的保存版本、集合分类和来源管理按需展开，索引作业仍从页头进入；失败及提取警告不随说明折叠。
- 专家常用参考按已选、知识修订、当前空间成果版本分组，支持本地标题/版本信息筛选。其他空间的成果单独折叠并禁选；已选失效或越范围的引用仍显示并允许移除。精确修订、用途与运行范围校验不变。
- 长正文且多动作的列表行使用 `ListRow actionsPlacement="below"`，正文独占一行，操作随后折行；槽位几何由基座拥有，页面不得覆盖 `.list-row-main` 或 `.list-row-actions`。
- 记忆页常驻显示自动提炼开关、当前同意状态、错误和活动作业；低频规则与历史作业用 `Disclosure`。没有候选只给简短状态，不再叠加空态卡片；新增经验表单优先于说明。切换开关仍必须经过代价与同意版本确认，候选不自动确认，来源/依赖/冲突警告保持可见。

## 9. 视觉系统

### 9.1 外观模型：模式与色系分离

算台从 UI Foundation 起就支持多外观，但不把“浅色 / 深色”和“青色 / 蓝色 / 暖色”等概念混成一个主题列表。外观由两个独立维度组成：

```text
AppearanceMode = system | light | dark
ColorScheme = jade | ink | ocean | sand | ...
ResolvedTheme = ColorScheme[系统或用户选择后得到的 light/dark variant]
```

- 外观模式决定当前使用浅色还是深色，并支持实时跟随操作系统变化。
- 色系决定品牌强调色、表面温度和中性色倾向。
- 每套正式色系必须同时提供浅色和深色 Variant。切换系统明暗时保留同一色系，不发生风格跳变。
- 用户选择应跨启动持久化，并在 React 挂载前恢复，避免启动时先闪现错误主题。

这比把每个主题直接标记为 light 或 dark 更适合长期产品：新增色系不会改变用户的明暗偏好，系统跟随也不会随机落到另一套视觉风格。

### 9.2 首批内置色系

UI Foundation 首批提供四套成对色系：

| 色系 | 定位 | 浅色倾向 | 深色倾向 |
| --- | --- | --- | --- |
| 青玉 `jade` | 算台默认品牌主题 | 暖灰纸面、克制青绿 | 墨绿黑、低饱和玉色 |
| 纸墨 `ink` | 最安静的阅读与写作主题 | 象牙白、近黑强调 | 中性炭黑、灰白文字 |
| 远洋 `ocean` | 冷静、专业的数据分析主题 | 冷白、深海蓝 | 蓝黑、低亮度青蓝 |
| 暖砂 `sand` | 温和的长时间办公主题 | 米白、暖铜点缀 | 棕黑、暗金铜点缀 |

首批不提供任意取色器。任意颜色很容易破坏对比度和组件状态一致性；后续如开放自定义主题，也必须经过 Token 完整性与可访问性校验。

### 9.3 主题 Token 契约

组件只能消费语义 Token，不直接绑定某套主题的色值。最小契约包括：

- 品牌：`brand`、`brand-hover`、`brand-soft`、`on-brand`
- 画布与表面：`canvas`、`surface`、`surface-raised`、`surface-hover`、`overlay`
- 文本：`text-primary`、`text-secondary`、`text-muted`、`on-danger`（品牌底前景用上行的 `on-brand`）
- 边界与输入：`border`、`border-subtle`、`input-border`、`focus-ring`
- 状态：`success`、`warning`、`danger`、`info` 及其柔和背景；实心危险按钮另带 `danger-hover` 作为 hover 背景，浅色 Variant 向暗取、深色 Variant 向亮取，与 `brand-hover` 同向
- 专用区域：`sidebar`、`composer`、`selection`、`scrollbar`
- 图表：一组经过对比度校准的有序数据色，但不替代状态色

每套 Variant 必须完整实现契约，禁止组件用 `#fff`、`black` 或仅针对 `.dark` 的局部补丁绕过主题系统。圆角、字体和密度属于独立 Design Token，不随色系任意变化。

落地现状：四套色系 × 明暗共 8 个 Variant 已完整定义在 `renderer/src/styles.css` 顶部的 `:root[data-theme][data-scheme]` 选择器组中，由 `appearance.ts` 在 React 挂载前写入 `data-theme` / `data-scheme`，并同步 Electron 标题栏背景与符号色。

契约缺口与已知违规：

- `border-subtle` 已在 8 个 Variant 中定义，用于成果来源列表、原始输出折叠区等次级分隔；主分隔仍用 `border`。
- 图表数据色尚未定义（无图表 Artifact，属 Phase 2 前置）。
- `text-on-dark` 曾在 8 个 Variant 中都定义却零消费，已删除；需要「深色底上的前景色」时改用语义明确的 `on-brand` / `on-danger`。
- 通知未读徽标曾硬编码 `color: #fff`，现已改为消费 `on-danger`。该 Token 在四个浅色 Variant 为白，在四个深色 Variant 为深墨——深色下 `danger` 被提亮，白字在其上不可读。
- 阴影与遮罩背板已 Token 化：`--scrim` 与五档 `--shadow-color-*`（strong / overlay / drawer / raised / soft）按**明暗**分别取值——深色画布上同样强度的黑色阴影几乎不可见，抬升感会消失，因此深色 Variant 的阴影更重。组件不得再写 `rgba(0, 0, 0, …)` 字面量。
- `artifact-canvas` 同样是**只按明暗取值**的中性画布（浅色 `#E6E6E4`、深色 `#2A2A29`），用于幻灯片等文档类 Artifact 周围的中性衬底：成果自身的配色属于用户内容，不随色系变化，因此它不进 8 个 Variant，而由 §9.4 单独约束。
- 外观模式与色系预览卡（`.mode-preview` / `.scheme-preview`）内的色值是**刻意硬编码**的：它们描绘的是各色系自身的样本，不能跟随当前主题变化，属本节的明确例外。

### 9.4 主题作用域

外观切换覆盖应用外壳、设置、Markdown 阅读、图表和系统标题栏，但不能污染用户成果本身：

- Word、PPT、Excel 与图表 Artifact 保留自身模板和配色。
- Artifact 预览放在中性画布或页面框中，清楚区分“应用主题”和“文档主题”；衬底用 `artifact-canvas` Token，不写白色字面值。
- 代码高亮、Markdown、图表和未来第三方组件通过 Theme Adapter 响应明暗变化。
- Electron 标题栏、启动画面、滚动条、系统菜单和浮层必须与当前主题同步。

### 9.5 外观设置交互

“设置 → 外观”包含：

1. 外观模式：浅色、深色、跟随系统，使用三个可识别的布局预览卡。
2. 色系：显示浅色与深色并列的小型色板预览，选择后即时应用。
3. 字号与密度：字号进入 UI Foundation；紧凑密度可以预留但首版不开放。

切换应即时预览并持久化，不依赖“保存全部设置”。如果应用主题失败，恢复上一个有效选择并说明原因。

实装状态：第 1、2 项已落地——三个模式预览卡与四套色系色板预览均为纯 CSS 样本，选择后即时应用并写入 `localStorage`（键 `betterwork-appearance`），跟随系统时监听 `prefers-color-scheme` 变化且保留用户所选色系。第 3 项字号设置**未落地**，紧凑密度按原计划不开放。主题应用失败后的回退与说明也未实现：当前 `parseAppearance` 对非法或损坏的持久化值静默回落到默认外观（system + jade），不向用户说明原因。

### 9.7 字体

使用系统字体栈，设计输入只有 macOS 中文字体（平台范围见 [ADR-0036](adr/0036-macos-only-platform-scope.md)；栈里留着 Windows 字体名只是回退顺序，不再作为适配目标或验收项）。**字号与行高的档位表只有一张，在 §9.13**，本节只管字体族、展示字体的唯一位置与小字号下限；不允许用小于 12px 的字体承载产品信息。全系统唯一使用展示字体的位置是欢迎页口号「以我所知，成我所作」，用 `Georgia + 楷体（Kaiti SC/STKaiti/KaiTi）` 衬线栈；其余所有界面文字（含各级页面标题、成果标题与成果内标题）一律使用系统默认字体栈，不用宋体或其他衬线承载展示文字。

### 9.8 间距、圆角与阴影

- 间距采用 4 / 8 / 12 / 16 / 24 / 32px 标尺
- **纵向堆叠必须有呼吸空间**：同一容器内上下相邻的块（控件、表单、提示、卡片、列表行）之间必须留出可见垂直间距。两个输入框或两道边框 0 间距贴合一律按缺陷处理，不因「别处有留白」而豁免——没有垂直间距的界面读起来是窒息的，这是排版常识而不是风格偏好。
- **一道缝只有一个所有者**：堆叠容器用 `gap` / `row-gap` 负责子块之间的垂直间距；组件自带的上下外边距属于「与后一块的缝」，所在容器要接管时必须显式置零，不得让两个机制在同一道缝上各占一半。
- **反馈与提示类组件不自带上下缝**：内联错误归 `InlineError`，不声明上下 margin；间距由所在容器的 gap 或精确承载位置负责。已退役的 `.inline-message` 与它的 `.error` 皮不得复活，反馈配色与出口见 §11.5.1。
- **设置页的纵向节奏由 `.settings-section` 的 `gap: 24px` 统一负责**：六个页签（模型／搜索／MCP／记忆／外观／通用）的直接子元素不再自带上下 `margin`——此前 `.model-filter` 的 `margin: 24px 0 12px`、`.settings-section > .inline-error` 的 `margin: 12px 0`、`.search-form`／`.mcp-connection-list`／`.mcp-editor` 的 `margin-top: 24px` 都是块级流没有 `gap` 时的补偿，容器一旦有了 `gap` 再叠 `margin` 就是两道缝在同一格上各占一半。记忆页 `.memory-settings` 覆盖 `gap: 12px` 是因为该页内容更密（错误、警告、候选、编辑并列），属于有意收紧而非遗漏。护栏锁两条：`.settings-section` 必须有 `display: flex` 与 `gap`，`.settings-section >` 子选择器不得声明纵向 `margin`（`standards/coding-standard.test.ts`「设置页纵向间距由容器 gap 拥有」）。
- **骨架组件自带机制**：`components/layout/` 的容器（`PageToolbar` 等）必须自己完成纵向堆叠（`display` + `gap`）；页面不得用 `.某页 .page-toolbar` 这类后代选择器替骨架补 `gap`——逐页覆写正是这类缺陷修不干净的原因。护栏锁两条：装控件的骨架容器必须有 `gap`，骨架的 `gap` 不得由页面补（`standards/coding-standard.test.ts`）。确需改变骨架盒模型的结构性特例（如工作视图对话列的 `display`）另按 §8.3 声明，不在护栏范围内。
- **表单控件不写 `width:100%`**：`FieldSelect` 这类控件不设 `width:100%`——放进纵向容器由 `align-items: stretch` 撑满，放进横向行按内容取宽。`width:100%` 在弹性行里等于「以父容器宽度为基准」，会把同排的标签与提示挤到逐字断行。
- **定宽列不放出横向滚动条**：侧栏（240px）、上下文面板（380px）、消息中心（360px）与 `Modal` 的 sheet 抽屉（480px）宽度是写死的，横向溢出换不来「多看一点」，只换来一条把注意力从内容挪到控件上的滚动条。这些表面的滚动容器一律 `overflow: hidden auto`；名字放不下就收短成省略号，并由 `Tooltip` 在悬停时就地补全全文（§10.1）。**收短必须落在看得见的那条边线上**：`display: grid` 的隐式列以 min-content 为下限，一句不折行的空间名就能把整列顶宽，省略号随之跑到可视区之外——用户读到的是「文字被砍断」而不是「名字太长」，所以列宽要显式收到 0（`minmax(0, 1fr)`），作为 grid／flex 项的行与 `NavItem` 基座也要带 `min-width: 0`。**同一件事在纵向上叫折行**：定宽抽屉里那句排不下的说明文字（`.knowledge-admin-profile small` 曾写 `flex: none`）该整句换到下一行，而不是钉在一行上把整列顶出可视区。护栏锁三条并做过变异验证：定宽列滚动容器的横向轴必须是 `hidden`／`clip`（登记清单含两处 sheet 抽屉）、分组外壳的列必须写成 `minmax(0, 1fr)`、`.nav-item` 基座必须自带 `min-width: 0`（`standards/coding-standard.test.ts`「定宽列的横向溢出纪律」）。
- **定宽列里的每一段都要自带内缩，而那道内缩只有一档 16px**：`.context-content` 不给整列补水平内距——分隔线要贯通整列宽，内缩因此归每一段自己的外壳。认可的壳以 `components/ContextPanel.test.tsx`「上下文面板的分段内缩」的 `INSET_OWNERS` 为唯一清单（`.context-section` 管绝大多数段落、`.activity-list` 管过程页、`.brief-panel` 管简报页、`EmptyContext` 自带内距的居中空态，外加 `InlineError`／`InlineLoading` 两枚基座）。漏掉壳的分段会直接贴到列的左边缘——2026-09-28「本次运行」「历史运行来源」「成果列表」「记忆警告行」四处就是这样，同一天由同一条护栏收口：五个页签各渲染一次，`.context-content` 的每一个直接子块必须命中那张清单，新增壳要写明它凭什么自己定内缩。**有壳不等于有档**：2026-10-01 家底核查时，同一格还散着 12／14／15／16 四种取值（`.activity-list` 15px、`.context-section` 与 `.brief-panel` 14px、`.context-panel .tabs` 12px、夹在段与段之间的 `InlineError` 16px），于是同列相邻两块会差 1–2px 而没有任何一道门禁报错——`.context-content > .inline-error` 那条注释一直写着「左右与 `.context-section` 的 padding 对齐」，而它当时比小节壳多缩 2px。并档到 **16px**：这个数不是新造的档，它已在 §9.8 那把尺上，也是 `--card-padding`（12px 16px）与 `--surface-padding-panel` 的水平格，「列里的块和卡片用同一把水平尺」一句讲得通；消息中心的面板头（360px 那一列）同档。两处刻意不并：`.empty-context` 的 28px 是居中空态的四周留白，不是段落缝；侧栏与设置空间的左导航不在这一轴——它们的段落是**行**，行的水平缝归 `NavList` 基座，整列的余量归下面那条「列壳」轴。护栏见 `standards/coding-standard.test.ts`「定宽列段落内缩档位」三条：列内声明的水平内缩必须命中清单且存量与清单等量、段落壳必须 16px、登记为「不在这一轴」的每一项仍与实测一致；六发变异验过（改回 14px、换成三值 shorthand 藏 14px、删清单条目、把清单指向不存在的规则、新增一处未登记的 `padding`、改动登记值）。**「谁给水平内缩」与「空态由谁渲染」是两件事**：简报的空态曾由 `.context-placeholder` 一个类同时管这两件，于是它长得跟别处的空态不一样；2026-09-29 拆开——空态归 `EmptyNotice`，内缩仍归 `.brief-panel` 这件已登记的壳，`.context-placeholder` 与 `.brief-empty` 一并退役。

### 9.9 动效

- 即时反馈：120ms
- 展开与切换：180ms
- Drawer 与大区域过渡：240ms
- 不使用循环发光和无意义等待动画
- 支持 `prefers-reduced-motion`

落地现状：已实施。时长与缓动提为 `:root` 上的独立 Token（`--motion-instant` 120ms、`--motion-expand` 180ms、`--motion-overlay` 240ms、`--motion-easing`），组件不得写死毫秒数。

交互控件的状态变化走 120ms transition；挂载即出现的浮层（Sheet、通知面板、Toast、上下文面板、动作错误条）走 keyframes，按浮层或展开档取时长；`prefers-reduced-motion: reduce` 下降级**分两轨**：keyframes 压到 0.01ms 一帧内结束（保留 `animationend`），transition 直接取 `0s`。「不使用循环发光和无意义等待动画」这一条天然满足。

两轨不能并成一句「一律压到 0.01ms」：`animation-name` 的初始值是 `none`，给 `*` 设动画时长造不出动画；`transition-property` 的初始值却是 `all`，给 `*` 设非零过渡时长等于**替每一个没声明过渡的元素声明了「所有属性都动一会儿」**——那条降级于是反过来开启动效。2026-10-02 焦点环就坏在这里：`.markdown-table` 不声明 transition，`outline-width`／`outline-offset`／`outline-color` 被拉进过渡后停在聚焦前的 `3px / 0px / currentColor`，环又跑到盒外（[ADR-0035](adr/0035-focus-ring-inside-control-box.md)）。护栏：「界面观感基线 › 全局动效降级只能关过渡、压动画」。

### 9.10 控件几何与浮层字号

**单行控件的真实高度也要一致**：Button、TextField 与 FieldSelect 同档时共用 `--line-height-normal`，sm 文字统一 `--font-size-caption`，md/lg 统一 `--font-size-body`。高度表给的是最小命中区；实际高度还受字号、行高、内距与边框影响，不能只比较 `min-height` 就宣称等高。2026-10-01 真实渲染发现 md 输入框 33.5px、按钮 32px：不仅按钮沿用默认行高，md 字号也曾为 12px、输入/选择为 13px。统一同档字号与行高后再比较自然高度（不能用 flex stretch 把差异遮住）；多行 TextArea 仍由 rows 与内容决定高度。

控件的边框、圆角与高度必须来自 `:root` 的 `--control-*` 档位，禁止各视图各写一遍——同一类控件在不同页面上长得不一样，就是「界面看着不统一」最直接的来源。

- **高度档与内距档必须成对**：只统一高度而不统一内距，同排的按钮与输入框仍会一个显得饱满一个显得瘦。护栏因此把 `padding` 与 `height`／`width` 一起纳进「控件几何」口径，裸 px 即红（`.composer textarea` 的 `11px 0` 是登记在案的例外——它的左右内距归 `.composer`）。
- **动作排（action row）：一排动作是一个契约单位，不是一个组件**。同一次治理把规则写在 `ActionBar` 这个**组件名**上，于是页头那一排（「+ 新建专家」与「+ 导入 Skill」就是在这里一个 36px、一个 32px）从来不受任何约束。契约的单位应该是「一排并排放着的控件」，因此定义七个槽位为一类：`ActionBar` 的 `children`、`PageHeader` 的 `leading` 与 `actions`、`SectionHeader` 的 `actions`、`Card` 的 `footer`、`ListRow` 的 `actions`、`PageToolbar` 的直接子控件。**同一排内所有承载文字或输入的可聚焦控件必须落在同一高度档**（28／32／36），隐式缺省也算一档：`Button`／`AsyncButton` 的 `size` 自 2026-10-01 起是**必填**属性，「不写」不再是第三种高度。**一排要么落在上面七个槽位之一，要么就不存在**：页面自己写一个 `display: flex` 的 `div` 把两颗按钮并排，护栏对它是盲的，同档契约等于没定。就地的一排用 `ActionBar as="div"`（这个档位本来就是为不带 `footer` 语义的页面内动作条开的），2026-10-01 记忆冲突条里的「替代…」＋「确认两条并存」就是这样从 `.memory-conflict-actions` 那个换行容器搬进基座的——搬之前它靠 `width: 100%` 的说明段落被顶到独立一行，一颗 `md` 一颗 `sm`。
- **选哪一档：整排一起选**，按排的性质取缺省——页头与**页面区块头**（`SectionHeader variant="block"`）的 `actions`（整页／整块主行动所在）用 `lg`；`ActionBar`、`Card.footer`、`PageToolbar` 与**表单尾排**（保存／测试／准备环境＋取消那一排）用 `md`；`ListRow.actions`、**面板小节头**（`variant="panel"`）的 `actions` 与密集行内用 `sm`；`PageHeader.leading` 只有后退入口，用 `sm`——它无底无框，只借命中区，不与 `actions` 那一排比高。**`lg` 只住在页头与区块头**：2026-10-01 收口时把 `.dependency-actions` 的「准备环境」与 `.search-actions` 的「保存并启用」两处 `lg` 降成 `md`，理由就是它们各自排在一片 `md` 的取消／测试按钮中间。缺省可以被整排一起抬高或压低（同排同档即可），不允许在一排里各选各的。`IconButton` 走自己的**命中区轴** 23／28／34（方块不是与文字按钮等高的控件，它按内容取档），不参与等高要求，但必须显式选档（`IconButton` 的 `size` 自 2026-10-01 起同为必填属性，隐式那一档就是没有覆写的 `md` 28px），且同排的图标方块之间也不得各选各的。
- **控件没有档位 API 时先补基座，不得就地写裸 px**：`SegmentedControl`、`Tabs`、`FieldSelect` 此前只有固定高度（28／28／32px），把它们和 `lg` 主按钮排在一行就必然混档。本轮给这三件补**必填** `size`（与按钮同一张档位表，`data-size` 一处出口），页面在页头那一排传 `size="lg"`。护栏见 `standards/coding-standard.test.ts` 的「一排动作里的控件必须同档（动作排纪律）」与「控件基座的 `size` 是必填属性，不得有隐式缺省」。
- **24–40px 的密集高度带已并档**（2026-09-27，产品拍板）：行内小按钮 26 → 28、筛选与次级按钮 30 → 32、侧栏行 34 → `--row-height`、工作空间行 23 → `--row-height-sm`。带内 **`min-height`** 裸值现为 0，护栏改为零容忍；原先登记为唯一例外的 `.expert-card-desc` 两行钳制高度，已随「卡片描述一律三行定高」移出这一带（§10.1），例外清单因此清空并被删除。**这条结论只覆盖 `min-height`**：2026-10-01 核查发现同一高度带在 `height` 属性上仍有 10 个裸值（22／24／28／30／32／34／36／38／40／54px），它们全是「图标底座方块」那一类装饰件，不属于控件几何，档位表由 §9.13 另立一条 `--mark-*` 轴收口。
- **圆角同样收进档位表**：样式表里 150 处裸圆角换成 `var(--radius-*)`，其中 7 → 8（`--radius-row`）、9 → 10（`--radius-card`）是两处有意的并档。剩下的 3–4px 只有 3 处（键帽 `kbd`、外观模式预览、色系预览各一），全是图形化小件，由 `MICRO_MARK_RADII` 按「只降不升」登记；新增一处必须写清它为什么不算某一档。清单里原有的 `.current-badge` 与 `.artifact-evidence-list b` 两条已随实现消失而删除。
- **焦点环住在控件自己的盒子里**（2026-10-01，[ADR-0035](adr/0035-focus-ring-inside-control-box.md)）：环一律 `outline: 2px solid var(--focus-ring)` ＋ `outline-offset: var(--focus-ring-offset)`（-3px；环带 = 边框盒往里 [+1, +3)，**整个 2px 都在盒内**，靠边那 1px 格轮到控件自己的边框，读作分隔缝），**偏移不得是正值或 0，也不得浅到环宽以内**。理由不是美观，是**可被裁**：画在边框盒之外的任何一段（`outline`、外扩 `box-shadow`、`inset: -Npx` 的伪元素同罪）都会被祖先的 `overflow` 裁剪吃掉，而「这一层会不会裁」写页面时预判不了——`overflow-y: auto` 还会把 `overflow-x: visible` 强制成 `auto`，一个只打算纵向滚的容器就顺手把左右两段的环切了。2026-10-01 由光哥指出记忆页搜索框聚焦后左右边框不见，扫出 `styles.css` 53 条 `overflow` 声明里至少 8 处会吃到环：`.memory-settings`、`.model-sheet form`、`.knowledge-drawer-body`、`.scroll-region`（覆盖面最大）、`.workspace-groups`、`.notification-list`、`.app-shell`，以及最严重的 `.segmented-control`——它的按钮填满容器且 `border: 0`，`outline-offset: 2px` 的环**四边全被吃**，Tab 到「卡片／列表」切换组时焦点指示器根本不存在（WCAG 2.4.7 失败）。同一轮还抓到 `.composer textarea { outline: 0 }`：全仓最重要的那个输入区，聚焦时**没有任何**焦点指示，而 §9.13 当时已写下「聚焦环现在各只剩一处出口」——文档结论与代码现实分叉，按 `--focus-ring` 计数才发现。**「画在盒内」这句话第一次只做到了一半**：收口后光哥量出记忆页搜索框的左右环比上下细一倍（2940×1698 截图、DPR 2，上下 4 设备像素、左右 2 设备像素），根因是 `-1px` 的环带跨在边线上（[-1, +1)），外半边照样被贴边的 `.memory-settings` 吃掉。这次不再靠推理定档：用仓库自带的 Electron 起一个不显示的窗口，把 0／-1／-2／-3 四档在「贴边 `overflow: auto`」与「不裁」两种容器里各渲染一遍、截图逐像素量（表与两条附带读数在 ADR-0035 的「第二轮」一节），定下 `-3px`——四边都是完整 2px，且带一道缝。护栏同步换成按**向内可达 ≥ 环宽 + 1px** 判，符号为负不再算通过。
  - **一种几何，五个出口**：`button`／`input`／`textarea`／`select` 由全局那一条规则覆盖；另四处是**这条按元素名点名的规则管不到、却要吃环的表面**——`.disclosure-label`（`summary`：「样式表不再点名 details／summary 元素」那条护栏锁着元素名，所以基座用类承接，见 §10.1）、`.scroll-region`（`div[tabindex]`）、`.single-select-picker-option`（`input` 被 `opacity: 0` 盖住，环要画在 label 上）、`.composer:has(textarea:focus-visible)`（任务输入区的环搬到卡片上，见下）。五条全部写 `outline: 2px solid var(--focus-ring)` ＋ `outline-offset: var(--focus-ring-offset)`；护栏另有一条**数出口**的断言——这五条与 `RING_OUTLETS` 清单等量，多一条要写明它为什么落不到全局那条元素规则上，少一条就是文档在讲一件不存在的事。
  - **复合表面可以把环搬到外层，但必须指名搬到哪**：`textarea` 在 `.composer` 里是透明底、无边框，环落在它身上会在卡片里长出第二个盒子，所以那条 `outline: 0` 保留、环改由 `.composer:has(textarea:focus-visible)` 承载。用 `:has(...)` 而不是 `:focus-within`：后者会在焦点走到卡片里的附件、能力选择器与主按钮时把整张卡点亮，那是「谁被聚焦」的假消息。护栏允许的是**登记过的** `outline: 0`，且必须能查到同文件里真有一条承载它的规则——「关掉环」与「搬走环」的差别就在这条回查上。
  - **1px 分隔缝由「裁到 padding 盒的背景」＋「环不盖住边框槽」两条一起让出**：`--focus-ring` 与 `--brand`／`--danger` 同色系（暗色 jade 下 #7ec6a6 压在 #65a990 上约 1.3:1），环直接贴在实心填充上等于看不见。`.btn` 本来就带 `1px solid transparent` 的边框槽，聚焦时把背景裁到 padding 盒，那一格就露出控件所在表面的底色，与环形成对比。带不透明边框的控件（输入框、下拉）不受影响——那一格本来就是它的边框，聚焦时读作「边框 + 环」。**两条缺一即无缝**：2026-10-01 晚第一次收口时偏移是 `-1px`，环带 [-1, +1) 正好把那格边框槽盖住，实测缝宽 0——这句当时写的是设计意图，不是量出来的事实，改到 `-3px` 才成立（ADR-0035 验证表 c 行）。
- **浮层字号跟随触发控件**：`PopoverMenu` 打开时读取触发元素的计算字号并内联到浮层根，菜单项不自带 `font-size`。浮层是触发器的延伸，两处字号不一致会让菜单看起来属于另一个控件（知识卡片「更多」曾继承正文 14px 而比自己的 12px 触发按钮大）。**只镜像有文字的触发器**：纯图标按钮（`IconButton`）不渲染文字，它的计算字号是从容器继承来的值（composer 的 `+` 一路继承到 UA 默认 16px），镜像过来等于把「浏览器没被设置过」当成控件的字号，菜单会比正文还大——这类触发器走基座兜底的 13px。
- 落地现状：2026-09-26 已把 50 处控件边框/圆角/高度声明换成 `--control-*` 取值，表单控件里裸值残留 0（由护栏强制，`textarea` 的编辑区高度除外）；三档高度都有真实消费者。**2026-09-28 起按钮几何不再靠「记得选对档」维持**：`Button` 基座把 `size` 与 `--control-height-*` 一对一绑死，护栏的 `CONTROL_SELECTOR` 口径同步换成 `.btn` 与 `.icon-button`，原先散在 11 套具名皮与 12 处页面级后代规则里的 16 种 `padding` 组合一并收进三档（[ADR-0031](adr/0031-button-base-and-skin-closure.md)）。

**同日把同一口径推到输入类控件**：29 处控件几何声明里的 12 种 `padding` 组合归进上表三档，勾选框边长 14／16 两套并成 `--control-check-size` 一套，`.capability-search input` 的 `height: 28px` 换成 `min-height: var(--control-height-sm)`；收口后控件几何里裸 px 残留 0，护栏变异验证 8/8 符合预期（含「`.artifact-input-card` 这类卡片名里带 input 不得误伤」这一条）。

**2026-10-01 批次③把这条轴接到组件上**：上面那次收口只改了 CSS，`<input>` 本身仍然没有档位 API——所以「同一排里的输入框与按钮差一档」依然只能靠人眼，而护栏对它是盲的（`rowControlOf` 认不出原生输入控件）。现在 `TextField` 的 `size` **必填**、与 `Button`／`FieldSelect` 同一张成对档位表，`TextArea` 不吃档高（多行区的高度由 `rows` 与内容决定），内距一律取 `--control-padding-lg`；底色、边框、圆角、聚焦环与字号归基座，只读态也由基座表达（`[readonly]` 是「你能看不能改」这一格的唯一出口）。护栏四条见「输入控件基座纪律」，动作排门禁同日开始把 `TextField` 计进一排——知识页检索那一排（`PageToolbar.children`）现在真的会被数到。

### 9.11 叠放层级

`z-index` 只允许取 `:root` 的 `--z-*` 档位，新增浮层必须先选档，不得随手写数字——数字各写各的，叠放关系就退化成「谁后渲染谁在上面」。

| Token | 值 | 层 |
| --- | --- | --- |
| `--z-inline` | 1 | 文档流内的抬升元素 |
| `--z-context-panel` | 4 | 上下文面板 |
| `--z-drag-strip` | 6 | 标题拖拽带 |
| `--z-notification-overlay` / `--z-notification` | 7 / 8 | 消息中心背板与面板 |
| `--z-modal-backdrop` | 19 | 模态基座背板（对话框、抽屉、放映层同一档） |
| `--z-popover-backdrop` / `--z-popover` | 20 / 21 | 浮层基座背板与菜单：**高于模态**，因为模态内也有下拉 |
| `--z-tooltip` | 22 | 文本提示：一档高于菜单，它可能从菜单项或模态里长出来 |
| `--z-toast` | 30 | 反馈堆叠 `#toast-stack`：短时确认与全局通知投影共用同一列（§11.5.1） |

相对顺序沿用改造前的实际叠放结果，两处有意改变：**菜单类浮层一档高于模态**（2026-09-27 凌晨修——模型抽屉里的「模型角色」曾以 12 压在 19 的模态面板之下，点了像没反应；模态内允许开浮层，浮层就必须在模态之上，护栏直接锁 `--z-popover` 与 `--z-popover-backdrop` 都要大于 `--z-modal-backdrop`）；`Modal` 基座落地后**抽屉与对话框背板合并为 `--z-modal-backdrop` 一档**（原 `--z-sheet` 10 与 `--z-dialog-backdrop` 19 并存没有语义依据）。面板本身不设 `z-index`，由背板这一层决定高低。`--z-banner`（40）已随顶部常驻错误横幅删除——那一档给的是第四个反馈落点，不是一个新的层级语义。

### 9.12 工作空间身份色与图标

侧栏按工作空间分组之后，一屏里会同时出现十几个空间，只靠文字名称认不出「这是哪一个」。因此外观有**第三个维度**：

```text
外观 = AppearanceMode（system｜light｜dark）× ColorScheme（jade｜…）× WorkspaceAccent（moss｜…｜slate）
```

- 身份色表达的是**这个空间是谁**，不是**应用长什么样**：切换色系或明暗都不改变某个空间的档位含义，只换它在这一档上的具体色值。
- 因此它只提供两套值（浅色与深色），**不随四套色系各出一份**。这与 §9.1 对色系的要求不同，理由就是上一条：它不参与品牌表达，只参与识别。护栏「工作空间身份色的每一档都在明暗两套 Variant 里成对定义」锁住这件事，少一档深色值即红。
- 8 档固定色板：苔绿 `moss`、青碧 `teal`、天青 `azure`、靛蓝 `indigo`、紫檀 `plum`、胭脂 `rose`、琥珀 `amber`、石墨 `slate`。**不提供取色器**，沿用 §9.2 的理由——任意颜色会破坏对比度与组件状态一致性。
- 色值只住在 `styles.css` 的 `--ws-*` Token 里；`appearance.ts` 只登记档位与中文名，组件一律经 `lib/workspace-identity.ts` 的 `workspaceAccentVar()` 取 `var(--ws-<id>)`，页面不得再写十六进制。
- 图标 12 枚（`folder / doc / sheet / slides / chart / client / research / writing / code / project / cycle / library`）先进 `icons.tsx` 再使用：形状承载「这是哪类持续工作」，颜色承载身份。两者都由协议枚举定档，图标集与色板各按 `Record` 穷举，漏一档即编译不过——枚举、色板、图标三处不会各说一半。
- 带身份图标的行仍然只是行：图标不着色块底，选中与悬停继续走 §9.8 的表面档位。

### 9.13 排版、图标与表面档位

§9.7 原先推荐了五档字号，却没有 Token、也没有护栏，行高只写「1.6 左右」；§9.10 管住了控件的高度与内距，却没有管**文字本身**。2026-10-01 的全仓家底核查因此抓到：`styles.css` 的 171 条 `font-size` 声明有 14 种取值、65 条 `line-height` 有 10 种，22–56px 的方块边长有 10 种，图标字形有 9 种。这不是「有规范不遵循」——**这几条轴从来没有档位表**，于是每个表面各挑一个数，谁都没有错可犯。

本节给六条轴定档，每条轴同时落 Token 与护栏。

| 轴 | 档位来源 | 档值与用途 |
| --- | --- | --- |
| 字号 | `--font-size-*` | `caption` 12px 说明与次要文字／`body` 13px 正文与控件／`emphasis` 15px 强调正文与对话／`heading` 18px 区块与表面标题／`page` 20px 页面标题／`hero` 28px 空态与欢迎页主标题 |
| 行高 | `--line-height-*` | `tight` 1.4 标题与单行截断／`normal` 1.5 单行控件与密集行／`body` 1.6 正文（缺省）／`loose` 1.7 长文与对话 |
| 表面内距 | `--card-padding`（§9.8 已有）·`--surface-padding-panel`·`--surface-padding-modal`·`--surface-padding-page` | 12px 16px 卡片与就地块／16px 面板、抽屉正文与编辑器／24px 模态、浮层面板与整页占位／28px 0 48px 页正文 |
| 输入框几何 | 沿用 §9.10 的 `--control-height-*` × `--control-padding-*` | 与按钮同一张表、**成对使用**；收口基座是 `TextField`／`TextArea`（2026-10-01 批次③落地，见 §9.10 与本节规矩 10） |
| 图标字形 | `icons.tsx` 的 `ICON_SIZES`，类型即 `IconSize` | 12 与说明文字并排的行内图标／13 按钮与下拉里的图标／16 独立出现（省略 `size` 时的缺省）／18 卡片身份块的强调图标／20 导航行图标（侧栏一级导航与设置导航） |
| 标记方块 | `--mark-row`·`--mark-card`·`--mark-hero` | 24px 行前小方块与通知条图标／32px 卡片·列表·抽屉标记与区域空态／40px 整页空态与错误页图标 |

**规矩**

1. **六条轴一律取档位，不写裸值**。字号与行高的 163／63 条声明已全部换成 `var(--…)`，护栏判的是「有没有落在档位表里」，所以将来调某一档只改 `:root` 一行。
2. **例外只有两类，且只降不升**：图形化标识（品牌字标 16px 与其 10px 副标、格式徽标 10px／9px、未读数徽标 10px）与两处绝对定位微标的 `line-height: 1`（它只为自身居中，不参与排版）。清单在护栏的 `TYPE_LADDER_EXEMPTIONS`，新增一处必须写明它凭什么不算某一档。§9.7 那句「不得用小于 12px 的字号承载产品信息」仍然成立——这些例外全是徽标，不是文字。
3. **成果文档正文不吃应用的字号档位**：`.markdown-preview` 是 Artifact 自己的排版，§9.6 已规定应用主题不得改它的配色，同理不替它重定字号（保留 22px 与对话内预览的 24px）。**行高是排版而不是文档语义**，因此 1.8 已并入 `loose` 1.7，§9.7「长文预览行高 1.7 左右」这句第一次有了唯一值。
4. **21px 被请下档位表，区块标题取 18px**。页面标题在 2026-10-01 由产品定为 20px（§9.7），若再留一个 21px 的区块标题，等于同时供着两个只差 1px 的档——这正是本轮要消的缺陷形状；而且版心里的小节会喊得比自己所在的页面还响。**层级由「页头带／版心内」与字重承担，不由 1px 承担**。
5. **1.45／1.55／1.65 全部并档**：它们与 1.4／1.6 的差别在任何一块屏上都读不出来，却是每次改样式都要重判一遍的三种「差不多」。`.composer textarea` 的 1.55 并入 `body` 1.6，`.card-title`／`.list-row-title` 的 1.45 并入 `tight` 1.4。
6. **图标尺寸是类型，不是「记得选对数」**：`IconProps['size']` 是 `IconSize`，写 `size={14}` 编译不过。原先的 14px 有 8 个调用点，另有 15／17／10 各一处，本轮分别并入 13／16／12；`IconButton` 的字形表 `GLYPH_SIZE` 直接引用 `ICON_SIZES`（`md` 那一档 14 → 13，与按钮文字同一档），不再自己写一份数字。
7. **表面内距只管「一块独立表面的内缩」**：行内节奏（徽标、chip、菜单项、代码块）、控件内距（§9.10）与堆叠的缝（§9.8 那把 4／8／12／16／24／32 的尺）各归各的轴，不要因为数字相同就混着用。**定宽列的段落内缩（`.context-section`／`.brief-panel`／`.activity-list`）由 §9.8 与 `components/ContextPanel.test.tsx` 的 `INSET_OWNERS` 清单管**，本条批次②不动它——一处有测试钉着的清单不该被另一条轴的批量迁移顺手改掉。同一天这条轴自己收了口：段落壳的水平内缩并到 16px 一档，判据、刻意不并的两处与护栏三条见 §9.8「定宽列里的每一段都要自带内缩」。数字撞上 16px 不等于并进了同一条轴——`.modal-panel[data-variant='viewer']` 用的还是 §9.13 的面板档。同日稍晚，列壳自己那道余量（侧栏／设置左导航／成果详情左列）也并到 16px，判据与护栏四条见 §9.8「整列的水平余量」。顺带记下本条护栏的口径盲区：它按「用了 `--surface-padding-*`／`--card-padding` 的规则」比对，看不见「该取档却写了裸值」的表面——`.settings-nav-list` 的 36px、`.dependency-operation` 的 10px 一路没被它拦下；列壳三处的水平格改由 §9.8 那份新清单钉住，纵向那一格仍待另案。
8. **卡片档沿用 `--card-padding`，不另起别名**：两个名字指同一份几何，正是这张表要消的东西。新增表面要先选档并登记进护栏的 `SURFACE_PADDING` 清单；`.modal-panel[data-variant='sheet']` 的 25px、`.empty-page` 的 40px 与 `.loading-page,.error-page` 的 32px 已并入模态档 24px，`.message p` 的 13px 15px 与 `.toast` 的 11px 12px 已并入卡片档。
9. **标记方块按所在表面选档**：`.card-mark` 36 → 32、`.knowledge-format` 34 → 32、`.completed-work-icon` 30 → 32、`.artifact-input-card-icon` 28 → 32、`.evidence-list` 行前方块 22 → 24、`.error-page-icon` 32 → 40。同一类方块此前有 10 种边长，其中 30／32／34／36 四种差的都是那 2–6px——没有人这样设计，是四个人各记了一遍。
10. **`font:` 简写不算档位**。简写会连带设置 `font-size` 与 `line-height`，而上面两条护栏只认这两个属性名——2026-10-01 核查时欢迎页口号与三处等宽块正是用简写写着 1.35／1.55 与裸字号，档位表改了它们不动，prettier 又把简写的值折到下一行，单行 grep 也看不见。字号与行高一律用长写法声明，元素复位那条 `font: inherit` 除外（它不带任何档位）。
11. **输入框与多行区走同一张成对档位表，出口是 `TextField`／`TextArea`**（2026-10-01 批次③落地）：`TextField` 的 `size` 必填、与 `Button` 同一张 `--control-height-*` × `--control-padding-*`（§9.10），三档在 CSS 里成对穷举；`TextArea` 没有档高——它的高度由 `rows` 与内容决定，内距一律取 `--control-padding-lg`，等宽正文另走 `mono` 属性（字体栈只有 `--font-mono` 一份）。底色、边框、圆角、聚焦环与字号归基座，领域钩子只留位置与尺寸。原生 `<input>` 只剩勾选轴（`type="checkbox"`／`"radio"`，见 §10.1 的 `Switch` 与 `CheckList` 那条），任务输入区的 `<textarea>` 归 `Composer`。

**不属于这三档的方块**（各有各的轴，护栏按理由登记）：`.switch-track` 一类的控件几何、外观页的模式与色系预览（54／38px）、窗口拖拽带（40／24px）、品牌算珠标与品牌字标容器。

**落地现状**：字号六档与行高四档已全量覆盖 `styles.css`（171 条 `font-size` 里 163 条、65 条 `line-height` 里 63 条换成档位 Token，例外 10 条声明按清单登记）；图标档位由 `IconSize` 类型强制，调用点裸数字残留 0；标记方块 10 件（20 条 `width`／`height` 声明）取 `--mark-*`；表面内距 27 条登记取四档。**输入框几何同日收口**：41 处迁进 `TextField`／`TextArea`（37 个 `<input>` ＋ 13 个 `<textarea>`，留原生的 8 处勾选行与 `Composer` 那一处任务输入区不算）。`styles.css` 里选择器点名原生输入控件的块原有 34 条，其中 **30 条真的在写外观或几何**；收口后基座之外只剩 **6 条**——一条全局 `:focus-visible` 复位、`Composer` 输入区两条、只钉 `min-height` 的布局钩子三条。退役的 24 条由基座那一个出口（9 条规则）承担；勾选轴那 6 条里有 1 条本就是替勾选框撤销页面后代规则的，被撤销的那条先走了，它也就没了存在理由。这 30 条里底色曾有 `--surface`／`--surface-raised`／`--canvas`／`transparent` 四种、字号曾跨 `caption`／`body`／`emphasis` 三档、内距 shorthand 曾有 `11px 0` 一把裸值加三档 Token、聚焦环曾有档位环／`outline: 0`／`outline: none` 三种处置（后两种把焦点环换成一条边框或干脆关掉），现在各只剩一处出口。**这句「只剩一处出口」当时并不成立**：`Composer` 那两条里的 `outline: 0` 作为例外留着，任务输入区因此一直没有焦点指示，而「页面不得替输入控件发几何与外观」那条护栏只扫选择器含 `.text-field`／`.text-area` 的规则，看不见它——同日由 [ADR-0035](adr/0035-focus-ring-inside-control-box.md) 把环统一收进控件自己的盒子（§9.10），并给「关掉环」加上「必须指名搬到哪」的回查。护栏见 `standards/coding-standard.test.ts`「排版与图标档位纪律」（六条，含新增的 `font` 简写一条）与「输入控件基座纪律」（四条，含 docs/10 档位表 ↔ `styles.css` Token 的双向同值比对——文档里写的数必须就是代码里那个数）。

## 10. 组件体系

### 10.1 组件台账与基座纪律

本节是 AI 检查、Review 和创建页面时的组件入口。**只登记真实导出与当前契约**；历史名称、迁移数量与修复过程见 [UI 治理评估](reviews/2026-10-02-ui-governance-alignment.md)及其引用的历史报告。不得从旧评估推导新任务或另造组件。下面路径以 `apps/desktop/src/renderer/src/` 为根，组件名按源码导出字面填写；门禁双向核对台账与 `components/` 的导出，不把纯函数、类型和样式钩子当组件。

#### 10.1.1 页面创建与 Review 的执行顺序

1. **确认页面形态与主要动作。** 名称查 §6.1。普通管理/详情页每个可见返回分支实际组合 `PageHeader`、`ScrollRegion`，内容落在 `.page-body`；有工具栏用 `PageToolbar`，集合用 `ViewContainer`。设置内嵌分区沿用设置宿主，标题用 `SectionHeader`；记忆有列表时用 `ScrollRegion`，首读/全库空集合允许 `EmptyNotice`，逐分支核验已登记的替代出口。工作页由 `App.tsx` 组装页头、消息列与 `Composer`，不是新造一个工作页。已登记的设置形态见 `PAGE_SHAPE_EXCEPTIONS`，不能把新普通页加入例外来省略骨架。
2. **按语义选组件。** 先查下表及真实 props；领域呈现优先找同类组件。已有组件缺能力时扩展它的变体/槽位，新的稳定组件再登记台账；不要为单个页面外壳或未来可能复用提前抽象。未实现的 Skeleton、PlanStep 等名称不充当开发模板，也不要求预先补齐。
3. **明确数据、状态与结果出口。** IPC 与有状态动作进 hooks，纯函数进 lib；视图只组合。逐项说明首读、空集合、搜索无匹配、刷新、失败、忙与取消哪些适用。只读对象状态、一次动作结果和空态按 §11.5 与下表分别选出口；无需给每个静态控件发明“成功/错误态”。
4. **确定几何所有者。** 页头/版心归 §8.3，缝归容器 §9.8，控件档位归 §9.10，排版/表面归 §9.13。领域 `className` 只承载位置、尺寸或已登记的状态，不复制基座底色、边框、圆角、内距、槽位结构。新名字也要检查表面所有者与版心。
5. **验证用户路径。** 长中文、英文路径、窄窗口、明暗主题、键盘可达性、焦点归还、失败后保留输入与重试必须按本次改动实测。页面首屏优先目标、内容和主要动作；来源、诊断与治理解释按需披露。已有批准交互仍以对应设计为准。
6. **给出 Review 证据。** 记录“页面/分支 → 所用骨架与组件 → 状态/反馈出口 → 自动检查与页面走查 → 仍未验证项”；运行 `npm run verify`。例外变更必须说明为何既有契约不适用、精确出口和回归证据，不能只写“门禁要求登记”。

普通页面的组合示意（领域类只承担页面位置，不覆写骨架）：

```tsx
<section className="example-page">
  <PageHeader eyebrow="按 §6.1 取名" title="用户目标" actions={pageActions} />
  <ScrollRegion ariaLabel="页面内容">
    <div className="page-body">
      <PageToolbar ariaLabel="筛选与操作">{filters}</PageToolbar>
      <ViewContainer mode="list">{content}</ViewContainer>
    </div>
  </ScrollRegion>
</section>
```

这段是组合示意，`pageActions`/`filters`/`content` 需由页面给出；不存在可以自动接管领域数据与 CRUD 的万能 Page。

| `WorkspaceSelector` | `components/WorkspaceSelector.tsx` | 当前工作空间入口与可搜清单；PopoverMenu 领域组合，特殊触发形态已登记 |

#### 10.1.3 组合约束与检查边界

- **所有者明确。** 普通卡片/行/徽标走 Card/ListRow/Badge；背景＋圆角＋内距或边框形成的新表面按 `SURFACE_SHELL_OWNERS`/`SURFACE_PADDING` 检查，同一选择器分开声明也合并。固定限宽按 `FIXED_MAX_WIDTH_OWNERS` 登记用途，不得另造页面版心。新领域表面不是普通卡片确需独特结构时，先说明用途与已有基座为何不适用。
- **内联样式精确出口。** 几何进样式表，动态浮层定位、工作空间语义色、成果排版仅按 `INLINE_STYLE_OUTLETS` 的文件/元素/表达式保留；不能整文件放行。对象、条件或展开不是规避 style 检查的理由。
- **槽位保留基座责任。** 不手排 card/section-header 等槽位类，不用后代 CSS 替按钮/输入/骨架发外观。一排动作走 §9.10 的登记槽位或 `ActionBar as="div"`；横向、内容宽、可换行。裸按钮只有明确的非动作形态清单，不表示页面可自造文字按钮。
- **目录事实与动作一致。** 技能/专家卡片与列表用同一 facts 函数；身份、署名/修订、说明与动作不能在另一档丢失。主行动可用 opacity 悬停显形，DOM/位置常驻且 focus-within 同样显形。点击身份/说明进入详情，标签与页脚动作在点击区外。内置专家复制后编辑，有历史引用的删除受 RESTRICT；Skill 删除的级联含运行绑定，确认文案按真实语义写，不能照抄专家。
- **浮层语义在基座。** 菜单归 PopoverMenu，夺走页面焦点的覆盖层归 Modal/useOverlaySemantics 并 portal 到 document.body；触发器提供 haspopup/expanded，Esc/Tab 只属最上层，菜单内焦点不被下层 Modal 抢走。不得复制焦点/键盘实现；非原生按钮角色回原生基座。
- **主题逐套检查。** 每个正式色系 light/dark 块各自实现 §9.3 的完整语义色集合；全局几何、动效、中性成果画布与工作空间身份色按自己的作用域处理。
- **状态按适用性验收。** 交互控件验证默认/hover/focus/pressed/disabled，异步动作再验 busy/终态，对象按领域验证状态。骨架、只读徽标和纯排版组件不强行补成功/错误 API；反馈按 §11.5 路由。

| 证据层 | 能保证什么 | 不能据此宣称什么 |
| --- | --- | --- |
| ESLint/类型 | 类型、显式档位、Hook 与部分交互语法 | 键盘处理真实有效、文案层级合理 |
| 结构护栏与违规变异回归 | 组件台账导出、页面可追溯组合、精确出口、档位/所有者/主题契约 | 任意运行时条件、动态 CSS 或未知包装都能静态证明 |
| 组件行为测试 | 用例覆盖的状态、输入、失败、键盘/焦点行为 | 所有页面的组合都已验收 |
| ui:check | 全正式主题 × 两档窗口的固定生产组件组合，自然高度/骨架/菜单/模态/焦点、工作空间色块实际尺寸与颜色及临时截图 | 完整页面视觉差异、文字对比度认证、屏幕阅读器或真实 Run |
| 本次页面走查 | 明确记录的主题、窗口、用户路径与状态 | 未走查页面或真实模型语义已通过 |

静态解析无法追踪的包装要改为可追溯组合或给出精确形态与行为证据；Review 必须看新增/扩大的白名单与规则变更。`npm run verify` 全绿是必要条件，不能独自证明产品与视觉验收完成。历史评估与日志只用于理解决策，不是当前待办；状态与开工授权仍查对应任务板。

## 11. 关键交互规则

### 11.1 启动与运行

- 发送后输入框保留当前上下文，发送按钮切换为停止按钮
- 第一时间反馈“已开始”和当前阶段，不等待模型首个 token 才响应
- 连续工具事件合并为一个 ActivityGroup，默认显示用户可理解的摘要
- 原始事件只在开发模式或过程详情中查看

当前实现状态：

- 发送后输入框文本被清空，用户目标以消息块形式保留在对话流顶部——「保留当前上下文」指任务上下文而非输入框文本。发送/停止按钮切换已落地。
- 提交即创建 Run、展开右栏并切到「过程」页签，不等首个 token。已落地。
- ActivityGroup 合并已落地（理解任务 / 处理工作材料 / 整理结果 / 任务完成），阶段标题通过 TOOL_LABELS 覆盖已登记工具（映射在 `lib/labels.ts` 的 `TOOL_LABELS`），检索类工具还会给出「已查阅 N 条来源」这种具体摘要。新增工具必须同步该映射。
- 对话按「用户要求 → 紧凑过程摘要 → 主要回答 → 成果操作」排列。每个 Run 的工具过程默认只占一行，显示次数、进行中/失败/停止状态；展开后以可键盘操作的工具药丸呈现，逐项打开参数、结果和错误。成功不铺满绿色卡片；长路径与输出不能撑宽对话列。中间轮次文本不拼入已完成的最终回答。
- 对话回答采用无外框的正文排版，不复用成果预览的纸张边框、阴影与大内边距。成果自身的预览样式不变。
- 过程面板复用同一套工具药丸与详情。参数与结果分区、结构化字段分组，文本保留换行，JSON 缩进；长输出在有高度上限的区域滚动，默认不挂载全部原始载荷。失败和取消有可见状态，不因折叠而伪装为成功。
- 流式生成仅在用户接近底部时自动跟随；用户上翻后保留阅读位置，提供「回到最新」入口。展开工具详情不触发强制滚动。打开历史任务定位到最新回答开头；无过程查看需求时右栏默认收起，开始执行不强制展开。

### 11.2 确认与错误

- 需要用户决定时，确认块出现在主内容流中，不藏在右栏或 Toast
- 错误说明发生了什么、受影响的对象和可执行的下一步
- 连接失败、模型不可用和工具失败使用各自具体文案，不统一显示“未知错误”

### 11.3 上下文面板

- “过程”按目标阶段分组，不按底层事件类型堆叠
- “资料”显示正在使用和已引用的文件或网页
- “成果”显示当前 Task 的 Artifact 与版本
- 面板关闭后，关键确认和完成状态仍必须在主工作区可见

### 11.4 模型配置

- 模型列表优先，编辑其次；不在同一窄弹层内永久并排
- 创建后不自动宣称连接成功，必须经过实际测试
- 默认角色包括文本、视觉和嵌入；同一模型可以承担多个角色
- Provider 高级兼容参数默认折叠，避免首次配置时产生认知负担

### 11.5 消息中心与通知

同一结果事件以三层呈现，三层是分工而不是三个独立功能：

| 层 | 载体 | 生命周期 | 职责 |
| --- | --- | --- | --- |
| 内联反馈 | `InlineError`（`components/InlineError.tsx`，danger／warning 两档） | 停留在页面期间 | 操作当时的直接说明（如导入跳过原因） |
| Toast | 右下角浮层 | 自动消失（常规 4s，错误 6s） | 用户可能已切走视图时的即时提醒 |
| 消息中心 | 侧栏铃铛 + 下拉面板 | 持久化，可回溯 | 所有长操作结果的统一留档与回溯入口 |

规则：

- 所有长操作结果一律写入消息中心（SQLite `notifications` 表，200 条滚动上限，超限淘汰最旧）；Toast 是否弹出由「同页抑制」决定：用户正在对应页面时不弹（页面已有内联反馈），在其他视图或查看其他任务时才弹。
- run 取消是用户主动行为，不产生通知。
- 通知条目必须携带可跳转 target（任务 / 成果 / 知识页）；点击条目复用既有导航入口（如最近任务、成果卡片）跳转并标记已读，不另造导航路径，不破坏进行中任务的状态。
- 铃铛固定在侧栏底部、设置入口上方，全局唯一入口；侧栏折叠或窄屏图标栏下退化为图标 + 红点。面板自铃铛向右侧主区展开，宽度约 360px，须挂在与铃铛同级的定位容器内，避免被 `overflow: hidden` 外壳裁剪。
- 未读徽标使用 danger 色圆点加数字，封顶显示 99+；面板内未读条目用 brand 色圆点与加粗区分，支持单条已读、全部已读与清空（清空需确认）。
- **未读数只数「还需要处理的」**：`level: success` 的通知照样落库、照样能在消息中心回看，但**写入即已读**，因此不计入铃铛数字，也不再投影成右下角浮层——它是一条留档，不是一次打扰。这一条的由来是铃铛一度挂着 40 条未读、其中 25 条是「任务跑成功」：一个不携带任何信息的数字，比没有数字更糟。失败（`error`）与部分完成（`warning`）继续计未读并投影。窗口失焦时的系统通知按 `systemNotify` 单独决定，不随本条降级——那已经是「你不在这儿」的另一套口径。
- Toast 堆叠上限 4 条，hover 暂停消失，可手动关闭，点击可按 target 跳转；位于右下角，短暂覆盖上下文面板属预期行为。
- 窗口失焦时，run 完成 / 失败发送系统通知（Electron Notification）；点击系统通知聚焦窗口并跳转对应任务。导入与导出不发系统通知。
- 通知颜色一律消费语义状态 Token；`warning` / `info` 及其柔和背景是 §9.3 契约的组成部分，引入时必须当场补齐全套色系 Variant，不得先出一套主题再补另一套。

### 11.5.1 反馈通道决策表（所有界面反馈的唯一归类入口）

任何「操作结果」先按下表归类，再选通道；**只有三个合法落点，且每个落点只有一个出口组件**。上表描述的是**长操作结果**的三层投影；短时确认与表单错误由本表裁定。多一个表面——哪怕只是「换个位置显示同一句话」——就是制造第二处真相。

| 事件类型 | 唯一出口 | 是否落库 | 生命周期 | 例 |
| --- | --- | --- | --- | --- |
| 用户当场发起、当场可见的结果（成功 / 信息 / 拒绝 / 失败） | `TransientToast`（`components/TransientToast.tsx`，成功与信息 4s、错误 6s 自动消失） | 否 | 数秒后自消 | 模型连接成功、Skill 已导入、成果已导出、打不开某条任务 |
| 需要停留、且当前表单／对象可据以行动的错误或警告 | `InlineError`（`components/InlineError.tsx`，`danger`／`warning` 两档） | 否 | 停留并随修正消失 | 保存校验失败、跨空间引用被拒、依赖检测阻塞 |
| 用户可能已切走的长操作结果 | `NotificationService.create` → 消息中心 + 全局 `ToastHost`（同页抑制） | 是（`notifications` 表） | 持久可回溯 | 任务 Run 终态、资料导入作业 |

三问按顺序判，判到哪个就停：

1. **用户还在这儿吗？** 发起与结果之间隔着秒级以上、期间可能已经切走视图 → 第三类。
2. **这句话需要停留吗？** 用户要读完它并据此改点什么 → 第二类；只需要「知道了」→ 第一类。
3. **当前对象承载得了吗？** 承载不了（导航失败、全局前置条件不满足）→ 第一类。**不得**为此造常驻横幅。

四条最易踩的边界：

- **一次结果只有一个落点。** 同一条失败消息既写进对象的 `error` 状态（内联）又交给上层再播报一遍，是本表被绕过最常见的方式——用户看到的是同一句话出现在两个地方，并且关掉一处后以为「关不掉」。规则：调用链上**最先能承载这条消息的那一层**负责呈现，其余层只 `trackAction` 记录，不再上传到别的通道。
- **代码里有两个「toast」，写文档或提 PR 必须指明是哪一个**：`TransientToast` 是局部、自消、**不落库**的短时确认；`ToastHost` 是全局右下角浮层，本质是**一条已持久化通知的投影**（必然伴随写入消息中心，并受「同页抑制」控制）。短时确认**不得**走 `NotificationService`，否则会把瞬时提醒沉淀进消息中心、污染可回溯列表。
- **两个浮层共用一个堆叠容器。** `TransientToast` 与 `ToastHost` 都挂在 `#toast-stack` 这一枚固定容器里（右下角，`gap: 8px` 纵向堆叠），页面不得再给自己的提示块写 `position: fixed`——两处各自 fixed 在同一坐标，结果是谁后渲染谁盖住谁。
- **内联反馈块不长出成功态。** 成功 / 信息一律用 `TransientToast`。禁止用常驻内联块充当「顶部成功横幅」，也禁止换个类名绕开护栏再开一条成功通道；列表页顶部的持久结果横幅、Hook 内自造的自动消失计时器都在禁止之列。**本条只管「表面」**——有底色、有内距、能自成一块的那种。`InlineError` 的档位因此只有 `danger`／`warning`，护栏直接锁死档位集合。**「无底纯文字」不等于自动出表**——分界看「说的是哪一件事」，不看「有没有底」：说的是「你刚点的那一下怎么样了」就是反馈，必须走上面三个落点之一；说的是「这个对象现在是什么」才是状态呈现，走 §11.5.2 的 `StatusNote`。据此 2026-09-29 收口三处：`.action-note`（唯一调用点写的是「保存成果」的成功／失败两档，是动作结果）拆成失败进 `InlineError`、成功进 `TransientToast`，三条规则删除；`.success-copy` 是只读状态说明，迁进 `StatusNote`；`.memory-projection`（`padding: 10px 12px` ＋ `--warning-soft` 底 ＋ 壳里手排图标／文字／按钮）是上一轮反馈收口漏掉的第 8 个带底错误条，迁进 `InlineError` 并登记进「不得复活」。**上一轮把 `.action-note` 整类划给状态轴是误判**，`.qoder/rules/betterwork-ui.md` 里那句同步作废。

落地现状：知识页曾把作业终态写成常驻 `.inline-message`（「来源检查完成（9/9）」与消息中心重复且不会消失），2026-09-27 已收口——钩子的反馈通道拆成 `error`（内联、可行动）与 `toast`（`TransientToast`、自消、不落库），作业**成功**不再在页面重复播报，只有部分完成与失败留内联并带「查看条目／重试」入口。2026-09-28 接着收两处同源病灶：顶部常驻横幅 `.action-error-banner`（本表之外的第四个落点，25 个调用点共用一个全局单槽，互相覆盖且跨视图串台）与成果页自己的一套 `.artifact-action-error`；内联错误表面从 8 套几何（四种 padding、一处无圆角、一处无字号、动作有 float／margin／无三种摆法）收成 `InlineError` 一处。2026-09-29 收掉同轮查出的剩余三处：`.action-note.ok` 这条内联成功通道按三问拆进 `TransientToast`／`InlineError`，`.success-copy` 迁进 `StatusNote`（§11.5.2），`.memory-projection` 作为第 8 个带底错误条迁进本基座。护栏见 `standards/coding-standard.test.ts`「反馈通道纪律」：渲染层出现已废弃的反馈表面类名即失败；`role="alert"` 的节点必须走 `InlineError`；内联通道出现成功配色即失败；`InlineError` 基座不得自带上下缝；右下角那一列浮层只有一个容器；`TransientToast` 的自消计时不得依赖 `onDismiss` 的标识。**「同一条消息不得占用两个落点」这一条静态测不到**——它要跨调用链做数据流分析，只能靠评审与本表约束；2026-09-28 的账本曾把它写成「已配护栏」，那是声明与强制点断线，2026-09-29 改正。

### 11.5.2 状态呈现（`StatusNote`）与反馈通道的分界

反馈轴（§11.5.1）回答「你刚做的那一下怎么样了」，状态轴回答「这个对象现在是什么」。后者常驻、不自消、不落库，因此不进那三个落点——但它同样只有一个出口：`components/StatusNote.tsx`。两轴各立一条，任何一句界面文字都能被问到「它是哪一轴的、由哪个组件出口」。

| 我要说的是 | 用什么 | 长相 |
| --- | --- | --- |
| 一小段只读状态词（已信任／已就绪／待确认） | `Badge`（tone × shape） | 有底的片 |
| 独立成行的一句状态说明（当前依赖已有有效授权／有 N 项阻塞） | `StatusNote`（tone 四档 × `problems` 槽） | 无底纯文字 |
| 一次操作的结果 | §11.5.1 的三个落点 | 按落点 |
| 这里还没有东西 | `EmptyNotice`／`EmptyContext`／`EmptyPage` | 占位 |

- **`StatusNote` 不带表面**：无底色、无内距、不自带上下缝（缝由容器 `gap` 或容器侧规则拥有）。它因此不会与 `InlineError` 抢「内联块」的观感，也不会成为第二个成功通道——一行绿字说的是「现在如此」，不是一句确认。
- **不得用它承载操作结果。** `tone="success"` 只描述持续为真的事实；「已保存」「已导出」这类一次性确认一律走 `TransientToast`，把它写成常驻一行就是 §11.5.1 禁止的常驻成功态换了个类名。这条判据静态测不到（组件不认文案时态），靠台账与本条约束，评审时按「这句话明天还成立吗」判。
- **档位只有四档**：`neutral`／`success`／`warning`／`danger`。`--info` 是**通知等级**那一套词汇（消息中心、作业行、轮询提示），不是状态语气，不为它补第五档；`Badge` 的 `brand`／`outline` 同理不镜像。
- **「要注意的一段」留在领域类是结构限制，不是口径松动**：`Field` 的 hint 是 `<span>`（只接受短语内容），块级基座放进去就是非法 HTML，所以 hint 里那句「随包资源缺少 …」只能是一段带色的文字。`.dependency-warning` 为此保留，且只为这一处保留——它不再承担任何独立成行的状态说明。
- **第二类有意保留：「该怎么读这一段」的说明**。上下文面板曾有三个只差字色的类承载 21 处一句话文字（`.context-hint` `--text-muted`／`.context-note` `--text-secondary`／`.context-phase` `--text-secondary` 且无行距）——同一件事三处真相，与收口前的 `Button`、`InlineError` 同源；`MemorySuggestionList` 另有 3 处 `.context-hint`，全仓共 **24 处**。2026-09-29 逐句分类后：**空态归 `EmptyNotice`（10 处）、对象状态归 `StatusNote`（12 处）**，`.context-hint` 与 `.context-phase` 连同 CSS 规则一并退役；剩下 3 处讲的是「以上是范围预览，以下方为准」「旧轮次只是这次不发送，对话没有被删除」这类**读法说明**——它既不是「这里没有东西」也不是「这个对象现在是什么」，硬塞进任何一条轴都是错的，所以 `.context-note` 作为唯一一件保留，且只承载这一类。判据：把这句话换成「这里没有东西」或「这个对象现在是 X」念一遍，两句都不通才是说明。其中 `MemorySuggestionList` 那处 `<p>` 原本用一个三元把「本轮没有待确认的建议。」与「当前有 N 条待确认候选」塞进同一个元素——**空态与状态混在一处**，分类时拆开，各归各的轴。
- 护栏四条见 `standards/coding-standard.test.ts`「状态呈现纪律」：已废弃的 **11** 个自造状态说明表面不得复活（清单里既有并入 `StatusNote` 的类，也有并入 `EmptyNotice` 的类——`.context-hint` 的 13 处里 8 处是空态）；`.danger`／`.danger-text` 这类「谁都能拿来给一句文字上红色」的裸字色 utility 不得复活；`.status-note` 基座不得长出底色／内距／上下缝且档位集合锁死；`styles.css` 里每一处语义状态字色必须命中四个出口之一或在登记清单内（清单自核——登记的类名在 CSS 里消失即红，防止护栏悄悄变成空跑）。

## 12. 无障碍与可用性底线

- 全部主要路径支持键盘操作
- 焦点顺序与视觉顺序一致，焦点环清晰可见——环画在控件自己的盒子里，不依赖任何祖先给它留余量（§9.10、ADR-0035）
- 正文和控件达到 WCAG AA 对比度目标
- 重要按钮使用文字或可访问名称，不能只靠难以识别的图标
- 界面功能图标一律使用内联 SVG 描边图标（`currentColor`、统一 24 网格与笔画粗细，见 `renderer/src/icons.tsx`）；禁止用 Unicode 字符或 emoji 充当界面图标，品牌字标与格式徽标（MD/PDF）除外
- macOS 无边框窗口：仅窗口顶部标题带（三栏各自的头部区域）承载拖拽与双击最大化，双击遵循系统「双击窗口标题栏」偏好；标题带以下的任何内容区与空白区不得承载拖拽、双击等窗口行为；红绿灯位置不得与侧栏内容重叠
- 空状态必须说明可以做什么，不使用纯装饰插画占位
- 允许系统缩放和较长中文文案，不以裁切作为默认处理

## 14. 界面工作实施边界

任何实施者（编码智能体或开发者）进行界面工作时，应遵守以下边界：

- UI Foundation 已完成；后续界面工作是在本文规范上的增量，不是再次重构
- 不在界面改动中改写 Agent Core、模型协议和数据库语义
- 允许重构 Renderer 组件结构，但保持现有类型化 IPC 契约
- 先做少量基础组件，不为追求“设计系统”引入过重框架（取舍理由见 [系统架构](03-system-architecture.md) §10）
- 每完成一个阶段都启动真实 Electron 应用进行视觉检查，不能只依赖静态代码判断；启停只用 `scripts/dev-start.sh` 与 `scripts/dev-stop.sh`
- 新增颜色先进 §9.3 的 Token 契约并当场补齐全套色系 Variant；新增图标先进 `icons.tsx` 图标集再使用
- 对照 LobsterAI 时先阅读对应实现，必要时启动观察，但以本文档和 BetterWork 领域模型为最终准则

## 15. 完成标准

UI Foundation 完成后应达到：

1. 首屏一眼能看出这是用于完成知识工作的产品，而不是 Agent 调试 Demo。**已达成**
2. 用户始终知道当前 Task、运行状态和主要成果在哪里。**已达成**
3. 过程信息可见但不喧宾夺主，右侧面板可以完全收起。**已达成**（收起后整体卸载，不留残条）
4. 模型配置具有独立、完整、可理解的操作路径。**已达成**（并扩展出搜索配置分区）
5. 字号、间距、颜色、圆角和组件状态来自统一 Token。**已达成**：颜色 Token 覆盖 8 个 Variant（含 `border-subtle` 与 `on-danger`），小字号已收敛到 12px 下限，动效时长来自 Token；硬编码色值只剩两类刻意例外：CSS 的色系预览卡（§9.3）与 TS 侧三个文件（首帧窗口主题、外观预览色板、品牌标志），清单以护栏白名单为准
6. 浅色、深色与常见桌面尺寸均通过视觉验收。**部分达成**：每轮改动均有真实桌面人工验收记录，但没有 §13 UI-5 要求的三尺寸 × 3 模式 × 4 色系验收矩阵；字号与动效收敛后还需要重新走一轮人工验收
7. UI 重构没有破坏现有 Agent 教学链路和真实模型链路。**已达成**（Fake Provider 与 OpenAI-compatible Provider 链路的回归测试持续通过）

第 5、6 条的残留缺口应作为独立收敛项处理，不要与功能切片混在一起。
