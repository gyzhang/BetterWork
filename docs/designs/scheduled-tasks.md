# 定时任务设计 v0.3

> 产品方向已按光哥补充澄清，技术方案仍为 Proposed。2026-09-25 归档；待办见 [SC00–SC11](../development/tasks-schedules.md)。光哥考虑在 2026-09-25 完成其他功能测试后，于 2026-09-26 开始推进，这是候选启动窗口，不是当前编码授权或完工承诺。本轮只形成设计与待办。

## 1. 产品定位与决策边界

**定时任务是“按约定时间，请一个已有专家在指定 Workspace 和选定知识范围内开展本期工作”，不是专家编辑器、自动化流程编辑器或无人负责的自动交付。**

专家负责工作方法；Workspace 承接长期工作的目录、资料与成果；知识库补充目录之外的参考；每期 Task 承接本期目标、协作和成果。Schedule 管理周期约定、资料范围与历次触发，人最终检查、修改和使用结果。

**一个定时任务 + 一个持续使用的工作目录 + 多次可分别回看的工作记录。** 光哥已确认：连续六个月通常沿用同一目录，生成物持续积累，人可按业务需要增删资料；下一次执行按届时的目录和已选知识范围取材。仅固定单次执行采用的材料版本，不锁死目录，不为各月创建六个独立 Workspace。

周期工作具有时间序列关系：上个月、上个季度、上半年等资料都可能对本期经营分析有价值。每期记录独立不等于割断历史，应该以可追溯的材料和成果引用支撑对比，而不是无限累加聊天。

### 1.1 光哥已确认，不重新讨论的事项

| 决策 | 设计约束 |
| --- | --- |
| 周期调用已有专家 | 复用已定义的专家；定时任务不创建、复制或修改专家定义 |
| 周期工作有时间序列关系 | 在明确来源范围内保留使用月度、季度、半年度等历史资料作对比的能力 |
| 错过不补跑，只提醒 | 重启、唤醒或恢复网络都不能偷偷补执行；人工决定是否做 |
| 后台执行，结束通知 | 不抢焦点、不切走正在工作的任务；复用现有通知机制 |
| 简单稳定优先 | 自动行为可预期，结果由人检查；具体技术取舍仍在本稿评审范围内 |
| 引入库，不自行解析 cron | 采用 `cron-parser` 方向；具体版本和 API 在实施前核对，不在设计中猜包体积或接口 |
| 独立“定时任务”导航 | 位于“专家”下方，业务主导航最后；底部消息与设置仍保留原位置 |
| 专家更新必须提示 | 不得省略“有新版本可用”；应用已存在的新修订只改调用绑定，不修改专家 |
| 创建时选择专家、工作目录，并添加知识或知识库 | 工作目录对应 Workspace；知识来源按需添加，作为这项周期工作的配置，不回写专家 |
| Workspace 将进一步定义为“项目” | 本轮保留 Workspace / workspaceId，不新增 Project 实体、字段别名或第二套目录关系；未来文案调整另行同步 |
| 实施排在 E 系列稳定之后 | 允许现在做设计，不自动提前编码，也不改写其他任务板状态 |

本次补充取代此前“创建只选 Workspace、不添加知识”的窄范围表述，不将知识库资料强制搬入工作目录。以下标为“建议”的技术行为仍待评审；永久 Task、级联删除历史、仅记录 lastRun、固定版本保证可复现等旧说法不作为基线。

### 1.2 三个目标场景

| 场景 | 已提出的时间 | 目标 | 尚需明确的业务输入 |
| --- | --- | --- | --- |
| AI 动态调研 | 每周一早上 | 全球 AI，重点智能体；国内办公类关注 WorkBuddy、千问办公、豆包工作，编码类关注 Qoder；形成可回看报告 | 调研期间、来源与检索能力 |
| 工作周报 | 每周五 17:00 | 总结本周工作，形成周报 | 工作记录在哪里、覆盖哪些工作，而非假定算台知道全部活动 |
| 月度经营分析 | 每月 5 日 | 阅读上月 GL，并结合人员、财务和主要项目进展形成例会 PPT | 本期报表、人员与项目资料、适用口径和模板 |

周一 08:00、每月 5 日 09:00 只可作为示例，光哥尚未指定具体时刻。GL 通常也不能独自证明项目进度和人员安排，缺少的依据必须说明，不能补造。

## 2. 现有基础：可以复用，但不是“依赖全部就绪”

本次核查以当前代码为证据，不把旧文档中的目标态或上一轮口头判断当作实现。

## 3. 对象关系：规则与每期工作分离

### 3.1 推荐模型

```text
Schedule：周期约定 + 已有专家引用 + 工作要求
  工作目录：一个 Workspace（未来可能显示为“项目”）
  知识来源：明确添加的知识资料或知识库范围
  历次 Occurrence：某个计划时刻的处理记录
    Task / Session：本期独立工作
      本期输入 + 历史对比资料 + 稳定参考
      首次 Run：由定时或人工触发
      后续 Run：人在原任务中补资料、反馈、修改
      Artifact / ArtifactVersion：本期产物，可供后续各期引用
```

Occurrence 是“本次触发记录”，不是新的工作流或 Run 替代品。错过、重叠跳过、启动前失败也要有记录，即使它们没有 Task 或 Run。

推荐每次实际开展工作都创建新 Task/Session，但同一周期工作沿用工作目录及已配置的知识来源。独立的是本期目标、对话和执行记录，不是切断资料与成果的时间序列。历史月份、季度、半年度资料可作为本期的 `historical-comparison` 材料；规则和模板仍可复用，不能把历史数据误标成本期输入。

不整批复制上期聊天、暂时排除项或旧输入作为新事实；历史对比也不要求把全部历史正文塞进 prompt。长期记忆继续经过既有裁决，它可以保留方法与偏好，但不能替代可核对的历史报表和成果版本。

一旦有了本期 Task，人继续补资料和修改就在该 Task 内产生后续 Run。Schedule 的下一期不等待上一期人工审阅完成，只有仍在准备或运行的实例构成重叠保护。同一个专家可被不同 Schedule 在不同工作目录和知识范围中调用，彼此不污染专家定义。

### 3.2 删除、暂停与历史保留

- 建议“删除定时任务”采用归档规则：停止未来触发，保留规则最小身份、实例记录与关联历史；不级联删除 Task、Run、成果或来源。
- 暂停只影响未来自动触发，不隐式取消已经开始的 Run。停止本次执行是另一项明确操作。
- 暂停/归档与派发共用同一串行边界：先为此前已到期但尚未占用的时刻登记未执行事实与原因，再切换状态，不再派发；只有暂停区间不计 missed，不能把暂停前的欠记录抹掉。
- 尚在材料准备、还没进入 Run 的请求，遇到暂停/归档必须取消准备并禁止继续发起模型请求。
- 专家停用、归档、规则删除均不得抹掉旧结果。Workspace 本身删除仍走原数据删除流程，本增量不改写其既有级联语义；实施时需核对新外键与删除确认文案。
- 人单独删除历史任务后，规则仍可继续未来执行；实例关联采用可解释的“历史任务已删除”状态或置空引用，不把旧实例当成未执行再跑。

## 4. 时间规则与“错过”的精确定义

### 4.1 规则与时区

建议首版提供每天、每周、每月的图形化选择，持久化对应五字段 cron；暂不开放自定义表达式、秒级触发、节假日历和补班规则。这是简化建议，不是新增产品批准事实。

- 分钟和小时都来自选择器，不把分钟硬编码为 0。
- 每条规则保存 IANA 时区，默认采用创建时确认的时区；北京时间可保存为 `Asia/Shanghai`。电脑出差改时区不静默改计划。
- 显示下次执行时间和至少接下来的三次时间，保存前校验 cron 在该时区确实存在后续触发。
- 月度 29/30/31 日遇到无对应日期的月份跳过，不改成月末；表单当场说明。
- 如支持有夏令时的时区，约定不存在的本地时刻跳过，重复的本地时刻只触发一次。必须通过选定库版本的转换与测试确认，不能把库默认行为未经核验写成产品承诺；无法满足时不得开放该时区。

### 4.2 定时器只是唤醒器，SQLite 才是事实

应用级维护一个调度协调器，查询持久化 nextScheduledAt。建议短周期唤醒并比较真实时钟，不为月度间隔挂一个超长 setTimeout，也不把“上次 Run 时间 + 固定毫秒数”当作 cron 运算。

自动触发仅在应用进程运行、电脑唤醒、初始化完成时进行。macOS 关闭窗口但进程仍在，可继续；完全退出或系统休眠时不运行。不引入 launchd、OS cron、云调度、自动唤醒或阻止睡眠。

### 4.3 错过、正常抖动与时钟变化

| 情形 | 建议处理 |
| --- | --- |
| 应用持续运行，定时回调轻微延迟 | 在一个很小的迟到窗口内允许开始；建议唤醒周期不超过 30 秒、迟到窗口 60 秒，具体常量在技术契约统一定义 |
| 启动或从休眠恢复时，计划时刻已过去 | 一律记为 missed，不借迟到窗口补跑 |
| 持续运行但卡顿超过迟到窗口 | missed，提醒人工处理 |
| 恢复时恰好还未到计划时刻 | 重建下一次等待，未来正常触发 |
| 电脑时钟大幅前调 | 已越过的时刻按 missed 处理，不集中执行 |
| 时钟后调 | 不回退已处理游标，不重新执行已占用时刻；无法确认连续时钟的自动派发先停止并说明原因 |
| 暂停后重新启用 | 从启用时刻之后计算下一次；暂停期间不生成欠账或补跑 |
| 修改频率/时区 | 先结算旧规则已到期时刻，再从保存时刻之后计算新规则；不回写旧记录 |
| 只改名称、要求或专家版本 | 不重置下一计划时刻；已占用实例使用其原配置快照 |

休眠、退出、规则变更会使旧 timer 的回调失效；即使回调后来执行，也必须重新查规则状态、调度代次和实例唯一键。不能只在启动时处理错过而在唤醒时把过期回调当作准点触发。

### 4.4 错过必须“记账并越过”

在事务中记录错过实例并推进 nextScheduledAt，然后才通知。否则每次启动都会提醒同一时刻，或一直卡在同一个过期 nextTick。

跨过多个周期时保留各次错过事实，界面分页；同一轮恢复按规则合并一条通知，例如“关闭期间错过 3 次，未自动执行”。大量历史按有界批次处理，恢复批次及通知回执持久化，重启继续记账但不再次发同一批提醒。暂停期间不计入 missed。

通知可清空、目前还有条数上限，不能作为调度游标或执行历史。

## 5. 统计期间与人工执行

### 5.1 触发时间不等于数据期间

建议在定时配置中增加一个轻量“处理哪个期间”选项，不做模板语言或可编程参数系统。默认值展示给人确认。

| 工作 | 推荐期间口径 | 注意 |
| --- | --- | --- |
| 周一 AI 调研 | 截至计划时刻的过去 7 个日历日 | 是否改为上一自然周可以选择；网页发布日期与抓取时间分开 |
| 周五周报 | 本周一 00:00 至计划时刻 | 周五 17:00 以后的工作不在本次截止范围；是否另有公司周报周期需确认 |
| 月度 GL 分析 | 上一自然月月初至本月月初 | 不是最近 30 天；跨年与月长由日历计算 |
| 无统计期间的工作 | 不指定 | 仍记录计划时刻与实际开始时刻 |

按规则时区计算半开区间 `[periodStart, periodEnd)`。Application 将计划时刻、时区、实际执行时刻、期间起止和触发方式写入实例快照，再以明确文字送给专家。保留光哥原工作要求，不把解析后的期间反向改写成另一份需求。

上述是本期报告的主期间，不是历史材料读取的硬截止线。上月、上季度、上半年等对比要求可写在工作要求中，读取时分别保留实际比较区间、材料版本与口径；不再强加一张复杂的对比期间配置表，也不能把季度数与月度数未经口径转换直接比较。

现有 Agent 的“今天是……”可保留，但不能代替这些字段。固定 ExpertRevision 也不能使外部网页、模型、记忆和本期数据可复现；承诺的是可追溯，不是相同文本输出。

### 5.2 两种人工动作不能混淆

- **立即执行**：从现在开展一项新工作，按当前配置和当前时刻确定期间；明确显示期间。不会改变下一次正常计划。
- **为错过的一期执行**：从历史 missed 项进入，预览原计划时刻与期间；人点击后创建新的人工实例，并关联原 missed 记录。原记录保留，不改写成准点执行。
- 人工重做使用当前有效的规则/专家绑定，并重新准备可用材料；显示与原实例的配置差异。期间沿用原期，但不声称可以重建当时网页或已丢失的历史源文件。
- 已有 Task 的失败/待补资料场景，优先打开原 Task 补资料或再次发送；“重新做一期”才新建 Task，不让一个按钮暗中覆盖历史。
- 暂停规则可以人工立即执行，归档规则只保留查看入口。人工执行仍要经过相同能力和材料边界。
- 连续点击同一提交使用请求回执去重；一次成功接受后的明确再次执行是新工作，不吞掉合法重做。

## 6. 工作目录、知识来源与跨期材料

### 6.1 持续的来源范围，每次执行的固定版本

创建顺序是选择已有专家、选择长期工作目录、按需添加知识资料或知识库范围，再填写工作要求与周期。工作目录和附加知识属于 Schedule，不属于专家定义；同一专家可以服务多个不同目录、不同知识来源的定时任务。

已确认工作目录是持续变化的资料空间，不要求人每月重新选目录或逐文件建立定时绑定。下一期应看到目录中新增的业务文件及此前生成的成果，文件被删除则不再作为该目录的候选。

**Schedule 保存持续的来源范围；每次执行根据当时的范围解析具体文件与知识修订，固定本次版本，再按需读取。** 这不把整个目录正文塞进模型，也不从选中目录推导出对其他路径、其他知识库或全部聊天的权限。

现行 [材料契约 §2.2](../development/material-contracts.md#22-workspace-候选与任务授权) 只定义逐任务显式选择，不包含这种持续范围的自动解析。本设计明确提出该增量：需在 SC01 定稿授权来源、范围快照与读取边界，不能直接用旧 UI 的候选清单冒充 Run 授权，也不能削弱已有人工任务的材料隔离。

### 6.2 知识或知识库如何添加

- 可以选择明确的知识文档，也可以选择一个有明确身份的知识集合/知识库范围；纯网络调研可以不添加知识。
- 复用现有知识选择体验，不复制知识正文到 Schedule，也不要求先改专家的常用参考。当前知识页有单层集合和全库视图（`packages/agent-protocol/src/index.ts:3063`），但集合筛选本身不是运行授权，多知识库管理也不能据此声称已存在。
- 首版具体映射在 SC01 固定：文档、已有集合、明确选择的个人知识库范围；不为这个功能另建知识库管理系统。选中一个集合不等于选中整个个人 Vault。
- 推荐文档选择跟随下次运行准备时已登记的可用内容修订，集合/库选择跟随当时的有效成员；每次固定成员与修订清单。UI 明示“后续执行使用该来源的更新”，不能暗中扩大选择范围。
- 专家自带的固定参考继续固定，不偷偷改成 latest。与定时任务的动态来源命中同一文档但不同修订时，不静默覆盖或双重注入；按 SC01 的冲突规则提示人确认，保留原选择来源。
- 移除/删除已选文档或集合后不得静默回退全库；可解释地标为来源缺失或范围为空。原始知识文件在磁盘改动但尚未完成知识刷新时，不冒充已取得最新内容。

知识的动态版本与集合成员语义是本稿推荐技术方案，不把它混同为光哥已经逐字段批准的协议。

### 6.3 本期数据、历史对比与稳定参考

| 材料 | 来源和使用方式 |
| --- | --- |
| 公司制度、财务口径、模板 | 来自专家固定参考或 Schedule 添加的知识；保留用途及具体修订，不因被称为“规则”就获得系统指令权限 |
| 本期 GL、人员与项目资料 | 从当前工作目录或明确添加的知识范围取得，核对实际统计期间，作为 current-input |
| 上个月、上季度、上半年等资料 | 同一来源范围内可作为 historical-comparison，不能只因文件早于本期就排除 |
| 历史报告/PPT | 引用精确 ArtifactVersion 或对当前目录文件创建快照；文件最后修改时间不代表最终审定状态 |
| 外部 AI 动态 | 通过已配置、已允许的搜索/网页能力在本 Run 中取得，记录实际来源和时间 |
| 周报工作记录 | 使用明确放入项目的记录或已选知识；不默认扫描全部聊天、其他 Workspace、日历或办公软件 |

本期统计区间不是资料读取的最早时间：月报可以同时分析本期、环比、季度或半年趋势。历史报告可提供已报告的结论，但不一定包含可重算指标的原始明细；不能仅有上月汇总就声称可以计算任意同比或累计值。

不强制按月份新建目录，也不强制目录改名来满足解析器。可利用名称、内容和既有标识判断期间，冲突或无法确定时留下待核对项；文件 mtime 不能作为唯一期间证据。缺本期输入不能拿历史数据顶替，但仍可说明已有历史对比资料。

### 6.4 新增、修改、删除与单次快照

| 变化 | 下一次工作 | 已开始或历史工作 |
| --- | --- | --- |
| 人新增文件或新成果保存到目录 | 进入该目录的候选范围，按任务需要使用 | 不回写已经固定的本次材料 |
| 人修改原文件 | 重新取得当前字节并创建新快照 | 仍读取旧快照；历史事实不被改写 |
| 人删除或移走文件 | 不再从目录获得它；缺项时说明 | 历史快照可保留供回看，不借历史存档偷偷重新授权给下一期 |
| 调整所选知识集合成员或内容修订 | 按明示的动态来源策略重新解析 | 旧成员与修订仍按当次快照回看 |
| 从 Schedule 移除一个知识来源 | 之后不再从该来源取得资料 | 不删除原知识，不重写历史；同一资料若仍被其他显式来源授权需能解释 |

保留审计快照不等于让已移除的资料通过历史聊天、旧材料或旧成果再次隐式进入新 Run；记忆与历史重放仍受现有依赖闭包裁决。删除目录里的可编辑成果副本也不等于删除算台的历史 ArtifactVersion，但下一期不能悄悄用该版本绕过目录删除动作。

### 6.5 每次准备与按需读取

1. 读取这次采用的 Schedule 配置，解析当前目录、所选知识范围与适用专家参考，形成带来源说明的清单；保留本期和历史对比用途，不按单一日期窗口过滤全部资料。
2. 核对目录真实边界、路径/格式和数量/总量限制；排除 `.DS_Store`、`._*`、临时锁文件、内部 `.betterwork` 目录等非业务内容以及越界/符号链接。声明的来源缺失要报告，不能静默当作空资料继续。
3. 对文件复用 InputSnapshotService，知识固定已登记的精确修订；目录和知识范围均在本次运行准备时固定，不能边运行边跟随 latest。
4. 正文按需读取/检索，所选范围不等于全部已读，更不等于全部被成果采用。来源范围很大时需要有界的清单与检索策略，不能把整库强塞进现有逐任务材料数组，或截取前若干项后声称覆盖完整。
5. 清单和 TaskContext/RunContext 的关系、范围大小预算、来源枚举及去重冲突规则在 SC01 明确定稿；实际读取和成果采用继续分别记录，自动装配不能伪装成人逐条选择。
6. 人在本期 Task 中补充/移除材料沿用既有规则，只影响本期后续 Run；要改变以后各期的知识来源，需要明确保存 Schedule 配置。工作目录的文件变化则按上表自然影响下一期。

这是 Main 层新增的调度来源解析，不新建 Agent 引擎，不把 Knowledge 管理筛选直接透传为权限。技术范围快照尚未实现；不能因底层快照/解析器已有，就把周报/月报自动闭环标为就绪。

### 6.6 成果在同一工作目录积累

光哥需要生成物持续进入工作目录，而不只是保存在算台内部。建议在原 Workspace 下使用一个清楚可见的成果输出位置；这是同一项目的普通子目录，不是每期新建 Workspace，也不重排光哥已有资料。

- 先按原管线登记 ArtifactVersion，再把已登记的文件/Markdown 保存为该目录中的可用成果；具体默认子目录与命名在 SC01 确定，避免与个人文件混淆。
- 文件名包含可识别的工作名与期间/版本，遇到重名不覆盖，保存关联回执并支持幂等；不能覆盖人修改后的文件、上期报告或原始输入。
- 下期可从该目录发现历史成果用于对比，但“刚生成”不等于“已审定”；同一成果被多入口命中应能去重并保留来源解释。
- 人用 Office 修改项目中的副本后，下次把修改后的文件当成新输入快照；不静默回写历史 ArtifactVersion，也不自动宣称人工批准。
- 目录保存失败时保留已登记成果，明确“成果已生成，但未保存到工作目录”；只重试保存，不重新调用模型。删除规则不会删除这些文件。

现有内部成果登记不自动等于上述目录交付已完成；这部分有独立待办与恢复验收，不留成隐含假设。

## 7. 专家修订、能力与后台执行授权

### 7.1 只调用既有专家，固定修订并提示更新

定时配置页只提供选择和只读摘要，不编辑人格、原则、Skill、模型、MCP 或专家常用参考。Schedule 的工作要求、工作目录与附加知识不能回写 ExpertRevision；保存、执行、归档定时任务均不调用专家定义写入接口。

推荐 Schedule 固定一个 ExpertRevision；列表及详情按固定 revisionId 与当前 revisionId 比较，显示“当前使用 v2，可更新至 v3”。需要修改专家时，到独立专家管理页另行操作，不嵌入定时配置流程。

- 仅有新版本不自动暂停，不自动同步；有效旧绑定仍可执行。
- 应用前只读查看人格/要求、Skill、模型策略、MCP、常用参考的差异，并显示失效项。
- 一次明确确认可应用已存在、已展示的版本；请求携带规则 expectedVersion 和目标 expertRevisionId，不执行一个含糊的“取执行那一刻的 latest”。
- Main 重验版本归属、能力与材料适用性，成功后只更新 Schedule 的调用绑定和配置版本；不创建或修改专家修订，失败保留旧配置与编辑草稿。
- 重装配新的专家参考时，完整保留 Schedule 自己选择的工作目录与附加知识；重复或版本冲突明确提示，不能把更新专家当作清空资料配置。
- 新版本影响之后尚未占用的实例，不热改运行中、准备中或历史实例。若准备中的旧实例尚未发起 Run，涉及授权撤销仍须阻止启动。
- 固定专家修订不豁免实时信任、停用和凭据校验。旧 Skill 修订已不可运行时显示具体阻塞原因，不能“为了固定”强行使用，也不能偷偷升级。

`hasNewerRevision` 可以作为投影，但不能只改 expertRevisionId 而忘了重新装配该修订的 Skill/MCP/参考选择；后台装配应复用与手动召唤一致的 Main 规则。这是读取已有定义并绑定，不是修改专家。

### 7.2 保存配置不是无限执行许可

建议区分“保存并暂停”和“保存并启用”。启用时用简短说明明确：会按所选专家能力周期调用已配置模型和工具，可能有费用；错过不补跑；结果需要人工检查。无需每次弹确认，也不新增模型配置入口。

- 在每次开始前验证实际采用的模型、Skill/信任/依赖、工具、MCP 连接及材料，不只看 ExpertSummary 的当前版本状态。
- 定时工作必须有有效配置的模型；不能在配置缺失时静默回落教学模型并发“报告完成”。现有 ModelProviderFactory 有真实配置检查能力，可复用其解析规则，不能另建模型入口。
- 不自动提权、授信、装依赖、执行需要人确认的外部写入，不能把“人会检查结果”当作事前批准。
- 本轮目标是资料读取、分析与本地产物，不包含邮件/IM 发送或远端业务数据修改。现有 MCP 并无普遍强制的只读保障，原生脚本也不是 OS 沙箱；后台适用能力需审核，不能只凭工具名字或提示词宣称只读。
- 无法证明适合无人值守的能力应在启用/预检阶段阻止并说明原因，而不是临时弹框等待无人响应。该判断契约须在实施前补齐；不借此建设完整权限平台。
- 沿用现有工具轮次、请求超时与脚本取消限制；调度器本身不无限等待准备、不自动重试失败 Run。

## 8. 可靠执行与持久化

### 8.1 最小需要两类事实，不需要完整工作流引擎

**Schedule：当前规则。** 建议保存 id、名称、Workspace、已有专家修订引用、附加知识来源、原始工作要求、频率/cron、时区、期间策略、交付目标、配置版本、enabled/archived、nextScheduledAt、创建/修改时间。来源选择、动态更新策略与输出目录约定的字段在 SC01 定稿，不复制专家定义或知识正文。

**Occurrence：一次计划时刻或人工触发的处理事实。** 建议保存 id、scheduleId、trigger（scheduled/manual）、scheduledAt（人工立即执行可无）、人工请求键/原 missed 关联、配置快照、期间、来源范围快照引用、处理状态/原因、Task/Session/首次 Run 关联、各阶段时间与通知回执。成果目录保存回执按实际 ArtifactVersion 关联，不以文件名代替身份。

- 自动触发对 `(scheduleId, scheduledAt)` 唯一；人工触发按请求键幂等。配置版本不是允许同一计划时刻再跑一次的理由。
- 配置快照保存本次采用的要求、规则版本、专家、知识来源与期间等必要事实，不复制凭据，不存第二份模型请求；来源快照保留实际文件/知识成员与精确版本。
- 修改知识来源或工作要求不重置下一计划时刻；已有实例使用原配置，后续实例解析新的选择。更换 Workspace 属显式配置修改，不搬迁旧文件或历史任务。
- 首次 Run 可为零或一个；Task 的后续人工 Run 由原关系查询，不伪装成新的自动触发。
- Run 的完成/失败/取消真相仍在 Run；实例维护调度状态及启动前原因，UI 联查呈现，不维护一套会漂移的 lastRunStatus。
- 错过和重叠跳过也能回看；最新一次只是查询投影，不能替代历史表。
- 只用版本化迁移，实施合并时分配下一可用版本。此时观察到 v33 不代表可以预占 v34，更不能在并行工作中写死编号。

### 8.2 正常派发顺序

1. 调度器确认进程初始化完成、未停止接单，并在同一规则内串行处理。
2. 事务占用计划时刻，保存配置快照和 preparing 实例，推进下一计划时间；重复回调遇到已存在实例即结束。
3. 准备有限材料、检查规则是否在准备期间暂停/归档或发生撤销；取消可终止准备。硬性缺项保存可解释原因，不先调用模型尝试“解决权限”。
4. 事务创建本期 Task/Session 和完整 TaskContextRevision，并把它们绑定到实例；需要人补材料时可停留为有 Task、无 Run 的待处理结果。
5. 通过 RunService 的窄 Main 入口启动：在其创建 Run 的同一个事务中登记实例与 runId 关联，成功提交之后才开始异步准备/执行。
6. 返回已持久化的实例与运行引用；终态复用现有 Run 管线，再由统一收口机制登记该实例结果及通知。

第 5 步是现有实现需要扩展的接点。不能用 `start()` 返回后再补 lastRunId 消除崩溃窗口，也不能把已经启动异步消费的 start 简单套进外层事务。

不得向 Renderer 暴露随意填写内部 runId/实例归属的旁路；所有关联必须由 Main 校验。StartRunRequest 的上下文修订与期望号仍要成对提交。

现有 Run 在异步准备前已经落库，材料/凭据/Skill/MCP 的后续失败可能产生 failed Run；调度不得把这些都称作“未执行且无 Run”。本轮不为整顿该管线重写 Agent Engine。

### 8.3 重叠、失败与崩溃

| 情形 | 处理 |
| --- | --- |
| 同一规则已有 preparing 或首次 Run 仍活跃 | 自动到期记录 skipped-overlap 并推进计划；不排队、不补跑；人工点击返回现有实例并说明 |
| 只是上期等待人工看报告 | 不阻塞下一期，也不把“未审阅”当作活跃 Run |
| 不同规则同时到期 | 交给现有 Run 并发能力；不得覆盖当前人工 Task，不额外建设通用队列 |
| 占用实例后、创建 Run 前崩溃 | 启动记为 interrupted-before-run，保留已建草稿/材料与原因；不自动再派发 |
| 已关联 Run，进程被强制结束 | 先沿用 Run 的中断恢复，再对账实例；不再启动第二个 Run |
| 外部请求可能已经发生但完成情况不明 | 显示中断/结果待核，不承诺外部副作用 exactly-once，不自动重试 |
| 取消本次准备/运行 | 使用统一取消路径，保留历史和已合法登记成果；主动取消不发失败通知 |
| 网络或服务恢复 | 只影响下次正常计划，不自动重试已失败实例 |

可靠性目标是**同一自动时刻至多派发一次，不丢失可解释记录**，不是保证每一期一定执行成功。宁可漏一次并告知，也不能因崩溃重复调用或重复消耗。

### 8.4 应用生命周期

- 单实例/唯一调度所有者必须在数据库中断恢复之前确立；当前没有这一保障，不能让第二个进程把第一个进程的活跃 Run 判成中断。优先应用级单实例约束，不建设分布式锁。
- 数据库、必要资源注册与恢复、凭据和执行依赖达到可判断状态后才允许自动派发。不能只在 whenReady 后立即打开 timer。
- 恢复先结算旧 Run/实例，再记错过，最后等待未来时刻。
- 退出时先同步停止新派发、使 timer/异步准备失效，再取消/收口 Run 和工具，最后关闭库。窗口重建不创建第二个 Scheduler。
- 多 worktree 只隔离源码，不隔离 Electron userData、数据库、端口和外部副作用；未来联调应使用独立测试数据目录，禁止两个分支同时调度同一真实工作目录。

## 9. 结果、通知与人工介入

### 9.1 不把 completed 当作业务验收

用已有 Run 状态表达运行结果，再附交付投影：

| 事实 | 用户看到什么 |
| --- | --- |
| 本期缺必要输入，未发起 Run | “需要补充材料”，打开本期 Task |
| Run 完成且本次已有目标 ArtifactVersion，并已保存到工作目录 | “本期产物已生成，请审阅”，链接本期任务、精确版本和目录位置 |
| 成果已登记，但目录保存失败 | “成果已生成，未保存到工作目录”，允许只重试保存，不重跑模型 |
| Run 完成，但没有约定格式产物 | “本次执行已结束，未生成约定产物，请查看回复”，不显示报告完成 |
| Run 失败/中断 | 具体原因和查看/人工处理入口，保留有效的部分成果 |
| 人主动取消 | 状态可见，不重复发失败通知 |
| 错过或重叠跳过，无 Run | 通知进入规则详情的对应历史项 |

建议交付目标使用现有产物类型，例如 Markdown 或 PPTX；判定必须关联本实例的 Run 与实际登记版本，不能捡同 Task 的旧文件或上一期成果当作本期成功。产物存在也不等于内容正确，不建立“AI 自己验收通过”的状态。

### 9.2 需要人介入时结束本次自动动作

保持“人会介入”：缺数据、口径冲突、专家要求审阅大纲时，留下回复/可回看的材料，通知人打开原 Task 决定下一步，不代替人确认、不自动串起下一 Run。

现有 DiscussionCheckpoint 是人工记录，不是能自动挂起/恢复的工作流，也不能可靠识别模型所有自然语言提问。因此：

- 可确定的准备缺项使用结构化原因。
- 已有明确人工节点沿用原记录；不从“请确认”等关键词猜出一个已批准状态。
- 普通模型回复统一等待人查看，未产出时如实说明；不引入自动审批协议。
- 一个专家若目前必须多轮确认才能生成 PPT，首轮定时运行只能推进到可继续协作的位置，不能声称到点后必有完整 PPT。完整月报场景要用光哥实际专家检验。

### 9.3 复用通知机制，但补齐可靠收口

完成/失败继续收口到 NotificationService，不能 RunService 发一次、ScheduleService 又发一次。建议同一应用收口路径读取实例元数据，定制名称、期间和交付提示。

- 实例结果与通知持久化回执需要事务一致性；使用实例/结果阶段的稳定键防重，提交后才广播。普通 Run 的路径保持原语义。
- 跨崩溃恢复补齐尚未写入的结果通知，不重做执行。清空通知或超过 200 条淘汰后不能把回执清掉再重发。
- 增加可导航的 Schedule/Occurrence 目标，补齐 protocol、仓储映射、preload、Renderer 路由与同页抑制；不能发送没有目标的“system”消息充数。
- 打开历史任务不依赖其还在“最近任务”列表；以真实 ID 查询，缺失时说明，不只跳到工作首页。
- macOS 无窗口但进程存活时仍需支持系统通知；点击时重建/聚焦窗口并在 Renderer 就绪后导航。系统权限关闭时保留消息中心结果，不承诺系统一定弹出。
- OS 通知本身不能保证 exactly-once，重启不重播历史系统弹窗；可靠回看以库内结果与消息中心为准。

“后台静默”只表示不主动抢占工作界面，不表示隐藏状态。打开本期任务仍可看过程、来源、取消和成果；所有交互遵循 [UI/UX §11.5.1](../10-ui-ux-system.md#1151-反馈通道决策表所有界面反馈的归类入口)。

## 10. 界面与接口边界

### 10.1 信息架构与低保真草图

业务主导航为“工作 → 成果 → 知识 → 技能 → 专家 → 定时任务”；底部消息与设置仍在原位。不新增专家子 Tab 作为第二扇门。

```text
定时任务                                         [新建]
按约定时间请专家开始工作；错过仅提醒。

周一 AI 动态调研                                  已启用
专家：调研专家 v2     有新版本 v3 [查看更新]
Workspace：AI 研究    每周一早上（时刻由配置确定）
下次：显示规则时区下的真实时间

```

草图只表达信息层次，不代表 UI 已实现。真正图标使用统一 SVG，不使用 emoji/Unicode 操作图标。

### 10.2 创建/编辑

顺序为选择已有专家、选择工作目录（Workspace）、按需添加知识资料或知识库，然后配置名称、工作要求、频率/时刻与时区。期间和交付目标用简单选择解释，不增加一套逐月输入准备表。

```text
新建定时任务
专家             [经营分析专家 v4]   [查看定义（只读）]
工作目录         [部门经营 / 已登记目录]
知识来源         [财务制度] [经营口径集合] [添加知识或知识库]
工作要求         [分析本期经营，并与上月、上季度及上半年对比……]
执行时间         [每月 5 日] [时刻] [时区]
本期统计范围     [上一自然月]
交付目标         [PPTX]
说明             持续使用此目录，后续执行读取当时可用资料；不修改专家
                 [取消] [保存并暂停] [保存并启用]
```

文件不需要每月重新逐项绑定；知识添加入口复用现有选择体验，清楚区分单篇资料与集合/库范围，显示已选范围及更新语义。专家自带参考与 Schedule 附加知识分别标来源，详情可展开但不把专家编辑表嵌进来。

保存动作区分保存并暂停与明确启用；采用 expectedVersion 冲突检测。取消保留原配置，失败不丢草稿。专家更新只读看差异再应用已存在修订，旧版本有效时不制造暂停警报。

### 10.3 详情与历史

规则摘要、长期工作目录、附加知识、下次时刻、启停状态、专家更新提示，以及分页执行历史；不把六个月运行显示成六个新项目。每行显示计划时刻、主期间、触发方式、结果、成果及本次材料版本入口；没有 Run 的 missed/blocked 项同样能解释。

后台状态变化不切换当前 Task、不清空 Composer、不切换当前 Workspace。只有人点击某一期工作才导航；离开再回来保留编辑状态。目录文件和历史 Artifact 的删除含义分别说明，不自动删除任一方。

沿用 `.page-header`、`.page-body` 与 860px 版心、语义 Token、统一反馈。保存/暂停等短时确认用局部 TransientToast，表单错误内联，跨页运行结果才进 NotificationService。原始 Run 事件不是列表中心。

### 10.4 IPC 语义，不在此冻结代码 Schema

| 接口职责 | 必要约束 |
| --- | --- |
| list / get / occurrences | 可按 Workspace 筛选，历史分页；查到的 ID 不等于授权 |
| create / update / set-enabled / archive | 校验 Workspace、知识来源及版本策略；expectedVersion；不接受客户端伪造 nextScheduledAt、状态或执行结果，不修改专家 |
| preview-times | Main 使用同一库/时区规则计算预览，不让 UI 自己算一套 |
| source selection / resolved-source detail | 复用知识选择，Main 校验范围；可回看每次解析的成员、修订和文件快照，不向未选择的库回退 |
| trigger-now / trigger-missed | 人工请求幂等键，明确期间与原 missed 引用，返回 occurrenceId 及可用 Task/Run 引用 |
| apply-expert-revision | expectedVersion + 明确目标 revisionId，只重建调用绑定；保留目录和附加知识，不写 ExpertRevision |
| cancel-occurrence | 准备阶段可取消；运行阶段转交既有 Run cancel；不等同于暂停规则 |
| retry-output-save | 只对已登记版本重试目录保存；校验目标路径及回执，不重新发起模型请求、不覆盖个人文件 |
| state-changed | 提交后通知列表失效重拉，不携带完整业务正文；通知事件不能替代所有状态同步 |

全部遵循共享协议、三个 IPC 注册 helper、preload 最小暴露、Hook 的 reportAction/trackAction。上述为接口设计要求，未新增任何 channel 或生产代码。

## 11. 设计验收矩阵

以下是后续自动化与人工走查的要求，不是本轮已执行测试。

| 轴 | 必须证明的结果 |
| --- | --- |
| 准点 | 应用持续运行时一次触发，实例/Task/Session/Run 关联完整 |
| 关闭、休眠、恢复 | 错过只记账通知；旧回调不补跑；macOS 关窗与退出可区分 |
| 首次启用与长时间暂停 | 只处理启用后的未来时刻，不产生历史欠账 |
| 日历 | 非零分钟、月末、跨年、固定时区、支持范围内的夏令时；预览与派发一致 |
| 时钟变化 | 前调不补跑，后调不重复已处理实例 |
| 重复与崩溃 | 重复 timer、双击人工执行、占用后崩溃、Run 落库后崩溃均无自动重复发包 |
| 退出与取消 | 退出先关派发；准备可取消；暂停/删除不隐式删除已产出内容 |
| 重叠 | 同规则 preparing/running 跳过；等待人审阅不永久阻塞下一期 |
| 连续六期 | 同一 Schedule/Workspace，六份工作记录；目录产物持续积累，历史月/季/半年资料可对比，不整批重放聊天 |
| 动态目录 | 人新增、修改、删除文件影响下一次取材；当前和历史快照不变；删除内容不从旧存档隐式复活 |
| 知识来源 | 文档、集合/库的选择持久化；集合成员和内容更新按明示策略进入下一次快照；缺失不回退全库 |
| 换期 | 新期间与本期快照明确；不把旧 GL 当新 GL，也不把所有历史资料按主期间过滤掉 |
| 材料权限 | 超出目录或未选择的知识范围、符号链接、元数据、格式/数量/总量超限都不能静默进入 Run |
| 材料就绪 | 缺失、歧义、版本冲突有具体原因；运行中修改源文件不改变快照 |
| 专家只读 | 保存、执行、归档 Schedule 和应用既有专家修订均不新增/修改 ExpertRevision，不清空附加知识 |
| 专家更新 | 必提示，可不应用；应用目标固定，配置冲突保留草稿，历史不热换 |
| 能力与费用 | 缺模型不回落教学模型；信任/依赖/凭据/MCP 不合格不偷偷放行 |
| 人工介入 | 多轮专家不会被自动代确认；本期原任务可继续协作 |
| 成果真假 | completed 无目标产物不提示“报告完成”；文件与来源关联到本次 Run |
| 目录交付 | 保存不覆盖原件/个人修改；重名和重复回调幂等；保存失败保留内部成果且不重跑模型 |
| 通知 | 同一结果只入库一次；清空/淘汰不重发；历史任务及无窗口点击可正确回看 |
| 历史保留 | 归档 Schedule 不删除历史；人工重做保留原 missed 与原期间 |
| 回归 | 人工召唤、材料收缩、记忆召回、取消、来源与原通知路由不退化 |

自动化用注入时钟、Fake Provider、真实临时 SQLite、受控文件与网络桩，不等待真实周/月，也不触网。真实模型、真实业务文件与窗口验收仍需单独授权。

## 12. 范围、顺序与本轮结论

### 12.1 不纳入首版

自动补跑/重试、通用 DAG、OS/云常驻调度、系统唤醒、自动审批、外部发送或业务写入、全量聊天扫描、工作行为监控、自定义脚本表达式、跨规则依赖、调度专属 Agent/记忆/模型设置。

### 12.2 待办与候选推进窗口

[定时任务待办 SC00–SC11](../development/tasks-schedules.md) 是本增量唯一任务状态入口，本设计维护行为，不重复维护完成状态。光哥已要求把功能列入待办，并考虑在其他功能测试后于 2026-09-26 推进；该日期是候选开始时间，不是整批开发或真实模型调用的预先授权。

建议顺序：

1. SC00 核对当前测试与专家能力基线，不重复要求确认本稿已明确的产品方向；若既有缺口影响调度，列出具体阻塞，不把历史任务板上的全部尾项一概变成新门槛。
2. SC01 完成技术契约，SC02 确认低保真交互；本轮只有文档草图，后续技术 ADR、原型和代码分别按授权推进。
3. SC03–SC06 形成从规则/来源持久化到自动取材、定时触发、既有专家执行的最小链路；先用无私有材料调研验证触发，再补齐目录和知识范围，不以 timer 单测代替功能。
4. SC07–SC09 完成目录交付、通知恢复与 UI，SC10 验证同一目录连续六期及边界，SC11 再做实际专家的人工业务验收。

不预占 ADR 或数据库版本；不改写 A/B0/E/CF/WM/MI/KM 的任务状态。本文和待办存在不表示功能已经实现。

### 12.3 产品已明确，技术仍需收口的事项

- **不再悬置的方向**：同一长期目录动态积累、每次工作分别留档、添加知识或知识库、历史月/季/半年资料可对比、定时任务不修改专家定义。
- **SC01 来源契约**：明确目录枚举与范围预算、知识文档/集合/库的实际映射、动态修订与固定参考冲突、运行范围快照。不能用旧逐材料限制暗中降级为“不支持知识库”，也不能绕开范围校验。
- **SC01 目录交付**：明确成果输出位置、文件命名、幂等回执和失败恢复，不覆盖个人资料；不因内部 Artifact 已存在就省略目录保存。
- **SC01 时间与能力**：确定主期间默认值、时间规则边界及无人值守能力校验；历史对比区间保持可表达，不强制增加复杂表单。
- 规则归档、原子派发、通知去重等具体技术建议仍须在开工契约中定稿，不能把产品确认扩大成全部技术协议已批准。

当前结论：产品工作方式已澄清，后续从待办的基线与契约收口开始；只有目录、知识、历史对比与产物保存一起走通，才能称为周期工作的完整交付。
