## 1. 实际工具识别揭示的缺陷

本机 Qoder IDE 1.32.2 的规则页同时将 `betterwork-code-style` 与 `betterwork-ui` 标记为“规则未启用：缺少文件路径通配符”。对应文件已有 `trigger: glob` 与带引号的 YAML `glob` 列表，旧静态测试也通过。因此，“格式通过”没有证明规则被实际工具识别；上一波把 CLI 文档的列表格式定为仓内标准，在 IDE 使用场景中是错误的。

[IDE 官方说明](https://docs.qoder.com/zh/user-guide/rules)要求指定文件规则的输入用逗号分隔；[CLI 文档](https://docs.qoder.cn/en/cli/memory)接受单个模式或列表，两份说明不应混用为实际运行证据。通过 IDE 编辑入口填写 UI 范围后，它实际保存的是 `glob: apps/desktop/src/renderer/**/*.tsx,apps/desktop/src/renderer/**/*.ts,apps/desktop/src/renderer/**/*.css`。代码规范同样采用每项完整的模式；两条规则在 IDE 中已显示完整范围且禁用警告消失。正文、唯一规范、例外与权限边界均未放宽。

同步修正 docs/12、规则索引、解析器与元数据护栏，新增 YAML 列表、扩展名简写及空模式的拒绝用例。旧解析器先在“列表必须拒绝”和“IDE 保存格式必须接受”两项失败，修复后通过。代表 Renderer 文件应匹配，其他目录应排除；静态样本仍不等于真实 IDE 对某次文件访问的触发证据。

这次只验证了工具的识别状态，没有向 Qoder 提交编码任务或发起模型请求。新会话中规则正文的实际注入与遵循仍未取得证据；不能从设置页启用状态代签。后续规则/工具更新时由 AI 检查，不能把 IDE 配置排查交给人类作为额外职责。

## 2. 从同进程重装配补到真实进程中断

保留第二波的完整离线应用旅程，新增独立进程恢复：真实 App 召唤专家 → 读取合成资料并声明来源 → 保存本期 Markdown → 手动经验设优先并对本任务排除 → 再次 Run 的真实 Provider 请求挂起 → 父 CLI 收到实际落库标记后 SIGKILL 自己创建的 Electron 进程组 → 新 PID 重开同一临时 SQLite → 生产中断收口/IPC/App 回读。

独立断言：已完成 Run 与有序事件不变；被中断 Run 恰好补一条 `run.failed`；原成果与精确版本、记忆及优先策略、TaskContext 与排除 ID 保留；没有新 Run 或启动模型重放；原合成资料不变、Renderer 无错误、窗口无意外网络请求。界面核对历史完成/中断说明、排除项恢复入口和设置中的优先策略，分别留下截图。只有父 CLI 在矩阵、应用旅程及进程恢复全部通过后才生成完整 `results.json`；矩阵中间证据为 `matrix-results.json`，不能替完整成功。

`npm run ui:check -- --recovery-only` 只跑这一层，不等于完整门禁；`--probe-crash-recovery` 跳过启动 Run 收口，必须因“强杀后的 Run 未收口”退出 1。这条反例避免只凭窗口打开或数据库可读就给恢复绿灯。父 CLI 只按自己创建的 detached 子进程组操作，不查杀用户应用，失败和超时也清理自己的辅助进程。

它复用生产服务与中断收口，但没有启动安装态完整 `main/index.ts`，不证明所有启动服务、任意崩溃点、真实 Skill、模型内容语义、签名/Gatekeeper 或真实用户库都通过。没有改 IPC/迁移/产品功能，也没有新增单独门禁；默认 verify 始终包含这层回归。

上一波真实 macOS CI 的 UI CLI 夹具单文件耗时为 50.391s（run 37048577071），已经命中既有重文件 ≥20s 判据。本批次将它移入现有 heavy 串行档，保持所有用例和超时预算；切档前后必须核对两档总文件/用例数相同，避免通过漏跑来获得绿灯。
