# UI 页面与后续 AI 开发约束评估

评估日期：2026-10-01。代码基线：`4f4c9b7`，评估开始时工作区干净。本文是评估记录与改进建议，不新增 UI 规范，不改变已接受的设计或开发范围。设计真相源仍为 `docs/10-ui-ux-system.md`，工程标准仍为 `docs/12-engineering-standards.md`。

## 1. 结论

**“当前 UI 治理已基本完成”这个判断成立；“后续 AI 新增页面已经无法自造组件或页面骨架”这个判断尚不成立。**

现有页面已经形成稳定的视觉语言、基础控件、页面布局、反馈通道和浮层语义。它已经超过“把几个按钮抽成组件”的阶段，可以继续功能开发，无须为了治理再做一轮全仓拆分或更换组件库。

目前最值得补的是新增代码的约束闭环：部分护栏善于防止已知旧写法复活，却不能完整识别换了名字的新实现。实际违规探针证明，新页面另造卡片/徽标/版心、部分内联几何，以及不可用键盘激活的交互元素仍能通过现有检查。主题检查也没有完整保证每个色系变体独立满足 Token 契约。

产品方面，主要短板是部分页面把治理解释、来源和高级配置放得过于靠前。视觉统一已经较成熟，下一步应提高用户找到内容和完成操作的效率。

| 维度 | 评价 | 判断依据 |
| --- | --- | --- |
| 视觉与基础控件一致性 | 较成熟 | 页头、版心、控件档位、卡片、行、主题和反馈出口已有共同基座 |
| 页面与组件的实际复用 | 较成熟 | 技能/专家共用目录展示，设置控件、成果/知识行与浮层均有共享实现 |
| 引导 AI 找到正确实现 | 强，但阅读成本偏高 | AGENTS 路由、场景规则、docs/10 台账与 docs/12 指向同一规范；正文混有大量治理历史 |
| 阻止 AI 换名字再造轮子 | 局部有效，尚未闭环 | 原生按钮/输入/披露被拦；新类名和部分内联写法仍可通过 |
| 键盘与浮层基础 | 有良好基础 | Modal、菜单、Tabs 等有语义封装和行为测试，预览弹窗实际焦点恢复正常 |
| 真实渲染回归保障 | 尚需补强 | 当前 CI 主要验证代码与行为；未发现纳入 CI 的通用页面截图/无障碍回归矩阵 |

## 2. 实际界面评价

走查了当前开发版 macOS Electron 窗口的工作、成果、知识、技能、专家与设置页，以及专家编辑表单、工作上下文、Markdown/PPTX 成果详情和预览弹窗。观感评价基于当前青玉深色窗口；没有把源码审查等同于其他七个主题变体的视觉验收。

### 2.1 已经做好的部分

- 导航固定为工作／成果／知识／技能／专家，设置独立放在侧栏底部，领域名称清楚，未见额外的“能力页”混淆。工作空间与任务区域服务于持续工作，不靠 AI 装饰营造产品感。
- 管理页的标题、正文列、操作按钮和表面层级基本统一。技能与专家卡片的身份区、简介和动作使用共同呈现方式，领域差异通过事实和状态表达，复用是实际发生的。
- 输入、选择、切换、错误、状态与空态已有固定出口。设置页的标签、帮助说明和配置分区比较完整，能表达本地凭据保持、启用状态和失败出口等真实产品条件。
- 工作首页相对克制，输入区是核心操作；右侧上下文可完全收起，展开后按过程、资料、记忆、简报、成果分组，符合渐进披露方向。
- 成果有版本、来源与引用关系，作为一等对象存在。PPTX 预览保留文档自己的白底和配色，没有被应用深色主题改写。
- 知识“更多”菜单可以 Esc 关闭；PPTX 放大预览期间主界面退出可操作的可访问性树，Esc 关闭后焦点回到原缩略图按钮。共享浮层行为有实际落地。

### 2.2 各页的产品取舍

| 页面 | 当前优点 | 值得改进的方向 |
| --- | --- | --- |
| 工作 | 目标和输入突出，工作空间入口与上下文面板清楚 | 本次未启动真实 Run；流式、取消、失败和恢复体验不能据此宣布人工验收完成 |
| 成果列表与详情 | 版本、打开/导出、质量状态和引用链完整 | 详情在正文/预览前安排了参考版本、采用依据、版本历史和多段契约说明，首屏更像管理记录；可保留重要状态，把解释与详细来源折叠到次级区域，使内容更早出现 |
| 知识 | 搜索、分组、索引状态与管理操作齐备 | 宽窗口下筛选、搜索、任务状态仍纵向堆叠；长路径和辅助状态较多。可依据使用频率优化工具栏占高和路径披露，保留必要来源能力 |
| 技能 | 信任、启用、准备状态和来源区别清楚，共享卡片有效 | 多种状态与动作同时出现，初次使用需要学习；优先验证用户能否快速找到“当前可用/为什么不可用” |
| 专家 | 与技能呈现一致，召唤到对话的路径符合既定设计 | 卡片召唤在 hover/focus 时出现，是已接受设计的取舍，宜验证首次发现率；编辑表单中的知识/成果参考材料清单较长，当前约 30 份知识的样本已显示选择成本，可评估复用已有选择器能力 |
| 设置·模型/搜索/MCP | 高级配置独立，标签、凭据说明和测试/保存入口清楚 | 技术信息对目标用户必要，但需区分“初次接入”与“高级诊断”层级；MCP 空态可更明确说明从哪里取得配置 |
| 设置·记忆 | 来源、范围、自动提炼开关和建议边界透明 | 解释和治理术语密集，单条记录同时解释命中、门槛、排除与来源约束；可把可操作的内容与解释分层，提高扫描效率 |
| 设置·外观/通用 | 模式与色系两个维度易理解，预览明确 | 产品文案仍有 `Variant` 等工程词；通用页为后续开放空态，说明配置产品完成度仍有阶段性边界 |

这些大多是信息层级与可发现性的优化，不是共享组件失效，也不需要推翻当前 UI 体系。专家召唤等已接受交互若要改变，应先遵循现有设计决策流程。

## 3. 规范与门禁的真实能力

### 3.1 已构成有效约束的部分

1. **入口统一。** AGENTS 要求先读 docs/10，Qoder 场景规则指向同一真相源；docs/10 §10.1 提供组件台账，docs/12 §8 给出工程要求。不是不同智能体各有一套风格。
2. **组件接口能缩小选择空间。** Button 的变体、必填尺寸档位，输入/选择控件、Tabs、Badge、EmptyNotice、CatalogCard/Row 和布局组件等，让正常开发不必重新决定基础几何和语义。
3. **反馈分流明确。** 短时确认、可行动内联错误、跨页长操作结果分别落到 TransientToast、InlineError、消息中心/ToastHost；状态呈现另有 StatusNote。该决策表很有价值，能减少成功横幅、重复 Toast 和错误出口漂移。
4. **历史回退防线扎实。** `standards/coding-standard.test.ts` 共 130 项护栏，包含原生控件出口、退役类、Token、字号/图标档位、焦点环、动作排档、导航名称和文档镜像等；例外需要可检查的清单，不靠口头放宽。
5. **验证进入 CI。** `npm run verify` 包含 lint、格式、类型、功能/heavy 测试与构建；`.github/workflows/verify.yml` 在 PR 和 main push 执行它。仓库托管侧是否设置为必须通过的合并检查，本次未核验。

### 3.2 通过违规探针确认的边界

在临时仓库副本中逐项注入最小违规实现，检查后还原。没有修改本项目生产源码、护栏或规范，也没有向运行中的应用注入代码。先确认副本基线 130 项全绿，再测试以下七种形态。

| 探针 | 当前结果 | 含义 |
| --- | --- | --- |
| 新页面直接写 `<button>`、`<input>`、`<details>/<summary>` | 3 项护栏失败 | 对已有明确基座的原生控件出口约束有效 |
| 新卡片类用 `padding: var(--card-padding)`，未登记表面 | 1 项护栏失败 | 表面 Token 使用清单有效，不是完全没有约束 |
| 内联几何包含 `fontSize: 10` | 1 项护栏失败 | 内联裸字号已有拦截 |
| 新 `.ui-audit-page/.ui-audit-tile/.ui-audit-flag`：自写版心、卡片/徽标，仅按钮复用 Button | 130 项全绿；定向 ESLint 与全项目类型检查通过 | 新名字避开已知卡片钩子/徽标后缀；`max-width: 720px` 和卡片 `padding: 16px` 未被识别 |
| 内联 `lineHeight: 1.1, padding: 7, margin: 7, borderRadius: 5, height: 27`，去掉字号 | 130 项全绿；定向 ESLint 与全项目类型检查通过 | 其他内联几何没有字号同等的出口约束 |
| `<div role="button" tabIndex={0} onClick={...}>`，没有键盘激活逻辑 | 130 项全绿；定向 ESLint 与全项目类型检查通过 | 看似带语义和焦点，仍无法通过 Enter/Space 执行动作；未被一般可访问性规则拦截 |
| 仅从 ocean 深色块删去 `--danger-hover` 定义 | 130 项全绿 | Token 检查验证全表定义集合，未验证每个变体的契约完整性；本项仅运行护栏 |

以上不表示当前页面存在这些人为注入的实现，也不表示为每个探针跑过完整 verify。新类名表面、内联几何、可点击 div 这三个绕过实现实际跑的是 130 项护栏、定向 ESLint 与全项目类型检查；完整 verify 是在未注入的本项目基线上执行的。

关键代码位置：

- `standards/coding-standard.test.ts:1377`：卡片外壳检查主要识别列出的领域钩子。
- `standards/coding-standard.test.ts:2301`：徽标检查仍依赖 `chip/badge/status/state/kind/pill` 等后缀，注释所说“不靠类名”与实际覆盖范围有差距。
- `standards/coding-standard.test.ts:3945`：版心检查识别 `width: min(数字px, ...)`，没有保证每个新视图实际组合现有页面骨架。
- `standards/coding-standard.test.ts:4834`：内联档位扫描主要针对裸 `fontSize`。
- `standards/coding-standard.test.ts:5001`：表面登记扫描的是指定表面 Token，裸内距无法借此归属到基座。
- `standards/coding-standard.test.ts:521`：Token 定义检查按样式表集合判断，不能替代逐主题契约检查。

因此，当前体系能够有效引导一个遵守规则的 AI，也能拦住不少常见退化，但仍不能把“新增页面一定复用现有骨架和展示基座”作为自动门禁已保证的事实。一个普通实现习惯是先写新类名、再用现有颜色 Token；它并不需要故意绕规则，就可能落入这些空隙。

## 4. 维护与验收风险

### 4.1 静态扫描不能替代真实渲染

共享 Modal、PopoverMenu、Tabs 等的行为测试是有价值的；近期焦点环治理还有真实 Electron 像素测量记录。现有工程不是缺少验证意识。

但一次性像素夹具与 jsdom 行为测试，还不是持续覆盖页面的真实渲染回归。源码中没有发现常规 Storybook/Playwright/axe 配置或页面快照矩阵纳入 CI；不能据此保证八个主题、长内容、小窗口、浮层碰撞和屏幕阅读器体验。

部分反馈问题也需要调用链和行为验收：使用了正确出口，并不自动证明同一结果没有在另一个出口重复播报。docs/10 已正确承认这类边界。

### 4.2 体系集中，但新功能仍有组合成本

App 约 1,835 行，主样式约 4,794 行，ContextPanel 约 995 行，多个视图约 500–1,100 行，护栏文件约 5,096 行。它们说明状态组合、领域布局与规则维护仍集中在少数大文件中。

这不是按行数判定坏代码，也不建议继续机械拆组件。更有价值的是让新页面有明确的组合入口、让重复的选择/筛选/状态模式可查，并让护栏识别这些入口的实际使用关系。否则 AI 会复用 Button，同时复制大量页面级布局和业务交互。

### 4.3 文档的可信度与读取成本

docs/10 的规则和组件台账很完整，但治理历史、退役说明和现行要求交织，文档已超过千行。新增页面时，需要更短的“先找什么、按什么骨架组合、缺能力怎么办”入口。

docs/11 §3 仍写 161 个功能测试文件、1,501 项测试、69 项护栏；本次实际为功能档 173 文件/1,559 项、heavy 档 6 文件/133 项、护栏 130 项。这是统计快照过期，不是检查本身失效。建议统计明确标注日期或由验证输出生成，避免 AI 把历史数字当成当前状态。

## 5. 建议优先级

以下是建议，尚未实施；实施时仍须同步现有规范、配置/护栏与必要行为测试，不能新增第二套规则源。

### 第一优先：让新增代码真正进入现有体系

1. **补页面组合的正向约束。** 明确普通管理页应组合 PageHeader、PageToolbar（有工具栏时）、ScrollRegion、ViewContainer 等现有基座；合法的设置/详情/工作区形态登记理由。检查应验证实际渲染关系或可追溯包装，而不只是文件里出现一个 import。避免强迫不同信息架构套同一个万能 Page。
2. **补卡片、徽标和内联样式出口。** 从“旧类名不能回来”推进到“新表面的外壳由谁负责”。用结构化解析及基座归属/明确例外减少类名猜测，覆盖内联行高、间距、圆角和控件高度。动态浮层坐标等合法内联值需要按用途豁免，不能一刀切禁用 style。
3. **补交互语义检查。** 默认复用原生语义的 Button 等基座；必要的自定义交互元素应有可核验的键盘行为。加入通用 JSX 可访问性检查并配关键行为用例，避免只加 `role` 就视为完成。

### 第二优先：补持续验收和产品效率

4. **逐变体检查主题契约。** 区分全局几何/动效 Token 与每个色系必须提供的语义色 Token，对八个正式变体逐项比较；关键文字、按钮、聚焦和禁用状态同时做真实渲染检查。
5. **建立小而稳定的视觉回归集。** 先覆盖代表性管理页、设置长表单、成果详情、菜单/弹窗、工作输入区与上下文面板；至少有浅/深、紧凑/宽窗口、长文本和错误/空态。无需先引入一整套新组件展示平台。
6. **调整信息层级。** 先解决成果正文出现偏晚、记忆解释密集、专家参考材料清单选择成本，再验证召唤入口发现率。尽量复用现有 Disclosure、选择器和版心，保留现有来源/范围契约。

### 第三优先：减少规则使用与维护成本

7. 在 docs/10 现有真相源内增加简短的新增页面操作入口：查台账 → 选页面形态 → 复用控件/反馈/空态 → 必要能力扩展现有组件 → 验证状态与主题。历史叙述可链接到日志/ADR，当前规则应更容易检索。
8. 为关键护栏保留有代表性的违规变异用例，验证“确实能拦住”而不是只有当前源码一直通过。优先替换误判风险大的文本匹配，不必把所有 130 条同时改写。
9. 确认 CI 检查在托管侧被设为合并必需项，并在审阅中关注新页面及规范/白名单变更。任何 AI 能改代码也能改护栏，自动检查不能独自承担规则变更审查。
