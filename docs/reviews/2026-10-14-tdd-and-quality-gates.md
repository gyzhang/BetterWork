## 3. TDD 的实际落实程度

### 已落实的强项

1. **核心测试具有业务语义。** Agent Core 断言有序事件、sequence 和取消终态；仓储和迁移使用真实 SQLite；IPC 测试验证非法输入、输出 Schema、归属和实际主进程旅程；Provider 注入请求替身验证 SSE 与错误；Hook 用可控 Promise 验证 A→B、A→B→A、迟到失败和保存所有权。
2. **负例能验证断言的检出能力。** `scripts/ui-render-check.test.ts` 验证主题画布、模态绘制、键盘、持久化与强杀恢复退化确实使 CLI 失败。QI07 日志保留隔离副本中四项变异的失败及恢复结果。这比一直在当前源码上得到绿灯更有说服力，但变异成功本身不能证明实现前先写测试。
3. **实现与测试通常共同交付。** 当次抽样最近 30 个 fix/feat 提交，27 个包含测试文件变更；其余包括资源哈希、DMG 品牌资源和 UI 操作模式变更。这个样本跨越近期合并和部分历史非合并提交，只说明测试同交付较普遍，不是 TDD 比例，也不证明每个未改测试的提交都缺保护。
4. **测试入口完整。** 当次 Git 跟踪的测试文件为 336 个，其中 16 个是 bench；功能档和重档实际执行的 320 个文件与远端一致。巡检另把导入的结构判据模块计为测试文件，因此其 344 的粗读数不能与 Vitest 文件数混用。
5. **测试没有普遍静默跳过。** 静态扫描只有真实解释器验收的条件 skip；本轮完整覆盖率运行与最新远端完整验证均未跳过用例。它仍具有环境依赖，不能由本次未跳过推导未来每次都会执行。

### 距离严格 TDD 的差距

- TC 任务板的“TDD 工作流”主要约束同 PR 配套测试、公共 API、行为断言和边界场景，未完整要求每项新增行为保留 Red → Green → Refactor 的执行证据。
- TC01–TC06 的大量工作是给已有实现补测试。它提升可重构性和回归保证，属于补测/特征测试；不能倒推过去实现遵循测试先行。
- Squash 后实现与测试同一提交只能证明共同交付，无法从 Git 时间确认编辑顺序。部分日志明确记录先红后绿，部分仅记录最终绿灯；本轮不能为所有功能证明严格 TDD。
- QI 复审曾在既有相关测试通过时发现数值串授权和成果乱序缺陷，说明测试数量和总体覆盖率仍可遗漏业务契约。后续反例已纳入回归；应继续围绕失败语义和业务不变量扩展测试。
- 部分仓储测试使用类型转换取得私有 db 并直接写 SQL。构造损坏数据和约束反例有合理用途，但普通正例夹具宜优先走公共 API，避免实现重构导致测试过度耦合。

建议把“严格 TDD”首先落实到新增领域行为和缺陷修复：记录最小失败场景、确认失败原因、最终绿跑，以及必要的重构回归。已有实现的补测如实归类，不为取得 TDD 标签强行制造无意义红灯。

## 4. 提交、推送、PR、合并后的门禁链路

| 阶段 | 实际检查 | 能保证与边界 |
| --- | --- | --- |
| 本机 pre-commit | 暂存差异空白；按暂存路径选择 ESLint/Prettier；涉及 Markdown 跑 docs:check | 快速反馈，不跑全仓类型、测试、构建和 UI；lint/format 读取工作树内容 |
| 本机 pre-push | 干净工作树、待推送对象等于当前 HEAD、差异空白、拒绝 main 目标 | 确认推送版本，不执行产品测试；不能把 push 成功称为质量验证通过 |
| 普通分支 push | workflow 不接 push 事件 | 未创建/更新目标为 main 的 PR 时，不会仅因 push 自动启动 CI |
| 代码/混合 PR | macOS：npm ci、lint、format:check、typecheck、docs:check、相关 functional → 相关 heavy | 验证合并候选；heavy 保持串行；不包含完整构建与 UI 矩阵 |
| 纯 Markdown PR | docs:check | 文档与结构一致性，不证明产品运行行为 |
| PR Gate | 分类成功且对应检查必须成功；失败、取消、跳过或无效分类拒绝 | 稳定的必需状态，实际脚本有正反例执行测试 |
| 手动/夜间 Full verify | lint、format、typecheck、全部功能/重档、build、ui:check | 检查该次 SHA；独立于 PR Gate，不追溯阻止已完成合并 |
| bench/真实模型/安装/人工 | 独立专项 | 完整 verify 不代表性能预算、真实模型语义或签名安装通过 |

2026-10-14 API 读回 main 保护：必需状态 `PR Gate`，strict=true，管理员受约束，禁止强推和删除；审批人数为 0，不要求 Code Owner、最后推送审批或讨论全部解决。因此有强制自动化合并门禁，但没有机器强制的人工互审。当前单人维护决策允许这一点。

本机 `npm run drift:check` 退出 0，Husky wrapper 与入口探针有效，无未推送提交或规则指纹漂移。它证明本次克隆入口有效，不能证明历史提交从未绕过钩子。

## 6. 已验证的缺口与优先级

### P1：动态依赖未进入相关测试选择

工作流两档均使用 `--changed="$BASE_SHA" --passWithNoTests`。文件系统读取、子进程启动脚本、内置资源和 Electron 夹具可能不进入 Vitest 静态依赖图。

本轮对 `resources/skills/release-manifest.json` 执行 related functional 和 heavy，两档都选中零测试并退出 0。[PR #185 的运行 38242064142](https://github.com/gyzhang/BetterWork/actions/runs/38242064142) 也显示两档 `No test files found` 后 PR Gate 成功。该文件实际上由发布预检动态读取并校验资源哈希，不能认为没有相关行为。

[QI07 PR 运行 38301757435](https://github.com/gyzhang/BetterWork/actions/runs/38301757435) 修改 UI 脚本与旅程夹具，却只选择 Office 适配器的 functional，heavy 选中零文件。该任务已有本地 UI 证据，因此不能称当时没有测试；可以确认远端快门禁没有独立重验这些 UI 变化。

建议在现有分类/选择入口补小范围强制映射：资源清单及 Skill 资源 → 发布预检；UI runner/旅程夹具 → 对应 CLI/旅程；运行脚本、迁移和关键配置按实际动态依赖补关联。合法的零测试仍可保留，但已登记的关键路径变化选中零测试必须明确报出或拒绝。无需恢复每个 PR 全量 verify。

### P1：覆盖率计划与可执行门禁未闭合

TC 任务板已批准“新代码行覆盖 ≥80%”，TC00 状态为 done，但配置没有 thresholds，CI 不调用 coverage，也没有差异行覆盖计算。当前整体 86.26% 超过 80% 不代表新代码均达标；全局阈值也不能代替差异覆盖率。

建议用当次可靠数据重新建立基线，先对新增/修改的领域行为接差异覆盖；记录纳入/排除理由，明确分支覆盖与核心契约测试要求。同步 TC00 的验收事实和历史 0% 的当前状态，保留历史日志，不把门槛存在写成已执行。

### P2：同 SHA 的 Full verify 失败缺少仓内归因收口

本轮在 docs 中未找到上述 `38317186411`、后续手动绿跑或 `kill EPERM` 的对应根因记录。可以定位失败操作，不能据同 SHA 的两次绿跑确认其已消除，也不能直接判定产品恢复有缺陷。

建议读取失败产物，分析 prepare/recover 阶段和 finally 清理的进程组生命周期，再用隔离夹具验证。保持“真实强杀”和新进程回读断言；不能通过忽略 EPERM 或放宽断言取得绿灯。修复/环境归因及对应 SHA 留入日志。

### P2：pre-commit 检查路径，不检查暂存快照

`pre-commit-check.mjs` 从 index 取得文件名后，将同名工作树文件交给 lint/format。若暂存了错误版本，再在工作树修好但未暂存，可出现“检查通过、提交仍含错误”。本轮独立临时 Git 夹具用确定性 lint 替身证实脚本退出 0，而 index 仍保留替身定义的违规内容；没有在本仓库提交或推送。

这不是 main 的直接绕过：pre-push 要求干净 HEAD，远端还跑全仓静态检查。建议在快检中明确拒绝被检查路径有未暂存差异，或读取隔离的暂存快照；先保留一个部分暂存行为回归。

### P2/P3：测试治理和发布尾项

- 覆盖率配置另起一个并发档，没有复用 functional/heavy 的隔离策略；本轮成功不说明高负载下一直可靠。宜共用测试范围和串行约束，避免覆盖率入口与正常测试入口渐渐分叉。
- 新行为同 PR 配套测试目前主要由规范与 Review 执行；没有等价的变更级检查证明每项行为已有测试，也没有普遍的 Red/Green 证据模板。优先覆盖业务不变量，不按一对一文件数机械设门禁。
- 性能预算只在 bench，未进入夜间 Full verify，符合当前规范；不能从全绿推导性能已验。性能相关变更继续定向运行现有 bench。
- UI 自动化覆盖生产组件、页面组合、真实 IPC/临时 SQLite 和特定强杀恢复；仍未证明所有主题/页面/真实 Skill/真实模型/屏幕阅读器/签名安装路径。发布或里程碑按原任务板单独收口，不把这些尾项称为普通单测欠账。

## 7. 建议实施顺序

1. 补动态依赖选择映射，消除关键资源和 UI 脚本变化的零测试成功。
2. 更新覆盖率基线及 TC00 验收事实，落实已经批准的差异覆盖门槛，优先提高 IPC、RunService 和设置关键分支的行为保护。
3. 关闭进程恢复失败的根因与证据，保留同 SHA 红/绿的区别；核对夜间发现延迟与期望的反馈时点。
4. 修正部分暂存快检边界，给新增行为/缺陷修复采用轻量 Red/Green 证据记录。
5. 延续现行快 PR/手动夜间分工，在发布节点补签名安装、真实模型和原任务板人工验收。

以上是评估建议，没有自动授权本轮修改实现、发布或启动真实服务。
