## 1. 已确认的产品决策

1. 定位保持「面向知识工作者的个人 AI 工作台」，专注个人提效；先服务自己，再服务周边同事。当前没有产品市场化、企业管理或组织提效目标，开源不改变这一边界。
2. 实际可用性优先。教学目标发生冲突时让位，经验文章和课程由用户后续独立总结。
3. 没有先建个人知识库也能开始工作；已有知识、工作目录材料、协作记忆和历史成果共同支撑新知识探索。
4. 首条真实场景是「集团智能体场景落地」：平台资料 → 业务及官方要求调研 → 场景提取 → 平台适配与落地方案 → 公司模板 PPT。
5. 一个专家调用多项 Skill 持续承担完整任务，不依赖多个专家交接或多 Agent 自主协作。
6. 专家包含人格、系统提示词、知识范围（共用和专家专属）、工具及 Skill。产品分发内置专家、Skill 和必要资源；用户配置模型、搜索等外部服务后可直接使用。
7. 工作材料倾向组织在长期工作目录中，以 Workspace 承接持续项目工作。
8. 围绕成果持续讨论和修改；最终 PPT 可编辑，用户在办公软件中完成最后调整并用于领导会议。
9. 六个讨论节点：理解与计划、网络调研完成、报告大纲、报告完成、PPT 大纲、PPT 完成后的持续修改。
10. 首个必须支持的 Skill 为用户提供的 `ppt-generation-expert`；Python 脚本、本地工具链依赖、文件生成与校验运行必须从阶段 A 支持（本轮后续确认）。
11. 开发顺序正式确认为 **A：Skill 管理与配置 → B：专家管理与配置 → C：研究到汇报完整路径**。基础配置前置，不等同于提前建设公开市场或完整扩展生态。

产品定位建议表述（用于现有定位的展开）：

> 算台是面向个人知识工作的 AI 工作台。用户通过配置化专家调用多项 Skill，结合长期工作目录、个人知识与协作积累，在持续讨论中完成研究、分析、文档和演示，并让成果成为后续工作的基础。

## 3. 阶段 A：Skill 管理与配置（建议）

### 3.1 用户可以做什么

- 浏览、搜索、按来源和启用状态筛选 Skill，查看用途、指令、工具需求和配套资源。
- 创建、编辑、复制用户 Skill；导入、导出本地包；停用或删除用户 Skill。
- 内置 Skill 可查看和停用，修改通过复制为用户 Skill，避免升级覆盖个人修改。
- 保存草稿与「可以用于任务」分开：草稿允许缺少依赖，启用和试运行前指出缺项并链接对应设置。
- 以首个脚本型 Skill 提供真实最小试运行，检查指令、资源、脚本/CLI、依赖与 PPTX 输出；不要求先完成专家编辑器。

### 3.2 配置范围

| 分组 | 建议内容 |
| --- | --- |
| 基本信息 | 稳定 ID、名称、描述、版本、来源、启用状态 |
| 方法 | 适用任务、输入要求、工作指令、交付要求、检查清单 |
| 工具需求 | 引用已注册工具；必要/可选需求；缺失工具或外部服务的提示 |
| 配套资源 | 参考文档、模板、示例；相对包目录的路径 |
| 运行环境 | Python 解释器、工作目录、环境变量、外部工具链及依赖状态 |
| 执行与产物 | 脚本/CLI 参数、文件读写范围、质量报告与成果登记 |
| 验证 | 配置有效性、资源存在性、工具可用性、真实脚本任务试运行结果 |

必须支持样本的 frontmatter + `SKILL.md` + scripts/references/templates/assets 目录结构，不强制用户先改写为算台专有 manifest。运行配置可由宿主补充；确切 Schema、ZIP 支持与冲突策略在实现 ADR 中确定。

已撤回仅支持指令与工具引用的建议。阶段 A 必须具备 Python 脚本与 CLI 调用、外部本地工具链、依赖准备、文件生成、进程树取消/超时及质量门，实际跑通用户提供的 PPT Skill。导入不自动执行代码；具体执行约束、依赖安装和资源访问在开工前设计。MCP 与其他解释器是否前置独立讨论，不能把它们与本样本的必需能力绑定。

模型和搜索 API Key 继续在独立设置中管理。Skill 引用服务需求，不在包中保存密钥。导出只包含所选配置与配套资源，不夹带用户工作目录、项目记忆或历史成果。

### 3.3 验收

1. 新建 Skill、保存、重启后仍可读取；修改工作指令在下一次试运行中可见。
2. 本地导出再导入，指令与相对资源引用可用；ID/版本冲突有明确处理，不静默覆盖。
3. 缺少工具、模板或搜索配置时给出具体缺项；禁用后不继续作为可选能力进入新运行。
4. 删除被引用 Skill 时说明影响，避免专家静默退化；运行中使用的配置保持稳定。
5. 导入失败不留下半安装状态；资源路径不能越出包边界。
6. 使用 Fake Provider 的确定性用例验证加载与工具限制；真实模型试运行单独人工验收。
7. 在专家配置 UI 之前，以合成内容通过样本原生 SVG → PPTX → 模板合并 → 校验链路，登记实际成果；缺依赖、取消、质量门失败与旧产物误认有验证，见样本边界文档 §7。

## 4. 阶段 B：专家管理与配置（建议）

### 4.1 用户可以做什么

- 浏览、创建、编辑、复制、启停和删除专家；选择专家启动任务。
- 配置人格/职责、系统提示词、Skill、工具范围、知识范围、模型与输出偏好。
- 看到「已配置但缺少能力」的原因，能直接进入 Skill 或外部服务设置修复。
- 使用产品内置专家，也可以复制后形成自己的版本。

### 4.2 关键关系

- 共用知识指该用户可供多个专家使用的个人知识；专家专属知识指该专家额外绑定的资料集合，不是企业公共知识库。
- 随产品分发的通用参考材料与用户公司文档分开；项目资料和公司模板属于用户工作区。
- Task 选择专家，专家绑定多个 Skill；人格与方法不替代 Task 的阶段决策和 Workspace 的项目事实。
- 建议有效工具集合为「运行时已注册且服务可用」与「专家允许」的交集；Skill 必需工具不在集合内时明确不可用，不能只靠提示词限制。
- 知识范围建议由共用范围、专家范围和当前工作区/任务选定资料组合；在检索边界真正执行过滤，不只写进提示词。
- 配置变更建议从下次 Run 生效；每次 Run 记录所用专家/Skill 的版本或快照，历史运行不随当前配置变化而改写。

知识隔离、配置快照、有效工具计算和包资源读取涉及跨模块设计，必须先新增实现 ADR、共享协议和迁移测试。本稿不决定新增数据库表名或扩张 Agent Core 的宿主依赖。

### 4.3 验收

1. 绑定两项 Skill 后，在同一专家的一次任务中加载并使用对应方法与工具，无需切换专家。
2. 专家提示词、模型选择、工具限制和知识范围均影响执行；不同知识范围的检索互不越界。
3. 删除/停用配置有明确关联影响，已存在任务和成果历史仍可查看。
4. 缺配置可以保存草稿；可用专家在用户配置外部服务后能直接启动任务。
5. 产品分发资源无需依赖开发机绝对路径，内置更新不覆盖用户副本。

## 5. 阶段 C：研究到汇报（建议拆分）

| 切片 | 能力与交付 | 用户讨论节点 |
| --- | --- | --- |
| C1 项目与研究准备 | 长期目录材料按需发现/读取、平台能力画像、研究目标与计划 | ① 理解与计划 |
| C2 网络研究 | 搜索与正文获取、官方文件适用范围/日期、业务流程、供应商主张、来源与缺口 | ② 调研完成 |
| C3 分析与报告 | 场景提取、数据与集成前提、平台适配、落地优先级、引用及报告修订 | ③ 报告大纲、④ 报告完成 |
| C4 汇报制作 | 汇报故事线、逐页大纲、公司模板输入、可编辑 PPTX、渲染与检查、局部及整体调整 | ⑤ PPT 大纲、⑥ PPT 完成与迭代 |
| C5 持续积累与分发验收 | 历史成果再利用、经确认的项目知识/记忆、安装包与外部服务配置后的全流程验收 | 验证下一项任务能够复用前一次工作 |

同一任务可有多份成果，用户可明确选定要改的成果与版本。关键事实变化后提示相关成果需要更新，不无条件自动覆盖后续成果。

六个节点必须有可持久化的审阅材料、用户反馈及继续/返工位置。不能只依靠提示词要求「请等待用户」。等待采用结束当前 Run 后续开 Run，还是引入 `run.waiting`，需在恢复语义 ADR 中选择；保留 Run 明确终态和启动中断收口约束。

网络搜索摘要不能替代官方正文核对；官方要求、供应商宣传、用户确认和模型推断应区分。未知业务前提作为待核实事项，不编造为事实。本阶段不实际接入集团业务系统或替集团作上线决策。

报告首版建议交付 Markdown 与 DOCX；PPTX 可编辑是已确认目标。Word 模板保真程度、复杂 PPT 元素保留范围、最终人工修改文件是否回收为新版本需进一步确认。应用内完整 Office 编辑器不作为建议首版前提。
