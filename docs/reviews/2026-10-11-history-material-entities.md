## 问题与范围

R10 的历史来源和最终回答已集中读取，材料实体检查仍对每个候选的已选、实际读取、继承引用逐项查询。同一精确成果版本反复加载正文、文件元数据及 Evidence，同一输入快照反复映射完整记录。E15 只整理这一步的读取；完整历史候选与保守依赖并集先于重放预算。

`historyMaterialAvailability` 在每次调用内收集精确 artifactVersionId、snapshotId，分别去重。成果仓储新增 `listVersionDetails`，以单个绑定 JSON 请求读取完整版本、必要文件元数据及全部来源；版本按请求首见顺序，Evidence 按 capturedAt DESC / rowid DESC。输入快照新增 `listByIds`，沿用完整映射和请求首见顺序。缺实体保持缺失，可读 Markdown 与文件成果沿用原详情解码器。

服务仍逐条判定引用，知识 sourcePath 的空白判据不能被另一个同列表身份引用覆盖。列表身份仅用于原历史理由集合；不替代精确实体 ID，也不授予读取权限。只有不可读版本行时仍不可用，损坏 Evidence JSON 或 Schema 仍抛出，未请求实体与外任务/未来 Run 的来源不被解码。调用间重新读取，不加全局 LIMIT、不跟随 latest。

本次可用性整理保留原行为：这里检查成果详情或快照记录是否存在；快照的 preparing/failed/cancelled 不在本层重新判为缺失。版本字段相等、哈希、范围及实际文件读取校验继续由现有准备与工具边界负责。本层没有新增或放宽材料授权。

| 实际读取量 | 原逐引用读取 | 批量读取 |
| --- | ---: | ---: |
| SQL 查询 | 3,072 | 4 |
| 完整成果详情 | 1,024 | 8 |
| 完整快照 | 512 | 4 |
| 解码 Evidence | 3,072 | 24 |

可用性结果逐项相等，详情仍完整读取与解码，减少的是重复实体。字节读数是解码对象的序列化大小，不是 SQLite 传输量、进程峰值内存或 RSS。样本包含大量重复材料，不能外推全部材料独有时的收益，也不代表端到端或容量结论。

E13 来源阶段对照仍为 768→3 查询、完整 1,536 行及 1,261,860 字节相等，中位 19.24→9.60 ms。E14 回答阶段仍为 256→1 查询，无空尾/混合空尾完整消费 256/511 条，消费及结果字节相等；混合空尾 p95 基本持平。二者仅作相邻读取切片回归，不与 E15 耗时累加成整链路结论。
