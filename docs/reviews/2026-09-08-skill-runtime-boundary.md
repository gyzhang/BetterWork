## 1. 样本究竟是什么

这是一个包含工作方法、模板规范、二进制模板和可执行脚本的文件夹 Skill，不是一个只有系统提示词的配置项。名称中的 expert 不要求把它转成 BetterWork 的 Expert；它可作为一个专家绑定的 PPT 制作 Skill。

实际执行链：

```text
读取 SKILL.md、模板档案、叙事与图表参考
→ 调用 ppt-master 初始化项目
→ Agent 编写/修改 SVG、spec_lock.md、pages.json
→ Python 子进程运行 SVG 质检与原生形状导出
→ Python 合并公司 PPT 模板
→ OOXML 校验、页面预览与检查
→ 登记可编辑 PPTX 与版本
→ 用户反馈后修改源页面并重新导出
```

不能把「文件夹能导入」「三个脚本能显示」或「用自建 PPT 工具替代该管线」视为支持这个样本。

## 2. 能力与首版要求

| 样本证据 | 实际需要 | 首版边界修正 |
| --- | --- | --- |
| SKILL.md 为 YAML frontmatter + Markdown，无专有 manifest | 读取元数据、按需加载完整指令，保存未知字段 | 支持此类目录直接导入；额外配置由宿主补充，不强制用户先改成算台专有格式 |
| references/、templates/ 与 assets/ | 相对路径读取文本及二进制模板 | 完整保留目录与资源，允许用户配置专属模板；不把公司资产自动加入公开分发 |
| `svg_native_export.py`、merge、validate | 本地 Python 执行和第三方包 | 脚本执行、解释器选择、包依赖检测与准备前移到 A |
| exporter 用 subprocess 调用 ppt-master 脚本，并可能 execve 重启 | 子进程树、环境变量、工作目录 | 支持子进程；超时/取消覆盖后代与重执行，不能仅终止父进程 |
| `PPTM_HOME` 外部仓库与图表/图标资产 | 本地工具链依赖与资产读取 | 支持注册外部依赖根、版本/校验信息、缺失诊断；依赖不必伪装成 MCP 或全部塞进 Skill 包 |
| SVG、spec_lock、pages.json 与 validation/、exports/ | Agent 文件创建、编辑与脚本产物写入 | 在任务工作目录中支持文件操作，保留中间源文件以便迭代 |
| 文档里的 shell 命令、cp、open | 命令执行、复制成果、系统预览 | 支持脚本/CLI 调用；复制与打开可由等价的宿主文件/预览工具承接，无需完全复制 WorkBuddy shell 语法 |
| `LATEST_PPTX`、JSON 报告、OOXML 校验 | 输出解析、质量门、成果登记 | 统一退出码、输出、报告及产物归属；校验失败不标记交付成功 |

该样本没有 MCP 或外部在线生成服务依赖；模型服务仍由宿主提供。脚本必须前置，不因此推导出 MCP 或在线市场必须同时实现。样本没有要求 JavaScript/Node 执行器，其支持范围可后续独立确认。

## 3. 管理与配置相应增加

除了名称、指令、启停和工具引用，阶段 A 还需承接：

- 运行环境：解释器、工作目录、必要环境变量（如 PPTM_HOME）及依赖状态。
- 依赖：Python 模块、外部本地工具链、字体与模板资源；显示缺项并有可操作的准备路径。
- 执行：可调用脚本/CLI、结构化参数、输出报告及成果路径约定。不能只允许三个预枚举脚本而阻止 Skill 中的项目初始化、图标同步等必要调用。
- 文件访问：Skill/工具链参考资源、任务输入、任务写入目录、产物导出位置分别处理。
- 试运行：真实执行这个 Skill 的缩小样例，查看进度、错误、报告和成果，不只验证提示词拼装。

确切字段、自动探测与手工配置的分工仍在实现 ADR 中定义。优先从原包自动发现信息，缺失内容在宿主配置中补齐，避免要求用户逐条改写所有示例命令。

## 4. 环境与分发

- 原文中的 `/opt/miniconda3/bin/python3`、`~/.workbuddy/skills/...` 和 `/Users/kevin/Dev4AI/ppt-master` 是这台机器的运行假设，不能成为产品固定路径。宿主应提供实际 Skill 根、解释器和外部依赖位置；明确映射或在导入副本中适配，原始文件夹不改写。
- 该样本至少直接依赖 python-pptx 与 lxml；ppt-master 的传递依赖需按选定版本核实，不能依据参考手册「标准库即可」判定环境就绪。
- 样本要求系统 Python 是针对 WorkBuddy shim 故障的经验。BetterWork 应提供可配置、依赖完整且无相同环境污染的解释器，不直接假设任意系统 Python 或托管 Python 都适用。
- 内置分发的 Skill 应连同兼容的运行环境/依赖提供，或通过产品内明确的准备流程完成，不能让普通用户靠手工 clone 和 pip 排障。采用内置 runtime 还是安装引导尚待设计。
- 外部 ppt-master 需要绑定可验证版本，产品内资源应满足其完整性和许可要求。本轮未克隆、更新或重新分发该仓库。
- 公司模板作为用户验收样本留在本地，不复制到 BetterWork Git 仓库或默认安装包；公开分发使用通用或具备分发条件的资源。

## 5. 执行与结果边界

脚本可以访问宿主文件和启动进程，仅检查输入路径或设置 cwd 不构成文件系统隔离。阶段 A 必须明确采用的执行约束及可达到的保护程度，不能宣称已有沙箱。真实路径/符号链接、脚本自身及后代进程的写入与网络能力需在运行时 ADR 中处理。

同时保留现有产品原则：源资料默认只读，结果写入任务输出区域并登记 ArtifactVersion；长操作有进度、取消、超时与明确结果。新执行器在 Application/Tool Runtime 一侧注入，Agent Core 不直接启动宿主进程、读取安装目录或数据库。

脚本型 Skill 是用户授权的产品能力范围；导入、依赖安装、开始执行和越界写入的交互语义应在设计中分别定义，不用每条正常子进程调用重复打断工作。

## 6. 样本适配注意事项（静态发现，未作缺陷复现）

- `validate_pptx.py` 主程序打印问题列表，却没有在发现问题时设置非零退出码。宿主不能把退出码 0 当作通过；需结构化调用 `validate()` 的 issues 结果、适配报告或在导入副本修正契约。
- 导出包装按输出文本与最新文件时间判断成功，未直接以 exporter 的 returncode 判定；宿主需验证当前执行产物，避免失败重试误认历史文件。
- SKILL.md 要求 `primary_language=zh-Hans`，导出脚本缺省值是 `zh-CN`；模板档案说封面标题继承 44pt，merge 脚本 `fill_title` 默认写入 28pt。导入成功不能等同于这些契约已经一致，需要真实样例验证及适配记录。
- 包装脚本执行时 capture_output 会缓冲部分子进程输出；阶段 A 的执行状态不应等到结束才出现，细粒度实时进度可能需要适配。
- `<p:pic>=0` 是该原生形状生成路线的要求；模板自身的图片与生成内容应分别核对。静态结构检查不替代 PowerPoint 实际打开、逐元素编辑和页面视觉检查。
- 默认验收按 flat 导出后 merge；structured 路线保留为该 Skill 的进阶能力。它明确不做既有 PPTX 单页原位编辑，用户修改通过修改 SVG 源再生成完成。

上述事项不改变必须支持此类 Skill 的决定，也不在本轮修改用户原包。

## 7. 调整后的交付门槛

### 阶段 A：真实脚本 Skill 可运行

导入该目录或其可追溯适配副本，配置解释器/PPTM_HOME 和必要依赖，用合成内容制作最小封面与内容页：读取模板规范 → 写 SVG/配置 → 导出 → 合入模板 → 校验 → 登记可预览/导出的 PPTX。该试运行在专家配置 UI 之前完成，可使用现有 Agent 和临时 Skill 选择入口；不需要先做完整市场研究。

必须另外验证：缺依赖错误、含空格/中文路径、脚本失败、零退出码但校验报告失败、取消后无残留子进程、旧产物不误认新结果、源模板不变、应用重启后配置与结果可回看。脱离本机 WorkBuddy 路径的环境也是验收条件。

### 阶段 B：专家真实绑定

同一专家绑定研究方法与该 PPT Skill；指令、资源、脚本能力和运行环境实际生效，不通过更换专家完成演示文稿。

### 阶段 C：真实研究到汇报

在六个讨论节点中使用平台资料、网络信息和报告，按确认的 PPT 大纲调用该 Skill，支持反馈后重新生成并保留版本；用户可在 PowerPoint 中做最终编辑。

阶段 A 的可运行样本不能代替 C 的真实场景验收；C 也不能用「脚本以后再做」作为延迟支持该样本的理由。
