## 2. 建议按收益和实施风险分两步

### 第一步：优先改善日常 PR 等待

1. **将独立检查放到不同的 macOS runner。** 可以先保持完整的类型感知 lint，单独作为一个 job；格式、全仓类型、文档和相关测试作为另一个 job，两者同时开始，最后汇总为 `PR Gate`。重档继续串行，功能档与重档继续依次执行。根据样本推算，小改动可能节省数十秒，大范围相关测试可与 lint 重叠；需要实际验证额外安装、排队和 runner 计费的影响。
2. **格式检查按 PR 实际变动文件执行，配置变化回退全仓。** 重命名、删除、文件名含空格、忽略规则和空集合都要明确处理；仍复用全仓唯一的 Prettier 配置。也可选内容缓存，依赖、配置、忽略规则及插件变化必须失效，缓存缺失时照常检查。
3. **为经过验证的资源类型建立明确分流。** 发布清单这种修改应执行清单结构、内容哈希、发布规则和实际消费者的检查，而不是启动与差异无关的 TypeScript 扫描。只有已建立专属检查的明确路径可进入资源档；未知 JSON、脚本、依赖、配置及混合代码变化仍走代码档。动态文件读取不能只依赖 Vitest 的 `--changed` 来证明覆盖。
4. **评估全仓类型检查的增量缓存。** 保留全仓 `tsc --noEmit` 的验证语义，试验 `incremental` 与 `.tsbuildinfo` 持久化；缓存按 Node/TypeScript、依赖及 tsconfig 区分，改变被依赖的类型也必须重新检查消费者。首次运行和缓存缺失应正确回退，不把缓存命中当作跳过检查。
5. **留下阶段读数。** 在 Actions summary 中记录目标 SHA、差异类别、每步耗时、选中测试文件数和缓存命中；区分实际执行时间与 job 间等待。至少覆盖资源小改动、局部 TypeScript 修改、共享协议修改和配置修改四类样本，才报告优化收益。

普通小改动可将 1–2 分钟设为后续优化目标，但目前不是实测承诺。第一步保留完整类型感知 lint，预计先减少重复等待；能否达到目标取决于 runner 调度、缓存收益及剩余全仓 lint 时间。

### 第二步：根据读数优化完整验证和类型感知 lint

完整验证主要瓶颈是所有阶段串行。后续可评估在独立 macOS runner 上并行运行静态检查、全部测试以及构建后 UI 检查；每条分支都必须收口，原有截图、成功读数和失败产物必须留存。全部测试仍保持功能档后接重档，UI 与重档不在同一台机器争抢资源。

这会改变当前“完整验证整条调用 `npm run verify`”的工作流契约，不能直接拆 YAML 后仍按旧护栏报告通过。需要先修订 ADR-0042 或新增后继 ADR，同步工程规范、交接、规则与结构测试，并明确本地完整入口和远端完整覆盖的等价判据。此处尚未实施。

类型感知 lint 是小代码 PR 的主要固定成本。若第一步后仍明显偏慢，可研究按变动文件及受影响的消费者选择 lint；共享协议、导出类型、重导出、路径别名、声明文件和配置变化需保守扩大，无法确定范围就全仓回退。只检查被编辑文件或仅加 ESLint 文件内容缓存，不能维持当前跨文件类型规则的覆盖。

## 3. 技术依据与落地判据

- 已有 `setup-node` 的 npm 缓存缓存的是下载数据，不是 `node_modules`；因此不能因为 YAML 已写 `cache: npm` 就认为安装和静态检查都已增量化。[setup-node 官方说明](https://github.com/actions/setup-node#caching-global-packages-data)
- ESLint 内容缓存不跟踪文件之间的依赖，类型感知规则可能复用过期结果。未经依赖失效设计，不能将简单的 `--cache` 作为全仓 lint 的等价优化。[ESLint 缓存说明](https://eslint.org/docs/latest/use/command-line-interface#--cache)
- Prettier 支持按内容缓存，但插件变化不自动成为缓存键，需要额外失效。[Prettier CLI](https://prettier.io/docs/cli#--cache)
- TypeScript 增量信息可用于后续类型检查加速，仍需在当前 `noEmit` 配置与 CI 恢复路径上验证。[TypeScript incremental](https://www.typescriptlang.org/tsconfig/incremental.html)
- Vitest 相关测试跟随依赖图，配置及 `package.json` 变化默认触发全套；这类扩大选择属于正确性要求。[Vitest changed](https://vitest.dev/config/changed)

实施前先更新现行规范与护栏，不在单次对话里放宽规则。落地回归应证明：分类失败/未知路径回退、任一必需检查失败或取消都使 `PR Gate` 失败；缓存未命中照常检查；依赖类型改变能拦住未修改消费者中的违规；资源哈希错误能被资源档拦住；夜间/手动完整覆盖与 UI 留证保持明确。

本轮仅完成只读调查和方案整理；没有启动完整 verify、真实模型调用、提交、推送或外部发布。

## 4. 日常代码校验与按需 UI 验证的分工

2026-10-14 用户进一步明确期望：日常修改、提交、推送和合并只执行快速代码校验；UI 验证放在手动入口或夜间校验。建议将该分工统一落实到本地命令、PR 门禁和 AI 执行规则。

| 时机 | 建议范围 | 入口状态 |
| --- | --- | --- |
| 本地提交 | 暂存差异空白、定向 lint/格式和文档检查 | 已有 pre-commit |
| 推送 | 干净 HEAD、目标分支和差异空白 | 已有 pre-push |
| 日常 PR / 合并 | 静态约束、类型、文档和受影响的逻辑/组件行为测试；不启动真实 Electron UI 验证 | 已有 PR Gate，需细化测试分流与提速 |
| 手动 UI 验证 | 真实渲染矩阵、截图、离线应用旅程和进程恢复 | 已有 `npm run ui:check` |
| 手动或夜间完整验证 | 所有检查及完整 UI 留证 | 已有 `npm run verify`、workflow_dispatch 和夜间 schedule |
| 本地统一快速入口 | 与 PR 的快速范围一致 | 可新增 `npm run check:quick`；当前尚不存在 |

当前 PR 已经不直接运行完整构建或 `ui:check`，所以仅从 PR YAML 删除 UI 步骤不会获得额外收益。但仍有两个未完全分离的入口：

- `scripts/ui-render-check.test.ts` 位于 heavy 档，其用例通过 CLI 真正启动 Electron，验证像素、几何、键盘、应用旅程和强杀恢复。PR 的相关重档测试或配置变化可能选中该文件，不能仅因未出现 `npm run ui:check` 就称 PR 完全没有真实 UI 验证。应将这类宿主检查保留在手动/夜间完整覆盖中，从日常快速范围明确分离；普通逻辑与组件行为测试仍参与相关测试选择。

  已有实际样本：[PR 快门禁 38146259870](https://github.com/gyzhang/BetterWork/actions/runs/38146259870) 的重档日志选中该文件，11 项用例耗时 91.588 秒。它不是普通小改动的普遍耗时，但证明真实 UI 探针确实可进入日常 PR 路径。

- UI/UX §10.1.1 第 6 步仍要求页面 Review 运行 `npm run verify`，第 5 步要求本次用户路径实测，§10.1.3 仍写完整 verify 全绿为必要条件。前者与 ADR-0042 的按需/夜间完整验证已有冲突；其余页面实测要求应按用户此次期望明确日常与专项时机，记录未验证项，不能让 AI 因 UI 文件变化自动扩大为完整验证。

这项分工能减少本地重复验证及某些 PR 中的真实 UI 宿主开销；此前那个仅改发布哈希的 219 秒样本主要耗时仍是全仓静态检查，继续提速仍需 §2 的并行、格式范围及资源分流。上述方案尚未实施，既有命令和范围保持原状。
