# AI 规则遵循与门禁审计（2026-10-02）

> 审计对象：本仓给编码智能体读的所有规则/规范/指引文件，加上提交、推送与 GitHub Actions 三层门禁。
> 审计问题：规则之间有没有相反或二义的说法；AI 写出的代码是否真的被机器约束住；一段时间后漂移了，有没有可重复执行的检查与回归手段。

## 1. 一句话结论

体系的骨架已经站住了：**一份规范（docs/12 + docs/10）+ 可执行形式（ESLint/Prettier/tsconfig）+ 139 条跨文件结构护栏 + 一条 verify 门禁 + 双向文档核验**，本次实测 HEAD 全绿，机器能判的部分确实没有违例。

风险集中在三处，且都是同一类病：**「文档写的」和「机器跑的」不是同一件事**。

1. 规则文件里的**文件指针与数字快照**没有任何机械核验——已经漂了（两处指针指向不存在的文件、四处数字互相不一致、docs/11 与 docs/10 对同一组件给出相反结论）。
2. **本地强制的门禁 ≠ 文档要求的门禁**：`.husky/pre-commit` 只跑 lint + typecheck，而 AGENTS.md／docs/12／docs/11／code-style 四处都写「提交前必须跑 `npm run verify`」。代价直接写在 Actions 历史里：**28 次 push 失败、2 次成功**，main 长期处于红状态。
3. **零豁免护栏对它自己的文件不设防**：`standards/` 与根级配置文件不在扫描根里，护栏文件和 `eslint.config.mjs` 里写 `eslint-disable` 不会红。

## 3. 问题清单

严重度判据：**AI 会不会因此写错代码或写错文档**。P0＝直接让门禁失效；P1＝AI 读到即会做错；P2＝削弱体系自身的可信度与可维护性。

### P0-1 提交/推送的门禁与文档要求的门禁不是同一件事

- 现状：`npm run verify` = lint + format:check + typecheck + test + build + ui:check（护栏「所有现行门禁摘要包含实际 verify 的完整步骤」把这句话钉在四处文档里）。实际强制只有 `.husky/pre-commit` 的两步：`npm run lint`、`npm run typecheck`。
- 后果（有账）：今天 02:13–05:57 三次连红是 `ui:check` 与用例超时，04:18 那次红在推之前本地就能测出来。红都在 main 上发生，而不是在提交前。
- 为什么文档没兜住：AGENTS.md §7、docs/12 §1、docs/11 §3、`betterwork-dev-cycle.md` 都写了「提交前跑 verify」，但这句话**没有任何机械执行点**——它是四条散文里的一句嘱咐。
- 修法（按 ADR-0036「真正拦人的是提交前那一次，不靠远端闸门」）：
  1. `.husky/pre-commit` 补 `npm run format:check`（+3.3s）与 `git diff --check`；
  2. 新增 `.husky/pre-push` 跑 `npm run verify`（本地实测约 90–120s，含 build 与 ui:check）；
  3. 加一条护栏钉住**钩子与门禁的对应关系**：`.husky/pre-commit` + `.husky/pre-push` 覆盖的 npm script 合集必须等于 `package.json` 里 `verify` 的六步，缺步即红。第 3 条是关键——没有它，下一次再有人（包括我）删一行钩子，文档依然全绿。

### P1-1 规则文件指向不存在的实现文件（已实测 2 处）

| 位置 | 文件里写的 | 实际 |
| --- | --- | --- |
| `.qoder/rules/betterwork-ipc-artifact.md:24` | SQLite 真相源在 `apps/desktop/src/main/run-journal.ts` | 无此文件；真相源是 `main/db/` + `main/persistence/`（docs/11 §4 写对了） |
| `.qoder/rules/betterwork-knowledge.md:8` | 实现主体在 `apps/desktop/src/main/knowledge-vault.ts` | 实际在 `main/services/knowledge-vault.ts` |

这两个文件都是 `model_decision` 自动加载的场景规则，AI 改 IPC／持久化或改知识索引时会先读到它们。指针过期不会报错，只会让 AI 去开一个不存在的文件或按错误的层次动手。

- 修法：同批改准两处路径；并加护栏「**规则与规范文档里反引号包住的仓库路径必须存在**」（允许清单登记模板占位与简写形式）。这条护栏的实现成本低于一次路径漂移的排查成本。

### P1-2 同一个数字住在四处，且四处都不一样

| 出处 | 说法 | 与本次实测的差 |
| --- | --- | --- |
| `README.md:125` | 20 个测试文件、131 个测试 | 实测 181 文件／1,745 例——差一个数量级，且这是新会话第一眼读到的文件 |
| `docs/12:200`（§9） | 164＋6＝170 文件、1472＋133＝1605 例，并写「与基线逐一相符」 | 实测 175＋6＝181、1612＋133＝1745 |
| `docs/11:79` | 功能档 175 文件／1,587 例、含 135 条护栏与检测器 21 项、共 1,720 项 | 文件数已对，例数与护栏条数过期（实为 1,612 例、139 条 `it`、检测器回归 17 项） |
| `docs/logs/2026-10-02.md` | 175／1,612 ＋ 6／133 | 与本次一致 |

这正是本仓自己付过代价的形状：docs/10 §9.7 因为「两份字号表并存」撤掉了一张表，`docs/reviews/2026-09-28-ui-governance-audit.md` P3-11 因为「四处并存两种措辞」治理过一轮。UI 那一类数字有「docs/10 档位表 ↔ `styles.css` Token 两侧同值」的护栏（`coding-standard.test.ts:2039`），**测试与护栏计数这一类一个都没有**。

- 修法二选一，需要拍板（见 §5 D2）：
  - **A（推荐）**：文档删掉计数句，统一改成「以当次 `npm verify` 输出为准」，只保留一处由脚本生成的读数（例如 README 那一段改为引用当次结果，或不写数字）；
  - **B**：加护栏钉住「文档写的数 == 实测数」——但它每加一个测试都要改文档，长期会变成红信号噪声的来源。

### P1-3 docs/11 的代码地图与「仍未解决」清单和 docs/10 台账直接矛盾

- `docs/11:149`：「Tooltip、Skeleton、Switch 未落地」。实际 `components/Switch.tsx`、`components/Tooltip.tsx` 都存在、都有测试，且都登记在 docs/10 §10.1 台账里；docs/10 §13 也写明 Tooltip 已于 2026-09-27 落地。
- `docs/11:111`：hooks「五个内聚状态簇」。实际 `hooks/` 有 23 个 hook 文件。
- `docs/11:108,146`：`App.tsx` 「1,736 行」（两处）。实际 1,835 行。
- `docs/11:112`：称 `lib/async-action.ts` 是「异步收口的唯一入口」——这句与 docs/12 §5 在 2026-09-30 特意改准的结论（「收口」不等于「必须字面调用某个函数」，helper 只是两类处置的缺省实现）方向相反，AGENTS.md §7 用的是改准后的说法。
- 为什么严重：docs/11 自己顶部有免责声明（§4–§7 是早期快照），但「Switch 未落地」这句话对一个要做记忆表单的 AI 来说是**行动指令**，它会去自造一个开关——而护栏「被 Button 基座收编的皮不得复活」这类断言根本不知道它造了第二个 `Switch`。
- 修法：docs/11 §4/§6 里凡与 docs/10 台账重叠的组件陈述一律改成指向台账的指针；加一条护栏「docs/11 不得断言台账内组件『未落地』」。

### P2-1 零豁免护栏的扫描根漏掉它自己

- `standards/coding-standard.test.ts:255`：`SOURCE_ROOTS = ['apps/', 'packages/', 'scripts/']`；第 421 行「源码里没有任何规则豁免注释」按此扫描。
- 结果：`standards/*.ts`（5,406 行护栏 + 检测器）与根级 `eslint.config.mjs`／`vitest.config.ts` 里写 `eslint-disable`、`@ts-expect-error` 都能通过——而 docs/12 §10 的字面是「源码里不接受单点豁免」。当前**实测没有违例**（全仓 4 处命中都是护栏文件里那些 needle 字符串本身）。
- 之所以排除 `standards/`：护栏文件里就有那些字面量。修法：把匹配从「字符串包含」换成「注释形状」的正则（要求 `/*` 或 `//` 前缀），从而把 `standards/` 与根配置纳入扫描而不误伤自己。

### P2-2 「复述与出处一致」只钉住了一个文件，且钉的是形式

- 护栏「编码规范速查文件的每条复述都要带出处」只管 `betterwork-code-style.md`，判据是行末有没有 `§N`。账本 §8 第 8 条已把另外 5 个文件的 38 条无出处复述登记为「待派发」，本次复核仍在（ipc-artifact 10 条 0 带、knowledge 7/0、dev-cycle 11 条 1 带、diagnosis 3 条 1 带）。
- 两个盲区：① `betterwork-ui.md` 通篇是表格与段落，护栏按 `- ` 行计数，对它一条都数不到；② **有出处不等于与出处一致**——`betterwork-code-style.md:27` 写「IPC 调用收在 `hooks/`（docs/12 §8）」，而 §8 的判据是「`views/` 与 `components/` 里不出现 `window.betterwork`」；按速查文件的字面，`App.tsx` 现有 42 处调用全部违规（实测 views/components 里为 0，达标）。这类分叉正是 P3-11 那次的形状。
- 修法：把 38 条按文件分批改准（每条先验目标小节存在），并把 `App.tsx` 这一处显式登记进 docs/12 §8；「复述必须与出处同判据」本身难以机械化，可行的替代是护栏锁「判据句的唯一出处」——同一判据的关键词只允许在一份文件里出现，其余引用文件只允许写指针。

### P2-3 文档具名引用的护栏名与 `it()` 标题对不上

- docs/10 有 12 处「护栏…『X』」式具名引用，7 处对不上实际标题（多数是中文引号被当强调用、或标题里的反引号差异，属噪声）；确有语义改写的是 docs/12 §9 写「护栏锁『功能档里不得出现 `performance.now()`』」，实际标题是「墙钟计时断言只允许住在 `*.bench.test.ts`」。
- 账本 2026-09-28:195 已写下判据「文档里写『已配护栏』之前必须 grep 到那条 `it()` 标题」——这条判据**自己没有被护栏化**，而它防的正是账本自己犯过的「假声明已配护栏」。
- 修法：加一条护栏做标题匹配（带同义改写白名单），同时把「护栏『X』」这种写法规定为专名引用格式，非专名不用中文引号。

### P2-4 规范句与落地叙事混排，AI 抽取时容易把历史当现状

docs/10 §9.10 的一条 bullet 里同时有：档位表引用、2026-09-27 并档决定、2026-10-01 核查发现的 10 个裸值、ADR-0035 的三轮排查经过。规范性内容（「必须取档」）和过程记录（「曾有 53 条 overflow 声明」）在版式上无法区分，靠读者自觉——而 §9.8 自己就提醒过「括号里是那一轮收口时的快照处数，会随开发漂移，别当现状读」。

- 修法：给落地记录定一个固定形状（统一小标题「落地记录（截至 YYYY-MM-DD）」），护栏拒绝**无日期标注**的计数句出现在 docs/10/docs/12/README/docs/11。低成本、能同时缓解 P1-2。

### P2-5 三条「铁律」与日志纪律没有任何机械保障

`betterwork.md` 的铁律一（写日期前先 `date`）、铁律二（中文编辑后 grep 回读）、以及 AGENTS.md §9 完成定义第 7 条（工作日志）目前全靠自觉。实测制度在被执行（`docs/logs/` 有 2026-10-02/10-01/09-30…），但护栏一个都没有。

可以机械化的三件事，都很便宜：

1. **中文静默损坏**：对跟踪文本文件断言不含 U+FFFD 与典型 mojibake 序列——这条拦住的是「工具返回 success 但文件里已是错字」这一类，tsc/vitest 都抓不到。
2. **空白错误**：`git diff --check` 已写进 `betterwork-dev-cycle.md` 的清单，但没进钩子（并入 P0-1）。
3. **日志同步**：CI 侧对每次 push 断言「非纯文档改动必须触及当天 `docs/logs/` 文件」，或本地 pre-push 提示。注意这条会误伤连续多笔小提交，判据要按「一次推送批次」而不是「一笔提交」。

### P2-6 第二份智能体入口只写着技术栈

`.codeartsdoer/AGENTS.md` 是 CodeArts 自动生成的本地文件（未跟踪、ESLint/Prettier/Git 均排除，docs/12 §10 登记为例外，护栏另查它未被跟踪）。它的全部内容只有 `Language Context: TS/TS_Strict` + `Architecture Stack: NodeJS`，**不指向 docs/12、不指向依赖方向**。在 CodeArts 里干活的智能体拿不到本仓任何一条硬约束。

- 修法：在 docs/12 §10 该条例外下面补一句现状说明（该目录由工具自管、不作为规范来源），或者接受现状。不建议为它写第二份规范。

### P2-7 CI 缺两个低成本能力

- 无 `workflow_dispatch`：想复跑一次门禁只能再推一笔，正是 28 红里的一部分噪声来源。
- `if: failure()` 上传产物是好设计，但**成功时不留读数**：`ui:check` 的 16 组读数在绿跑里就地丢弃，跨轮无法比对「焦点环宽度这一档有没有悄悄变了」。建议成功时也上传 `results.json`（体积小、保留 3 天）。

## 4. 「不漂移」的机制建议

目标是把今天这一次审计变成**能反复跑、结果可比较**的动作，而不是一篇会过期的报告。

**第一层（补强制点）**：新增 5 条护栏——① 文档引用路径必须存在；② 钩子覆盖 == verify 六步；③ 扫描根扩到 `standards/` 与根配置；④ docs/11 不得与 docs/10 台账对同一组件给出相反结论；⑤ 无日期的计数句即红。

**第二层（补本地门禁）**：pre-commit 补 format:check，pre-push 跑完整 verify。ADR-0036 已定案「不靠远端拦推送」，所以这一层是唯一的实质拦截点。

**第四层（周期巡检，本日已落地）**：`npm run drift:check`（`scripts/drift-check.mjs`）查护栏看不见的三类漂移——

- 仓库外部的状态：这个克隆有没有真的把钩子接到 `.husky/_`（`git config core.hooksPath`）、本地攒了多久没推的提交；护栏跑在 `npm test` 里，**看不到没装钩子的机器**，而那正是「门禁形同虚设」的第一号形状。
- 跨时间的读数：测试文件／用例／结构护栏条数／例外登记条数（`reason:` 计数）／`eslint.config.mjs` 配置块数／规则文件数／产品源码行，对照 `docs/development/drift-readings.json` 上次留档给出增减。判据是：**例外登记变大本身就是漂移**，必须改回收紧的那侧或 `--save` 重新留档并在日志写理由。
- 制度有没有被执行：窗口内每个有提交的日子都要有 `docs/logs/YYYY-MM-DD.md`；可用 `--require-log=` 补点名字段。

另报一条覆盖率读数（判据总数 / 现行文档点名次数 / 被点过名的判据条数）：谁都没被引用过的判据等于没人知道它存在。触发时机写进了 docs/12 §1：审计前、每完成一个批次后、同类问题第二次出现时；**刻意不进 `verify`**（判据含 `git log` 与本机克隆配置，换台机器结论不同，随机红的门禁下一个被牺牲的永远是门禁本身）。

上面 §5 表里那五条护栏是**第一次**审计的一次性逻辑，现已全部固化为 `it()` 判据（跑在 `npm test`），巡检脚本只补它们结构上够不着的部分。因此这四条不再是待办，而是每次巡检后的复核口径：

回归口径（每次巡检照抄这四条判据，写进账本模板）：

1. 新增的每一条例外/白名单，是否有对应的文档条款（docs/12 §10 已有此要求，缺护栏）；
2. 规则文件里所有反引号路径、所有计数句，与当次实测是否一致；
3. 三层门禁（ESLint/Prettier、结构护栏、hooks+CI）各自的**最近一次真红**是什么时候——一个从未红过的护栏要当作可疑，做一次变异验证（改坏一行、确认它红、再还原）；
4. 四处「提交前跑 verify」的嘱咐，是否仍然只等于 `.husky` 里那两行。
